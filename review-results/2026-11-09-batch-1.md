# Review Findings - Batch 1: src/exec Security, Redaction & Parsing

## Overview
- **Scope**: Batch 1 (`src/exec/masker.rs`, `src/exec/secret_patterns.rs`, `src/exec/leak_detector.rs`, `src/exec/parser.rs`, `src/exec/analysis.rs`, `src/exec/kernel.rs`, `src/exec/risk.rs`)
- **Review Methodology**: `/rust-occams-razor` static analysis (removal of unnecessary concepts, preserving contracts, eliminating redundant allocations, flattening control flow, identifying logic and regex flaws).
- **Summary**: 19 findings total (3 P1, 10 P2, 6 P3).

---

### Finding 1
- File & Line: `src/exec/secret_patterns.rs:6-13`
- Severity: P1
- Invariant / Rule violated: Shape 16 (孪生子系统 / 第 N 次复发), Shape 1 (同一事实的两份表述), Occam's Razor
- Concrete Finding: Two parallel, ununified secret detection catalogs exist in the codebase: `src/exec/secret_patterns.rs` (used by `exec::masker` and `exec::leak_detector`) and `src/secrets/vendor_patterns.rs` / `src/secrets/leak_detector.rs`. As admitted in the file docstring, `secrets::vendor_patterns` knows modern vendor formats (Slack `xapp-`, Stripe, SendGrid, HuggingFace, Replicate, Groq, xAI, Perplexity, npm, PyPI, DigitalOcean, Google OAuth, Telegram, Twilio, GitLab) which `src/exec/secret_patterns.rs` completely lacks. This leaves execution logging, diff presentations, and tool output masking blind to dozens of common credentials, allowing them to leak in clear text.
- Proposed Occam Simplification: Unify the secret catalogs under a single authoritative source in `crate::secrets`, and have `exec::masker` and `exec::leak_detector` consume that canonical catalog without duplicate pattern vectors.

### Finding 2
- File & Line: `src/exec/secret_patterns.rs:203-205`
- Severity: P1
- Invariant / Rule violated: Rule 5 (Logic bugs, boundary leaks, regex flaws) / RFC 3986 URI parsing invariant
- Concrete Finding: The URL credential regex `r"://([^\s:/@]+):(\S*)@"` uses greedy `(\S*)@` to match passwords. Under RFC 3986, the userinfo authority component is terminated by `/` (path), `?` (query), `#` (fragment), or whitespace. If a URL contains an `@` symbol anywhere in its path or query string (e.g. `http://user:pass@host.com/api?email=test@example.com` or `https://user:pass@git.internal/org/repo@v1`), the greedy `\S*` matches past the hostname and path all the way to the last `@`. The replacement `://${1}:***REDACTED***@` then obliterates the actual host, port, and path, corrupting valid URLs.
- Proposed Occam Simplification: Restrict the password character class to exclude path and query delimiters: `r"://([^\s:/@]+):([^/\s?#]*)@"`.

### Finding 3
- File & Line: `src/exec/parser.rs:106-120`
- Severity: P1
- Invariant / Rule violated: Shape 2 (恒真的谓词等于没判), Occam's Razor Rule 1 & Rule 5 (Dead / buggy control flow)
- Concrete Finding: In `contains_unquoted_redirect`, line 103 unconditionally returns `true` on ANY unquoted `>` or `<`: `'>' | '<' if !in_single && !in_double => return true;`. Then lines 106-120 attempt to check:
  ```rust
  '&' if !in_single && !in_double && (prev == '>' || prev == '<') => return true;
  ```
  As admitted in the code's own comment (`// The only way prev is > or < here is an *escaped* one (\>)`), this branch can NEVER be reached for any unquoted redirect like `2>&1` or `>&2` because the `>` already returned on line 103! The only scenario where `prev == '>'` at line 106 is when `>` was preceded by a backslash (`\>&`), which is an escaped character (NOT a redirect). This branch is dead for unquoted redirects and causes false-positive rejections on escaped input.
- Proposed Occam Simplification: Delete lines 106-120 entirely. Unquoted `<` and `>` are already completely and correctly handled by line 103.

### Finding 4
- File & Line: `src/exec/kernel.rs:83-92`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 3 / Performance & DoS protection
- Concrete Finding: `SecurityKernel::assess_custom` evaluates `self.custom_blocked.iter().any(|p| p.is_match(cmd))` and `self.custom_danger.iter().any(|p| p.is_match(cmd))`. It runs individual linear regex passes over `cmd` for every configured custom rule. Furthermore, unlike `src/exec/masker.rs` which explicitly caps operator patterns at `MAX_OPERATOR_PATTERNS = 64` to prevent regex DoS, `SecurityKernel::from_config` has no upper bound on the number of compiled regexes, exposing every command execution check to quadratic regex evaluation costs under large user configurations.
- Proposed Occam Simplification: Introduce an upper bound cap on custom patterns (e.g. `MAX_CUSTOM_PATTERNS`) or compile them into `RegexSet` instances (one for blocked, one for danger) to evaluate all patterns in a single pass with O(1) matching time relative to pattern count.

### Finding 5
- File & Line: `src/exec/analysis.rs:18-23`, `28-35` (and `src/exec/parser.rs:198-200`)
- Severity: P2
- Invariant / Rule violated: Shape 1 (同一事实的两份表述) & Occam's Razor Rule 2 & 3 (redundant allocations and dual storage)
- Concrete Finding: `CommandAnalysis` stores both `pub segments: Vec<CommandSegment>` and `pub chains: Option<Vec<Vec<CommandSegment>>>`. In `analyze_shell_command`, every `CommandSegment` is cloned twice: once for `chains` and once for `segments`. Outside of a single test in `parser.rs:543`, `chains` is never consumed by any production code across the entire codebase (`ExecApprovalManager`, `guardian_requester`, `action.rs`, etc. all consume `.segments` exclusively). Storing both doubles the memory footprint of parsed commands and serializes redundant structures across RPC boundaries.
- Proposed Occam Simplification: Either remove `chains` if non-essential or make `segments` an accessor/iterator that flattens `chains` on demand, avoiding duplicate owned vectors and multi-level deep cloning.

### Finding 6
- File & Line: `src/exec/secret_patterns.rs:211-213`
- Severity: P2
- Invariant / Rule violated: Rule 5 (Regex flaws / boundary leaks)
- Concrete Finding: Pattern 14 (`password|passwd|pwd|secret`) uses `([^\s'"]{8,})` for the secret value. When a password is configured in a JSON or `.env` file with quotes and contains spaces (e.g., `password = "correct horse battery staple"` or `secret = "api key with spaces"`), the `[^\s'"]` class stops at the first whitespace. If the first word is under 8 characters, the pattern fails to match entirely, leaking the complete passphrase in the clear. If the first word is >= 8 characters, it masks only the first word and leaks the remainder.
- Proposed Occam Simplification: Separate the quoted value match from unquoted value match: for quoted values, allow spaces inside the quotes (e.g. `"[^"\r\n]{8,}"|'[^'\r\n]{8,}'`).

### Finding 7
- File & Line: `src/exec/secret_patterns.rs:50-60` and `src/exec/leak_detector.rs:21-28`, `76-85`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 1 & Shape 10 (identical structs with zero abstraction value)
- Concrete Finding: `LeakPatternDef` in `secret_patterns.rs` and `LeakPattern` in `leak_detector.rs` have identical fields (`name: &'static str`, `regex: Regex`, `action: LeakAction`). In `secret_patterns.rs`, `LeakDetectorAssets` is a single-field wrapper around `Vec<LeakPatternDef>`. Furthermore, `leak_detector_assets()` returns `LeakDetectorAssets` by cloning the entire vector of 10 compiled `Regex`es. Then `LeakDetector::default_patterns()` consumes `assets` and maps each `LeakPatternDef` into `LeakPattern` via an iterator loop.
- Proposed Occam Simplification: Delete `LeakPatternDef` and `LeakDetectorAssets`. Define `LeakPattern` in one place and have `leak_detector_assets()` return `&'static [LeakPattern]`, avoiding struct duplication, unnecessary wrapper types, and vector/regex cloning.

### Finding 8
- File & Line: `src/exec/leak_detector.rs:126-137`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 3 (Redundant allocations on clean inputs)
- Concrete Finding: `redact(&self, content: &str) -> String` unconditionally allocates `let mut current = content.to_string();`. Then, for every `LeakAction::Redact` pattern in `self.patterns`, it calls `pattern.regex.replace_all(&current, "...").into_owned()`. Because `.into_owned()` is called unconditionally on the `Cow` result, it allocates a new `String` on every loop iteration, even when no match occurred and the input was completely clean.
- Proposed Occam Simplification: Use `Cow<'_, str>` lazily (matching `SecretMasker::mask`): only promote to an owned string if a pattern actually fires (`if let Cow::Owned(masked) = pattern.regex.replace_all(...)`). If no patterns fire, return `Cow::Borrowed(content)`.

### Finding 9
- File & Line: `src/exec/masker.rs:103-128`, `139-169`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 3 (gratuitous allocation on hot path)
- Concrete Finding: `SecretMasker::mask(&self, text: &str) -> String` has a comment claiming: `// replace_all returns a borrow on no-match; only promote to an owned accumulator when a pattern actually fires, so clean text costs zero copies instead of one full allocation per pattern.` However, line 127 calls `result.into_owned()`, forcing a full heap allocation even when no secrets matched. When `mask_json_strings` walks a JSON payload, every single string leaf in the tree calls `masker.mask(s)`, allocates a new `String`, compares `masked == *s`, and drops it. On large tool results or JSON payloads with hundreds of strings, this produces thousands of short-lived allocations for 0 modifications.
- Proposed Occam Simplification: Expose `pub fn mask<'a>(&self, text: &'a str) -> Cow<'a, str>`. In `mask_json_strings`, check `match masker.mask(s) { Cow::Borrowed(_) => false, Cow::Owned(new_val) => { *s = new_val; true } }`. This delivers true zero-allocation on clean text.

### Finding 10
- File & Line: `src/exec/masker.rs:280-289`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 3 (redundant processing and allocations)
- Concrete Finding: In `mask_file_change`, all hunk lines are already individually masked in-place on lines 270-272. Then lines 280-285 collect all hunk lines into an intermediate `Vec<&str>` just to `.join("\n")` into a large joined string. Then line 286 runs `masker.mask(&joined) != joined`, which re-runs all 17 single-line patterns and all operator patterns over the entire joined diff, and allocates another full string copy just for an inequality check. Since the only multi-line pattern in the entire catalog is the PEM private key pattern, running all other regexes is completely redundant.
- Proposed Occam Simplification: Check only the multi-line PEM pattern against `joined` using `.is_match(&joined)`, avoiding both the 17+ redundant single-line regex sweeps and the allocation of a second masked copy of the joined diff.

### Finding 11
- File & Line: `src/exec/parser.rs:146-150`
- Severity: P2
- Invariant / Rule violated: Shape 2 (恒真的谓词等于没判) & Occam's Razor Rule 1
- Concrete Finding: `analyze_shell_command` checks:
  ```rust
  const MAX_COMMAND_BYTES: usize = 64 * 1024;
  const MAX_COMMAND_CHARS: usize = 64 * 1024;
  if command.len() > MAX_COMMAND_BYTES || command.chars().count() > MAX_COMMAND_CHARS
  ```
  In UTF-8, every unicode scalar value occupies between 1 and 4 bytes. Therefore, `command.chars().count() <= command.len()` is a mathematical invariant of UTF-8. If `command.len() <= 64 * 1024`, `command.chars().count()` can NEVER exceed `64 * 1024`. Calling `command.chars().count()` forces a full O(n) UTF-8 character decode across the entire string for a condition that is mathematically impossible to trigger.
- Proposed Occam Simplification: Remove `command.chars().count() > MAX_COMMAND_CHARS`. Checking `command.len() > MAX_COMMAND_BYTES` is O(1) and strictly bounds both bytes and characters.

### Finding 12
- File & Line: `src/exec/parser.rs:380-384`, `395-397`
- Severity: P2
- Invariant / Rule violated: Rule 5 (Logic bug / shell semantics violation)
- Concrete Finding: In `tokenize_segment`, `tokens.push(...)` is guarded by `if !buf.is_empty()`. When an empty quoted string (e.g. `""` or `''`) appears in a command, quotes are consumed without pushing characters to `buf`. When the next whitespace or EOF is reached, `buf.is_empty()` is true, so no token is emitted. For example, `git commit -m ""` parses to `argv = ["git", "commit", "-m"]` instead of `["git", "commit", "-m", ""]`, silently dropping empty arguments from command analysis.
- Proposed Occam Simplification: Track whether a token was opened (e.g. `has_token: bool` or `in_token: bool`) so that empty quoted strings push an empty `String::new()` into `tokens`.

### Finding 13
- File & Line: `src/exec/parser.rs:158-202`
- Severity: P2
- Invariant / Rule violated: Occam's Razor Rule 2 & Rule 3 (repeated parsing and excessive heap allocations)
- Concrete Finding: `analyze_shell_command` scans the command string up to five separate times with nearly identical quoting state machines:
  1. `contains_unquoted_subshell`
  2. `contains_unquoted_redirect`
  3. `split_command_chain`
  4. `split_pipeline`
  5. `tokenize_segment`
  Each pass re-iterates through the characters tracking `in_single`, `in_double`, and `escaped`. At each layer, intermediate `String`s are allocated and trimmed, followed by multiple `.clone()` calls on `CommandSegment`.
- Proposed Occam Simplification: Combine early rejection checks or parse directly into segments/tokens using a single-pass quote-aware lexer, avoiding multiple intermediate `Vec<String>` allocations.

### Finding 14
- File & Line: `src/exec/risk.rs:1-19`
- Severity: P3
- Invariant / Rule violated: Occam's Razor Rule 1 & Module Sizing (do not create one-file-per-type fragmentation)
- Concrete Finding: `risk.rs` is a 19-line file defining a 2-variant enum `RiskLevel { Danger, Blocked }` whose only producer is `SecurityKernel::assess_custom` in `src/exec/kernel.rs`. It contains no methods, traits (other than standard derives), or logic. Separating this single enum into its own standalone file introduces unnecessary file and module boundaries.
- Proposed Occam Simplification: Define `RiskLevel` directly in `src/exec/kernel.rs` (or keep a re-export in `src/exec/mod.rs` for backwards compatibility: `pub use kernel::RiskLevel;`).

### Finding 15
- File & Line: `src/exec/kernel.rs:63-70` and `114-122`
- Severity: P3
- Invariant / Rule violated: Occam's Razor (accidental duplication of logging)
- Concrete Finding: When a custom regex fails to compile, `compile_patterns` logs a warning for that specific pattern: `tracing::warn!(kind, pattern, error, "security kernel: dropping invalid custom regex")`. Then `from_config` checks `!dropped.is_empty()` and logs a second aggregate warning: `tracing::warn!(count, patterns, "security kernel: dropped invalid custom pattern regexes...")`. This creates duplicate and noisy log entries for every invalid pattern.
- Proposed Occam Simplification: Rely on the aggregate warning or the per-pattern warning alone rather than emitting both.

### Finding 16
- File & Line: `src/exec/analysis.rs:105-158`
- Severity: P3
- Invariant / Rule violated: Occam's Razor (redundant fields and allocations)
- Concrete Finding: `CommandResolution` contains `raw_executable: String` and `executable_name: String`. In `CommandSegment`, `argv[0]` already contains the raw executable string. When `CommandResolution` is created, `raw` is cloned into `raw_executable`, and when `file_name` matches or is unparseable, `raw` is cloned again into `executable_name`. Storing 3 identical strings for simple commands like `git` or `ls` triples string allocations per command segment.
- Proposed Occam Simplification: Avoid storing `raw_executable` if `CommandSegment.argv[0]` already holds it, or borrow/compute `executable_name` on demand.

### Finding 18
- File & Line: `src/exec/parser.rs:434-442`
- Severity: P3
- Invariant / Rule violated: Occam's Razor Rule 3 (gratuitous `.cloned()`)
- Concrete Finding: `let actual_path = env.and_then(|e| e.get("PATH")).cloned().unwrap_or_default();` clones the entire `PATH` string on every executable resolution call.
- Proposed Occam Simplification: Borrow the path as `&str`: `let actual_path = env.and_then(|e| e.get("PATH")).map(|s| s.as_str()).unwrap_or("");` and split directly without heap allocation.

### Finding 19
- File & Line: `src/exec/parser.rs:412`, `421`
- Severity: P3
- Invariant / Rule violated: Rule 2 (Invariants / platform compatibility)
- Concrete Finding: `resolve_executable` checks `executable.starts_with('/')` for absolute paths and `executable.starts_with("./") || executable.starts_with("../")` for relative paths. On Windows, absolute paths start with drive letters (e.g. `C:\`) or UNC paths (`\\`), and relative paths often use backslashes (`.\` or `..\`). While line 438 has `#[cfg(windows)] let path_sep = ';'`, lines 412 and 421 fail to recognize valid Windows paths.
- Proposed Occam Simplification: Use `Path::new(executable).is_absolute()` and `Path::new(executable).components().count() > 1` which work cross-platform.
