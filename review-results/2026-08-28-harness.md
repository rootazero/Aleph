## Findings

### [Warning] Dead `error_class` bind after the conditional `Cancelled` switch

- **Location**: `src/harness/agent.rs:869`
- **Title**: `error_class` is computed with a full classification match in
  `HarnessError::class()` (4 arms) and then logged, but the value is no longer
  used to drive the `trace_outcome` projection (which now branches on
  `matches!(e, HarnessError::Cancelled)` instead).
- **Risk**: Stale local variable; `clippy::no_effect_underscore_binding` or
  future `unused_variable` lint may flag it after a clippy bump, and the
  long comment justifying its removal is now the only signal that it was
  deliberately preserved for the log field.
- **Suggestion**: Either drop the `let error_class = e.class();` binding
  (and the `?error_class` field in the `tracing::warn!`) and rely on
  `error = %e` for the debug surface, or thread it back into the trace event
  (`error_class` field on `LoopTraceEvent::SessionCompleted`) so the bind
  has a real consumer.

### [Warning] Tool-result pair-integrity upgrade relies on session-event ordering, not a sequence-equality check

- **Location**: `src/harness/agent/prompt.rs:104–110` (orphan scan) and
  `src/harness/agent/prompt.rs:158–207` (orphan/duplicate result downgrade)
- **Title**: Pair integrity is enforced by index-then-turn-id, with
  `result_call_id_of_turn` filtering by exact `turn_id == turn`. The synthesis
  paths (`act::emit_deferred_tool_results`, `think::close_unexecuted_tool_uses`)
  must thread the **original** turn id of the assistant turn the synthetic result
  is closing out. The code is correct as written, but a future refactor that
  "simplifies" the turn_id thread-through (e.g. adopts the orchestrator's
  "current turn" without disambiguating) would silently un-orphan blocks in
  reused-id scenarios — exactly the regression the bounded orphan scan was
  added to prevent (see `a_reused_call_id_cannot_un_orphan_an_earlier_turn` test).
- **Risk**: Low under the current code; preserves the invariant by construction.
  Medium if a maintainer deletes or weakens the `result_call_id_of_turn`
  filter on the grounds that "turn_ids are unique anyway" — they are, but
  reusing ids **across** turns is the failure mode the filter prevents.
- **Suggestion**: Add an assertion (debug-only `debug_assert!`) that the
  `expected_results` set is exactly the size of `open_tool_use_ids` filtered
  by `resolved`, or move the pair-integrity invariant into the doc comment
  on `result_call_id_of_turn` more prominently. (Both already exist as
  test + comment, but the comment lives 200 lines below the call site.)

### [Warning] `cap = self.deps.parallel_tool_concurrency.unwrap_or(0).max(2)` could mask disabled state inside `act_parallel`

- **Location**: `src/harness/agent/act.rs:893`
- **Title**: `act_parallel` derives its buffer size from
  `parallel_tool_concurrency.max(2)`. Today this is unreachable: `act()`
  pre-checks `!parallel_enabled` and the parallel admission in
  `can_parallel_dispatch` (line 704–707) re-checks `par_n >= 2`. So the
  `.max(2)` is defensive, not load-bearing. But a future change that
  bypasses the fast-path gate (e.g. ad-hoc call to `act_parallel` from a
  testsuite helper) would silently get `cap = 2` while the producer
  assumed serial.
- **Risk**: Low — current call topology eliminates the path. The brittleness
  is the kind of "comment claims one invariant, code holds another" the
  repo keeps paying down.
- **Suggestion**: Either replace `.max(2)` with an `expect("act_parallel
  requires Some(n>=2); checked above")` (mirrors the policy elsewhere) or
  factor the gate into a single helper used by both `act()` and
  `act_parallel()`. Task 6 / Q1 in the R10 sense: scaffolding that
  duplicates an invariant is a future drift source.

### [Info] `system_time` fallback to `u64::MAX` on epoch-rollback is silent

- **Location**: `src/harness/chain_context.rs:13–17`
- **Title**: `generate_chain_id()` falls back to `unwrap_or_default()` for
  the `SystemTime::duration_since(UNIX_EPOCH)` failure (clock before
  epoch) and then to `u64::MAX` from `try_into()` for an absurdly-large
  `u128`. The result is silently `chain_id` ≈ `"ch-ffffffffffff-..."`
  on a clock-rollback event.
- **Risk**: Low. A clock rollback produces duplicate chain ids only when
  the `seq` counter also wraps (effectively never). The output just looks
  ugly in the logs.
- **Suggestion**: For R10 a future cycle could format the failure as a
  deterministic prefix (`"ch-cb-{seq:x}"`, "cb" = clock-back) so the
  fallback is at least self-describing in observability.

### [Info] `_ => {}` catch-all in `build_prompt_with_transient_tail` matches an open set of `SessionEvent` variants

- **Location**: `src/harness/agent/prompt.rs:238`
- **Title**: The walk over `SessionEvent` enumerates
  `AssistantMessage | UserMessage | SystemMessage | ToolResult | ToolError |
  RunFinished(Cancelled only)`, with `_ => {}` swallowing the other 11
  variants (`SessionWoken`, `RunStarted`, `TurnStarted`, `ToolCallRequested`,
  `ToolCallApproved`, `ToolCallDenied`, `SubagentSpawned`, `SubagentReturned`,
  `CompactionPerformed`, `SessionForked`, `Error`). The swallowed events
  are exactly the bookkeeping ones a prompt replay should ignore, so the
  wildcard is correct — but `SessionEvent` is **not** `#[non_exhaustive]`,
  so adding a new variant will compile silently through the wildcard.
- **Risk**: Very low. The implicit contract is documented in adjacent
  comments and a new bookkeeping variant is unlikely to want a model-visible
  surface.
- **Suggestion**: Either mark `SessionEvent` (the harness-side re-export if
  applicable) `#[non_exhaustive]` at the prompt boundary, or add a
  `// No prompt relevance — bookkeeping only.` comment on `_ => {}` so a
  reviewer deleting the wildcard would land on the rationale.

## Phase 4 — Red-Teaming (3 concrete scenarios)

### Scenario 1: Concurrent identical call ids across non-adjacent turns

A weaker/proxied model emits an assistant `tool_use{c1}` on turn 5, runs out of
context, and on turn 7 the same provider re-emits `tool_use{c1}` with a fresh
`tool_result`. The orphan scan filters by `result_call_id_of_turn(turn_id == T5)`,
so the turn-7 result (turn_id=T7) does NOT count for the turn-5 orphan scan.
**Coverage**: pinned by the explicit test
`a_reused_call_id_cannot_un_orphan_an_earlier_turn` in `prompt.rs`. ✅

### Scenario 2: A `prompt_too_long` that fires AFTER the `max_output_tokens` resume loop drained the rescue slot

The rescue slot is a single CAS (`compare_exchange`-shaped `fetch_update`).
Round 10 noted that the slot AND `MAX_REACTIVE_COMPACT_ATTEMPTS` (in context
layer) had drifted. Per `agent.rs:159–169`, the slot now reads the cap from the
context layer's `pub const`. A late overflow arriving after the slot is spent
surfaces `Failed` (via the third `await` arm in
`rescue::try_reactive_compact_and_retry`), not an infinite retry. ✅

### Scenario 3: Steering message arriving during `act_parallel`'s buffer_unordered

Buffer_unordered is non-interruptible by design; the steer checkpoint runs at
group boundary (before `act_parallel` is called) and inside `run()`'s Done-arm
follow-up continuation. The serialized `deferred` result shape keeps the
`tool_use`↔`tool_result` pairing valid for the next prompt. **Coverage**:
`act.rs` parallel-path tests + the prompt steering-message ordering test in
`prompt.rs:steering_message_mid_tool_turn_keeps_results_contiguous`. ✅
