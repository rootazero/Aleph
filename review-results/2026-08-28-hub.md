## Findings

### [Warning] `verify.rs:165` — catch-all `_` on `HealthStatus` silently classifies new variants as "not running"

- **Location**: `src/hub/verify.rs:159-166`
- **Trigger condition**: A future variant added to `mcp::manager::types::HealthStatus` (currently 6 variants) is added and Rust compiles cleanly because the match has `_ => (false, HealthObservation::Unknown)`. The new variant is reported as "not running" with no compiler hint.
- **Expected behavior**: Either (a) the function compiles fine AND a future variant is treated semantically correctly, or (b) adding a variant produces a compile-time reminder to reclassify.
- **Actual behavior**: A new variant is silently treated as "not running", so a newly-added "starting" state would defame a working install.
- **Suggested fix**: Either list the variants explicitly (`Healthy` / `Degraded` / `Unhealthy` / `Restarting` / `Dead` / `Stopped`) with explicit mapping, or add `#[non_exhaustive]` upstream and assert the default. The same shape appears in `reconcile.rs:44` (`!matches!(info.health, Stopped | Dead)`) which silently treats `Unhealthy` and `Restarting` as "enabled" — likely wrong for the UI badge.

### [Warning] `cache.rs` — `hub::cache::gc_git_checkouts` is documented but does not exist

- **Location**: `src/hub/install.rs:224-226` references `hub::cache::gc_git_checkouts` in a doc comment as the bound on the disk leak created by keeping `.git-cache/<id>` after a successful install for re-pin.
- **Trigger condition**: Any non-trivial usage of skill installs. Each install leaves a per-id clone directory behind. Without a sweeper, this leaks disk indefinitely.
- **Expected behavior**: Either the GC exists (per the doc) or the doc is removed and an alternative bound is documented.
- **Actual behavior**: `grep -rn "fn gc_git_checkouts" src/` returns **zero hits**. The function is referenced in a comment as if implemented, but no code path runs it. This was already surfaced as "added separately, not by this fix" in commit `938e71f32`; it remains unimplemented.
- **Suggested fix**: Either (1) implement `hub::cache::gc_git_checkouts` that removes `.git-cache/<id>` rows whose `entry_id` no longer has a live install, called from `prime_official_catalog_if_empty` or a periodic task, or (2) remove the disk-keeping optimization (clear `.git-cache/<id>` after install), or (3) update the comment to acknowledge it is unimplemented and assign an owner.

### [Warning] `start/mod.rs` — two `CatalogCache::open` call sites still exist (previously deferred)

- **Location**: `src/bin/aleph-server/commands/start/mod.rs:1226` (`early_catalog_cache`) and `src/bin/aleph-server/commands/start/mod.rs:2081` (extensions handlers block)
- **Trigger condition**: Boot path. Both sites open `~/.aleph/hub_catalog.db` with separate `Connection`s, then wrap in independent `Arc<CatalogCache>`. One feeds `BuiltinToolConfig` (the `hub_*` tool face), the other feeds the gateway `extensions.*` handlers.
- **Expected behavior**: One `Arc<CatalogCache>` shared by both faces (single instance, single connection).
- **Actual behavior**: Two independent caches both call `init_schema` (idempotent), both can hold their own mutex state, both serialize/deserialize the same SQLite file. The previous review flagged this as deferred; this audit confirms it remains in the same state and is load-bearing for the tool/RPC wiring split. The `WAL + busy_timeout` pragma mitigates the worst case (lost updates via SQLite file-level locking), but the structural ideal is still a single `Arc`.
- **Suggested fix**: Lift the early-open cache out of the `BuiltinToolConfig` constructor and thread the same `Arc<CatalogCache>` through both wire sites. Smaller refactor than feared — the constructor already takes the cache as a parameter.

### [Warning] `install.rs:216` — manifest save error is silently discarded after a successful install

- **Location**: `src/hub/install.rs:212-226` (`install_git_skill`, the trailing block after `std::fs::rename`).
- **Trigger condition**: `manifest.save(skills_dir)` returns an `io::Error` (disk full, permission revoked, FS error). The error is bound to `_` and discarded; the function returns `Ok(target.display().to_string())`.
- **Expected behavior**: At minimum, a `tracing::warn!` so the operator can see "install reported ok but the registry wasn't updated".
- **Actual behavior**: Silent partial failure. The skill is on disk and visible to the skill system, but the `InstallRegistry` does not list it as `SkillOrigin::Github`, so the next `official sync` could re-process it as if newly added. The doc-comment ("best-effort") describes the *intent* but the implementation is silent.
- **Suggested fix**: Replace `let _ = manifest.save(skills_dir);` with `if let Err(e) = manifest.save(skills_dir) { tracing::warn!(...); }` so the failure surfaces.

### [Warning] `trust.rs:165` — `nbsp_replaced` lowercasing bypasses the invisible-char strip pass

- **Location**: `src/hub/trust.rs:165-179`
- **Trigger condition**: Text with both zero-width characters *and* NBSPs interleaved through a phrase, e.g. `"ig\u{200b}nore\u{00A0}previous"`.
- **Expected behavior**: Both the invisible-char scan and the phrase scan should fire on this input.
- **Actual behavior**: The invisible-char scan iterates `text.chars()` directly (so `\u{200B}` is found). The stripped-text phrase scan uses `stripped` (so `\u{200B}` is removed and the phrase is matched). The `nbsp_replaced` scan uses raw `text` with NBSP→space — which **also** still contains the zero-width characters. So it is not strictly worse than the stripped scan, but the two phrase scans are not symmetric and a future "fold NBSP in `stripped`" change would silently regress. The current code is correct but the ordering of operations is fragile.
- **Suggested fix**: Compute a single normalized view (`strip_invisible_chars` + NBSP→space + lowercase) and run the phrase scan once on it. The current two-pass redundancy protects against regressions, but the redundancy is not documented in the test corpus.

### [Info] `cache.rs` — `init_schema` is `pub` but only called from `CatalogCache::open`

- **Location**: `src/hub/cache.rs:44` (`pub fn init_schema`), `cache.rs:68` (`pub fn upsert_entry`), `cache.rs:90` (`pub fn query_entries`), `cache.rs:128` (`pub fn clear_source`), `cache.rs:135` (`pub fn count_source`).
- **Risk**: The free functions on `&Connection` are `pub` to allow intra-module sharing, but the `Connection` itself is private (wrapped in `Arc<Mutex<Connection>>`), so external callers cannot get at one. They could call the free functions directly with their own `Connection`, bypassing WAL/transaction wrapping in `CatalogCache::upsert_many` and `CatalogCache::replace_source`.
- **Current impact**: low — no observed external call site, but `pub` invites future misuse.
- **Suggestion**: Tighten visibility to `pub(crate)`.

### [Info] `origin.rs` — `pub fn delete_origin`, `pub fn origin_for`, `pub fn spec_digest` are unused outside tests

- **Location**: `src/hub/origin.rs:52` (`spec_digest`), `origin.rs:148` (`upsert_origin`), `origin.rs:192` (`all_origins`), `origin.rs:199` (`origin_for`), `origin.rs:206` (`delete_origin`), plus `reconcile.rs::mcp_to_entry`/`plugin_to_entry`/`skill_to_entry`.
- **Risk**: `pub` functions with no in-tree callers outside `src/hub/` itself. The wiring audit's "pub fn added with no caller" red flag.
- **Current impact**: low — these are plausibly intentional library surface for tests and future handlers, and the binary only uses them via `record_install` and `cache.origins()`.
- **Suggestion**: Either `pub(crate)` (most of them are intra-module) or add a smoke test from a gateway handler if they are intended public API.

### [Info] `install.rs:144-148` — leaf-splitting guard allows single-segment "." or empty leaf only after splitting

- **Location**: `src/hub/install.rs:144-148`
- **Risk**: The guard `split(['/', '\\']).any(|seg| seg == ".." || seg.is_empty())` catches `..` segments and empty segments, but a leaf of exactly `"."` (single segment, not empty, not "..") passes. `safe_name.rsplit(['/', '\\']).next()` then returns `"."`, and `skills_dir.join(".")` resolves to the skills dir itself. The downstream `std::fs::rename(&staging, &target)` would fail at the rename step (can't rename into a non-empty directory), so the failure surfaces — but a malicious catalog entry `subdir: "."` would cause an opaque "rename failed" instead of the clear "unsafe skill subdir" error.
- **Current impact**: low (no path-escape; just an opaque error message and wasted staging IO).
- **Suggestion**: Tighten the predicate to also reject `seg == "."`.

### [Info] `install.rs:354-366` — `McpTransport::Stdio` for a remote spec silently maps to HTTP

- **Location**: `src/hub/install.rs:354-362` (`match transport { McpTransport::Sse => http(), McpTransport::StreamableHttp | McpTransport::Stdio => http() }`)
- **Risk**: A wire spec declaring `transport: "stdio"` on a remote URL is silently made into an HTTP connection. Comment claims "defensively" but the silent normalization is a future-debugging hazard.
- **Current impact**: low (no security implication — the URL is from the catalog, not user input — but a typo in the catalog will be silently fixed).
- **Suggestion**: Log a warning when the coercion happens, or return an error.

### [Info] `verify.rs:88-89` — doc-comment claims `symlink_metadata` "resolves symlinks" but it does the opposite

- **Location**: `src/hub/verify.rs:88-89`
- **Risk**: Doc-claim contradicts the function's actual behavior. `symlink_metadata` returns the lmetadata of the symlink itself (does NOT follow); `metadata` is what follows. The code is correct (it rejects symlinks via `file_type().is_symlink()`); only the comment is wrong.
- **Current impact**: none functionally, but readers will trust the wrong docs.
- **Suggestion**: Fix the doc comment to read "does not follow symlinks" and explain why.

### [Info] `secrets.rs::id_hash` — uses `sha2::Sha256`, but a hostile entry that mutates the same vault key after install can still shadow the secret

- **Location**: `src/hub/secrets.rs:32-49`
- **Risk**: 16 hex-char suffix is collision-resistant (2^64), and tests assert distinct ids sanitize to distinct keys. Not a bug.
- **Current impact**: none — the test `field_keys_are_collision_resistant_across_sanitize_collisions` is a real regression test for the previous collision issue.
- **Suggestion**: None — kept here only to confirm the previous-review's `requires_config`-related "inconsistent `requires_config` between stdio and remote" was correctly classified as by-design rather than fixed. `secrets_of` (stdio: `required || secret`) and `requires_config()` (stdio: only `required`) differ for `secret=true, required=false` env fields; in practice such a field would have a default, so the install still resolves. Documented as design.

## Notes

### Code quality
- **No `unsafe`, no `static mut`, no `lock().unwrap()`**. The lock used is `tokio::sync::Mutex`, whose `lock()` returns the guard directly (no `Result` to unwrap). The only `expect()`/`unwrap()` in production paths are in test code.
- **`map_err` is used consistently** for error context preservation in `catalog_client.rs` (`CatalogError::*`), `origin.rs` (`FromSqlConversionFailure`), `cache.rs` (`ToSqlConversionFailure`).
- **No `&s[..n]` byte-slicing** anywhere in `src/hub/`. All substring handling goes through `split`, `rsplit`, `replace`, `strip_prefix`, or `char_indices`.
- **HMAC constant-time comparison**: not applicable — the module only does SHA-256 over content for the integrity pin (`origin::spec_digest`, `marketplace::installer::directory_digest`), no HMAC. Content equality via `String == String` and `String.contains` is acceptable since these are local-only comparisons of attacker-controlled-but-trust-tier-gated text, not authentication tokens.

### Hub architecture evaluation
- The **single-source catalog** design (`ALEPH_HUB_URL` constant, no `SourceProvider` trait, `docs/engineering-reports/review-results/hub.md` §1) is well-scoped: ingest is the only ingest path, install resolution is a pure cache lookup of `ExtensionEntry.install_spec`, and the **replace** semantics keep the integrity reasoning local. The **three ingestion gates** (schema version → `validate()` → trust clamp) are layered correctly.
- The **install pipeline** (§4 of ALEPH_HUB.md) correctly enforces: HTTPS-only git URLs, path-traversal guard, SHA-256 before first write, atomic stage-then-rename, idempotent provenance write. The two consumer paths (RPC + agent tool) share `run_install` and `record_install` — verified in `src/gateway/handlers/extensions/install.rs:242` and `src/builtin_tools/hub/install_run.rs:276`.
- The **install provenance ledger** (`origin.rs`) is correctly designed: narrow scope ("what did we install, from what"), not the join key for "is it still installed" (which `reconcile.rs` reads from live backends). The "stale row is inert" property is upheld by `reconcile::mark_installed_state` only consulting the ledger after the live set reports installed.
- The **state machine in `reconcile::mark_installed_state`** handles the **name collision** case gracefully (warning + skip), and the **disambiguate-by-ledger** fallback is correct under the documented assumptions. The `update_available` predicate never lights the badge for a non-installed entry.

### Things I was uncertain about

1. **The `start/mod.rs:2081` dual-open.** I assumed both call sites run on every boot, but if the first one (`early_catalog_cache`) short-circuits on error before the second reaches its block (e.g., a flag-gated path), the dual-open might be tolerable. Reading `start/mod.rs:1217-1247` + `:2070-2135` side-by-side confirms both run unconditionally on a normal boot, so the warning stands.
2. **`mcp_server_id` not stripping `\`**. The previous review's Info-3 mentioned "mcp_server_id does not sanitize beyond `:/`". On Unix `\` is a valid filename character, so no escape. On Windows `\` is a path separator, but the path is always `.git-cache/<mcp_server_id(entry_id)>` and entry_ids are catalog-controlled (validated against `RESERVED_LOCAL_ID_PREFIX` and the `local:` namespace), so `\` shouldn't appear in practice. Left as Info rather than Warning — the threat model depends on the catalog publisher, not on user input.
3. **The `update_available` spec_digest re-computation**. If the catalog's `InstallSpec` is serialized with a different field order than at install time, the digest will differ even if the spec is logically identical. This is a potential false-positive update flag. I did **not** flag this because the catalog spec's `InstallSpec` is a Rust enum with declared field order — serde_json is deterministic for the same struct definition. Not a real issue today, but worth a regression test if the spec types ever get a HashMap field.
