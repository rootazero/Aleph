## Findings

### [Warning] `set_log_level` CAS-loop emits "Log level changed" trace even when level was already equal — pollutes audit log
- **Location**: `src/logging/level_control.rs:192-218`
- **Trigger condition**: Operator retries `logs.setLevel(info)` when the global level is already Info (e.g., boot idempotent retries, or two RPCs in quick succession with the same level).
- **Expected behavior**: Either (a) skip the "Log level changed" event when `old_u8 == next`, or (b) downgrade to `debug!` and emit a separate "no-op" notice. Audit log should reflect reality.
- **Actual behavior**: The CAS loop at lines 196-206 breaks with `current == next` early (`if current == next { break current; }`), so no atomic write happens. **But** the `tracing::info!(old_level, new_level, "Log level changed")` at lines 215-218 fires unconditionally with `old_level == new_level`. Repeated no-op set calls flood the audit log with misleading "level changed" entries.
- **Suggested fix**: Gate the `info!` on `old_u8 != next`; emit `trace!(old_level, new_level, "log level set was a no-op")` otherwise. Or fold the equality case into the loop as `break current` and only `tracing::info!` after the CAS-broke-with-different-value path.

### [Warning] `LogLevel::from_u8` silently fakes Info on a corrupt atomic and never corrects it — caller's view desyncs from storage forever
- **Location**: `src/logging/level_control.rs:84-100`
- **Trigger condition**: The atomic contains any `u8 > 4` — realistically only on memory corruption / ABI mismatch across hot-reload (the function-level comment correctly identifies this), but the recovery model is one-sided.
- **Expected behavior**: Either (a) reset the atomic to `Info` (the safe fallback) so subsequent reads of the same value go through the cheap path without the warn re-firing beyond Once, **and** so the atomic reflects the same fallback the caller observes; or (b) leave the atomic untouched but expose the corruption as an enum/triple-state in the public API.
- **Actual behavior**: The function warns once (correct), returns `Info` (correct for the immediate call), but does **not** `store` Info back into the atomic. Result: every subsequent `get_log_level()` reads the same corrupt `u8`, calls `from_u8` again, and silently returns `Info` — masking the corruption indefinitely. There is no path for an operator or test to detect that the storage is corrupt beyond the very first warn.
- **Suggested fix**: Inside `_ =>` arm, also `CURRENT_LOG_LEVEL.store(LogLevel::Info.to_u8(), Ordering::Release);` so the atomic and the reported value agree. Add a proptest that mutates the atomic via a `loom`-equivalent (or a private setter in a test) and reads back both via direct atomic load + `from_u8` — the test should pin the invariant that *they agree*.

### [Warning] `init_log_level` doc string disagrees with implementation: per-alephcore `target=` directives are adopted, not just "simple-level entries"
- **Location**: `src/logging/level_control.rs:120-126` (doc) vs `132-156` (impl)
- **Trigger condition**: An operator sets `RUST_LOG=alephcore=trace,info` expecting the doc to apply ("keep the last simple-level entry" — implying `info` wins). Or runs `RUST_LOG=alephcore=trace` followed by `RUST_LOG=` unset later.
- **Expected behavior**: Either the comment is narrowed to match behavior ("walk all directives; keep the last match, whether simple-level or alephcore-targeted") OR the implementation skips `target=` entries outside of `h2=warn`-style skip for non-alephcore.
- **Actual behavior**: Code at lines 145-152 adopts `alephcore=value` entries normally, so `RUST_LOG=alephcore=trace,info` ends at Info, and `RUST_LOG=alephcore=trace,debug` ends at Debug. The doc on lines 122-124 reads as if simple-level directives were the only thing kept ("keep the **last** simple-level entry (i.e. one without a `target=` prefix). Per-crate directives like `h2=warn` are skipped"). This is the **opposite** of what the code does. Confusing: a future contributor tightening the implementation to match the doc would silently break operator intent.
- **Suggested fix**: Edit the doc to: "walk all comma-separated directives; the last match wins, where a match is either (a) a plain-level directive, or (b) a `target=value` whose target names us (see `is_alephcore_target`). Per-target entries for non-alephcore crates (e.g. `h2=warn`) are skipped."

### [Warning] `test_set_log_level_returns_filter_unavailable_outside_runtime` does not verify the contract it claims to verify
- **Location**: `src/logging/level_control.rs:303-318`
- **Trigger condition**: Any CI run of `cargo test logging`.
- **Expected behavior**: A test named "...returns_filter_unavailable..." should at minimum attempt to assert that `set_log_level` returns `Err(FilterUnavailable(_))` when the shared logging is not initialized — the comment says "outside a runtime the result is FilterUnavailable" but then deliberately `let _ = result`s it.
- **Actual behavior**: The comment at lines 314-317 admits: "Both are correct — we only assert that the atomic was updated regardless of which branch fired." That is: the only meaningful assertion is `assert_eq!(get_log_level(), LogLevel::Warn, ...)`. The `let _ = result` discards the very thing this test is named for. Whether the failure path returns `Err` or `Ok` is up to whatever the surrounding test rig does — this test will catch a regression only of the wrong-Ok direction if the test was set up to FAIL, but with `let _ = result`, it catches nothing on the return path.
- **Suggested fix**: Pick a side and pin it. Either (a) run inside a process that does NOT call `init_component_logging`, then assert `assert!(matches!(result, Err(LoggingError::FilterUnavailable(_))));`; or (b) rename the test to `test_set_log_level_always_updates_atomic` and remove the FilterUnavailable claim from doc/title. Renaming is cheaper and avoids ordering coupling.

### [Info] `is_alephcore_target` accepts any `aleph-`-prefixed target — over-broad match surface
- **Location**: `src/logging/level_control.rs:156-161`
- **Risk**: A future helper crate named `aleph-tools-extra` or `aleph-foo-bin` would be silently treated as "our crate" and its directives would set our log level. Currently no such target exists in the workspace (`desktop/{macos,linux,windows}` are separate crates, `aleph-desktop-shared` exists as `aleph_desktop`). Edge case, not a present bug.
- **Current impact**: low
- **Suggestion**: Pin to a concrete allowlist (the three workspace crate names that trace back into `alephcore`: `alephcore`, `aleph_server`, plus the explicit RUST_LOG env's source-target if any) rather than prefix-match. Doc why any prefix match exists if it must remain.

### [Info] `LogLevel::parse` `trim_matches('\"')` is greedy — collapses internal quotes wrong
- **Location**: `src/logging/level_control.rs:39`
- **Risk**: `LogLevel::parse("\"foo\"bar\"")` → trim → `\"foo\"bar\"`, trim_matches → `foo\"bar`. Parses as `None`. Probably intended (string-quote stripping is a heuristic), but the contract is silent.
- **Current impact**: very low (RPC layer rejects unknown levels upstream with INVALID_PARAMS)
- **Suggestion**: Either document the contract ("strip a **single pair** of surrounding quote characters") or use `s.strip_prefix('"').and_then(|x| x.strip_suffix('"')).unwrap_or(s)` for symmetry.

### [Info] `set_log_level` calls `aleph_logging::set_log_level` which REPLACES the live EnvFilter wholesale — destroys per-crate RUST_LOG structure on every successful RPC mutation
- **Location**: `src/logging/level_control.rs:209` → `shared/logging/src/file_appender.rs:62-71`
- **Risk**: Operator sets `RUST_LOG=h2=debug,alephcore=info` for cross-crate tuning. A single `logs.setLevel(Info)` call replaces the live filter with bare `"info"`, losing `h2=debug`. RUST_LOG env remains untouched, so on next process restart the original structure returns — but for the lifetime of this process, h2 is now at the global level.
- **Current impact**: medium (silent surprise for operators); the level_control.rs doc does NOT mention that the per-crate structure gets dropped.
- **Suggestion**: Either (a) merge the new filter string with the existing `tracing_subscriber::EnvFilter` semantics instead of replacing it (e.g., set `*=info,alephcore=debug` form to scope only alephcore), or (b) document the destructive behavior in the `set_log_level` rustdoc so callers know the trade-off.

### [Info] `set_log_level` does not log on `FilterUnavailable` failure in the "level changed" path
- **Location**: `src/logging/level_control.rs:209-213`
- **Risk**: When the atomic is updated but the live filter fails, the function returns `Err` after a single `tracing::warn!`. The "Log level changed" `info!` is suppressed. An operator looking only at `info!` will think nothing changed; one looking at `warn!` will see a "filter unavailable" but no actual `level changed` breadcrumb — leaving the audit log fragmented across two levels.
- **Current impact**: low (the warn IS emitted, just at a different level)
- **Suggestion**: Emit `info!(old_level, new_level, "log level atomic updated; live filter failed: {error}")` before returning the error so the audit chain is whole.

### [Info] `INIT.call_once` runs RUST_LOG parsing at most once per process — test isolation is fragile
- **Location**: `src/logging/level_control.rs:127-156`; tests at `285-318`
- **Risk**: A test suite that runs `cargo test logging::` in a process already primed by a prior test (or by the binary's main that called `initialize_tracing`) will see the same RUST_LOG-derived value forever. The `TEST_LOCK: Mutex<()>` serializes parallel runs but doesn't reset INIT. Today `test_get_set_log_level` / `test_set_log_level_returns_filter_unavailable_outside_runtime` only modify the atomic, never RUST_LOG, so this is latent.
- **Current impact**: low
- **Suggestion**: Either add an `unsafe fn reset_for_tests()` behind `#[cfg(test)]` that resets the atomic + a `Once` reset hook (note: `std::sync::Once` cannot be reset — would need `OnceLock<bool>` + a generation counter) OR document the constraint in the test module's header.

### [Info] `mod.rs` re-exports cover the four pub surface symbols but inherit `pub(crate)` `init_log_level` invisibly — wiring is correct but the surface is small
- **Location**: `src/logging/mod.rs:10-12`; `src/lib.rs:168`
- **Observation**: `LogLevel::{parse,to_filter_string,default,PartialEq,Eq,Clone,Copy,Debug}` are accessible on the re-exported type, and `get_log_level` / `set_log_level` / `get_log_directory` / `LoggingError` are re-exported. `init_log_level` is `pub(crate)` and only ever called from within `level_control.rs`. No `pub fn` is orphaned. `pub use crate::logging::LogLevel;` at `lib.rs:168` lifts the type to `alephcore::LogLevel` for external consumers. Wiring audit clean.
- **Suggestion**: None — flagging only because the audit checklist requires explicit confirmation that each re-exported symbol has a live consumer (verified via grep across `src/`, `desktop/`, `shared/`, `bin/`, `tests/`).

- No mutex unwrap on user-facing paths. Test paths use `unwrap_or_else(|e| e.into_inner())` consistently (P7 compliance).
