## Findings

### [HIGH] `guard.rs:103-118` — Prompt-injection regexes are unbounded against `MAX_SCAN_BYTES = 8 MiB` of adversarial input; ReDoS window is the per-file cap, not a per-iteration cap
- **Category**: security / DoS
- **Description**: The four `injection_*` patterns are each `(?:a|b|c)*\s+(?:x|y|z)*` — star-quantified alternation groups chained with `\s+`. `RegexSet` compiles them to an NFA that, on adversarial input, backtracks across the alternation groups. The per-file `MAX_SCAN_BYTES = 8 MiB` guard (line 136) bounds the *size* of a single regex invocation but not its *time* — a 8 MiB string of repeating `all the your these those ...` characters walks the full backtracking state for each `\s+` position. The other branches of the regex (e.g. `destructive_rm_rf_root`, `curl_pipe_shell`) also use bounded `{0,N}` quantifiers, so the cost is dominated by the four injection patterns. A malicious skill bundle whose biggest file lands just under 8 MiB (or is split into chunks just under that) and contains a payload constructed to maximise NFA backtracking can spend many CPU seconds on a single `scan_skill_directory` call, which runs inside the install RPC path.
- **Suggested fix**: Either (a) bound the input string at a lower cap (≤256 KiB matches the rest of the skill pipeline's typical sizes and makes the backtracking cost tolerable), or (b) replace the four `injection_*` patterns with literal-substring scanners (the threat model is "the obvious phrasing", not "the determined attacker" — `str::contains_ignore_ascii_case` on a curated list of stems matches the doc-comment's stated goal and is linear-time). If the regex shape must stay, add a `regex::Regex::captures_iter` early-exit on elapsed wall-clock via `std::time::Instant`.

### [HIGH] `mod.rs:628-650` — `SkillSystem::reload_file` and `SkillSystem::rescan_dirs` skip the install-time guard; a SKILL.md tampered after install loads with no `Dangerous`/`Caution` audit
- **Category**: security / guard bypass
- **Description**: The `SkillSystem` facade exposes three load paths: `init`, `rescan_dirs`, and `reload_file`. None of them call `guard::scan_skill_directory` or `guard::scan_content`. The guard is only called by the external install RPC handler (which lives outside this module and is the only place that knows to call `install_allowed` / `merge_verdicts` before writing the skill onto disk). Once a skill is installed, an attacker who can write to `<skills_dir>/<skill>/SKILL.md` — a co-tenant LLM tool via `skill_manage(action='edit')`, a malicious plugin, or any process running as the daemon user — can inject the dangerous patterns (`/dev/tcp/`, `curl | sh`, `eval base64 -d`) and the next `reload_file` / `rescan_dirs` will register the new manifest without any guard verdict. The prompt-injection patterns are even more relevant here because the skill body is injected directly into the system context.
- **Suggested fix**: Route every parse path through the guard. Concretely: `parse_skill_file` takes the file's bytes (already loaded by `fs::read_to_string`), so call `guard::scan_content("SKILL.md", bytes.as_bytes())` and gate `parse_skill_content` on `install_allowed(verdict.level, TrustLevel::Community)`. The per-skill dir-scan should be `merged` with the per-file scan when loading a directory so a multi-file injection still trips the verdict. The `SkillSystem::reload_file` API contract becomes "reload iff the on-disk content still passes the same trust gate that admitted it".

### [HIGH] `manifest.rs:373-414` (`split_frontmatter`) + `manifest.rs:152-168` (`parse_skill_content`) — no size cap on the loaded SKILL.md, no depth cap on the YAML; serde_yaml billion-laughs OOM possible
- **Category**: security / DoS
- **Description**: `parse_skill_file` calls `std::fs::read_to_string(path)` with no `MAX_BYTES` check, then hands the whole string to `serde_yaml::from_str` for the frontmatter. Two independent DoS vectors stack: (1) a multi-hundred-MiB SKILL.md is read into memory before any parse, and the file lock path inside `parse_skill_content` holds no lock so any concurrent reader also copies the bytes — a 1 GiB file under a `SkillSystem::rescan_dirs` plus an unrelated status build is two 1 GiB allocations; (2) serde_yaml has a default recursion limit (100) but no explicit limit is configured in the deserializer, and the YAML schema here (`RawFrontmatter` → nested `RawEligibility` → nested `RawInstallSpec` → arbitrary `serde_yaml::Value` for `automation`) accepts nested mappings and sequences — a hand-crafted YAML with `a: &a [*a, *a, *a, ...]` aliases expands exponentially. The guard's `MAX_SCAN_BYTES` only fires for the scan-content path, not for the parse path that runs first inside `rescan_dirs`.
- **Suggested fix**: Cap `read_to_string` with `fs::metadata(path)?.len()` and bail at a `MAX_SKILL_FILE_BYTES` constant (~1 MiB is plenty for any legitimate SKILL.md). For the YAML, build a `serde_yaml::Deserializer::from_str` and pass `Deserializer::from_str` with an explicit `recursion_limit` via a custom `YamlRead` wrapper, or reject deeply-nested input in `RawFrontmatter` via `#[serde(deserialize_with = "…")]` validators on each nested field. The same constant should gate `read_to_string` in `cooccurrence.rs` (no — cooccurrence has its own MAX_ENTRIES) and in `usage.rs` (no — bounded by HashMap size).

### [HIGH] `mod.rs:323-340` (`owning_dir`) — O(dirs × entries) filesystem walk per status/use/locate, no cache; serialised via `spawn_blocking` so it bypasses the tokio budget under load
- **Category**: performance / DoS
- **Description**: Every call to `locate_skill_file`, `usage_for`, `set_pinned`, `set_skill_state`, `record_use`, `record_patch`, `remove_skill` invokes `owning_dir(id)`, which does `dir.join(id).join("SKILL.md").exists()` for **every registered skills_dir**, then falls through to a `UsageStore::new(dir).get(...)` scan for every registered dir. With 3 registered dirs and 200 skills, a `full_status` call (which itself doesn't use this path) followed by 200 `record_use` calls = 200 × 3 = 600 stat calls per turn, plus a `tokio::task::spawn_blocking` per use so the runtime's blocking-task budget is consumed for path-only checks. There is no caching of the `(skill_id → owning_dir)` mapping; the registry already knows which `scan_directory` call produced each manifest, and that data is dropped on rescan.
- **Suggested fix**: Store `(SkillId, Option<PathBuf>)` in the registry alongside the manifest, populated by `scan_directory` (the walk already knows the dir it descended into). `owning_dir` becomes an O(1) lookup; remove the `spawn_blocking` and the fallback `UsageStore` scan entirely (if the dir for the id is missing, the skill is not installed). Same fix unblocks `skill_dir_for_id` at line 359 which currently parses every `SKILL.md` it finds.

### [MEDIUM] `cooccurrence.rs:148-175` (`cluster_chains`) — `Vec::contains(&e.skill)` is O(n) per element → O(n²) chain build; for MAX_ENTRIES=512 the worst case is ~131 k comparisons, easily minutes under repeated calls
- **Category**: performance
- **Description**: Inside the chain-build loop, `if !current.contains(&e.skill) { current.push(...) }` is a linear scan of the chain so far. With `MAX_ENTRIES = 512` and a worst case where every entry is a distinct skill, the total work is 1+2+…+512 ≈ 131 k `String::eq` comparisons — bounded but lazy. The downstream consumer is `memory::dreaming::stages::WorkflowProposalStage`, which calls `cluster_chains` on every dreaming cycle, and dreaming is the single cost the sidecar exists to amortise.
- **Suggested fix**: Replace the in-chain dedup with a `HashSet<String>` tracked alongside the `Vec<String>`; insert + push remain O(1) amortised. The `Vec` is still needed for "first occurrence order" (which `HashSet` doesn't preserve), but the membership test moves to O(1).

### [MEDIUM] `config.rs:107-125` (`SkillsConfig::save`) — fixed-name `path.with_extension("toml.tmp")`; sibling of `utils::atomic_io::write_atomic` already in the workspace does this right
- **Category**: security / race
- **Description**: `save()` writes to `path.with_extension("toml.tmp")` (i.e. literally `skills.toml.tmp`) via `std::fs::write` + `std::fs::rename`. Two concurrent saves — one from the daemon's `update_config` path, one from a hypothetical second daemon process or a hand-edited script — both write to the same tmp path, and `fs::rename` is not atomic on Windows against an open handle. The sibling primitive `utils::atomic_io::write_atomic` (`src/utils/atomic_io.rs:18-37`) already exists in the workspace and uses `tempfile::Builder::new().prefix(".aleph_atomic_").tempfile_in(parent)?` so the tmp filename is unique per call, plus `sync_all` before `persist`. The twin `plugins.toml` writer cited in the doc-comment was already supposed to be the model.
- **Suggested fix**: Replace the body with `write_atomic(path, content.as_bytes())` (the function takes `&[u8]` and `content` is already a `String`). Add a test that calls `save()` twice in two threads against the same path and asserts the final file is byte-identical to one of the two writes (not a torn half).

### [MEDIUM] `installer.rs:30-50, 76-83` — `Download` kind's `-o <package>` is interpolated **unquoted** in the curl command; the allowlist plus `..`-segment check is the only protection; no canonical-path / symlink resolution
- **Category**: security / command injection (defence-in-depth)
- **Description**: The `Download` branch emits `format!("curl -fsSL -o {} '{}'", spec.package, url)`. `spec.package` is the **output path** the manifest sets, interpolated unquoted — the only protections are `is_safe_shell_arg` (ASCII alnum + `-_./:@+=~`) and `is_safe_path_arg` (additional `..`-segment rejection). The check is correct against a single-segment `..`, but it is silent against (a) a `..` embedded inside a longer segment (`./..hidden/foo` passes — `..hidden` is not equal to `..`), (b) a `package` value that, after the `curl -fsSL -o <path>` runs, lands in a directory that the rest of the install pipeline assumes is *inside* the skills dir (the snapshot picks it up regardless of where it was written). The URL is single-quoted so shell metacharacters in the URL are inert, and `'` is rejected by the URL check, but a URL containing `\n` is caught only by `c.is_control()` — single CR or LF inside a URL is enough to break some shells; the check covers that, but the check is **only applied to the URL**, not to the package.
- **Suggested fix**: Quote the `-o` argument too: `format!("curl -fsSL -o '{}' '{}'", spec.package, url)` — once both sides are single-quoted the only escaping needed is `'`, which both fields already reject. Add a canonical-path check post-build: `std::path::Path::new(package).components()` must not include `Component::ParentDir` (already true) and must, after `std::fs::canonicalize` against the skills dir root, start with that root. The `..hidden` bypass alone justifies the canonical-path check.

### [MEDIUM] `eligibility.rs:107-114` — `evaluate_spec` does `which::which(bin)` for every `required_bins` entry on every snapshot rebuild; no cache, no parallelism; O(skills × bins) PATH lookups per status build
- **Category**: performance
- **Description**: `for bin in &spec.required_bins { if which::which(bin).is_err() { ... } }` is a sequential PATH-walk per bin, per skill, per `rebuild_snapshot` (which is called by every `update_config`, `set_skill_state`, `remove_skill`, `install_dependency`, and `rescan_dirs`). `which::which` is itself a sub-millisecond syscall but it walks every directory in `$PATH`. A skill declaring 10 `required_bins` × 100 skills = 1000 PATH walks per rebuild, every rebuild. The `which` crate has no caching across calls (it re-walks each invocation) and `EligibilityService` is stateless (`#[derive(Default)]`, no field). `full_status` then re-evaluates each manifest independently, doubling the work.
- **Suggested fix**: Memoise per-process via a `Mutex<HashMap<String, bool>>` on `EligibilityService` (the service already wraps state — adding a cache field is one extra constructor parameter, or just `LazyLock`). Better: stash `Vec<bool>` per-bin alongside the manifest at install time so the snapshot builder doesn't redo the work. Either is O(skills) per rebuild instead of O(skills × bins).

### [MEDIUM] `snapshot.rs:120-180` (`build`) — clones every eligible manifest into the snapshot, then `mod.rs:485` overwrites `prompt_budget`; the deep-clone of every manifest on every rebuild is the dominant allocation cost of the snapshot path
- **Category**: performance / memory
- **Description**: `SkillSnapshot::build` does `let mut effective = match entry.and_then(|e| e.scope_override.clone()) { Some(scope) => { let mut m = manifest.clone(); m.set_scope(scope); m } None => manifest.clone() }` per eligible skill — a full `SkillManifest` clone (13 owned `String`/`Option<String>`/`Vec`/`Vec<InstallSpec>` fields, `InstallSpec` itself contains 4 strings). For 200 eligible skills this is ~200 × ~600 B = ~120 KB allocated and freed per rebuild, every time. `mod.rs::rebuild_snapshot` then overwrites `new_snapshot.prompt_budget = prompt_budget;` (line 489) so the default-budget rendering inside `build` is wasted (the field is replaced before the snapshot is published).
- **Suggested fix**: Wrap the manifest in `Arc<SkillManifest>` once at registration (registry's `HashMap<SkillId, SkillManifest>` becomes `HashMap<SkillId, Arc<SkillManifest>>`), and have the snapshot hold `Vec<Arc<SkillManifest>>`. The scope override clone becomes a cheap `Arc` clone. As a bonus, the `eligible_manifests` Vec in the snapshot no longer needs to deep-clone for the user's scope override — hold an `Arc<SkillManifest>` and a `PromptScope` override separately.

### [MEDIUM] `mod.rs:1050` — facade at 1050 LoC mixes the `SkillSystem` struct, free helper functions (`scan_directory`, `is_skill_file`, `default_skill_dirs`, `plugin_id_from_path`, `guess_source`), module constants, and `OnceLock` cache state; `R10` thin-harness discipline is the wrong shape for this file
- **Category**: architecture
- **Description**: `mod.rs` is the largest file in the module by 2.5× and combines four unrelated concerns: (1) the `SkillSystem` struct + its async facade (lines 60-510, ~450 LoC), (2) the `scan_directory` / `is_skill_file` recursive walker (~70 LoC), (3) `default_skill_dirs` / `plugin_id_from_path` / `guess_source` path heuristics (~150 LoC), (4) tests (~380 LoC). The path-heuristics block is genuinely a separate concern — it knows about `~/.claude/skills` and `plugins/<id>/skills` shapes but lives in the same file as the registry façade. `R10` doesn't apply directly (`mod.rs` is not the harness), but `P2` (high cohesion) and the project rule that "files over 500 lines should be split" (CLAUDE.md, code-org section) both push for a split.
- **Suggested fix**: Move the free functions and `guess_source` into a new `src/skill/discovery.rs` (it already reads like one cohesive module — path → `SkillSource` derivation). Move the facade into `src/skill/system.rs`. `mod.rs` then becomes the re-export + shared `SkillSystem` type file, ~50 LoC. The `static CACHED_MANIFEST: OnceLock<...>` on line 850 moves with `guess_source`.

### [MEDIUM] `manifest.rs:226-247` (`parse_install_specs`) — unknown `kind` is silently dropped via `filter_map`; a typo'd install spec is a no-op with zero diagnostic
- **Category**: logic / observability
- **Description**: The `kind` match covers `brew|apt|scoop|winget|npm|uv|go|download`; anything else returns `None` and `filter_map` drops it. A typo like `kinf: brew` or a future kind added to `InstallKind` but not to this match yields an empty `install_specs` and the dependency the user expected to be installed just never appears. The parse continues (other install specs in the same `install:` block are kept), so the manifest looks fine and the user has no signal that one entry was lost. `trace::warn!` is not emitted.
- **Suggested fix**: Branch on the unknown kind and emit a `tracing::warn!(skill = %manifest.name(), raw_kind, "install: unknown kind — entry ignored")` before returning `None`. Better, return a typed `Result<Vec<InstallSpec>, SkillParseError::UnknownInstallKind(String)>` so the caller can decide whether to surface the error or downgrade to a warning; the test for typo-detection becomes a single `assert!(matches!(err, SkillParseError::UnknownInstallKind(_)))`.

### [LOW] `preprocess.rs:166-185` (`frontmatter_allows_inline_shell`) — re-parses the frontmatter a second time per skill load; the parser that produced the manifest already saw the field
- **Category**: quality / performance
- **Description**: `preprocess_skill_content` calls `frontmatter_allows_inline_shell(content)` which does a full `serde_yaml::from_str::<Probe>` on the frontmatter string — *after* `parse_skill_content` already parsed it. Every `skill_read` (and the inline-shell option is read on every skill load) does the YAML parse twice. The `Probe` struct here is a separate type from `RawFrontmatter`, so the cost is not just "do the same parse twice" — it's "do two unrelated parses that overlap on 90% of the fields". The single-parse fast path lives on the manifest side; reaching the inline-shell check happens after `parse_skill_content` has already returned.
- **Suggested fix**: Add an `allow_inline_shell: bool` field to `RawFrontmatter` (with `#[serde(default)]`) so the parser surfaces the flag in one pass, and `frontmatter_allows_inline_shell` becomes a `SkillManifest::allows_inline_shell()` accessor. Plumb the flag through `SkillManifest` (with a setter mirroring the existing `set_when_to_use` etc.) so the policy lives next to the other frontmatter-derived state.

### [LOW] `usage.rs:155-175` (`mutate`) — reads the entire `.usage.json` sidecar into memory on every record; O(n_skills × sidecar_bytes) per use
- **Category**: performance
- **Description**: `mutate` is the single chokepoint for `record_view`, `record_use`, `record_patch`, `set_state`, `set_pinned`. Each call does `self.load_map()` (full `read` + `serde_json::from_slice`) → mutate → `self.save_map` (full `write`). With 1 000 skills in the sidecar, that's ~50 KB parsed + ~50 KB serialised per skill use, serialised through a cross-process fs2 lock. A user typing `/skill-a` ten times in a minute — and `record_use_in_dir` is now wired into both the slash path and `skill_read` — pays ten full-map round trips.
- **Suggested fix**: Either (a) keep the sidecar flat but cache the loaded map in the `UsageStore` struct (with mtime invalidation so concurrent external edits still take effect), or (b) split the sidecar by skill id (`<dir>/.usage/<id>.json`) so each mutate is O(file_size) for that skill only. (a) is the cheap one and matches the existing cooccurrence sidecar's lifetime; (b) is a bigger change but lines up better with the per-skill `state`/`pinned` model.

### [LOW] `registry.rs:33-44` (`register`) — silently rejects lower-priority newcomer; the docs claim `register_all` is the dedup point, but the rejection is a no-op with no `tracing::debug!`
- **Category**: logic / observability
- **Description**: `register` returns `bool` but the doc-comment only describes the `true` branch; on the `false` branch (lower-priority duplicate) the function returns `false` and the new manifest is dropped without any log. A user who installs a higher-priority plugin that *should* override a bundled skill but doesn't (because of a priority-table mistake, or because the source-mapping mis-classifies one of them as `Bundled` instead of `Plugin`) gets no diagnostic — the bundled copy just keeps winning. `register_all` swallows the `false` return for every call.
- **Suggested fix**: Emit `tracing::debug!(skill_id = %id.as_str(), existing = ?existing.source(), newcomer = ?manifest.source(), "register: lower-priority duplicate rejected")` in the rejection branch. Add a sibling `tracing::warn!` for a much rarer case: when an equal-priority duplicate is rejected (currently silent) — this is the case where two `Workspace` skills collide and the user genuinely has no way to tell which one won.

### [LOW] `mod.rs:687-707` (`scan_directory`) — `entries.flatten()` silently drops `Err(_)` from `read_dir`; a partial-walk is invisible
- **Category**: quality / observability
- **Description**: The recursive walker uses `for entry in entries.flatten() { … }` which discards `Err(io::Error)` entries from `read_dir` — exactly the failure shape CLAUDE.md §0 names ("a `walkdir` mid-walk error is dropped… silently indexes a partial vault"). When `read_dir` returns `Err` mid-iteration (a subdirectory's permissions flip during the walk, a file vanishes between `next_entry` and the entry), the loop silently skips that entry. The result: the `SkillSystem` registers a partial registry, `full_status` is missing skills, and the user has no audit log to investigate.
- **Suggested fix**: Replace `for entry in entries.flatten()` with `for entry in entries { let entry = match entry { Ok(e) => e, Err(e) => { tracing::warn!(dir = %dir.display(), error = %e, "skill scan: read_dir entry error"); continue; } }; }` — pattern matched, error named, error path surfaced. Same change applies in `manifest.rs::split_frontmatter` (already uses `?`-style errors so fine) and in `guard.rs::scan_skill_directory_inner` (uses `entries.flatten()` at line 217 with the same silent-drop shape).

### [LOW] `guard.rs:208-237` — scan can be evaded by splitting injection across many small files; the per-file `scan_content` is correct, but `merge_verdicts` joins them into a flat finding list that ignores cross-file context
- **Category**: security / design limitation
- **Description**: `scan_skill_directory` scans every file individually and `merge_verdicts` concatenates the finding lists. A bundle structured as `<SKILL.md>` + `<scripts/legit.sh>` + `<docs/intro.md>` where the payload is fragmented — e.g. `eval` at the end of one file, `base64 -d` at the start of the next — passes the per-file scan (each file's content independently has no dangerous pattern) but the runtime combination has both halves. The 8 MiB per-file cap reinforces the bypass: a malicious bundle of fifty 1 MiB files is never scanned as a single corpus. This is the classic "individual-pass / cross-corpus" limitation of pattern scanning; the doc-comment acknowledges "a regex scan is bypassable; this catches the obvious" so the maintainer is aware.
- **Suggested fix**: Document the limitation explicitly on `scan_skill_directory` ("per-file scan only — adversarial bundles structured across files are not detected"). The structural fix would be a corpus-level concatenation scan on `; [warn]` for the install path: take `total_size = sum(file_size for file in dir if not oversized)` and if `total_size ≤ MAX_SCAN_BYTES`, concatenate and re-scan once. Note the cost: this is a double scan of legitimate bundles, so gate it behind the trust level (only for `Community`).

### [LOW] `prompt.rs:46-52` — 32-bit content hash has ~1-in-4B collision risk; acknowledged in doc, but two skills with identical bodies still share the version tag
- **Category**: logic / design limitation
- **Description**: `content_version` truncates `Sha256` to 4 bytes (8 hex chars = 32 bits). For change-detection of a single skill (the stated goal) a 1-in-4B collision per turn is acceptable — the worst case is one stale re-read. But the version tag is rendered into the global `<available_skills>` index, and the *cross-skill* collision rate is much higher: with 100 skills in the index, the expected number of hash collisions between *different* skills with identical bodies is ~100 choose 2 × 1/2³² ≈ 1.2 × 10⁻⁶, and identical bodies are realistic (a copy of an upstream skill placed in `Workspace`, or two plugin skills backed by the same `~/.claude/skills` clone). When the model reads `SkillA`'s body once, sees the same `<version>` on `SkillB`, and skips `skill_read` for `SkillB`, it has loaded `SkillB`'s body from a cache populated by `SkillA` — two distinct skills with different instructions, identical bytes by coincidence.
- **Suggested fix**: Compose the hash from `(skill_id, content_sha256)` — `Sha256(skill_id || "|" || content_sha256)` truncated to 8 hex chars. Cross-skill collisions collapse to "same id and same body" which is one skill, not two. The cost is four bytes added to the input and a marginally higher per-render compute; for 100 skills this is negligible.

## Cross-References

- `guard.rs` (HIGH #1, #2) ↔ `mod.rs` (HIGH #2): the guard exists but the runtime load paths skip it. The two together are the trust-boundary gap — fixing only one (e.g., adding a regex-bounded scan) without also wiring it into `parse_skill_content` leaves the seam open.
- `manifest.rs:152` (HIGH #3) ↔ `guard.rs:136` (`MAX_SCAN_BYTES`): the same file-size bound the guard uses is the bound `parse_skill_file` should adopt. They diverge today because they live in different modules and the parser doesn't import the guard's constant.
- `installer.rs:30-83` (MEDIUM #7) ↔ `manifest.rs:226-247` (MEDIUM #11): the install path's hardening lives in the shell-string builder, but the path the manifest author writes has no validation — a `Download` spec with `package: ../relative/path` is rejected only because of the `..` segment check, and a `kind: breew` typo in the same block is silently dropped. The hardening and the laxness are in two different files and could be unified by pushing both into the manifest parser (where the trust boundary already lives).
- `mod.rs::owning_dir` (HIGH #4) ↔ `mod.rs::scan_directory` (LOW #15): `scan_directory` already walks every file and could record the `(path → id)` mapping into the registry, removing `owning_dir`'s filesystem walk. The two never talk to each other.
- `snapshot.rs::build` (MEDIUM #9) ↔ `mod.rs::SkillSystem` (MEDIUM #10): the snapshot's `Vec<SkillManifest>` deep-clone is the cost of not wrapping the manifest in `Arc` at the registry level; the refactor that fixes the facade split can introduce the `Arc` at the same time.
- `cooccurrence.rs::cluster_chains` (MEDIUM #5) ↔ `usage.rs::mutate` (LOW #13): both sidecars are scanned/serialised in full on every write. The dream pipeline reads `cooccurrence` once per cycle, so the cost is on the write path; the user slash path hits `usage` much more often. The fixes are independent (HashSet vs cached map) but the cluster is the same shape.

## Strengths

- `guard.rs`'s prompt-injection catalog (`injection_override_instructions` / `reveal_system_prompt` / `deceive_user` / `role_override`) plus the deferred-to-SSOT `unicode_guard::is_invisible_char` check covers the obvious Trojan Source / ASCII-smuggling vectors that the original 14-char local list missed. The `Caution` classification (allowed for `Trusted`, blocked for `Community`) is the right gradient for prompt-engineering-themed skills that legitimately quote the phrasing.
- `snapshot.rs::build`'s archived-set / scope-override / config-disable handling is the right shape — `eligible_manifests` is the projected set the prompt layer needs, `eligible` keeps the broader status set, and the deleted `prompt_xml` was the right CUT (a full render paid for on every rebuild to produce a string no one consumed).
- `prompt.rs::build_skills_prompt_xml_with_budget` has the right compact-tail-not-omitted degradation: a 150-skill library under the default budget stays *fully discoverable* via name + when, even when only the first ~12 kB carries descriptions. The omission `<note>` only fires when `max_skills` actively drops entries.
- `installer.rs`'s `is_safe_shell_arg` / `is_safe_path_arg` allowlist plus `..`-segment rejection blocks the obvious command-injection and path-traversal paths the doc claims; the gap is the depth of the defence (no canonical-path check, no symlink resolution) rather than the shape.
- `usage.rs`'s `with_file_lock` chokepoint is the right SSOT for cross-process safety — every mutator routes through it, the lock is on a sidecar so the data file is never held across the lock window, and `concurrent_bumps_do_not_lose_counts` (test at line 444) is the right shape of regression test for the lock contract.
- `registry.rs::register`'s priority-based dedup is the simplest correct shape for the override problem; the gap is the *observability* of the rejection (LOW #13), not the *correctness* of the replacement.
- `mod.rs::guess_source`'s `plugin_id_from_path` is the right robustness move — taking the component immediately *before* the `skills` segment (rather than assuming it's the component right after `plugins`) handles both `plugins/<id>/skills` and `plugins/cache/<market>/<id>/skills` layouts without a separate code path.
