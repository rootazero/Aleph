## Findings

### [HIGH] `session/in_process.rs:184-227` — Concurrent `wake()` doubles the `SessionWoken` marker
- **Category**: logic
- **Description**: Two `wake()` calls racing each other both remove the old `senders[id]`, both run `spawn_actor`, and the second `spawn_actor` finds the first one's fresh sender still `!is_closed()`, returning the same sender via the double-check branch. Both calls then enqueue a `SessionWoken` event on that single inbox. The new actor processes both markers and appends two `SessionWoken` rows to the event log; `load_head_seq` advances by 2 instead of 1; the consumer that observes the `wake` sees two "session woken" transitions where it expected one. The single-marker invariant that `wake`'s doc comment relies on ("Capture prior_head BEFORE spawning the new actor so the marker records the exact head the consumer observed pre-wake") is not enforced anywhere — both wake()s read the same `prior_head`, but only the first marker is semantically correct. The second is a duplicate stamped with a stale observation.
- **Suggested fix**: Serialize concurrent `wake()` calls on a per-session mutex (e.g. `tokio::sync::Mutex<()>` keyed by `SessionId`) so only one caller can run the "shutdown old / spawn new / emit marker" sequence at a time. The second caller waits and re-reads `head_seq` after the first has finished — its handle is just `attach`'s output plus the now-correct prior_head, not a re-emit. Cheap: per-key `Mutex` only held for the duration of the wake dance.

### [HIGH] `session/in_process.rs:21` + `session/actor.rs:88-95` — `broadcast::Sender::send` discards overflow; laggy subscribers silently miss events
- **Category**: logic / DoS
- **Description**: `BROADCAST_BUFFER = 256` slots. `let _ = self.broadcaster.send(record);` in `actor.rs` discards the `SendError<T>` returned both when there are zero receivers AND when the buffer is full. The actor continues as if delivery succeeded. Subscribers who fall 256 events behind (UI thread paused, slow downstream consumer, debugger attached) get `RecvError::Lagged(n)` on their next `recv()`, but the actor never knows; from its perspective every event was "broadcast". The doc-comment does not advertise this best-effort semantics, and the projector-side consumers documented elsewhere in the codebase rely on the broadcast for "live" views — a 257th event within a tick means the live view silently shows a hole, with no event emitted, no log line, and no path for the subscriber to know which `seq` was the first missed one. The retry path inside `EmitEvent` will also fail silently here: if `head_seq` advanced via self-heal, the recovery path doesn't re-broadcast either.
- **Suggested fix**: Either (a) make the actor subscribe to its own broadcast before sending and treat a `SendError` as "no live subscribers, skip the broadcast" while logging at debug; or (b) replace the fire-and-forget `let _ =` with a tracing event keyed on the broadcast drop, so a slow consumer shows up in `tracing` rather than as a silently missing row in the live UI. Either way, document the contract: "broadcast is best-effort; subscribers must call `get_events(from=last_seen_seq+1)` to recover from `Lagged`." A `LastSeenSeq` advisory returned on the broadcast subscription would close the loop.

### [HIGH] `session/actor.rs:88-96` — Observer panic strands the broadcast and the caller's reply
- **Category**: logic / reliability
- **Description**: The emit order is `append OK → head_seq = seq → observer.on_appended → broadcast → reply`. If `observer.on_appended` panics (a fully-allowed path: the trait is `Send + Sync` only, with a doc note that says "non-blocking" but no enforcement), the actor task dies. The event is durable in SQLite, but the broadcast never happens and the `reply` oneshot is dropped — so the caller awaiting `rx.await` gets `RecvError` and surfaces `SessionError::ActorShutdown`, with no signal that the event was in fact appended. Subscribers never receive the event for this turn nor for any subsequent turn until the session is manually re-attached. A retry by the caller collides on `(session_id, seq)` and propagates as `Storage(...)` — the opposite lie ("nothing was written"). The whole reliability story of the actor depends on the observer behaving; the trait spec does not require it to.
- **Suggested fix**: Wrap the observer call in `std::panic::catch_unwind` (it is `UnwindSafe` since the closure only takes `&self.id, &record`) and on panic log at `error!` and continue. Better still, reorder the emit to `broadcast → reply → observer.on_appended`, so the durable-write contract is honoured regardless of observer health. Observers that need to see the event before subscribers see it have the append receipt already (the event is durable before any of this runs); the ordering is a leftover, not a guarantee.

### [HIGH] `session/actor.rs:130-141` — Idle-timeout fires with a buffered command; the command is silently dropped
- **Category**: logic / reliability
- **Description**: `tokio::select! { biased; cmd = self.inbox.recv() => ..., _ = tokio::time::sleep_until(idle_deadline) => return; }`. With `biased`, the recv arm is polled first; if a command is already buffered, it is consumed and idle is reset. But if no command is in flight at the exact `Instant` the deadline hits, the sleep arm wins, the actor returns, and the `mpsc::Receiver` is dropped — taking any command that lands in the buffer between the sleep returning and `run()` returning with it. The `mpsc::Sender::send` of that command returns `Ok` (the buffer had room — `COMMAND_BUFFER = 64`), the caller's `oneshot::Receiver` then gets `RecvError` because the actor's oneshot `Sender` was dropped with `run()`. The caller surfaces `SessionError::ActorShutdown` and cannot tell whether the event was appended. For an idle-timeout this is the right behaviour for a "no traffic" case, but the door is open to losing exactly one in-flight command in a narrow window — and the error returned to the caller is identical to a "real" actor shutdown, with no `was_appended` flag.
- **Suggested fix**: Before returning, drain the inbox non-blockingly with `try_recv` and reply to each pending command with a typed `SessionError::ActorShutdown` (the oneshot is still alive). Or, simpler: on the idle arm, transition into a "draining" state — process remaining commands for up to one additional `idle_timeout` before returning. The first option is the right shape: drain-and-acknowledge is what `Shutdown` already does at line 122, and the idle path should not be the place that silently drops an envelope.

### [MEDIUM] `session/in_process.rs:171-189` — `subscribe()` race between `spawn_actor` and the broadcaster read leaks as `SessionError::Other`
- **Category**: logic
- **Description**: The slow path calls `self.spawn_actor(id).await?`, then `self.sender_for(id).await` (sanity), then `self.broadcasters.read().await.get(id).cloned().ok_or_else(|| SessionError::Other("broadcaster missing after spawn".into()))?`. A concurrent `detach()` between the spawn and the broadcaster read removes the broadcaster entry; the caller gets the generic `SessionError::Other` with a string describing an internal invariant. The caller cannot act on this — it is not retriable, not a "session not found", not a "transient" — but it is also not a "session was just detached", which is what actually happened. The same race exists between the `subscribe()` fast path and a concurrent `detach()`: the fast path clones the broadcaster while it is still in the map, the detach drops the service's clone and (per the spawn_actor cleanup) removes the entry; the subscriber keeps its `Receiver` clone of the `Sender`, which is fine — `broadcast::Sender::subscribe` does not require the service to hold a Sender — but the broadcaster is otherwise orphaned until the session is re-attached.
- **Suggested fix**: Add `SessionError::SessionDetached(SessionId)` (or reuse `NotFound`) for the "broadcaster missing after spawn" case; surface it to the caller so they can re-attach + retry. The fast-path orphan case is correct behaviour (subscriber keeps receiving until the broadcaster truly has no senders), but a doc comment noting that subscribers persist across `detach` would prevent the next reader from misreading it as a leak.

### [MEDIUM] `session/in_process.rs:84-85` — Inconsistent backpressure between mpsc (bounded-block) and broadcast (bounded-drop)
- **Category**: architecture
- **Description**: `mpsc::channel(COMMAND_BUFFER = 64)` blocks the caller when full; `broadcast::channel(BROADCAST_BUFFER = 256)` drops the message silently. The two are coupled (an emit goes through both — mpsc to the actor, then broadcast to subscribers), but the failure modes diverge: a slow producer of commands causes backpressure all the way back to the caller, while a slow consumer of broadcasts causes a silent hole in the live view with no signal back to the producer. Both buffers are also fixed at compile time and not configurable per session, so a long-running session with chatty activity will eventually overflow either side and the failure mode will depend on which side is the bottleneck — usually the broadcast side, because it has fewer receivers in the typical UI integration.
- **Suggested fix**: Pick one policy and apply it symmetrically. The pragmatic shape is "mpsc blocks, broadcast tracks its slowest receiver via Lagged and the projector drains via `get_events`"; document the asymmetry and the Lagged-recovery path so the asymmetry is intentional, not accidental. The constants themselves should live alongside the `mpsc::Sender` that owns the policy (i.e. on `InProcessActorSessionService`), not in `actor.rs`.

### [MEDIUM] `session/actor.rs:88-103` — Event-emit ordering couples actor liveness to observer reliability
- **Category**: architecture
- **Description**: The single emit path performs, in order: `append → head_seq update → observer.on_appended → broadcast → reply`. The `observer.on_appended` is a synchronous user-supplied call from inside the actor's task. A panicking observer kills the actor (per the HIGH finding above); a blocking observer stalls the broadcast and the reply (no enforcement of "non-blocking"). The trait says "implementations enqueue and return immediately", but the actor treats `on_appended` as if it were infallible and instantaneous — neither is guaranteed. Because the broadcast and reply come AFTER the observer, a slow observer delays the live-view notification that the event is durable, even though subscribers could safely consume it earlier.
- **Suggested fix**: Move observer notification off the hot path. Two options: (a) replace the synchronous callback with an `mpsc::Sender<SessionEventRecord>` that the actor pushes onto (full backpressure, decoupled); (b) keep the trait but spawn a `tokio::task::spawn` per callback with a `JoinHandle` ignored, so a panicking observer cannot kill the actor and a blocking observer only delays itself. (a) is the right shape for R7-adjacent subsystems (per "every observer is one of N producers, all of which must look the same"); the trait contract becomes "non-blocking, infallible because enqueueing is infallible".

### [MEDIUM] `session/steer_signal.rs:117-120, 222-235` — `SteerWatch::Drop` takes a std `Mutex` from the executor thread
- **Category**: quality / performance
- **Description**: `Drop::drop` for `SteerWatch` acquires the global `STATIONS` `std::sync::Mutex`. `Drop` runs synchronously, so if a watcher's owner drops it inside an async context (the common case — `SteerWatch` is held across `select!` arms and falls out of scope at task end), the executor thread blocks for the duration of the lock acquisition. The critical section is small (`get_mut` + optional `remove`), so contention is bounded, but under heavy parked-tool load this becomes one global mutex serializing every park/unpark on every session. There is no `tokio::sync::Mutex` here, and there can't be (Drop is sync), but `parking_lot::Mutex` would shave the contention cost; `DashMap` keyed by `session_key` would remove the global bottleneck entirely. As written, every `note_steer` and every `SteerWatch::Drop` for the entire process contends on the same lock.
- **Suggested fix**: Use `parking_lot::Mutex` (cheaper than `std::sync::Mutex` under contention) or shard the map (e.g. `HashMap<SessionKey, Arc<Station>>` behind a `RwLock`, where the per-station refcount is the contention-free part). The lock here protects a `HashMap<String, Station>` — a structure whose every operation is "look up one session, mutate one station" — so the global mutex is doing nothing the shard cannot do better.

### [MEDIUM] `session/store.rs:642-650, 561-579` — `session_id` round-trips through JSON-escape; wastes bytes and locks in a serde contract
- **Category**: quality / architecture
- **Description**: `session_id_to_string` does `serde_json::to_string(id)` and stores the result in `session_events.session_id`. The on-disk form is therefore `"agent:main:reflect"` (with literal quotes), and the read path does `serde_json::from_str(&session_id_str)` to reconstruct the `SessionKey`. `SessionKey::to_key_string()` already produces a stable, unambiguous, non-quoted string for the same purpose and is used by `steer_signal.rs::station_key`. Two producers of the canonical session-id string, one JSON-escaped and one not, means a row written by one path and read by the other would silently mismatch — `from_str` of `"agent:main"` is `SessionKey`, but `from_str` of `agent:main` is also `SessionKey` only via serde's lax parsing. The persistence path picks one; the routing path picks another. Today they happen to agree because no row written by `steer_signal` lands in `session_events`, but the next caller that bridges the two (a session-merge operation, say) will trip on it.
- **Suggested fix**: Use `SessionKey::to_key_string()` (the same key `steer_signal` uses) as the single canonical form. Persist that string in the column. For the read path, parse with `SessionKey::parse_rest` (or whatever the canonical deserializer is) rather than `serde_json::from_str`. This makes the on-disk form bytes-shorter (no embedded quotes) and removes the second-producer drift risk. If the canonical form is not yet stable enough, document which API produces the persisted form and grep the codebase to ensure no other call site is also producing it.

### [MEDIUM] `session/actor.rs:78-100` — Self-heal retry assumes no concurrent writer between `load_head_seq` and the second `append`
- **Category**: logic
- **Description**: The retry path is `if first append failed → load_head_seq → seq = stored_head + 1 → second append`. The doc comment correctly identifies the target scenario (a direct-store writer racing the actor). But it does not bound the scenario: if TWO direct writers are racing, the first retry could collide too, and the second failure propagates as `SessionError::Storage` to the caller, who then has no way to know whether the event was appended on the second attempt. The retry is one-shot, and a one-shot retry is exactly the wrong shape for "N concurrent writers may be present" — it works for `N = 1`, fails for `N ≥ 2`. The audit-trail comment "audit 4.1" is the only place this assumption is named; nothing pins it to "N ≤ 1".
- **Suggested fix**: Either tighten the contract — "the actor is the only writer to its session's events; direct writes are forbidden, period; the self-heal handles a one-off historical row that landed via migration" — and reject direct writes in the trait, or relax the retry to bounded loop (e.g. `for _ in 0..MAX_HEAL_ATTEMPTS { ... }` with `MAX_HEAL_ATTEMPTS = 4`) so two-writer races converge. The first is the right shape; the second papers over a violation that should not exist. Pick one and pin the invariant with a test.

### [LOW] `session/store.rs:807-823` — `install_test_event_store` shares a single in-memory store across the entire test binary via static `OnceLock`
- **Category**: quality
- **Description**: The helper installs one `SqliteEventStore` into the process-wide `GLOBAL_EVENT_STORE`, used by tests that need the real `retire_live_events` / `is_event_retired` path. Per the doc comment, tests must use unique session keys — but nothing enforces it. A test that uses `SessionKey::ephemeral("test")` will collide with every other test in the binary that does the same, and the loser of that race silently observes a store it never wrote to (because `set_global_session_event_store` is `OnceLock::set`, idempotent). The existing tests dodge this by using label strings like `"obs"`, `"scope-a"`, `"keep-a"` — but a new contributor copying the closest example (which is `sample_session_id()` returning `ephemeral("test")` at line 856) will inherit the bug.
- **Suggested fix**: Drop the static and let each test own its own store; the helper should be removed and replaced by a per-test `Arc::new(SqliteEventStore::new(conn))` that is installed into the global exactly once via a `#[ctor]`-free per-test `OnceLock` reset (or by exposing a `set_for_test(store)` only available behind `#[cfg(test)]`). If the static cannot go (e.g. some integration test reaches into the global), add a `cfg(test)` panic when two different stores are installed in the same process, so the collision is loud rather than silent.

### [LOW] `session/steer_signal.rs:148-156` — `OnceLock<Mutex<HashMap>>` is now `Mutex::new(HashMap::new())` at const since Rust 1.63
- **Category**: architecture / quality
- **Description**: The wrapping `OnceLock` exists only to defer `Mutex::new(...)` past the const-evaluation boundary. `std::sync::Mutex::new` is `const fn` since 1.63 and `std::collections::HashMap::new` is `const fn` since 1.66. The whole helper reduces to `static STATIONS: Mutex<HashMap<String, Station>> = Mutex::new(HashMap::new());` — fewer indirections, one fewer type-level indirection for readers, and one fewer runtime branch in `get_or_init`. The current shape also exposes the `OnceLock` poison behaviour: `get_or_init` panics on a poisoned `OnceLock` but the inner mutex uses `unwrap_or_else(|e| e.into_inner())` — two different poison-handling paths for two locks that protect the same thing.
- **Suggested fix**: Replace the `OnceLock` with a `static` item; collapse the helper. Also aligns with the rest of the module's style (`static GLOBAL_*` in `service.rs` and `store.rs`).

### [LOW] `session/store.rs:472-509` — `retire_through` relies on autocommit for atomicity; explicit `BEGIN IMMEDIATE` would be symmetric with `retire_from`
- **Category**: quality
- **Description**: `retire_from` (line 422) wraps `UPDATE + DELETE-FTS` in `BEGIN IMMEDIATE … COMMIT` because the BM25 mirror must be kept consistent. `retire_through` (line 472) deliberately preserves the BM25 mirror (no paired FTS delete), so it relies on SQLite's per-statement autocommit to keep the single `UPDATE` atomic. The asymmetry is by design, but the consequence is that `retire_through` has no transaction wrapper around the SQL even though `retire_from` does. If a future maintainer adds a paired FTS operation to `retire_through` (the doc already hints this could happen for "manual compaction" use cases), the lack of a transaction wrapper will turn the next round of edits into a latent bug — the comment that says "single statement, so no explicit transaction" reads as a justification now, but it is also a tripwire for the next person.
- **Suggested fix**: Wrap `retire_through` in the same `BEGIN IMMEDIATE … COMMIT` as `retire_from` even though there is only one statement today. Cost is one round-trip; benefit is "the next paired FTS op lands in the same transaction automatically". Alternatively, leave a TODO comment anchored at the file location naming "the next paired operation must add BEGIN IMMEDIATE here".

## Cross-References

- `actor.rs:88-103` (event-emit ordering) and `observer.rs:5-8` (the trait) — the trait says "non-blocking" with no enforcement, and the actor treats it as if it were infallible. The two together produce the HIGH finding about observer-panic wedging; both must change together for the fix to hold.
- `in_process.rs:84-85` (channel buffers) and `actor.rs:88-95` (broadcast drop) — the bounded-drop semantics of broadcast combined with the bounded-block semantics of mpsc is a single design decision that is currently split across two files. The MEDIUM finding is the same finding seen from two sides; pick a policy in one place and apply it to both.
- `in_process.rs:184-227` (concurrent wake) and `actor.rs:78-100` (self-heal retry) — both rely on "the actor is the sole writer for its session" as an unwritten assumption. If the codebase ever introduces a second writer path (recovery, replay import, audit export), both findings become CRITICAL simultaneously because the safety net (single retry) and the marker invariant (one SessionWoken per wake) collapse together.
- `store.rs:642-650` (session_id serialization) and `steer_signal.rs:174-179` (station_key via `to_key_string`) — two producers of the same canonical string. Today they agree by accident (no row written by `steer_signal` lands in `session_events`); the next bridge between them is a bug.
- `service.rs:38-40` (`SessionError::Other(String)`) and `in_process.rs:185-187` ("broadcaster missing after spawn") — the generic `Other` variant is the bucket the broadcaster-race error leaks into. Introducing a typed variant (`SessionDetached`) at the same time as the broadcaster-race fix avoids two coordinated changes.

## Strengths

- `actor.rs:78-100` self-heal pattern (retry once with `load_head_seq` resync) is the right shape for the documented scenario and is pinned by a controlled `CollideOnceStore` test that exercises the exact collision-and-recover path. The bounded retry (no loop) is the correct posture — a loop would mask real bugs.
- `steer_signal.rs` is unusually well-instrumented for the size: source-level census of `note_steer` call sites (`tests::note_steer_has_exactly_one_production_call_site`, lines 481-535) prevents the silent-divergence failure mode that "this question has exactly one producer, by construction" claims protect against. The test is deliberately `== 1` rather than `<= 1` so over-eager splitters fail loudly — that posture matches CLAUDE.md's "a source-level guard only covers the block shape its recogniser knows".
- `store.rs` `retire_from` / `retire_through` asymmetry is deliberate and well-documented: `retire_from` (clear/rewind) wipes the BM25 mirror, `retire_through` (compaction) preserves it. The contract is captured in two integration tests (`retire_through_keeps_the_search_index_unlike_clear`) that fail loudly if the asymmetry is silently reverted.
- `events.rs` clean-up of `ApprovalSource::Autoconfirm` and the `Llm`/`Tool`/`Sandbox`/`Harness`/`Serialization`/`Other` `ErrorKind` variants (documented in the doc-comments as "removed for the same reason: nothing constructed them") is exemplary P6 / R7 discipline. The comment "a variant is a claim about what the log can contain, and an unproduced one is false" is the kind of architectural statement that prevents the next contributor from re-adding a `Sandbox` variant because the case "looks plausible".
- `in_process.rs::spawn_actor` double-check on stale senders (lines 100-108) is the correct mitigation for "actor idle-timed-out but the map still holds a Sender": it is_closed() + evict before creating a replacement. The cleanup of the matching broadcaster is part of the same critical section, so the orphan-broadcaster race is closed.
- `tool_trace.rs::with_session_scope` is a clean single-chokepoint pattern: every tool-dispatch site funnels through it, and the test (`session_id_task_local_is_visible_inside_with_session_scope`) confirms the task-local leaks neither in nor out. The "single entry point" framing in the doc comment matches the actual API surface.
- `events.rs::synthetic_user` collapses three call sites that built the literal by hand, with the comment correctly identifying that the load-bearing invariant is `synthetic: true` (a harness-authored message has no human author by construction), not just "make the call site shorter". The same pattern would benefit `ToolError::synthetic_failure` if it ever exists.
- `projection.rs::parse_source_seq` correctly handles `session_key` containing `':'` by `rsplit_once` (the only separator `row_id` appends). The test `parse_source_seq_rejects_foreign_ids` pins the "boot-time orphan notice / legacy rows" exclusion by name.
- `epoch_registrar.rs::retire_superseded` default-no-op keeps test doubles honest — the production implementor (gateway session store) is the only thing that holds the handle this needs, and the default behaviour (a no-op) is the correct behaviour for tests that do not exercise the cross-epoch continuation path.
