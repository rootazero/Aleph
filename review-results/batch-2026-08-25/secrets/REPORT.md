### [CRITICAL] `leak_detector.rs:332-352` + `:344-352` — `find_injected_substring` returns FIRST match only; `scan_inbound` calls `content.replace(matched, …)` so every other echoed injected secret leaks in `redacted_content`
- **Category**: security / information disclosure
- **Description**: `find_injected_substring` returns `Option<&'c str>` — the first window in `content` whose `(hash, len)` matches a registered fingerprint — and the caller in `scan_inbound` then builds `redacted_content` with a single `content.replace(matched, REDACTED_INJECTED)`. If the inbound body carries two distinct injected secrets, or one secret appears more than once, only the first occurrence is replaced; the rest pass through to the LLM verbatim. The detector advertises bidirectional scanning ("every registered secret is looked for as a substring") and the doc on `scan_inbound` goes out of its way to defend its windowed-hashing algorithm — but it only ever redacts one window. The same `register_injected` is called once per request, and a multi-secret response (a tool that echoes every Authorization header back) is realistic. There is no test for ≥2 leaked secrets in the same response.
- **Suggested fix**: Loop `find_injected_substring` until it returns `None`, collecting every match; then run a single non-overlapping redact pass (`Vec<(start, end)>` → sorted, deduped, splice into a fresh `String`). The matcher should also keep `len` in scope so two distinct lengths can be detected in parallel, not by re-walking the content.

### [CRITICAL] `vault.rs:103-117` + `bincode 1.3` — `bincode::deserialize(&bytes)` parses an attacker-controlled vault file with no project-side size bound
- **Category**: security / DoS
- **Description**: `SecretVault::open` calls `bincode::deserialize(&bytes)` on the entire vault file (after `io.read()` already slurps the file into a `Vec<u8>`). `bincode 1.3`'s high-level `deserialize` uses `DefaultOptions`, whose `Limit` is per-`Vec` length-prefix — it caps a single `Vec<u8>` to `BINCODE_MAX` (~`usize::MAX/4`) but does **not** bound the number of `Vec`s, the total allocated bytes, or the deserialization depth. A vault file containing `HashMap<String, EncryptedEntry>` with thousands of `Vec<u8>` ciphertext fields each at the legal maximum can therefore bind `n × BINCODE_MAX` heap; the daemon is happy to OOM rather than reject. There is no `with_limit(MAX_VAULT_DECODE_BYTES)` and no streaming. Cold-start path: not behind a lock or rate-limit, so a local attacker who can drop a file at `~/.aleph/secrets.vault` triggers the OOM before `open_or_backup` ever sees the bytes. The `tests/test_set_and_get_*` family bypasses this because their vaults are tens of bytes; nothing in the test suite reaches a multi-MB vault.
- **Suggested fix**: Construct a `bincode::config::standard()` with `with_limit(MAX_VAULT_BYTES)` (e.g. `1 << 24` = 16 MiB) and pass to `bincode::serde::decode_from_slice(&bytes, config)`. Add an early `bytes.len() > MAX_VAULT_BYTES` check before deserialization so the rejection path is one errno, not a stack-unwinding `Err`. Same fix on `bincode::serialize` if you adopt `bincode 2.x`'s API in a follow-up.

### [HIGH] `leak_detector.rs:355-385` — `find_injected_substring` is `O(content.len() × distinct_lengths)` and unbounded in `content.len()`; a malicious 1 MiB response with `INJECTED_LRU_CAP=1024` distinct lengths does ≥1 B sip-hash operations per scan
- **Category**: DoS / performance
- **Description**: For each registered `len` in `injected_lens`, the function re-walks `content.char_indices()` from start to end, hashes every in-bounds window, and probes `self.injected_hashes.contains(...)`. With `L = |distinct_lengths|`, total work is `O(L × content.len())` sip-hash invocations plus `O(L × content.len())` `is_char_boundary` checks (already short-circuited but still walked). The `L ≤ 1024` cap is enforced via LRU but no project-side sanity check limits `content.len()` itself — `scan_inbound` is invoked from every inbound API response at `src/security/runtime_guard.rs:200` and the guard does not bound the request body. A 1 MiB response with 1024 distinct lengths in the LRU is ≈2 billion sip hashes; this dwarfs the rest of the runtime guard and is observable as request latency. (The comment says "long enough to cover a multi-turn tool resolution + follow-up reflection prompt (typical: < 50 entries)"; the operational reality of a long-running daemon with many distinct injected values per session is the upper end.) There is no test exercising the upper-bound path.
- **Suggested fix**: Bound the inbound content size at the caller (in `runtime_guard::process_inbound`) before handing it to `scan_inbound`. Inside `find_injected_substring`, replace the nested loop with a single pass: for each `start` from `content.char_indices()`, check every `len` against the precomputed boundary; or bucket the matches by length and short-circuit. Add a `default-features`-style cap constant (`MAX_INBOUND_SCAN_BYTES`, e.g. 256 KiB) and reject longer inputs after a truncated scan with a clear `Block` reason.

### [HIGH] `onepassword.rs:121-127` — `tokio::process::Command::output()` has no timeout and no `kill_on_drop(true)`; a hung `op` CLI blocks `health_check` indefinitely and leaves zombies on task drop
- **Category**: reliability / resource leak
- **Description**: `health_check` spawns `op whoami` and awaits `cmd.output()`. There is no `tokio::time::timeout(...)` and no `kill_on_drop(true)` set on the command. If the user's interactive 1Password session is waiting on Touch ID / biometric / TTY, the child `op` process hangs forever; the `async fn` returned to the caller never resolves (it is the only return type, so callers are forced to gate `health_check` themselves, which the runtime guard does not). If the future is then dropped (timeout at the caller, cancellation token, panic unwind), the kernel still has the child running until the parent exits — i.e. a zombie whose stdin/stdout is connected to the daemon. The single test that exercises this path is `#[ignore]`-ed, so the regression surface is unobserved.
- **Suggested fix**: Wrap `output()` in `tokio::time::timeout(Duration::from_secs(5), cmd.output())`; convert timeout into `ProviderError { message: "`op whoami` timed out".into() }`. Set `cmd.kill_on_drop(true)` at the top of `base_command` so any task drop reaps the child.

### [HIGH] `injection.rs:62-91` — `render_with_secrets` calls `resolver.resolve(...)` once per occurrence; identical placeholders decrypt the vault entry multiple times per request
- **Category**: performance / amplification
- **Description**: The placeholder walker (`placeholder::extract_secret_refs`) returns one `SecretRef` per `{{secret:NAME}}` literal — which the comment in `extract_secret_refs` confirms is cursor-advanced but does not dedupe by name. The renderer loop is `for secret_ref in &refs { resolver.resolve(...).await?; ... }`. A prompt that legitimately uses `{{secret:OPENAI_KEY}}` five times decrypts the AES-GCM blob, allocates a `DecryptedSecret`, hashes the value, and discards — five times — per `render_with_secrets` call. The vault helper (`SharedTokenManager::get_secret`) takes a `RwLock` read; five parallel `render_with_secrets` on five clones multiply reader contention. There is no per-render cache. `test_render_multiple_placeholders` only covers the deduplicated case (two distinct keys).
- **Suggested fix**: Add a `HashMap<String, DecryptedSecret>` cache scoped to a single render: walk `refs` once, dedup names through the cache, then do the second pass for substitution. Long-term, push the cache down into `AsyncSecretResolver` itself (a `CachingResolver` decorator) so the behavior is independent of who calls.

### [HIGH] `runtime_guard::process_outbound` (consumer) + `secrets::injection` — `InjectedSecret` fingerprints are NOT registered with `LeakDetector` until AFTER `register_injected` runs, and the renderer substitutes plaintext into the prompt before `process_outbound`'s scan sees the rendered text; absence of synchronisation is documented but un-tested
- **Category**: race condition / TOCTOU
- **Description**: `runtime_guard::process_outbound` calls `extract_secret_refs` and `resolver.resolve(...)` to build `injected: Vec<InjectedSecret>`, then `register_injected(&injected)`, and then runs `scan_outbound(&current_text)` on **the still-placeholder-bearing** string (the substitution happens later, in a separate `for (raw, value) in resolved_map` block). The `test_render_replaces_placeholder` test asserts the rendered output contains the plaintext secret but does not assert that `register_injected` runs after substitution. The detector therefore tracks the fingerprint but `scan_outbound` at this moment operates on text containing `{{secret:NAME}}` — a subsequent outbound that quotes the placeholder back (e.g. an LLM echo) is **not** caught by either the pattern rules (no vendor prefix) or the fingerprint (it never matched a literal value). The renderer in `injection.rs::render_with_secrets` does substitution and registration in one go, but `runtime_guard` does NOT call `render_with_secrets` — it does both steps inlined and in the wrong order. The "no plaintext secret is ever retained" invariant is upheld, but the "echoed injected value is blocked" invariant has a hole here.
- **Suggested fix**: Either (a) call `crate::secrets::render_with_secrets(text, resolver).await` once at the top of `process_outbound`, get the already-substituted string and the `Vec<InjectedSecret>` in one go, then `register_injected` and re-scan the *substituted* string; or (b) move `register_injected` to occur after the substitution loop and add a regression test that asserts the substituted text is what is scanned.

### [HIGH] `leak_detector.rs:226-232` + `:268-279` — `LeakDetector` registrations under `MIN_INJECTED_MATCH_LEN = 8` are silently dropped; pattern rules cannot substitute
- **Category**: security / information disclosure
- **Description**: `register_injected` filters out any `InjectedSecret` whose `value_len < MIN_INJECTED_MATCH_LEN`. The comment says "short values are covered by the pattern rules". Pattern rules only catch vendor-shaped credentials (sk-, ghp_, AKIA…, etc.). A generic 5-character password or short-lived OAuth refresh token that has no distinctive prefix will be SUBSTITUTED into the outbound request, but the inbound scan has no fingerprint for it and no pattern matches it. `test_short_injected_values_not_tracked` explicitly asserts the inbound side *allows* the echo. This is the documented behavior, but the doc is wrong: pattern rules do *not* cover generic short secrets. An attacker controlling the downstream response (e.g. a malicious MCP server) gets to echo the cleartext back.
- **Suggested fix**: Either (a) drop `MIN_INJECTED_MATCH_LEN` for generic secrets but raise the *false-positive floor* by requiring the entire window hash to match BOTH `value_hash` AND `value_len` AND a placeholder-origin tag (the `name` field), reducing collision odds for short windows by using the placeholder name as a context hint; or (b) document explicitly which short-secret shapes are matched (with vendor prefixes) so the limitation is visible.

### [HIGH] `vault.rs:99-117` — `open_or_backup` uses `chrono::Utc::now().timestamp()` (1-second resolution) as the backup suffix; two restarts in the same second silently overwrite the first backup, and on Linux the corrupted bytes silently overwrite the previously-moved-aside file
- **Category**: race condition / data loss
- **Description**: `open_or_backup` constructs the backup filename as `<path>.corrupt-<ts>`. If two processes (or two daemon restarts within the same second) both find the vault unreadable, both call `std::fs::rename(path, backup)` against the same `backup` path. On Unix, `rename` is atomic and **overwrites** the existing file — the second invocation clobbers the first set of "unreadable but recoverable" bytes, making recovery impossible. The `test_open_or_backup_preserves_unreadable_vault` test only covers a single backup; the collision case is structurally the same as the original bug the doc highlights ("silent overwrite destroys every stored secret") and the new code reintroduces it in the backup path. The wider `duplicate-instance` sentinel in AGENTS.md is the only protection, and it is documented as missing on dev.
- **Suggested fix**: Use an atomic suffix (`AtomicUsize` + PID, or a UUID fragment from `uuid::Uuid::new_v4()`); or check `backup.exists()` and pick a uniquified name (`..corrupt-<ts>-<n>`). Verify with a regression test that calls `open_or_backup` twice in quick succession and asserts both `.corrupt-*` files survive.

### [HIGH] `crypto.rs:43-50` — `SecretsCrypto::new(impl Into<String>)` accepts arbitrary-length master keys as a heap-allocated `SecretString`; weak / short keys are accepted without validation
- **Category**: security / key strength
- **Description**: The constructor types the master key as `impl Into<String>` and stores it in a `SecretString`. There is no minimum-length check (a 1-byte master key would still derive a 32-byte AES key, but with effectively `2^8` entropy per HKDF salt cycle), no recommendation to pass a 32-byte random secret, and no KDF-over-the-KDF (passphrase-stretching) for human-entered passphrases. The downstream `SharedTokenManager::new` feeds in a 32-byte HMAC secret serialized to a `String` (see `set_shared_token_with_secret(&hash, &self.secret, …)` in `gateway/security/shared_token.rs`), which works, but anyone re-using the SecretsCrypto with a 4-character passphrase is silently within spec. The HKDF "info" label `b"aleph-secrets-v1"` is static and versioned — good — but the absence of a key-strength gate is the hole.
- **Suggested fix**: Add a `SecretsCrypto::new_with_strength_check(master, min_entropy_bits)` constructor (or an `assert_master_strength` debug-only check). Expose a separate `SecretsCrypto::from_bytes(Zeroizing<[u8; 32]>)` that takes a pre-derived 32-byte key, so the caller can ensure they are passing a CSPRNG-derived key and never a user-typed passphrase. Add a doc comment that the master key is expected to be 32 random bytes; refuse anything under 16 bytes.

### [MEDIUM] `leak_detector.rs:140-182` — char-side `LEAK_PATTERNS` lumps `sk-proj-…` under "OpenAI API Key" because `sk_proj` and `sk_ant` entries exist only in the byte-side `SECRET_PATTERN_SOURCES`; downstream `Block { reason }` labels are wrong for project-prefixed keys
- **Category**: quality / mis-labels
- **Description**: `SECRET_PATTERN_SOURCES` deliberately keeps `sk_proj` / `sk_ant` separate for byte-level scrub. `LEAK_PATTERNS` was written earlier and never grew the same partitioning: the OpenAI pattern is `\bsk-[a-zA-Z0-9\-]{20,}`, which matches `sk-proj-…` AND `sk-ant-…` and labels both as "OpenAI API Key". The Anthropic-specific pattern `\bsk-ant-…` is more specific and runs first, so it preempts `sk-ant-…`, but `sk-proj-…` slips through to the OpenAI bucket. In `Block { reason: "Outbound leak detected: OpenAI API Key", … }` the operator sees the wrong vendor name and pivots their rotation toward the wrong dashboard. The architecture comment in `SECRET_PATTERN_SOURCES` admits the asymmetry ("intentionally independent … kept separate by design") but does not acknowledge the label error.
- **Suggested fix**: Promote a shared `match_list` table (regex source + label + block-class flag) consumed by both byte and char builders. The label can be derived once; the regex compiled twice. Delete the two near-duplicate arrays; let the catalog drive both surfaces.

### [MEDIUM] `placeholder.rs:38-43` + `mod.rs:44-49` — secret-name validator duplicated in two places; both must be updated together
- **Category**: architecture / single-source-of-truth
- **Description**: `placeholder.rs::extract_secret_refs` enforces "ASCII alphanumeric / `_-.:`" inside the parser. `mod.rs::validate_secret_name` enforces the same charset at the public API surface. The two copies must agree by hand — a new allowed character would require editing both, and the failure mode of forgetting one is silent (one surface rejects, one accepts, no compiler help). The validators do not even share the constant limit (`SECRET_NAME_MAX_LEN = 128`).
- **Suggested fix**: Extract `mod.rs::validate_secret_name` (already `pub`-visible in `src/secrets/mod.rs`) and call it from `placeholder.rs::extract_secret_refs` via `super::validate_secret_name(name)` after the boundary check. One source, one constant, one test.

### [MEDIUM] `crypto.rs:93-105` — `derive_key` returns `SecretError::EncryptionFailed` for an HKDF expansion error, but `EncryptionFailed` is for encryption, not key derivation; the discrimination makes callers treat a `derive_key` failure as a "could not encrypt" condition rather than a "key material is unusable" condition
- **Category**: logic / error semantics
- **Description**: `derive_key` returns `Result<Zeroizing<[u8; 32]>, SecretError>`. The only error variant it ever produces is `SecretError::EncryptionFailed(format!("HKDF expand failed: {e}"))`. The variant name is the wrong one — `EncryptionFailed` is used by callers to surface "couldn't encrypt plaintext" to the user; a HKDF failure is "the master key + (salt, info) is so degenerate that it cannot even produce a 32-byte output, which is mathematically surprising since HKDF-SHA256 will always accept the request as long as the requested length is ≤ 255 × hash_length (i.e. ≤ 8160 bytes)". The error is unreachable in normal operation; using `EncryptionFailed` confuses the user-facing message and hides which subsystem actually broke.
- **Suggested fix**: Add a new `SecretError::KeyDerivationFailed(String)` variant; map HKDF expand errors to that. Bonus: include the requested length in the error (today `e` already does, but the variant name does not communicate what failed).

### [MEDIUM] `vault.rs:222-235` — `default_path()` silently falls back to `secrets.vault` in CWD when `get_config_dir()` errors; the warning is `tracing::warn!` and operators in restricted envs (containers, read-only configs) may miss it
- **Category**: security / defence-in-depth
- **Description**: When `crate::utils::paths::get_config_dir()` errors (permission denied, missing HOME in containers, read-only mount), `default_path` returns `PathBuf::from("secrets.vault")` — the current working directory at daemon start. The vault is then created next to whatever binary invocation happened to be the CWD (e.g. `/`). Two unintended consequences: (a) the vault file's permissions are set to `0o600` but its `parent` is `/`, which likely has different perms — meaning another process on the box can read the secret blobs from there; (b) two unrelated daemons started from different CWDs create independent vaults and can't share secrets. The warn message gets logged but is not fatal.
- **Suggested fix**: Refuse to construct a vault when `get_config_dir` returns `Err`. The caller (typically `SharedTokenManager::new`) must already be prepared for this (it logs to tracing; if it cannot pick a path, the daemon should refuse to start rather than scatter secrets into CWD). At minimum, when the fallback fires, refuse to set the env-var-configured path; require explicit operator opt-in to legacy CWD placement.

### [MEDIUM] `types.rs:140-142` + `provider/mod.rs` — `SecretError::ProviderError { message: String }` is opaque to callers; the message field's provenance is implementation-dependent and could carry stderr verbatim from future providers
- **Category**: API ergonomics / information disclosure
- **Description**: The variant carries a free-form `message: String`. Today, `onepassword::classify_error` populates it with constant strings only — so the current surface is safe. But the variant is the public extension point: a future provider implementation writing raw `output.stderr` into `message` would, via `Display`, leak vault names, account emails, paths, or tokens to log lines and to whoever sees the error. The variant is also `#[error("Provider '{provider}' error: {message}")]` — so the message is embedded literally in user-visible error text. There is no convention for sanitization.
- **Suggested fix**: Replace the free-form `String` with an enum (`ProviderFailureKind { CliNotFound, AuthRequired, NotFound, Other }`) so callers cannot accidentally inject raw stderr; let providers supply structured information that is then formatted by the standard `Display` impl. Add a contract doc stating `provider implementations must not embed raw stderr in any user-visible field`.

### [MEDIUM] `injection.rs:36-45` + `:96-100` — `INJECTED_HASH_KEY0/INJECTED_HASH_KEY1` are `pub(crate) const`; if any future cross-crate caller subscribes to the fingerprint set, the keys leak by virtue of being embedded in the binary's `.rodata`
- **Category**: security / capability creep
- **Description**: `InjectedSecret::from_value` uses SipHash with hardcoded keys, which provides HashDoS resistance (the documented purpose) but does not provide attacker-unobservability (the keys are compiled into the binary's read-only data section and `pub(crate)` means anyone with a `cargo doc` can read them). The leak-detector fingerprint scheme relies on "no attacker can compute `SipHash(K0, K1, x)` without reading the binary". The keys ARE in the binary, so the no-attacker model is wrong: anyone who can `strings(1)` the daemon's executable gets them. The current architecture is fine — the detector is internal — but if a future plugin is granted access to `InjectedSecret` hashes for fingerprint building, the keys become a load-bearing secret they aren't today.
- **Suggested fix**: Move the keys to a `static` `OnceCell<[u8; 16]>` populated at startup from `getrandom`. Comment explicitly that the keys provide HashDoS resistance and are not security-sensitive in their current internal-only scope. If the type becomes cross-crate-public, regenerate keys per-process via OS RNG.

### [MEDIUM] `leak_detector.rs:218-223` — `for &len, _ in self.injected_lens.iter()` iterates LRU oldest-first; the freshly-registered (most-likely-to-be-echoed) secret is scanned LAST
- **Category**: logic / hot-path ordering
- **Description**: `lru::LruCache::iter()` yields from least-recently-used to most-recently-used. The leak detector registers secrets via `register_injected`, which `put`s into both `injected_hashes` and `injected_lens`. After many calls, the most recently injected secret scans last; an inbound echo of *that* secret is hit only after the entire content has been rehashed against every older length. The asymmetry is invisible to tests (which register exactly one secret) but visible in production tool traces. There is no comment committing to a scan order, so the choice is accidental.
- **Suggested fix**: Switch the LRU order: iterate `injected_lens.iter().rev()` to scan newest-first. Or, replace the LRU-iteration order with a `BTreeMap` sorted on length only (the doc-comment claims lengths are "a handful" and "scan cost is linear in their sum", which is consistent with either iteration order but does not justify the oldest-first pick). Either way, add a sentence to the doc that commits to the choice.

### [MEDIUM] `vault_resolver.rs:31-35` — `Self::inner.get_secret(name)` errors are flattened via `format!("vault resolve error: {e}")`, swallowing structured information and pushing it through `io::Error::other`
- **Category**: quality / error handling
- **Description**: `VaultSecretResolver::resolve` converts any inner error into `SecretError::Io(std::io::Error::other(format!("vault resolve error: {e}")))`. The format is one-shot: callers cannot distinguish "vault file missing", "permission denied", "AES decrypt failed", "key mismatch" — they all become a generic IO. The downstream effect is that an LLM-visible error says "vault resolve error: …" with no actionable signal. Note also that `inner.get_secret` (per `SharedTokenManager`) likely returns its own rich enum (`SharedTokenError::Storage(...)`) which has been collapsed; the error message ends up in `SecretError`'s `Display` impl, which is fed to the model.
- **Suggested fix**: Convert `SharedTokenError` to a `SecretError` variant explicitly. `SharedTokenError` should `From` into `SecretError::ProviderError { provider: "shared_token", message }` or a new `SecretError::VaultResolveError { reason }`. The blanket `format!(...)` is an antipattern — at minimum wrap with `SecretError::VaultUnavailable(format!("{e}"))`.

### [MEDIUM] `vault_resolver.rs:39` + `virtual_key_resolver.rs:34` — both resolvers lock-step "alias not found → return input verbatim"; an attacker who can place an alias-shape string in a placeholder reaches the inner resolver with whatever the user chose
- **Category**: security / threat model
- **Description**: `VirtualKeyResolver::resolve` does `self.aliases.get(name).map_or(name, String::as_str)` — names not in the alias map pass through unchanged. This is the documented behavior, but the consequence is that aliases are not "the only allowed names" — they are optional decorations. A misconfigured or attacker-controlled config (e.g. a YAML file with `aliases: {}`) means there is no allowlist at all; placeholders reach `inner.resolve(...)` unrestricted, and `inner` (the `VaultSecretResolver`) accesses the vault with whatever name the user typed — which only fails if the name is not a vault entry. Compare to the more conservative "alias fallthrough is forbidden" design.
- **Suggested fix**: Document the chosen threat model explicitly in the doc-comment ("placeholders not in the alias map are passed through to the inner resolver, which is what enforces the vault-side allowlist"). If the threat model is "aliases ARE the allowlist", reject unmapped names with `SecretError::InvalidPlaceholder("unknown secret name: {name}".into())` and require the operator to opt-in explicitly.

### [LOW] `mod.rs:44-49` — `validate_secret_name`'s length check uses `normalized.len()` (byte count), not character count; safe today because the validator forbids non-ASCII, but a future validator loosening will silently change the limit semantics
- **Category**: quality / invariant pinning
- **Description**: `normalized.len()` is the byte length. The ASCII-alphanumeric constraint is enforced immediately below, so byte-count and character-count currently agree. If a future commit adds Unicode to the allowed set, the 128 limit quietly becomes 128 bytes (so 32 CJK chars are allowed). Without an explicit invariant comment, the next refactor will treat `len()` as "characters".
- **Suggested fix**: Pin the invariant in a doc-comment: `// length is in BYTES; the ASCII-only charset makes byte-count == char-count today.`. Or change to `normalized.chars().count()` and a comment.

### [LOW] `crypto.rs:73 + :84` — `SecretError::EncryptionFailed(format!("AES init failed: {e}"))` and `… format!("HKDF expand failed: {e}")` embed underlying-error messages which originate from third-party crates; in a future version these could carry plaintext or stack hints
- **Category**: quality / information disclosure
- **Description**: `aes_gcm::aead::KeyInit::new_from_slice` and `hkdf::Hkdf::expand` errors are passed through `format!`. Today, neither `aes-gcm 0.10` nor `hkdf 0.12` includes plaintext in their error messages. But the contract is undocumented; future versions could. The error then flows through `SecretError::Display` into log lines that the operator sees. The cost is small (low-grade info disclosure) and the probability is low, but the code path makes it trivially hardenable.
- **Suggested fix**: Log the underlying error at `tracing::debug!` (with full detail) but return `SecretError::EncryptionFailed("AES initialization failed".into())` to the caller. Same for HKDF.

### [LOW] `vendor_patterns.rs:14-16` — `(label, src)` pair has unbounded pattern body strings; an upstream rename of `label` requires hand-edits in `leak_detector.rs` (`is_block_class_secret`) and `sandbox/scrub.rs` (`filter(name)`), and the cross-references are not type-checked
- **Category**: architecture / naming consistency
- **Description**: `BLOCK_CLASS_SECRETS: &[&str] = &["private_key"]` references the label string from `SECRET_PATTERN_SOURCES`. The string `"private_key"` is not a typed reference; renaming the label in `SECRET_PATTERN_SOURCES` silently changes the meaning of `is_block_class_secret` without compiler help. The same applies to `sandbox/scrub.rs:64`'s `filter(|name| is_block_class_secret(name))`.
- **Suggested fix**: Use a typed `#[repr(...)] enum SecretPattern { PrivateKey, AnthropicApiKey, ... }` and `const fn name(&self) -> &'static str`. Or, generate a const table once and const-fn-check it. The label becomes a single source of truth.

### [LOW] `onepassword.rs:76-90` — `classify_error` uses `stderr.to_lowercase().contains("not signed in")` etc.; the heuristic is brittle against the `op` CLI's evolving error copy and against stderr content that happens to contain the substring as a debug message
- **Category**: quality / contract drift
- **Description**: The five error categories are matched on substrings of a stderr blob. A future `op` version rephrasing the message (e.g. "you're not signed in to 1Password" → "your session is inactive") bypasses the auth-required detection. Conversely, a debug log like "[1password sdk] we are not signed in yet because…" would trigger the branch. Today, only `health_check` calls this path, which spawns `op whoami` whose stderr is constrained — but the function is `pub(crate)` and likely to be reused for `get_item` etc.
- **Suggested fix**: Switch from string-match on stderr to the exit code (`output.status.code()`). The `op` CLI publishes documented exit codes: 0 (success), SESSION_EXPIRED, ITEM_NOT_FOUND, etc. Match on those; stop parsing stderr for the auth classification.

### [LOW] `leak_detector.rs:96-100` — `BLOCK_CLASS_SECRETS` is a flat `&[&str]` of one entry; the constant is tested as a frozen list but the module-level doc-comment promises it is "intentionally minimal" and "block-class is a frozen hard-filter, not a config knob"; the two promises are not enforced
- **Category**: architecture / doc-vs-code drift
- **Description**: The doc says "intentionally minimal — limited to categories that have essentially no legitimate reason to be echoed to the model and a near-zero false-positive rate". The code is `&["private_key"]`. There is no test that pinning the list to that size and that one entry is part of the contract; an editor adding `&["private_key", "openai"]` will not see a test go red. The "not a config knob" claim is also unenforced — anything that loads the function from `is_block_class_secret` indirectly has bypassed config gating by virtue of the public API.
- **Suggested fix**: Add a `#[test] fn block_class_secrets_is_frozen()` that asserts the slice is exactly equal to a known good set. Mark the const with `#[deprecated(note = "frozen filter")]` would be wrong — but a `#[cfg(test)]` guard that snapshots the contents would catch silent growth.

## Architecture / Cross-cutting Notes (informational, not scored)

- **R1 compliance**: `provider/onepassword.rs` shells out to an external CLI rather than linking a native library — this is consistent with R1's "process-isolation" carve-out ("spawn-time side effects that cannot be delegated over IPC"). No platform APIs are imported by core; `no_window` is a helper utility.
- **R3 (core minimalism)**: the crypto subsystem adds `aes-gcm`, `hkdf`, `secrecy`, `zeroize`, `rand`, `siphasher` — these are necessary building blocks, not heavy lifting. The bytecode-level and char-level redaction systems are tightly coupled to `regex` (also a foundational crate). OK.
- **R7 (LLM sovereignty)**: `placeholder.rs` and `vendor_patterns.rs` are explicit lookup-by-prefix systems; they are FORMAT parsers (machine-readable text), not "regex for natural language intent". They comply with the R7 carve-out.
- **Single source of truth**: `InjectedSecret` fingerprinting and `default_patterns_bytes`/`LEAK_PATTERNS` share `SECRET_PATTERN_SOURCES` / `vendor_patterns::VENDOR_SECRET_PATTERNS` — this is the right shape, but as noted in finding M-1, the char-side catalog drifted from the byte-side one. Logging it as architectural debt.
- **Defensive double-checks**: `crypto::encrypt` and `crypto::decrypt` both call `derive_key` and rely on `Zeroizing` for key wipe — the comment correctly notes this is defense-in-depth over the older "manual zeroize on every error path". OK.
