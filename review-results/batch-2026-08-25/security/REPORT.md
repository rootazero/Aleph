### [CRITICAL] `runtime_guard.rs:166-205` — `process_outbound` resolves `{{secret:…}}` placeholders AFTER the leak scan, so a freshly resolved secret value passes straight to the LLM with no detection
- **Category**: security / logic (information disclosure)
- **Description**: The pipeline comment claims "Leak Detection (on text still containing placeholders)" is intentional. Step 1 resolves placeholders into a `resolved_map` but does not mutate `current_text`. Step 2 leak-scans `current_text`, which still contains `{{secret:api_key}}` placeholders. Step 4 then does `current_text.replace(*raw, value)`. A placeholder whose *value* is itself a high-entropy secret (the common case — `sk-…`, `ghp_…`, `AKIA…`) is therefore introduced into the outbound string AFTER every outbound leak/redact pass, with no second scan. The only protection is the inbound `register_injected` round-trip, which requires the LLM to echo the value back, not to leak it onward to a tool.
- **Suggested fix**: After step 1, write the resolved values back into `current_text` (under a placeholder form that does NOT itself match a leak pattern — e.g. a NUL-padded internal marker) and re-scan in step 2. Or run step 2 a second time after step 4. Either way the secret value must see the leak detector before it is shipped to the model.

### [CRITICAL] `content_sanitizer.rs:185-197` — `wrap_external_content` runs sanitizer BEFORE generating the id, so the id is emitted after the body has been mutated (homoglyph folds can shift label-text boundaries; truncation back-off in callers can drop the opening line)
- **Category**: security / correctness (fence spoof)
- **Description**: The id is generated from `rand` and embedded into the opening and closing fence lines. The body inside is `sanitize_external_text(content)`, which folds homoglyphs (fullwidth → ASCII) and strips invisibles. The label attributes (`source_label`) are produced from the *original* source enum fields. The escape step only escapes literal `<<<EXTERNAL_` / `<<<END_EXTERNAL_` prefixes in the body, not in the label. A `ContentSource::WebFetch { url }` whose URL contains the substring `<<<EXTERNAL_` would slip the bytes through the label verbatim — and the label is emitted into the header *before* the body. `sanitize_label_attr` does cover the fence prefix in label values, but it does NOT call `normalize_homoglyphs` first, so a fullwidth `<` in a URL (`\u{FF1C}<<EXTERNAL_UNTRUSTED_CONTENT …`) survives label emission. The forged-marker pass only inspects the body interior, never the label attributes. The model reads the label and the model is the trust boundary.
- **Suggested fix**: Funnel label values through `normalize_homoglyphs` + `strip_invisible_chars` + `sanitize_label_attr` (in that order) before interpolating them into the opening/closing header. Treat the label as part of the boundary surface, not as trusted caller input.

### [HIGH] `ssrf/ip.rs:155-168` — NAT64 detection only matches the well-known prefix `64:ff9b::/96`; locale-dependent RFC 6052 prefixes (`64:ff9b:1::/48`, `2001:db8::/32` …) silently bypass embedded-IPv4 extraction
- **Category**: security / SSRF bypass
- **Description**: `extract_embedded_ipv4` requires `segments[0] == 0x0064 && segments[1] == 0xff9b && segments[2..5] == [0, 0, 0, 0]` — a literal `64:ff9b:0:0:0:0:x.x.x.x`. RFC 6052 §2.2 defines the prefix as variable (Network-Specific Prefix, well-known plus service-suffix and customer-relative prefixes), and many production NAT64 gateways use `64:ff9b:1::/48` or a ULA-translated prefix. An attacker who controls an authoritative DNS for a hostname and points the AAAA record at `64:ff9b:1::a00:1` (i.e. NAT64 of 10.0.0.1) would pass the IPv6 classification (the address is globally routable by 6to4-style reasoning), reach the resolver pinning layer, and only be caught if the embedded-IPv4 path actually fires. It does not. The reqwest `.resolve(host, addr)` then connects to the NAT64 gateway, which routes to a private IPv4 host.
- **Suggested fix**: Match the prefix `64:ff9b::/32` (segments[0..2] only) and extract the trailing 32 bits whenever the upper 96 bits match the NAT64 prefix family. Apply the same prefix-agnostic matching for the customer-relative prefix format. Add a regression test for `64:ff9b:1::a00:1` and `2001:67c:2b0::/48`-style customer prefixes.

### [HIGH] `ssrf/hostname.rs:230-244` — `is_legacy_ip_literal` does not flag a bare all-digit hostname shorter than 4 chars (`"10"`, `"127"`) even though every major OS resolver interprets them as short-form IPv4
- **Category**: security / SSRF bypass
- **Description**: `is_decimal_ip_literal` rejects anything with `s.len() <= 3`. A request to `http://10/` is interpreted by glibc/musl resolver and many language runtimes as `10.0.0.0` (this network), and `http://127/` as `127.0.0.0` (loopback). The legacy-literal detector says "not legacy", the IP-literal path doesn't fire (no dots), and the request is sent to the OS resolver which then connects to the private/loopback address. The host blocklist does not apply because there is no `host` field for a name that resolves to an IP. The whole class of short-form bare-integer hostnames is the bypass.
- **Suggested fix**: Either (a) make `is_decimal_ip_literal` accept ANY all-digit string that parses as u32 (and let downstream IP policy decide), or (b) explicitly reject `len() == 2 || len() == 3` all-digit strings with a "short-form IPv4" reason. Either path closes the bypass; (a) is the more conservative change because it keeps a single source of truth in IP classification.

### [HIGH] `ssrf/hostname.rs:250-258` — `has_url_credentials` misses `http://@host/` and `http://:@host/` (empty user, empty password) because the check is `!username().is_empty() || password().is_some()`
- **Category**: security / URL parser confusion
- **Description**: The `url` crate returns `username() == ""` and `password() == Some("")` for `http://:@host/` (the empty-pair URL grammar allows the colon even with both sides empty). The current predicate catches this. BUT `http://@host/` — the degenerate "at-sign only" form — parses with `username() == ""` and `password() == None`, so the predicate returns `false`. RFC 3986 §3.2.1 explicitly allows `@` to mark the start of an authority; the empty userinfo is well-formed. An attacker who needs credentials-in-URL as a probe signal (the validator exists for credential-leak defense; the LLM would have been given `user:pass@…` to interpret as "log in as X") can use `http://@internal/` to set up the SSRF target while the validator pretends there is no userinfo. The matching on `has_url_credentials(url_str)` does NOT re-parse and re-validate the string.
- **Suggested fix**: Switch to a STRING-LEVEL check on the original `url_str` (look for `://[^/?#]*@` in the authority section), then re-validate that the parsed `Url` has the expected fields. The string check catches `://@` and `://:@` regardless of how the parser normalizes them.

### [HIGH] `injection_patterns.rs:97-201` — 25+ individually compiled `Regex` instances run sequentially per scan; a 1 MB external content payload incurs 25+ MB of linear scans with no early-exit shortcut
- **Category**: performance / DoS
- **Description**: `scan()` runs `p.regex.find(content)` for every compiled pattern and returns the FIRST offset per pattern. There is no `RegexSet` and no early bail-out after the first hit. A 1 MB `web_fetch` payload (well within the truncation cap discussed elsewhere) feeds every pattern; Rust's regex is linear but the linear cost is `O(Σ pattern_length × content_length)`. Patterns are unanchored, so the engine scans from every byte position. Per pattern, worst case ~10 KB of pattern + 1 MB of content = ~10 GB of byte comparisons. With 25 patterns the realistic wall-clock cost on a single core is tens to hundreds of milliseconds per scan, on the synchronous thread that called `first_threat_message_canonicalized`. `scan` is also re-invoked at every Strict scope for every memory-write (`remember` / `note_manage`), so the cost compounds.
- **Suggested fix**: Use `regex::RegexSet` to find "did any pattern match" cheaply in a single pass, then resolve WHICH pattern matched with a second pass on the smaller candidate set. Patterns are split between All / Context / Strict scope, so three `RegexSet` instances (one per scope) are sufficient. The `find` set is reused per `Lazy` slot, the per-pattern `Regex` objects stay for offset extraction. This typically yields a 5-10× speedup on long inputs.

### [HIGH] `headers.rs:35-37` — CSP allows `'unsafe-inline'` for `script-src`, so a model-injected inline `<script>` tag executes with the gateway's own origin
- **Category**: security / XSS pivot
- **Description**: The CSP_VALUE string grants `script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval' blob:`. The module comment justifies `'unsafe-inline'` for the AudioWorklet registration, but `unsafe-inline` removes the only defense-in-depth that would stop an inline `<script>` payload from running if a model-influenced string ever reaches the DOM as HTML. The `frame-ancestors 'none'` and `object-src 'none'` cover other vectors but do not compensate for inline-script execution in the same origin. If the Panel ever renders a model-influenced string as HTML (e.g. a Markdown viewer that does not strip `<script>`), the boundary surface is the model output, not the network surface — and the model is exactly what the strict-CSP artifact route was added to defend.
- **Suggested fix**: Drop `'unsafe-inline'` and replace the AudioWorklet bootstrap with a hash-based nonce (`'nonce-{rand}'`) emitted per response, or move the worklet behind a same-origin `<script src="/worklet/bootstrap.js">` static asset served under the `script-src 'self'` clause. This is the R10 ("LLM Sovereignty") enforcement point: the boundary is the LLM's output, and `'unsafe-inline'` is the firewall-off switch.

### [HIGH] `audit.rs:339-347` — `SecurityAuditLog::log` uses `try_send`; under burst load, security events are dropped with only a periodic `tracing::error!` (every 100th), not a hard backpressure on the producer
- **Category**: security / DoS / log integrity
- **Description**: The audit channel buffer is 256 (set in `runtime_guard.rs:128`). When the channel is full, `try_send` returns `Err`, the entry is dropped, `dropped_count` increments, and a tracing line is emitted only every 100th drop. The actual security events (auth failures, exec blocks, authority changes, scoped-content reads) are lost without any operator-visible signal at the rate at which they happen — the per-100 throttling makes the operator think "we lost 1" when "we lost 99". For `ExecBlocked` and `AuthorityChange` the lost entry is the only post-incident record that the action occurred; the drop is silent in the SQL log. The audit drain loop's `spawn_blocking` insert adds tail latency under load, making drops more frequent.
- **Suggested fix**: Either (a) make the channel `unbounded` (audit is bounded by the rate at which actions can be performed, which is small), or (b) emit the `tracing::error!` on EVERY drop with the event_type and severity, and add a per-event-type drop counter so an operator can `SELECT count(*)` later to see how much trail was lost. (a) is the right answer because audit fidelity is the whole point of the log; backpressure on the security guard is the wrong place to push the loss.

### [HIGH] `runtime_guard.rs:373-390` — `process_inbound` returns `Redacted` (not `Blocked`) when PII is detected; the redacted text is passed downstream as if it were clean
- **Category**: security / logic (PII leakage)
- **Description**: When the inbound PII engine reports `blocked_count > 0`, the response is `GuardResult::Redacted { text: result.text, reasons: vec![...] }`. The redaction replaces the PII spans with placeholders, but the *behavior* of a `Redacted` result in many call sites is "log a warning, continue with the text". A caller that does not branch on the reasons vector (or that pattern-matches only `Blocked` / `Clean`) will silently forward the redacted text to the model as if the PII filter had succeeded. The same inbound redaction pattern is used for `leak_detection` redacts (correctly distinguished from `Block` there), but PII redaction shares the variant with leak redaction — and a downstream call site that handles them identically will not know which one fired.
- **Suggested fix**: Add a separate `GuardResult` variant (`PiiRedacted` or a generic `Redacted { kind, text, reasons }`) so the type system forces the caller to acknowledge which kind of redaction happened. Or return `Blocked` for inbound PII (the caller's existing `Blocked` handler will log + abort), matching the outbound PII behavior.

### [MEDIUM] `secret_env.rs:58-76` — Suffix list misses `_KEY`, `_CERT`, `_AUTH`, `_PASS` and bare `MY_SECRET_NAME`; real secret names leak into child processes
- **Category**: security / information disclosure
- **Description**: `SECRET_SUFFIXES` is `[API_KEY, SECRET, SECRET_KEY, TOKEN, PASSWORD, CREDENTIALS, ACCESS_KEY, PRIVATE_KEY]`. A production secret named `SSH_KEY`, `MY_GPG_KEY`, `TLS_CERT`, `K8S_AUTH`, `MY_DB_PASS`, or `SOMEONE_SECRET_NAME` is not matched (the latter fails because `SECRET` suffix requires `_SECRET`, not `SECRET_*`). The exact-match list does cover common provider names but is a snapshot. Per the module doc, "False negatives would leak a credential" — but the suffix heuristic is too narrow to deliver on that promise.
- **Suggested fix**: Add `_KEY`, `_CERT`, `_AUTH`, `_PASS` (case-insensitive, `ends_with`). Broaden the existing list to include `*SECRET*` as a substring check. The "false positive strips a non-secret" cost is documented as acceptable; the false-negative cost is a credential in a child process.

### [MEDIUM] `ssrf/ip.rs:247-270` — IPv6 classification misses `100::/64` (discard prefix), `2001::/23` (IETF protocol assignments), `2001:db8::/32` (documentation), and the IPv4-compatible `::0.0.0.0/96` shape
- **Category**: security / SSRF coverage
- **Description**: `is_blocked_ipv6` blocks loopback, unspecified, link-local, ULA, multicast, and embedded IPv4 transitions. It does NOT block `100::/64` (RFC 6666 discard prefix — blackhole route, useful for an attacker to silently drop packets or to hide traffic), `2001::/23` (IETF assignments), `2001:db8::/32` (documentation — should never appear in real traffic; its presence is a sign of fabricated logs OR an attacker probing for an SSRF validator that special-cases it), or the IPv4-compatible `::` form past `::1` (covered by `is_loopback` and `is_unspecified`, but the IPv4-compat case `::1.2.3.4` extracts to `1.2.3.4` which is correctly blocked; however `::` itself short-circuits before the extraction, which is fine).
- **Suggested fix**: Add explicit prefix checks for `100::/64`, `2001:db8::/32`, and `2001::/23`. Document the rationale (discard, documentation, protocol-assignment) in the function header so future maintainers understand why these ranges are blocked.

### [MEDIUM] `ssrf/fetch.rs:166-228` — A new `reqwest::Client` is built per redirect hop; the redirect-loop HTTP client construction is duplicated and any future global reqwest settings (timeouts, pool, TLS) must be re-applied each hop
- **Category**: quality / maintainability
- **Description**: `safe_fetch` constructs a fresh `reqwest::Client::builder()` for the initial URL and then again for every redirect target. The builder configuration is identical except for the `.resolve(host, pinned)` line. If reqwest global config (connection pool, default headers, TLS settings, keep-alive) is ever tuned — and it will be — every hop's client must be updated to match, with no compiler help to catch the divergence.
- **Suggested fix**: Build one `reqwest::Client` outside the loop with `.redirect(Policy::none())` and `.timeout(...)`; on each iteration call `.resolve(host, pinned)` on the same client via a wrapper (reqwest doesn't expose `resolve` mutably, so this requires cloning the client). OR keep a `HashMap<String, SocketAddr>` of pin mappings and use a custom DNS resolver (`reqwest::dns::Resolve`). The duplicated-builder smell will compound.

### [MEDIUM] `ssrf/fetch.rs:107-119` — `CROSS_ORIGIN_STRIPPED_HEADERS` is a hardcoded 11-entry list; new auth-header conventions (e.g. `Authorization: Bearer …` via a custom `X-…` header) are not stripped on cross-origin redirects
- **Category**: security / credential leak
- **Description**: The strip list is hardcoded. The named headers cover the common cases (Authorization, Cookie, X-API-Key, X-Auth-Token, X-Access-Token, X-Amz-Security-Token, X-Goog-Api-Key, X-Functions-Key, X-Csrf-Token), but bespoke API conventions that put a token in a `X-Service-Token`, `X-Tenant-Auth`, `X-User-Signature`, etc. are NOT covered. A redirect to a different origin preserves them, and they go to a third party.
- **Suggested fix**: Either (a) extend the hardcoded list (cheap, but always playing catch-up), or (b) strip ALL request headers on cross-origin redirects, requiring the caller to re-add the headers they want to forward. (b) is the safer default; (a) is the incremental fix.

### [MEDIUM] `injection_patterns.rs:407-415` — `COMPILED` panics on the first `scan()` call if a hardcoded regex fails to compile; the failure is fatal in production, not surfaced through `Result`
- **Category**: quality / reliability
- **Description**: `Lazy::new(|| … unwrap_or_else(|e| panic!(…)) …)` is justified in the doc comment ("a bad hardcoded regex is a programming error"), but a panic at runtime inside a `Lazy::new` body surfaces as a stack trace from the `scan` call site — which is the production runtime hot path. If a future refactor introduces a pattern that compiles on stable but fails under a sanitizer or special build, the first `scan` call kills the process. The `#[allow(clippy::panic)]` suppresses the lint that would normally ask for a typed error.
- **Suggested fix**: Validate the catalogue at boot via a `#[ctor]`-style init or a `try_init` that returns `Result<(), regex::Error>` and is called from `main`. If a hardcoded pattern fails to compile, the process refuses to start with a clear message instead of crashing on first user input.

### [MEDIUM] `audit_drain.rs:39-58` — `tokio::select!` between `rx.recv()` and `cleanup.tick()` always prioritizes the recv branch; under sustained audit burst, the cleanup tick is starved indefinitely
- **Category**: logic / maintenance window
- **Description**: `tokio::select!` is fair in `tokio`, but the `rx.recv()` branch is always ready when entries are queued. With a constant trickle of audit events, the cleanup tick (`CLEANUP_INTERVAL = 6h`) may never fire because the select arm sees a fresh entry on every iteration. The cleanup's purpose is retention pruning; missing a cleanup for an unbounded number of hours means the table grows without bound until the OS kills the process or the disk fills.
- **Suggested fix**: Move cleanup to a separate `tokio::spawn` task with its own `tokio::time::interval`. The drain task then has only the receive path and stays simple; cleanup runs on a wall-clock schedule regardless of audit volume.

### [MEDIUM] `runtime_guard.rs:127-128` — `tokio::sync::mpsc::channel(1).1` allocates a sender-receiver pair and immediately drops the sender to signal "no audit"
- **Category**: quality
- **Description**: When `audit_enabled == false`, the function returns `(guard, rx)` with `rx` from `mpsc::channel(1).1`. The sender is allocated and dropped; the receiver is later polled by no one. This is a tiny allocation per `new_with_audit` call but signals "no audit" through the type-erased channel pattern instead of an explicit `Option`. A reader of the code cannot tell whether the absence of audit is intentional.
- **Suggested fix**: Either return `(Self, Option<Receiver<AuditEntry>>)` and let the caller branch, or return a sentinel `()` from a separate constructor `new_without_audit`. The current shape forces every caller to handle a `Receiver` that can never produce.

### [MEDIUM] `ssrf/hostname.rs:67-92` — IDNA homograph detection relies on `url::quirks::domain_to_unicode` and the Cyrillic fold list from `content_sanitizer::normalize_homoglyphs`; IDN 2008 confusables outside the Cyrillic↔Latin table (Greek, Cherokee, Mathematical) bypass the check
- **Category**: security / SSRF bypass
- **Description**: `is_blocked_hostname` checks (1) the literal hostname against the ASCII blocklist, (2) the IDNA-decoded form against the blocklist, (3) the homoglyph-normalized form of (2) against the blocklist. Step 3 only normalizes Cyrillic, Greek Κ/κ, fullwidth ASCII, and a few uppercase Latin confusables. Cherokee confusables (e.g. `ꓤ` → `T`), Mathematical Bold (U+1D5D8 `𝐘`), and fullwidth forms not in the FF01-FF5E block pass through. A `localꓑost` with Cherokee `ꓑ` decodes via IDNA to a non-`localhost` Unicode string that the Cyrillic fold doesn't touch; the blocklist miss is silent.
- **Suggested fix**: Use the `idna` crate (or `unic-idna`) which provides a full UTS-39 confusables table, or extend `normalize_homoglyphs` to cover Cherokee (U+AB70-U+ABBF) and the Mathematical Alphanumeric Symbols block. Either fix requires either a new dependency or a substantial expansion of the fold table; flag as design debt.

### [MEDIUM] `content_sanitizer.rs:170-183` — `wrap_external_content` generates a single random id per call; a flood of `web_fetch` calls against the same page allocates many ids but the LLM cannot distinguish them after invisible-char stripping
- **Category**: logic
- **Description**: The id is the only handle the LLM has to "the boundary that started at line N". After `strip_invisible_chars`, the id is still embedded in the header attribute, but any model-side re-stitching that drops header attributes (which some downstream parsers do) loses the id. The id is also the join column for `split_external_fence` re-emission. If two consecutive fenced payloads get their header attributes stripped downstream, the model can no longer pair opening/closing fences, which is the "unbalanced fence is worse than no fence" failure mode the module comment warns about.
- **Suggested fix**: Either (a) make the fence delimiter include the id in the body as a comment (so attribute stripping doesn't lose it), or (b) document the assumption that the header attributes survive all downstream processing. Currently neither is done.

### [LOW] `runtime_guard.rs:62-66` — `SecurityGuardError` is not `#[non_exhaustive]`; adding a variant breaks downstream callers
- **Category**: quality / API
- **Description**: The enum has a single variant `SecretResolutionFailed`. A future addition (e.g. `ConfigInvalid`, `PolicyDenied`) is a breaking change for any external user of the type. The module is consumed by other in-crate code, so the surface is internal — but the type is `pub`, and `#[non_exhaustive]` is the standard Rust idiom for forward-compatible enums.
- **Suggested fix**: Add `#[non_exhaustive]` to the enum. The crate's redline R7 (one core, many shells) implies the type will grow as new shells add new error conditions.

### [LOW] `secret_equal.rs:42-50` — `provided.get(i).copied().unwrap_or(0)` is a constant-time-claimed operation but the `unwrap_or(0)` short-circuit introduces a data-dependent branch
- **Category**: quality / crypto
- **Description**: The pad-to-equal-length loop iterates `0..max(len)`. For indices past the shorter length, both `provided.get(i)` and `expected.get(i)` return `None`, both pad with 0, XOR is 0. For indices in the shorter length, one side returns the actual byte, the other returns `Some(byte)` or `None`. The `unwrap_or(0)` is on a `Option<u8>::copied()` which compiles to a conditional move (`cmov`) on x86_64 — not a branch. The pattern is constant-time on modern CPUs. The concern is documentation: the module doc says "the comparison cost is `max(provided.len, expected.len)` regardless of where bytes first differ", but the language leaves open whether the *bound* on the loop is constant-time. It is.
- **Suggested fix**: Add a sentence to the module doc explicitly noting the `cmov` dependency and that older architectures (pre-Haswell ARM, pre-Pentium 4 x86) without `cmov` may exhibit measurable timing. This is a documentation fix, not a code change.

### [LOW] `headers.rs:163-167` — `inject_security_headers` silently skips a header if `HeaderName::from_bytes` or `HeaderValue::from_str` fails on the hardcoded entry
- **Category**: quality
- **Description**: The loop pattern-matches on `if let (Ok(name), Ok(value))`. For hardcoded constants this never happens, but a future refactor that adds a non-ASCII value to the table would silently fail to emit that header. The cost of a `tracing::warn!` per skip is negligible.
- **Suggested fix**: Replace the `if let` with a `match` that logs the failure case. The fail-silent shape hides regressions during refactors.

### [LOW] `dangerous_tools.rs:181-193` — `gateway_surface_override` reads `std::env::var` per call; concurrent reads while a test or installer mutates the env var are unsynchronized
- **Category**: logic / test stability
- **Description**: The function does `std::env::var(GATEWAY_TOOLS_ALLOW_ENV)` per invocation. In tests, `ENV_LOCK` serializes the env-var mutations. In production, no such lock exists. An installer or operator script that updates `ALEPH_GATEWAY_TOOLS_ALLOW` at runtime while requests are in flight sees non-deterministic reads (the env var is process-global mutable state). A long-running daemon would benefit from an atomic `Arc<RwLock<HashSet<String>>>` refreshed on SIGHUP.
- **Suggested fix**: Cache the parsed allowlist in an `OnceCell` or `ArcSwap` and refresh via signal handler. For now, document the production expectation that the env var is set at boot and not mutated at runtime.

### [LOW] `audit.rs:344-346` — `try_send` failure increments `dropped_count` even for benign drop reasons (e.g. shutdown sequence draining the channel)
- **Category**: quality
- **Description**: The drain loop reads `rx.recv()` in a `tokio::select!`. When the drain task exits, all `Sender` clones are dropped, and any in-flight `log` call's `try_send` fails with `SendError`. The dropped_count increments for what is actually a clean shutdown, not a log-loss event. A operator inspecting `dropped_count` sees a non-zero number after every restart, conflating "we lost audit entries" with "we shut down".
- **Suggested fix**: Distinguish `SendError(value)` from a closed channel. Track "shutdown drops" separately or skip the increment when the drain receiver is closed (which can be checked via `Sender::is_closed()` if available, or by a sentinel `AtomicBool` set during graceful shutdown).

### [LOW] `secret_env.rs:34-55` — `SECRET_ENV_EXACT` and `SECRET_SUFFIXES` are hardcoded; an organization-specific secret (e.g. `COMPANY_API_KEY`, `MY_CORP_TOKEN`) is not flagged unless it matches a suffix
- **Category**: architecture (R3 — core minimalism)
- **Description**: The list is curated from common providers (Anthropic, OpenAI, AWS, etc.) and common suffixes. Per R3, the security boundary should be Skill/MCP-driven for non-core concerns; an operator who deploys with a custom secret-naming convention has no way to extend the list without recompiling. The list is a snapshot of "what the Aleph maintainers expect", not an interface.
- **Suggested fix**: Move the lists to a config file with a documented schema; let operators extend via config without recompilation. The `is_secret_env` function then becomes a small engine over `(config + defaults)`. Aligns with R3 (configurable, not core-hardcoded) and R9 (configurability exposed as tools).

## Cross-References

- `runtime_guard.rs:166-205` and `injection_patterns.rs:97-201` — both are linear-time consumers of untrusted input. The first because the *order* of operations lets resolved secret values skip the leak detector; the second because the *count* of regex passes multiplies the linear cost. A unified "scan once, decide once" pass over the outbound string would close both.
- `ssrf/hostname.rs:230-244` and `ssrf/ip.rs:108-128` — the legacy-literal detector and the IPv4 policy classifier have a coverage gap. A bare-decimal hostname shorter than 4 chars slips past the legacy check and then gets handed to the OS resolver, which interprets it as short-form IPv4. The IP classifier never sees it.
- `content_sanitizer.rs:185-197` and `content_sanitizer.rs:495-509` — the label-emission path and the forged-marker pass operate on disjoint slices of the wrapped output. The body interior is scanned for forged markers; the header attributes are not. A fullwidth-`<` in a URL escapes label emission into the header where no detection runs.
- `audit.rs:339-347` and `audit_drain.rs:39-58` — `try_send` is the upstream loss surface, `spawn_blocking` insert is the downstream latency surface. The two compound: the drain's latency makes `try_send` fail more often, which increments `dropped_count`, which is reported every 100 entries. An unbounded channel at the producer (a) in this report closes the upstream; separating the cleanup tick closes the downstream fairness issue (MEDIUM above).
- `headers.rs:35-37` (CSP with `'unsafe-inline'`) and `dangerous_tools.rs:100-110` (per-tool arg-level deny) — both are defense-in-depth choices that accept a risk to enable a feature (AudioWorklet registration / loop_graph `root:` writes). Neither choice is wrong in isolation, but together they sketch a security model that relies on every other layer holding. A nonce-based CSP would let the AudioWorklet feature keep working AND remove the inline-script pivot.

## Strengths

- `secret_equal.rs` is the right shape: pad-to-equal-length, XOR-OR, ct_eq, length-checked, with thorough tests including high-bit bytes. The `Option<&str>` wrapper handles the common "either side is missing" case without forcing callers to branch.
- `ssrf/ip.rs` `extract_embedded_ipv4` handles the major IPv6 transition mechanisms (IPv4-mapped, NAT64 well-known, 6to4, Teredo, IPv4-compatible) with explicit RFC references in the comments. The `is_cloud_metadata` carve-out for `fd00:ec2::254` (AWS IMDSv6) is the kind of subtle carrier-grade-network overlap that often ships missing.
- `ssrf/mod.rs:155-170` resolves allowlisted hosts with `SsrfPolicy::for_allowlisted_host()` rather than `SsrfPolicy::disabled()`. This is the right call: an allowlist entry trusts the *name*, not "any address the name resolves to", and the floor (loopback + cloud metadata) is preserved. The module doc explicitly narrates the bypass it closes.
- `ssrf/hostname.rs:30-35` `normalize_host` lowercases AND strips trailing dots. The trailing-dot denylist bypass is closed with a battery of tests that exercise both directions (blocked list, allow list, wildcard, IDNA).
- `content_sanitizer.rs:182-197` runs the sanitizer pipeline in the right order: homoglyph fold → invisible strip → fence escape → forged-marker pass → token scrub. Each step's purpose is documented and the ordering is enforced by the function body. The restored regression tests (`escape_runs_after_stripping_…` and `escape_runs_after_normalization_…`) pin the order against future refactors.
- `injection_patterns.rs` divides patterns into `ThreatScope` tiers (All / Context / Strict) and the `first_threat_message_canonicalized` variant is the documented escape hatch for memory-write paths that hold raw text. The scope ordering test (`scope_ordering_is_supersetting`) catches drift between tiers.
- `audit.rs` test `every_declared_authority_producer_still_records_one` is the kind of backward-direction census that catches silent regressions. The forward-direction limit (name list maintenance) is honestly acknowledged in the doc rather than papered over.
- `runtime_guard.rs:11-19` documents the lock discipline (sync RwLock, must not be held across `.await`) explicitly at the top of the file. Future contributors who need to await between take and drop will see the constraint first.
- `safe_regex.rs` is a clean drop-in `RegexBuilder` wrapper with a size limit + dfa_size_limit. The module doc makes the design choice (in-crate patterns need no bound; operator-supplied patterns do) explicit.
- `unicode_guard.rs` enumerates invisible/directional/tag characters with a per-character rationale comment. The `is_tag_character` carve-out for `U+E0001-U+E007F` is the documented ASCII-smuggling vector.
- `dangerous_tools.rs` argument-level deny reads `ExecTier::Auto::asks_for_arguments(tool_name, args)` rather than re-listing the rule. The `loop_graph` test pins the design: a `root:` write is denied because the predicate fires, not because the name is on a list. New exec-tier rules are covered automatically.
