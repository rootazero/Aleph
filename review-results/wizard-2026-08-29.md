The module shrank by ~300 LOC since round 1 and most of the round-1 dead
weight is genuinely gone (`StepType::Action`, `StepExecutor::Gateway`,
`WizardStep::progress()`, `WizardStep.validation`, `RpcProgressHandle`,
`imessage_transport_options`, the fake `tokio::time::sleep` "work"). The
step-channel ownership model is now documented and correct: `WizardSession`
deliberately does not hold a `step_tx` clone, so channel close is the
flow-completion signal, and `settle()` makes terminal status sticky so a late
`cancel()` cannot clobber a `Done` flow. Poisoned-lock handling is uniform
(`unwrap_or_else(|e| e.into_inner())`), and there are no `unwrap()`s outside
tests.

What remained was concentrated in three places:

1. **Unbounded waits** — `RpcPrompter::prompt` awaited a client answer with no
   deadline. A client that starts a wizard and disappears parks a tokio task
   *forever* and pins its entry in the gateway's session map. Fixed with a
   bounded `ANSWER_TIMEOUT`.
2. **Trusting the client** — `WizardSession::answer` accepted any JSON for any
   step, so a select answer that was never offered (or that belonged to a
   `disabled` option) reached the flow and became config. Fixed with
   server-side `validate_answer`.
3. **Lost steps and lost data** — `next()` short-circuited on terminal status
   before draining buffered fire-and-forget notes (fixed), and the whole
   `OnboardingData` payload is still discarded when the flow ends (deferred —
   needs an API seam on `WizardFlow`).

## Findings

### [High] Unbounded wait for a client answer leaks a task and a session per abandoned wizard
- **Location**: `src/wizard/prompter.rs:101-171` (`RpcPrompter::prompt`)
- **Perspective**: 1 (Security & Robustness) / 2 (Logic & Correctness)
- **Trigger condition**: Any client calls `wizard.start`, receives a step, and
  never calls `wizard.answer` or `wizard.cancel` — a closed browser tab, a
  dropped socket, or a deliberate loop of `wizard.start` calls.
- **Expected behavior**: The flow gives up after a bounded interval, settles the
  session as `Error`, and lets the gateway evict it.
- **Actual behavior**: `rx.await` had no deadline. The spawned flow task lived
  for the lifetime of the process; `WizardSessionManager` only evicts a session
  when a client polls it into a terminal status, so the `Arc<WizardSession>`,
  the task, the collected answers (including plaintext API keys already typed
  into earlier steps) and the pending oneshot all stayed resident. Repeating
  `wizard.start` grows both maps without bound. `wizard.*` is `Class::Admin`,
  which caps the blast radius to an authenticated caller but does not remove it.
- **Fix**: **APPLIED**. Added `pub const ANSWER_TIMEOUT: Duration = 15 min` and
  wrapped the wait in `tokio::time::timeout(ANSWER_TIMEOUT, &mut rx)`. On
  expiry the pending sender is reclaimed from the `answers` map (so it cannot
  leak) and a new `WizardSessionError::AnswerTimeout { step_id, timeout_secs }`
  is returned; the flow task then exits and the session settles as `Error`.
  The timeout branch is race-safe: `&mut rx` (not `rx`) is polled, so if
  `answer()` won the race and already took the sender, the value is recovered
  with `rx.try_recv()` instead of being thrown away.
- **Residual**: the *session map* entry still needs a client poll to be evicted.
  A reaper on `WizardSessionManager` belongs in `src/gateway/handlers/wizard.rs`
  and is out of this module's scope — see Deferred #2.
- **Test**: `prompter::tests::prompt_times_out_and_reclaims_pending_sender`
  (`start_paused`, so it costs no wall-clock time).

### [High] Every answer the onboarding wizard collects is silently discarded
- **Location**: `src/wizard/flows/onboarding.rs:323-336` (`review_and_finalize`),
  `src/wizard/session.rs:121` (`WizardFlow::run` signature)
- **Perspective**: 2 (Logic & Correctness)
- **Trigger condition**: A user completes the onboarding wizard and confirms
  "Apply this configuration?".
- **Expected behavior**: The selected provider/model/keys land in `Config` and
  the vault.
- **Actual behavior**: `OnboardingFlow::run` builds `OnboardingData` on the
  stack, `review_and_finalize` renders it into a summary note, prints
  "Aleph is ready! Run 'aleph chat' to start.", and then `run()` returns `Ok(())`
  and the data is dropped. `WizardFlow::run` yields only `Result<(), _>`;
  neither `WizardSession` nor `WizardSessionManager` exposes any channel for a
  flow's result, and the boot path
  (`src/bin/aleph-server/commands/start/mod.rs:795-812`) only registers a flow
  *factory*. Nothing reads the answers. The round-1 report described this as
  "`prompter.finish()` is never called"; the `finish()`/`WizardNextResult.data`
  API has since been deleted, so the symptom is now "there is no result path at
  all" — the outro is a lie. The in-code comment claiming "the caller routes
  them onto the live `Config`" was factually wrong and actively misleading.
- **Fix**: **DEFERRED** — closing this requires a result seam on the
  `WizardFlow` contract plus wiring in `src/gateway/handlers/wizard.rs` and the
  server boot path, i.e. an API change across three modules. Out of scope for an
  in-module fix, and inventing a `with_sink()` constructor that nothing calls
  would just recreate the dead-seam smell round 1 flagged.
  The misleading comment **was** replaced with an accurate `KNOWN GAP` note
  naming the exact call sites that must change.

### [Medium] `answer()` accepted any JSON value for any step (no server-side validation)
- **Location**: `src/wizard/session.rs:43-110` (`validate_answer`), called from
  `src/wizard/session.rs:303-355` (`WizardSession::answer`)
- **Perspective**: 1 (Security & Robustness) / 4 (Code Quality)
- **Trigger condition**: A client sends `wizard.answer` with a value the step
  never offered — e.g. `{"step_id":"step-2","value":"my-own-provider"}` for the
  provider select, or the `disabled` Slack option in the messaging multi-select.
- **Expected behavior**: The gateway rejects answers outside the offered domain;
  option `disabled` is a server-side rule, not a UI hint.
- **Actual behavior**: `answer()` checked only that `step_id` matched the current
  step and forwarded the raw `Value` to the flow. `RpcPrompter::select`'s
  `serde_json::from_value::<String>` accepts *any* string, so an arbitrary
  provider/model id flowed into `OnboardingData` (and would flow into `Config`
  once the result path exists). The multi-select path likewise accepted disabled
  options. Round 1 flagged this as "`validation` regex is client-only"; the
  `validation` field has since been deleted, so today there is no validation on
  either side.
- **Fix**: **APPLIED**. Added `validate_answer(step, value)`, called before the
  pending sender is taken: `Note` accepts anything; `Confirm` requires a bool;
  `Text` requires a string; `Select` requires a non-disabled offered value;
  `MultiSelect` requires an array whose every element is a non-disabled offered
  value. Steps with no `options` list get the shape check only (they cannot be
  domain-checked). The match is exhaustive with no wildcard, so a future
  `StepType` variant fails to compile rather than silently defaulting to accept.
- **Test**: `session::tests::answer_rejects_values_outside_the_offered_options`,
  `session::tests::validate_answer_enforces_step_shape`.

### [Medium] `next()` dropped buffered notes when the flow finished first
- **Location**: `src/wizard/session.rs:244-300` (`WizardSession::next`,
  `record_step`, `terminal_result`)
- **Perspective**: 2 (Logic & Correctness)
- **Trigger condition**: A flow ends shortly after emitting fire-and-forget note
  steps (`intro`/`note`/`outro` go through `prompt_no_wait`, which does not
  block), and the client's next poll arrives after the flow task settled.
- **Expected behavior**: Queued steps are delivered, then the terminal status.
- **Actual behavior**: `next()` checked `status != Running` *before* touching the
  receiver and returned `done()` immediately, abandoning up to 16 buffered steps
  in the channel. For `OnboardingFlow` this is exactly the final
  `outro("Aleph is ready!")` — a genuine race in which the closing message is
  shown or not depending on scheduler timing. A notes-only flow could lose every
  step it ever emitted.
- **Fix**: **APPLIED**. `next()` now acquires the receiver first and drains with
  `try_recv()` before consulting the status; buffered steps outrank a terminal
  status. To preserve the old non-blocking behavior for an already-settled
  session, the settled path uses `try_lock()` and falls back to reporting the
  terminal status if a concurrent `next()` owns the receiver. The duplicated
  status→result mapping (round-1 low finding) collapsed into
  `terminal_result()`, and step recording into `record_step()`.
- **Test**: `session::tests::buffered_notes_survive_flow_completion`.

### [Medium] Answering a note step stalled the wizard with `StepNotFound`
- **Location**: `src/wizard/session.rs:340-347`, `src/wizard/prompter.rs:171-183`
- **Perspective**: 1 (Security & Robustness) / 2 (Logic & Correctness)
- **Trigger condition**: A client uniformly calls `wizard.answer` for every step
  it is handed — the natural implementation, since `wizard.answer` is the
  advancing call — and is handed a note emitted via `prompt_no_wait`.
- **Expected behavior**: The note acknowledgement succeeds and the wizard
  advances.
- **Actual behavior**: `prompt_no_wait` registers no `PendingAnswer`, so
  `answers.remove(step_id)` returned `None` and the client got
  `StepNotFound` (JSON-RPC `INVALID_PARAMS`) for a step it was literally just
  given — pointing the client at a nonexistent bug. Round 1 reported this;
  still open at review time.
- **Fix**: **APPLIED**. When no pending answer exists *and* the current step is
  a `Note`, `answer()` logs and returns `Ok(())`. The pending-sender lookup is
  still tried first, so notes pushed through `prompt()` (as the gateway's
  `TestFlow` does) keep their normal answer path.
- **Test**: `session::tests::answering_a_note_is_acknowledged_and_flow_continues`.

### [Low] The answer value was interpolated into an error string
- **Location**: `src/wizard/session.rs:333-339` (was: `format!("Failed to send answer: {e}")`)
- **Perspective**: 1 (Security & Robustness)
- **Trigger condition**: `answer()` races a flow that stopped waiting (timeout,
  cancel); `oneshot::Sender::send` returns `Err(value)` — the value being the
  answer itself.
- **Actual behavior**: The rejected value was formatted into
  `WizardSessionError::Internal`, which is returned to the client and logged.
  For a `sensitive` step that value is a plaintext API key.
- **Fix**: **APPLIED**. The error now names the step only:
  `"Failed to deliver answer for step '<id>': flow is no longer waiting"`.

### [Low] Duplicate pending step id silently evicted the first prompt's sender
- **Location**: `src/wizard/prompter.rs:105-122`
- **Perspective**: 1 (Security & Robustness — step_id reuse)
- **Trigger condition**: A flow issues two prompts carrying the same `step.id`
  while the first is still pending. `next_id()` is monotonic, but `prompt()`
  keys on `step.id`, and flows may hand in their own steps (both the session and
  gateway `TestFlow`s do).
- **Actual behavior**: `HashMap::insert` dropped the first `PendingAnswer`,
  making the older prompt fail with a misleading "channel closed unexpectedly
  (flow may have panicked)".
- **Fix**: **APPLIED**. Registration uses the `Entry` API and rejects an
  occupied slot with `Internal("Duplicate pending step id '<id>'")` plus a
  `warn!`. A sequential re-ask of the same id is unaffected: the entry is
  removed when the earlier prompt resolves.
- **Test**: `prompter::tests::duplicate_pending_step_id_is_rejected`.

### [Low] Answering the same step twice reported `StepNotFound`
- **Location**: `src/wizard/session.rs:348-353`
- **Perspective**: 2 (Logic & Correctness)
- **Actual behavior**: A duplicate submit (double-click, retry after a timed-out
  RPC) returned "Step not found", sending the client hunting for a missing step.
  Round-1 finding; still open at review time.
- **Fix**: **APPLIED**. When the id matches the current step but nothing is
  pending and the step is not a note, the error is now
  `InvalidAnswer("Step '<id>' has already been answered")`. Both variants map to
  `INVALID_PARAMS` in `wizard_error_code`, so the wire contract is unchanged.
- **Test**: `session::tests::second_answer_reports_already_answered`.

### [Low] `cancel_tx` is an `RwLock` that is only ever write-locked
- **Location**: `src/wizard/session.rs:142`
- **Perspective**: 4 (Code Quality)
- **Actual behavior**: `Arc<RwLock<Option<oneshot::Sender<()>>>>` where the sole
  access is `.write().take()`. A `Mutex` states the intent. Round-1 finding,
  still open.
- **Fix**: **DEFERRED** — pure cosmetics on a correct code path; not worth the
  diff noise in a review commit.

### Perspective 3 — Architecture Compliance (R1–R10)
No violations found.
- **R1**: no platform APIs; the module is pure async Rust over channels.
- **R3**: dependencies are `serde`, `serde_json`, `tokio`, `thiserror`,
  `async-trait`, `tracing`, `uuid` — all already core.
- **R4**: the module holds no business logic; `OnboardingFlow` is a question
  script and option catalogue, and the (missing) persistence explicitly belongs
  to the caller. Note that the *model catalogue* in `model_options()` is a
  hardcoded list that will rot — it is presentation data, not routing logic, so
  it does not violate R8, but it is a maintenance liability worth a follow-up.
- **R7/R10**: no shell-specific behavior, no middleware layer.

## Deferred

1. **Onboarding result path** (High #2) — needs `WizardFlow` to expose a result,
   `WizardSession`/`WizardSessionManager` to carry it, and the boot path to apply
   it to `Config` + vault. Cross-module API change.
2. **Abandoned-session reaper** — `WizardSessionManager` (in
   `src/gateway/handlers/wizard.rs`) only evicts sessions when a client polls
   them into a terminal status. `ANSWER_TIMEOUT` now guarantees the *task* dies,
   but the map entry survives until someone asks. Out of module.
3. **`AnswerTimeout` error code mapping** — `wizard_error_code` funnels the new
   variant into `INTERNAL_ERROR` via its `_` arm. A dedicated code would be
   clearer, but the mapping lives outside `src/wizard/`.
4. **`cancel_tx` `RwLock` → `Mutex`** (Low) — cosmetic.
5. **`model_options()` hardcoded catalogue** — will drift out of date; belongs
   behind the provider registry rather than a `match` in a wizard flow.
