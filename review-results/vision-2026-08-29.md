# Logic Review Report — src/vision
**Module**: `src/vision/`
**Scope**: full module (5 top-level `.rs` files + 1 in `src/vision/providers/`, ~845 LOC)
**Date**: 2026-08-29
**Mode**: strict
**Supersedes**: `review-results/vision.md` (2026-07-20, stale — referenced a removed `claude.rs` provider and a `validate_confidence` helper that never existed in this module).

## Summary

- Issues found: **3 high-confidence** (1 high / 2 medium), **5 low**, plus 2 informational observations.
- The module is small (~845 LOC) and the architecture is clean (R1 verified — only `aleph_desktop` traits / `NativeScreen` struct; no platform-API imports; no heavy deps).
- The fallback-chain logic in `VisionPipeline` and the `VisionProvider` trait ergonomics are solid.
- The main exposure is the `resolve_png_bytes` function in `platform_ocr.rs`: it trusts user-provided format labels and reads whole files / decodes whole base64 blobs before applying the size cap. That is the only security-relevant surface in this module.

## High-Confidence Issues

### [High] Base64 input has no pre-decode size bound — DoS via `String` allocation + base64 decode before the cap fires
- **Location**: `src/vision/providers/platform_ocr.rs:78-93` (`resolve_png_bytes` → `ImageInput::Base64` arm)
- **Trigger condition**: A caller submits `ImageInput::Base64 { data: "<huge base64>", format: Png }`. The `data` field is a `String`, so a 1 GiB submission already costs 1 GiB of `String` allocation before the function runs. `base64::engine::general_purpose::STANDARD.decode(data)` then materialises a ~750 MiB `Vec<u8>`. Only *after* the decode does `decoded.len() > MAX_IMAGE_FILE_SIZE` fire — and the function returns `Err`, but the 750 MiB has already been allocated and is now waiting to be freed. Under concurrent requests this is a trivial DoS vector against the agent host.
- **Expected behavior**: The size cap is a *DoS guard*, not a property of the decoded payload. Reject oversized encoded payloads before allocating the decoded buffer.
- **Actual behavior**: The cap is checked *after* `String` + `Vec<u8>` allocation + base64 decode. Equivalent to no cap at all for `ImageInput::Base64`.
- **Suggested fix**: Derive an encoded-size bound from `MAX_IMAGE_FILE_SIZE` (base64 standard: `N` decoded bytes ⇒ `((N + 2) / 3) * 4` encoded chars, no line breaks). Reject `data.len() > MAX_BASE64_ENCODED_SIZE` before calling `decode`. The constant belongs in `types.rs` alongside `MAX_IMAGE_FILE_SIZE` so it is grep-able as a single source of truth. See the corresponding fix in this commit.
- **Severity rationale**: HIGH because (a) the surface is reachable from any agent that handles attached images, (b) the cap name ("MAX_IMAGE_FILE_SIZE") advertises a DoS guarantee the code does not provide, and (c) the fix is small (one const, one `if`, one error path).

### [Medium] `ImageInput::FilePath` reads the whole file into memory before the size cap fires
- **Location**: `src/vision/providers/platform_ocr.rs:102-117` (`resolve_png_bytes` → `ImageInput::FilePath` arm)
- **Trigger condition**: A caller submits `ImageInput::FilePath { path: "/tmp/huge.bin" }` where the file is 100 GiB. `tokio::fs::read` reads the entire file into a `Vec<u8>` and *then* the size check rejects it. The host has now allocated 100 GiB and is paging it back out, which OOM-kills other tenants on shared machines.
- **Expected behavior**: Check the file's reported size (`tokio::fs::metadata`) before allocating the read buffer.
- **Actual behavior**: Cap is post-allocation. Same DoS shape as the Base64 case.
- **Suggested fix**: `let meta = tokio::fs::metadata(path).await...?; if meta.len() > MAX_IMAGE_FILE_SIZE { return Err(...); }` before `tokio::fs::read`. The metadata call is a single `stat(2)` — orders of magnitude cheaper than reading the file. The post-read check stays as a defence-in-depth (TOCTOU between `metadata` and `read` could otherwise let a writer sneak extra bytes in).
- **Severity rationale**: MEDIUM because (a) the FilePath variant is less exposed than Base64 (caller needs filesystem access — but the agent *does* have that, and a steered model can pass any path the harness permits), and (b) the metadata-first pattern is the same shape already used by `builtin_tools/desktop/set_of_marks.rs` and `native.rs` (`aleph_desktop::perception::DEFAULT_SCREENSHOT_MAX_BYTES` short-circuits on `metadata.len()`).

### [Medium] `ImageInput::Base64` PNG label is trusted without magic-byte verification — passes JPEG bytes as PNG to the platform OCR backend
- **Location**: `src/vision/providers/platform_ocr.rs:78-94` (`resolve_png_bytes` → `ImageInput::Base64` arm)
- **Trigger condition**: A caller submits `ImageInput::Base64 { data: "<base64 of JPEG bytes>", format: Png }`. The current code decodes the base64, sees a non-PNG declared format would be rejected at line 94, but a *declared PNG* with non-PNG bytes passes through unchanged. The upstream macOS Vision framework tolerates this (it sniffs magic bytes), but the inline comment at line 91-93 explicitly notes "other platform providers will not".
- **Expected behavior**: When the caller labels the bytes as `Png`, the bytes should actually be a PNG. Reject obvious mismatches at the boundary instead of pushing them through to the platform layer.
- **Actual behavior**: Declared format and actual format are decoupled. The size cap and the format-vs-magic-byte mismatch are orthogonal — fixing only the size cap leaves the magic-byte hole.
- **Suggested fix**: After decoding, when `format == ImageFormat::Png`, verify the 8-byte PNG signature (`89 50 4E 47 0D 0A 1A 0A`). Any other declared format is already rejected at line 94 with the explicit "PNG only" error, so the magic-byte check only fires on the declared-PNG path. The check is ~10 lines, no new dependency (`image` is already in the workspace but a hard dep on it here would be heavier than necessary for a single magic-byte sniff).
- **Severity rationale**: MEDIUM because (a) the comment in the file already acknowledges the gap, (b) the failure mode is "wrong OCR output" rather than a host crash, (c) only the platform-OCR provider has this shape today — a multimodal-LLM provider would re-validate the format server-side — and (d) the fix is self-contained.

## Per-perspective findings

### Security
- The three cap points (`MAX_IMAGE_FILE_SIZE`) at `platform_ocr.rs:83, 110` and the FilePath metadata-less read — see High and Medium above.
- No payload-size cap on the `data: String` field of `ImageInput::Base64` at the *type* level — see High above.
- No MIME sniffing — see Medium above.
- Provider-error semantics: `VisionError::ProviderError(String)` is a single-variant catch-all. The fallback chain treats every error as transient. A real distinction between "rate-limited (retry)" and "auth-failed (don't retry)" is not surfaced; today only one provider is wired in production so this is dormant. **Defer** until a second provider lands.
- No `unwrap()` / `expect()` in production paths (verified via `grep`; all `.unwrap()` calls live inside `#[cfg(test)]` modules — `mod.rs:221-398` and `platform_ocr.rs:229-255`).
- No `unsafe`, no `tokio::task::spawn` of untrusted futures.

### Logic & Correctness
- **Provider fallback chain**: `VisionPipeline::understand_image` and `VisionPipeline::ocr` (mod.rs:42-83, 87-117) both implement "first-success-wins, last-error-surfacing" cleanly. The capability-gate loop is correct: a provider without the capability is `continue`d without recording an error, so a provider that genuinely fails does not get masked by a no-op skip earlier in the chain.
- **Empty pipeline** returns `VisionError::NoProvider`. Distinct from "no capable provider" (`VisionError::UnsupportedCapability`) and "all capable providers failed" (`VisionError::ProviderError(last)`). Three distinct error variants for three distinct failure modes — correct.
- **`ImageFormat` parse-don't-validate**: the enum is the boundary; the `#[non_exhaustive]` attribute lets us add formats without an API break. Currently the `Base64 { format }` path *trusts* the label (see Medium above), but the type itself is parse-don't-validate.
- **Confidence bounds**: there is no confidence surface in this module. `convert_platform_ocr_result` discards the `lines` field (which carries `confidence: Option<f64>` in `aleph_desktop::OcrLine`). The TODO comment at `platform_ocr.rs:181` acknowledges this and the explicit `let _lines =` binding makes the omission greppable per the inline comment. Per R10 (YAGNI), this is acceptable. The stale `vision.md` review mentioned a `validate_confidence` helper — that function does not exist in this module and the prior review was based on an out-of-date state of the code.
- **Duplicate provider registration**: `add_provider` always pushes; duplicates are not deduplicated by name. Not a bug today (callers register once at startup), but worth a one-line guard if a future caller registers dynamically. **Defer**.

### Architecture (R1-R10)
- **R1 — verified clean**. `src/vision/` imports only `crate::vision::*` and `aleph_desktop::{ScreenCapability, DesktopPlatform, OcrResult, NativeScreen}`. The `NativeScreen` is the shared `desktop/shared` cross-platform implementation; the macOS-specific / Linux-specific / Windows-specific implementations live in `desktop-macos`, `desktop-linux`, `desktop-windows` and are reached via the bridge JSON-RPC IPC. **No** `cocoa`, `appkit`, `coregraphics`, `objc2`, `metal`, `windows`, `x11`, `wayland`, or other platform-API imports in `src/vision/`. Verified via `grep -rn "cocoa|appkit|coregraphics|objc2|metal" src/vision/` → 0 hits.
- **R3 — verified clean**. Crates used: `async-trait`, `base64`, `schemars`, `serde`, `thiserror`, `tokio` (already workspace deps). No new heavy deps.
- **R4 — verified clean**. The vision module is pure capability plumbing — no business logic. The pipeline's `Default` returns an empty pipeline; the only consumer wiring is `aleph-server/commands/start/builder/agent_init/mod.rs:1266-1285` (registers `PlatformOcrProvider::new()`).
- **R5**: not applicable to this module.
- **R8**: not applicable (no routing decision).
- **R9**: not applicable (no LLM-driven config).
- **R10**: not applicable (no middleware tax).
- **`Default` for `PlatformOcrProvider`** uses `Arc::new(aleph_desktop::NativeScreen::new())`, which is documented in the inline comment as returning `NotImplemented` for OCR on macOS (macOS routes OCR through the Swift bridge). The wiring at `agent_init/mod.rs:1277` uses `PlatformOcrProvider::new()` and accepts this degradation — the comment chain is consistent.

### Code Quality
- **`mod.rs` module-level docstring** (3 lines) covers the trait and the pipeline. Could mention the production wiring (image-attachment fallback in `MediaProcessor::describe_image_fallback`) and the size cap, but not blocking. **Defer** (low value, no functional impact).
- **`provider.rs` trait** is clean: 4 methods, async_trait, `Send + Sync`. The trait docs name the orchestrator (`VisionPipeline`) so the reader can find it.
- **`types.rs`** exposes only what is needed. `MAX_IMAGE_FILE_SIZE` is `pub` so other modules can reference the cap consistently.
- **`error.rs`**: thiserror with `#[non_exhaustive]` on the enum so future variants don't break callers. `Clone` is derived — needed because `VisionError` is `Send + Sync`-friendly across `Arc<dyn VisionProvider>` boundaries. Reasonable.
- **Error messages** are clear (`"decoded image exceeds maximum size of 10 MB"`). After the High fix above, the new pre-decode path should follow the same wording pattern so callers see a single message shape regardless of which arm rejected the input.
- **`with_screen` constructor** in `platform_ocr.rs:54` is documented as "for testing" but no test in this file uses it (and the test in `builtin_tools/desktop/native.rs:2695-2811` uses a `FixedOcrProvider` that impls `VisionProvider` directly, not `PlatformOcrProvider::with_screen`). Effectively dead code today. **Defer** — it's the natural injection seam and may light up when a test mock is added.
- **Tests** (12 total: 7 in `mod.rs`, 6 in `platform_ocr.rs`):
  - **Gaps**: no test for the size cap (current tests use 5-byte "hello" data); no test for mislabeled format; no test for metadata-first short-circuit; no test for the pre-decode base64 bound. These will be added as part of the fixes above.
  - **Strengths**: capability dispatch is well-tested (`skips_providers_without_capability`, `no_provider_supports_capability_returns_unsupported`); empty-pipeline / fallback / last-error all covered.

## Suggested Test Additions (informational)

```rust
#[tokio::test]
async fn oversized_base64_is_rejected_before_decode() {
    // Build a base64 string larger than MAX_BASE64_ENCODED_SIZE without
    // actually allocating a correspondingly large Vec. The fix replaces
    // "decode then check" with "check then decode", so a 100 KiB base64
    // string (representing ~75 KiB decoded) must fail before the decoder
    // runs even though the decoded payload would be under MAX_IMAGE_FILE_SIZE.
    let huge_b64 = "A".repeat(MAX_BASE64_ENCODED_SIZE + 4);
    let image = ImageInput::Base64 { data: huge_b64, format: ImageFormat::Png };
    let err = PlatformOcrProvider::resolve_png_bytes(&image).await.unwrap_err();
    assert!(matches!(err, VisionError::ImageError(_)));
}

#[tokio::test]
async fn mislabeled_png_payload_is_rejected_by_magic_byte_check() {
    // JPEG bytes (FF D8 FF ...) labeled as PNG. The fix verifies the
    // 8-byte PNG signature; this test must fail before the fix.
    // Use a minimal 1x1 JPEG byte sequence.
    let jpeg_bytes = b"\xFF\xD8\xFF\xE0\x00\x10JFIF\x00";
    let b64 = base64::engine::general_purpose::STANDARD.encode(jpeg_bytes);
    let image = ImageInput::Base64 { data: b64, format: ImageFormat::Png };
    let err = PlatformOcrProvider::resolve_png_bytes(&image).await.unwrap_err();
    assert!(matches!(err, VisionError::ImageError(_)));
}

#[tokio::test]
async fn oversized_file_is_rejected_via_metadata_before_read() {
    // Create a temp file > MAX_IMAGE_FILE_SIZE bytes, assert the call
    // rejects without reading the body. The current code reads then checks.
    let dir = tempdir().unwrap();
    let path = dir.path().join("huge.png");
    let f = std::fs::File::create(&path).unwrap();
    f.set_len(MAX_IMAGE_FILE_SIZE + 1).unwrap();
    drop(f);
    let image = ImageInput::FilePath { path: path.clone() };
    let err = PlatformOcrProvider::resolve_png_bytes(&image).await.unwrap_err();
    assert!(matches!(err, VisionError::ImageError(_)));
}

#[tokio::test]
async fn valid_minimal_png_passes_through() {
    // The well-known 1x1 transparent PNG. After the magic-byte check
    // lands, this is the canonical positive test.
    let b64 = "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR4nGNgYGD4DwABBAEAfbLI3wAAAABJRU5ErkJggg==";
    let image = ImageInput::Base64 { data: b64.to_string(), format: ImageFormat::Png };
    let bytes = PlatformOcrProvider::resolve_png_bytes(&image).await.unwrap();
    assert_eq!(&bytes[..8], &[0x89, b'P', b'N', b'G', b'\r', b'\n', 0x1a, b'\n']);
}
```

## Cross-Module Findings

- **Wiring verified**: `VisionPipeline` is built at `aleph-server/commands/start/builder/agent_init/mod.rs:1274-1282` with `PlatformOcrProvider::new()` (no platform injection — the bare-`NativeScreen` path). The `MediaProcessor::describe_image_fallback` calls into this pipeline (`src/gateway/execution_engine/run_loop/inner.rs:505`) for image-attached turns. A second wiring site at `builtin_tools/desktop/vision_bridge.rs:84` (`VisionToolService`) is constructed with the pipeline for the `screenshot { describe: true }` tool.
- **Architecture consistency**: `builtin_tools/desktop/set_of_marks.rs:558` and `native.rs:646-663` already use the `metadata().len() <= DEFAULT_SCREENSHOT_MAX_BYTES` short-circuit pattern before reading screenshot bytes. The fix to `resolve_png_bytes` mirrors that pattern, which keeps the codebase internally consistent.
- **No dead public API in production**: every `pub fn`/`pub struct` in this module is referenced somewhere in the crate. `PlatformOcrProvider::with_screen` is the closest to orphaned but is documented as the injection seam.
- **Constants**: `MAX_IMAGE_FILE_SIZE` is the only public numeric constant in this module. After this fix, `MAX_BASE64_ENCODED_SIZE` joins it; both live in `types.rs` next to each other, so a future bump is a single edit.

## Conclusion

`src/vision/` is a small, well-scoped capability module that respects the R1 brain–limb separation. The static review surfaced one HIGH (base64 pre-decode DoS), two MEDIUM (FilePath whole-file read, missing PNG magic-byte verification), and five LOW issues. The HIGH and the two MEDIUMs are fixed in this commit (pre-decode base64 bound, metadata-first file size, PNG magic-byte check). The LOWs are documented but deferred per R10 (YAGNI).
