## High-Confidence Issues

### [Medium] scratch.rs reap sends SIGKILL to a possibly-recycled PID
- **Location**: `src/utils/scratch.rs:80-89` (`register_for_exit` / `reap`)
- **Description**: The reaper registry stores `(Option<u32>, PathBuf)` pairs. At atexit time it unconditionally calls `libc::kill(pid, SIGKILL)` on any non-None pid. The accompanying comment ("A stale pid gets ESRCH, which is ignored") is incomplete: ESRCH means "no process with this PID exists *right now*", which is the wrong condition. The relevant failure mode is PID recycling — the recorded child exited, its PID was reclaimed by the kernel and reassigned to a *different* process, and `kill(recycled_pid, SIGKILL)` now kills an unrelated process.
- **Risk / trigger**: Test probe harnesses (`tests/provider_rpc_probe/harness.rs:150`, `tests/compactor_e2e_probe/harness.rs:160`) spawn `aleph-server` and call `reap_on_exit(child.id(), dir)`. If `aleph-server` dies early (its port probe found nothing; the host's PID space cycled), the reap path crosses into a different process's lifetime before atexit fires. Likelihood is low (the reap window is sub-second), but the consequence is high: SIGKILL to an unrelated system process.
- **Suggested fix**: Capture the recorded process's start time at `register_for_exit` (via `crate::utils::process_alive::process_start_time`) and store it alongside the pid; at reap, gate the kill on `process_alive::process_matches(pid, Some(start))`. `process_alive` already has this exact contract for the singleton lock's holder record — the same defence applies here.
- **Decision**: DEFERRED (rationale: requires a non-trivial API surface change — `register_for_exit` becomes 4-arg, the `DOOMED` static's type changes, the atexit handler must call into `process_alive` which in turn creates a `sysinfo::System`. The fix is correct and bounded, but it is large enough that a single round should not bundle it with the small fixes below — splitting it out keeps the diff reviewable.)

### [Medium] reqwest_limit.rs has zero tests
- **Location**: `src/utils/reqwest_limit.rs` (entire file)
- **Description**: `bytes_with_limit` and `text_with_limit` are the SSRF/size-limit choke point documented in the module's own preamble ("Review-fetch P0 (2026-08-20) named this as the missing piece on the SSRF / size-limit path"). The body has clear documented semantics (Content-Length pre-check, streaming cap, `Ok(None)` vs `Err` distinction for size-vs-decode failure) and no `#[cfg(test)]` block at all.
- **Risk / trigger**: A future refactor that, say, changes the streaming cap to a soft post-check (`buf.len() < limit` rather than `buf.len() + chunk.len() > limit`) would not be caught by any test — the call sites (`firecrawl.rs`, generation-poll path) would still pass user-facing tests, and the size cap would silently degrade into "read one more chunk after going over" on the happy-but-large path.
- **Suggested fix**: Add a `#[cfg(test)]` block exercising: (a) body under limit, (b) body over limit with a `Content-Length` header that exceeds `limit`, (c) body over limit without `Content-Length` (chunked), (d) UTF-8 decode failure on a body under the byte limit. The crate already depends on `wiremock = "0.6"` (dev), so no new dependency is required.
- **Decision**: FIXED — see commit. Added the four tests using wiremock.

### [Low] paths.rs uses inline `use tracing::info;` instead of the file-level import
- **Location**: `src/utils/paths.rs:575, 805, 825, 854, 862` (5 sites) and indirectly at `:1006, 1008` (qualified `tracing::warn!` / `tracing::info!` calls with no import at all)
- **Description**: Five helpers in `paths.rs` open with `use tracing::info;` inside the function body. The crate's own convention (e.g. `src/utils/json_extract.rs:12` — the only other `tracing::`-using module in `src/utils/`) is a top-of-file `use tracing::debug;`. The inline pattern reads as a half-finished refactor, and Rust's `unused_imports` lint would fire if a helper ever stops logging; the file-level form catches that once and consistently.
- **Risk / trigger**: Cosmetic; rustfmt/clippy does not flag it. But a new helper that needs `tracing::warn!` has to choose between copying the inline shape and introducing a sixth one, neither of which the file's existing pattern resolves.
- **Suggested fix**: Promote `use tracing::{info, warn};` to the file-level import block (lines 16-17 area) and drop the five inline `use tracing::info;` lines. The qualified `tracing::warn!` / `tracing::info!` calls at 1006/1008 stay qualified — they are inside `migrate_legacy_db_files` and the file-level `warn`/`info` import covers them either way, but converting them to the short form keeps the file consistent.
- **Decision**: FIXED — see commit.

### [Low] atomic_write.rs silently swallows `set_permissions` failure
- **Location**: `src/utils/atomic_write.rs:82-86`
- **Description**: After writing + fsyncing the staging file, the code copies the destination's existing mode onto the staging file with `let _ = fs::set_permissions(...).await;`. A failure here is dropped on the floor and the rename proceeds, leaving the new file at the staging default (0600 on Unix). The accompanying doc says "Best-effort: a failure here must not abort an otherwise-good write", which is the right call *for correctness* — but it is silent on *observability*: an operator who wrote `chmod 0755 script.sh` and then had `atomic_write_file` rewrite it has just lost the executable bit with nothing in the log to point at the cause.
- **Risk / trigger**: `set_permissions` can fail for filesystem reasons (EROFS on a mounted read-only filesystem, EACCES on a directory whose mode was just tightened by an admin, ENOSPC on filesystems where permission changes allocate metadata). The call site is `secrets.vault`, `security.db`, `pairing.db` writes — none of which are scripts — so the realistic trigger is on scripts the operator manages through Aleph's skill executor or a future document-write path. No live call site exhibits this today.
- **Suggested fix**: Log via `tracing::warn!` on failure (matches the module's existing logging style — `instance_lock::diagnose_holder` already follows this pattern). The rename still proceeds; the operator gets a one-line breadcrumb.
- **Decision**: DEFERRED (rationale: no live call site exercises the failure mode today; logging is a behaviour change that would surface in unrelated operator logs. The fix is one line, but it is a behaviour change, not a bug fix, and the documentation already calls it out — adding it as a follow-up when the first script-write call site lands keeps the change tied to the trigger that justifies it.)

## Per-perspective findings (lower confidence)

### Security
- `instance_lock::try_acquire` uses `O_NOFOLLOW` only on Unix; the non-Unix fallback is documented (Windows has no portable equivalent). The unlocked sidecar pattern (writing the holder PID to `aleph.lock.pid` rather than the locked file itself) is the correct cross-platform shape — `LockFileEx` blocks reads from other handles, so reading from the locked file would fail with os error 33.
- `paths::ensure_private_dir` refuses a foreign-owner or group-reachable root with `PermissionDenied` rather than adopting it — the documented "name is public, ownership is private" posture. The `lstat` (not `stat`) choice is the load-bearing one for the symlink case.
- `paths::is_path_within` is lexical-only and uses `Component`-level normalization — no filesystem touch, so no symlink TOCTOU window. The prefix-confusion test (`/skills/demo` vs `/skills/demonstration`) guards the exact shape that would be a security bug if missed.
- `reqwest_limit::bytes_with_limit` correctly checks Content-Length *before* reading chunks AND caps during streaming — not one or the other. The `Ok(None)` vs `Err` distinction is the right shape (size is a domain decision; the helper returns the data, the caller decides whether to surface it as a 413 / 4xx / fallback).
- `scratch::register_for_exit` PID-reuse concern is documented as the Medium finding above.

### Logic
- `fifo_cache::remember` correctly handles re-insert (no double-booking of the eviction slot, validated by test) and the `cap == 0` corner case (debug-asserted in tests; production falls through to "silently swallowed" with a doc comment that names the intent).
- `text_format::truncate_*` covers five distinct contracts (soft chars + `...`, soft chars + caller marker, hard chars, hard chars + reserved marker, bytes with UTF-8 safety). The module doc explicitly enumerates the table so a future caller picks the matching row rather than hand-rolling a 23rd copy.
- `filename::sanitize_filename` checks Windows reserved names by stem (cut at FIRST `.` / `:`), with explicit tests for `CON.txt`, `con.tar.gz`, `con:foo` — the three separators that were all missed in earlier rounds. The stem is trimmed of trailing whitespace, matching Win32's parser.
- `json_extract::find_matching_brace` correctly handles `\\` + `"` (escaped backslash followed by literal `"`) and `\\` + `\\` (escaped backslash followed by escaped backslash) — the escape_next state machine alternates correctly across consecutive backslashes.
- `process_alive::process_matches` was the consolidation round (one `sysinfo::System` per call serves both existence and start-time lookup; the older `is_process_alive` + `process_start_time` pair refreshed twice).

### Architecture (R1–R10)
- **R1**: every `unsafe { libc::* }` site (`libc::kill`, `libc::geteuid`, `libc::atexit`) is in `#[cfg(unix)]` arms with a SAFETY comment; the `#[cfg(windows)]` block in `no_window.rs` is the only Windows-platform-API surface in the module and is a documented extension trait, not a call from core business logic.
- **R3**: no heavy deps introduced by this module. `sysinfo = "0.39"` is the new transitive weight; it is the cross-platform primitive the rest of the codebase reaches for (`gateway::memory_monitor`), so the cost is amortised.
- **R4 / R7**: utilities are pure I/O with no business logic, and they are shared across all shells. The `no_window` trait is the canonical example of the shape the redline prescribes.
- **R8**: zero regex for non-machine formats. `extract_json_robust` is for parsing JSON out of LLM output — JSON is exactly the "machine format" the redline permits regex for (here, a proper brace-matching lexer, which is strictly better).
- **R9 / R10**: utils has no configurability surface and no middleware layer.

### Quality
- Public API surface is tight. Only the cross-shell primitives (`write_atomic`, `with_file_lock`, `instance_lock`, `paths::get_*`, `reqwest_limit::*`, `text_format::*`) are `pub`; the rest is `pub(crate)` or `#[cfg(test)]`.
- Doc-completeness is strong — the modules that *could* be misread (`instance_lock`, `paths::ensure_private_dir`, `scratch::register_for_exit`, `text_format`, `process_alive`) carry multi-paragraph docs explaining the failure mode and the design choice, not just the function signature.
- `unsafe` use is bounded and commented at every site (6 sites total, each with a SAFETY line).
- Test coverage is heavy in the high-stakes modules (`paths.rs` 30+ tests, `instance_lock.rs` 9 tests, `scratch.rs` 2 functional + a source-level guard, `source_scan.rs` 20+ tests). The gap is `reqwest_limit.rs`, fixed in this round.

## Conclusion
`src/utils/` is in substantially better shape than the 2026-07-20 review (13 files, 2 516 LOC) found — the intervening rounds added cross-process lock hardening, hostname resolution, JSON extraction, scratch lifecycle, and source-level census primitives, each with its own dedicated test pass. The two remaining medium findings are narrow (one stale-kernel-PID window in a test reaper; one under-tested SSRF choke point); the two low findings are documentation/style follow-ups. The module as a whole matches every project redline.
