# Review Findings - Batch 2: src/exec Approvals & Execution Manager


## Overview
- **Scope**: `src/exec/mod.rs`, `src/exec/manager.rs`, `src/exec/approval/channel_bridge.rs`, `src/exec/approval/mod.rs`, `src/exec/approval/types.rs`, `src/exec/allowed_decisions.rs`, `src/exec/decision.rs`, `src/exec/bridge.rs`, `src/exec/socket.rs`
- **Method**: Static logic and Occam's Razor audit against contracts, concurrency semantics, state machines, allocation overhead, and architectural redlines (R1-R10).
- **Total Findings**: 16 (P1: 2, P2: 6, P3: 8)

### Finding 1: Core Approval Engine Inverted Dependency on Discord Audit Hook & Cross-Channel Audit Misattribution
- File & Line: `src/exec/manager.rs:989`
- Severity: P1
- Invariant / Rule violated:
  - Architecture Redline R1: Brain & limbs separation (Core must not call platform/interface APIs).
  - Architecture Redline R4: Interface layer prohibited from containing business logic; channels are pure I/O.
  - Architecture Redline R6: Single Core Brain, multi-interface symmetry.
  - Occam's Razor: Conceptual inversion / inappropriate intimacy. Core engine should never depend on downstream channel interface.
- Concrete Finding:
  In `ExecApprovalManager::resolve_by_id`, when an approval resolution succeeds, the core manager directly invokes:
  `crate::gateway::interfaces::discord::security::audit_hooks::record_approval_resolved(actor, session, label, &cmd).await;`
  This introduces an inverted module dependency (`src/exec/manager.rs` -> `src/gateway/interfaces/discord`) and causes severe semantic pollution in the security audit ledger: ANY approval resolved anywhere in Aleph (CLI, WebChat, Telegram, Slack, Desktop Panel, cluster node, cron) is permanently recorded in the audit log as `"discord.command.approval.resolved: {decision_label} {command_shape}"`. Non-Discord resolutions are misattributed to Discord.
- Proposed Occam Simplification:
  Move approval audit recording into `crate::security::audit` with a generic event type (e.g. `approval.resolved`), or publish a resolution event on `GatewayEventBus` so audit consumers subscribe uniformly. Remove the direct dependency on `crate::gateway::interfaces::discord` from `src/exec/manager.rs`.

### Finding 2: Clock Discrepancy & Split-Brain Liveness in Expiry Handling
- File & Line: `src/exec/manager.rs:1463-1487` vs `src/exec/manager.rs:220-226`
- Severity: P1
- Invariant / Rule violated:
  - Engineering Criteria Shape 1: Two expressions of the same fact ("同一事实的两份表述").
  - Occam's Razor: Invariant consistency across approval lifecycle and clock stability.
- Concrete Finding:
  Approval expiry is evaluated against two different clocks across the lifecycle:
  1. `ExecApprovalRecord::is_expired` (and `PendingEntry::is_live`) evaluates wall-clock time: `now_ms_or_warn() > self.expires_at_ms` using `SystemTime`.
  2. `ExecApprovalManager::cleanup_expired` evaluates monotonic time: `now.duration_since(entry.created_at) > Duration::from_millis(timeout_ms)` using `Instant::now()`.
  If the wall clock steps forward (e.g., NTP adjustments, VM resume), `is_expired()` becomes `true` while `cleanup_expired` does not trigger because monotonic elapsed time has not elapsed. The entry becomes "not live" (blocking resolution via `resolve_by_id` and `resolve_for_session` with `NotLive`), but remains trapped in `pending` without sending `None` to wake the waiting oneshot channel until monotonic time catches up.
- Proposed Occam Simplification:
  Unify the expiry predicate to a single expression. In `cleanup_expired`, retain entries based on `!entry.record.is_expired() && entry.sender.as_ref().is_some_and(|s| !s.is_closed())` (or `entry.is_live()`), ensuring identical liveness semantics across all code paths.

### Finding 3: Memory Leak in `session_listings` for Button-Resolved or Expired Approvals
- File & Line: `src/exec/manager.rs:514`, `1223-1226`, `1459-1488`
- Severity: P2
- Invariant / Rule violated:
  - Decision hierarchy: Logic bugs, unhandled error cases, cascade inconsistencies.
  - Occam's Razor: Resource lifecycle alignment and memory cleanliness.
- Concrete Finding:
  When multiple cards are pending in a session, `resolve_for_session` caches the shown listing snapshot in `session_listings: RwLock<HashMap<String, Vec<String>>>`. While line 1331 notes that leaving entries behind grows this map indefinitely, removal only occurs in `resolve_for_session`. If the user resolves the approval via an inline button callback (`resolve_for_channel`), or if the cards expire via `cleanup_expired`, or if the request is cancelled/retired via `retire_pending`, the entry in `session_listings` is never removed, causing an unbounded memory leak over time.
- Proposed Occam Simplification:
  Evict the session from `session_listings` when the last pending card for that session is resolved in `resolve_by_id`, retired in `retire_pending`, or cleaned up in `cleanup_expired`.

### Finding 4: Redundant RAII Guard Abstraction & Double Write-Lock on Drop
- File & Line: `src/exec/manager.rs:308-349`, `588-607`
- Severity: P2
- Invariant / Rule violated:
  - Occam's Razor Rule 1 & 2: Simplicity is removal of unnecessary concepts. Every abstraction must earn its existence.
  - Decision hierarchy: Accidental complexity and unnecessary indirection; lock scopes.
- Concrete Finding:
  `register_operator_once` returns both a `RegisteredApprovalReceiver` (which already encapsulates `PendingRegistration` as an RAII drop guard) and an `OperatorApprovalRegistration` guard. Both guards implement identical `Drop` cleanup logic (`pending.get(&id).is_some_and(|entry| Arc::ptr_eq(&entry.generation, &self.generation)) => pending.remove(&id)`).
  Furthermore:
  1. `RegisteredApprovalReceiver` disarms on successful completion (`this.cleanup = None`), but `OperatorApprovalRegistration` lacks a disarm mechanism. When it drops after normal completion, it unconditionally acquires the write lock on `pending` just to find the entry already removed.
  2. `OperatorApprovalRegistration::wait` only delegates to `manager.await_registered`, which already performs the exact same generation check.
  3. On early exit or cancellation, both guards drop in immediate succession, contending and taking the exclusive write lock twice.
- Proposed Occam Simplification:
  Delete `OperatorApprovalRegistration`. `RegisteredApprovalReceiver` already tracks generation, cleans up on drop, disarms on completion, and is checked by `await_registered`. Return `(String, RegisteredApprovalReceiver, Option<Duration>)` directly.

### Finding 5: Double Write Lock Acquisition in `register_pending_inner`
- File & Line: `src/exec/manager.rs:640-643`
- Severity: P2
- Invariant / Rule violated:
  - Occam's Razor: Lock scopes and critical section boundaries.
- Concrete Finding:
  In `register_pending_inner`, line 640 calls `self.cleanup_expired()`, which acquires the `pending` write lock, performs a sweep, and drops the lock. Immediately at line 643, `self.pending.write()` is acquired a second time to insert the new entry. Under concurrent registration load, this doubles lock round-trips and introduces an unnecessary interleaving window between the sweep and the insertion.
- Proposed Occam Simplification:
  Perform the expired cleanup and the insertion under a single write lock acquisition, passing `&mut pending` to a private cleanup helper.

### Finding 6: Triple Hash Map Lookups Under Exclusive Lock in `resolve_by_id` & `resolve_for_session`
- File & Line: `src/exec/manager.rs:852, 904, 917` and `1288, 1306, 1314`
- Severity: P2
- Invariant / Rule violated:
  - Occam's Razor: Redundant operations and unnecessary indirection.
- Concrete Finding:
  In `resolve_by_id`, the manager performs three sequential lookups on `self.pending` under the same lock:
  1. Line 852: `pending.get_mut(id)` to retrieve `entry` and apply resolution.
  2. Line 904: `pending.get(id)` to extract `session_key`, `grant_key`, and `originator_user_id` for cascading.
  3. Line 917: `pending.get(id)` to extract `command` and `session_key` for audit snapshot.
  Similarly, in `resolve_for_session`:
  1. Line 1288: `pending.get(&id)` to check originator.
  2. Line 1306: `pending.get_mut(&id)` to check decision acceptance and resolve.
  3. Line 1314: `pending.get(&id)` to fetch `grant_key` and `originator` for cascading.
- Proposed Occam Simplification:
  In both methods, extract all necessary fields during the first `get_mut` lookup. Eliminate 4 redundant hash map lookups.

### Finding 7: Spawning Background Task and Formatting Under `pending` Write Lock
- File & Line: `src/exec/manager.rs:955-998`
- Severity: P3
- Invariant / Rule violated:
  - Occam's Razor: Lock scopes and async boundaries. Critical sections must be as small as possible.
- Concrete Finding:
  In `resolve_by_id`, the `pending.write()` exclusive guard is held throughout lines 850-999. Lines 955-998 perform audit checks, runtime handle detection, string matching, formatting, and `tokio::spawn`. None of these operations require the `pending` map, which finished its mutations at line 954. Holding the exclusive write lock across task spawning needlessly blocks all readers (`list_pending`, `get_pending`, `record_originator`) and other resolvers.
- Proposed Occam Simplification:
  Explicitly drop `pending` (`drop(pending);`) immediately after `cascade_to_identical_cards` finishes at line 954, releasing the write lock before executing audit checks and `tokio::spawn`.

### Finding 8: Excessive Clones and Ephemeral Allocation in `build_request` -> `manager.create` Pipeline
- File & Line: `src/exec/approval/channel_bridge.rs:78-117, 198-205`, `src/exec/manager.rs:153-209`
- Severity: P2
- Invariant / Rule violated:
  - Decision hierarchy: Eliminate unnecessary allocations, clones, conversions, and owned parameters.
  - Occam's Razor: Avoid gratuitous cloning when transferring ownership.
- Concrete Finding:
  `build_request` constructs an owned `ExecApprovalRequest` containing 8 strings and 1 vector. In `request_for_tool`, this request is passed by reference to `approval_manager.create(&request, timeout_ms)`, where `ExecApprovalRecord::from_request` clones every single string and vector into `ExecApprovalRecord`. Immediately after `create` returns, the original `request` is dropped. This pattern repeats in `node_requester.rs` and `operator_requester.rs`. Additionally, `build_request` redundantly returns `(ExecApprovalRequest, String)` where the second string is an exact clone of `request.session_key`.
- Proposed Occam Simplification:
  Implement `From<ExecApprovalRequest> for ExecApprovalRecord` or `ExecApprovalRecord::from_request_owned(request: ExecApprovalRequest, timeout_ms: u64)`, moving the allocated strings and vector directly into the record with zero clones. Access `request.session_key` directly instead of returning a duplicated string from `build_request`.

### Finding 9: Inefficient Duplicate Full-String Iteration for Truncation
- File & Line: `src/exec/approval/channel_bridge.rs:448-451` and `src/exec/manager.rs:1347-1354`
- Severity: P3
- Invariant / Rule violated:
  - Decision hierarchy: Consolidate genuine duplication; accidental complexity.
- Concrete Finding:
  In `channel_bridge.rs:448-451`:
  `let mut summary: String = action.summary.chars().take(MAX_SUMMARY_CHARS).collect();`
  `if action.summary.chars().count() > MAX_SUMMARY_CHARS { summary.push('…'); }`
  And in `manager.rs:1347-1354`:
  `let mut line: String = record.command.chars().take(MAX).collect();`
  `if record.command.chars().count() > MAX { line.push('…'); }`
  Both locations iterate over the entire string twice (once for `take(MAX)` and a second full pass with `chars().count()` across potentially unbounded strings). Meanwhile, `truncate_with_marker` is already imported at `channel_bridge.rs:13` and used elsewhere.
- Proposed Occam Simplification:
  Replace both manual truncation loops with `crate::utils::text_format::truncate_with_marker(&str, MAX, "…")`, which truncates in a single pass without redundant character counting.

### Finding 10: Unconditional Allocation of `GatewayEventFrame` When Event Bus is Unconfigured
- File & Line: `src/exec/approval/channel_bridge.rs:265-277`, `306-324`, `349-364`
- Severity: P3
- Invariant / Rule violated:
  - Decision hierarchy: Eliminate unnecessary allocations.
- Concrete Finding:
  In `request_for_tool`, `announce_request`, and `close_undelivered`, `GatewayEventFrame` is constructed by cloning `approval_id`, `session_key`, `channel_id`, `conversation_id`, and `tool_call_id`, and passed to `self.publish_mirror`. `publish_mirror` immediately returns if `self.event_bus.is_none()`. When `event_bus` is `None` (the default for `ChannelApprovalBridge::new` and in tests), all these string allocations are constructed solely to be dropped.
- Proposed Occam Simplification:
  Guard event frame construction with `if self.event_bus.is_some()`, avoiding 4 heap allocations per event on unconfigured bridges.

### Finding 12: `allowed_decisions` Static Sets Allocate Unnecessary Vectors
- File & Line: `src/exec/allowed_decisions.rs:62-87`
- Severity: P3
- Invariant / Rule violated:
  - Decision hierarchy: Eliminate unnecessary allocations; references over gratuitous allocations.
- Concrete Finding:
  `once_only()`, `session_max()`, and `with_persistent()` construct and return a newly allocated `Vec<ApprovalDecisionType>` via `vec![...]` on every call. Because `ApprovalDecisionType` is a 1-byte `Copy` enum, these sets are compile-time constants. Multiple callers (e.g. in `bridge.rs` and `socket.rs`) call `&session_max()` or `&with_persistent()` solely to borrow them as `&[ApprovalDecisionType]`.
- Proposed Occam Simplification:
  Define static slice constants (`pub const ONCE_ONLY: &[ApprovalDecisionType] = ...; pub const SESSION_MAX: &[ApprovalDecisionType] = ...; pub const WITH_PERSISTENT: &[ApprovalDecisionType] = ...;`). Provide functions returning these constants or slices directly, while retaining `.to_vec()` only where an owned `Vec` is strictly required.

### Finding 16: Misleading Zombie Module `src/exec/socket.rs`
- File & Line: `src/exec/socket.rs:1-10`
- Severity: P3
- Invariant / Rule violated:
  - Occam's Razor: Accurate conceptual modeling; dead abstractions.
- Concrete Finding:
  `src/exec/socket.rs` contains no socket code. Its module doc states: "Historically this file also defined a Unix-socket UI protocol ... that transport was never wired into the server and has been removed." Its sole implementation line is `pub use aleph_slot_api::approval::ApprovalDecisionType;`. Other modules import `ApprovalDecisionType` from `crate::exec::socket`, creating a false impression of a socket dependency.
- Proposed Occam Simplification:
  Re-export `ApprovalDecisionType` from `crate::exec::decision` or `crate::exec::mod`. Keep `socket.rs` only as a thin deprecated backward-compatibility alias if external crates require it, updating all internal callers to import from `crate::exec::decision` or `crate::exec::mod`.
