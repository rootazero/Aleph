# Aleph × NSH 重构 --- ADR-001\~009

-   文档状态：实施基线（部分 Accepted，部分 Proposed）
-   项目：Aleph（通用 Rust AI Agent）
-   适用范围：Aleph Server、Desktop、NSH Runtime、Protocol、插件和动态
    UI
-   文档目的：将已确认的架构选择转化为编码 Agent 可执行的工程约束
-   重要说明：本文件规定目标架构，不代表当前仓库已具备相应
    Crate、接口或能力。实施前必须盘点现有代码并渐进迁移，不得为了匹配目录示例而大规模重写现有业务。

## 决策状态约定

-   **Accepted**：用户已明确确认，实施时必须遵循；若需改变，先提出新的
    ADR。
-   **Proposed**：推荐方向，尚未得到用户最终确认；可以进行验证和原型，但不得当作不可变约束。
-   **Superseded**：被后续 ADR 替代。
-   **Rejected**：明确不采用。

## 总体架构原则

1.  Aleph 是通用 AI Agent，不是 OSINT 专用系统。
2.  核心原则：**Everything is a
    Capability**。能力通过明确接口注册、授权、调用和撤销。
3.  Server 是 Agent 业务状态和执行状态的唯一权威来源。
4.  Desktop 是交互宿主，不拥有 Agent Task、Session、Message 的权威副本。
5.  Server 不依赖 NSH、TSX 或任何 Desktop UI 框架。
6.  所有跨进程业务交互通过版本化 Protocol，不直接引用对方内部 Rust
    类型。
7.  插件、动态 UI 和 Native Component 必须遵守明确的信任边界。
8.  先抽取协议和客户端，再迁移 UI；不同时重写 Server 和 Desktop。
9.  保持现有外部行为和数据兼容；不为追求理想目录结构而制造无收益的大规模重构。
10. 优先选择简单、可测试、低分配、符合现有异步模型的 Rust
    实现；避免无必要的 `Box<dyn Trait>`、重复 Clone、层层包装和过度拆
    Crate。

# ADR-001：Desktop UI 采用 Mixed Runtime

-   状态：**Accepted**
-   决策：Rust Native Components + TSX Screens / Modules，统一运行于 NSH
    Runtime。

## 背景

Aleph 需要兼顾高性能核心交互、快速页面迭代、插件 UI 扩展和 Agent
生成的临时界面。单纯 Rust UI 会增加页面迭代成本；全部 TSX
则可能让高频组件、复杂原生交互和宿主能力边界变得难以控制。

## 决策

采用混合 UI：

-   Rust 实现高频、复杂、需要稳定生命周期或原生宿主能力的核心组件。
-   TSX 实现页面组合、低频业务页面、插件 UI 和受限动态 UI。
-   Rust 与 TSX 使用同一 NSH Runtime，不维护两套独立渲染系统。
-   UI 技术只存在于 Desktop；Server 不得依赖 NSH、QuickJS、TSX 或 UI
    类型。

建议的 Rust
核心组件包括输入框、消息列表/虚拟列表、流式文本、Markdown/代码展示、Tool
Call 卡片、审批卡片、文件/浏览器预览等。具体组件归属以性能测试和 NSH API
验证为准，不要求预先全部 Rust 化。

## 状态所有权

  状态                                          权威所有者
  --------------------------------------------- ---------------------------------
  Session、Message、Agent Task、Tool 执行状态   Server
  Capability 授权、审批结果、插件 Core 状态     Server
  窗口尺寸、焦点、滚动位置、展开状态            Desktop
  未提交表单、临时筛选、局部动画状态            对应 UI View
  UI 缓存                                       Desktop，可丢弃并从 Server 重建

Desktop 可以维护投影和缓存，但不得把缓存升级为业务事实来源。

## 约束

1.  TSX 不得直接访问任意系统 API。
2.  Rust Native Component 必须由 Host 注册，定义
    Props、Events、允许的信任等级和所需 Host API。
3.  组件内部状态不得成为 Agent 业务状态的第二份权威副本。
4.  通过 `aleph-ui-bridge` 暴露有限、版本化的 UI Host API。
5.  NSH 的具体 API 应封装在 `aleph-desktop-nsh`，避免业务组件直接绑定
    NSH 内部类型。

## 后果

优点：核心交互可控，页面开发灵活，插件 UI 与动态 UI 可共享组件体系。

成本：必须维护 Rust/TSX 边界、组件注册、类型/Schema 同步和跨 VM
生命周期。禁止为了"统一"而让 Rust 与 TSX 各自保存一份相同业务状态。

## 验收条件

-   Rust 与 TSX 能在目标 NSH 版本中协同渲染。
-   View 销毁后监听器、VM 和资源按生命周期释放。
-   UI 重建后能从 Server 恢复业务状态。
-   中文输入、文本选择、复制粘贴、撤销、长列表和流式输出通过测试。

# ADR-002：Server 采用 Standalone 独立进程

-   状态：**Accepted**
-   决策：Aleph Server 始终作为独立进程运行；Desktop
    不提供正式的进程内嵌 Server 模式。

## 背景

Server 承担 Agent Loop、Session、Tool、Capability、Plugin、Browser
和持久化。将其嵌入 Desktop 会把业务生命周期与窗口生命周期绑定，并增加 UI
Runtime 与 Server 的耦合。

## 决策

-   `aleph-server` 是独立可执行程序。
-   Desktop 通过本地 IPC 连接 Server。
-   Server 可以独立 CLI 启动和运行，不依赖 Desktop。
-   Desktop Supervisor
    负责发现、启动（如配置允许）、健康检查、版本握手和重连。
-   Server 的生命周期由 Server 进程/系统服务管理；Agent Task 生命周期由
    Server 管理；UI View 生命周期由 NSH 管理。

## 生命周期规则

1.  关闭窗口或退出 Desktop 不得隐式取消 Task。
2.  用户明确取消任务时，Desktop 调用取消 RPC。
3.  Server
    退出前应执行可控关闭；未完成任务状态必须按既定恢复策略持久化。
4.  Desktop 重启后通过 Snapshot + Replay 恢复 UI。
5.  Server 崩溃恢复不得盲目重放 Shell、文件写入、外部 API
    等非幂等副作用。
6.  同一用户/配置目录应防止意外启动多个竞争 Server 实例。

## 进程拓扑

``` text
Aleph Desktop
  ├─ NSH Runtime
  ├─ Desktop Runtime / UI State
  ├─ Server Client
  └─ Desktop Supervisor
          │ Local IPC
          ▼
      Aleph Server
        ├─ Agent Runtime
        ├─ Session / Task
        ├─ Capability Kernel
        ├─ Tool Runtime
        ├─ Plugin Host
        ├─ Event / Persistence
        └─ Browser Supervisor
```

## 安全要求

-   macOS/Linux：优先 Unix Domain Socket，Socket 放在用户专属运行目录。
-   Windows：使用 Named Pipe，并配置 DACL / 用户 SID 校验。
-   不把"监听 localhost"视为充分认证。
-   IPC 连接必须绑定当前 OS 用户，并进行连接级认证/握手。
-   凭据不得写入普通日志。
-   Server 应限制单用户实例并安全处理陈旧 Socket/锁文件。

## 后果

优点：Server 可独立运行、支持多客户端、UI 可替换、故障域清晰。

成本：需要 IPC、Supervisor、版本协商、重连、事件恢复和安装升级管理。

## 验收条件

-   Desktop 退出时运行中的 Task 不被自动取消。
-   Server 可独立启动和接受受认证客户端。
-   Desktop 可检测 Server 不可用、版本不兼容和异常退出。
-   重连恢复不丢失已持久化业务状态，也不重复执行非幂等副作用。

# ADR-003：插件 UI 采用 Hybrid

-   状态：**Accepted**
-   决策：插件由 Server-side Core 与 Desktop-side UI Module
    组成；两者通过受控协议和 UI Bridge 协作。

## 决策

插件逻辑上包含：

``` text
Plugin
├── Manifest
├── Core
│   ├── Capabilities / Services
│   ├── Event Handlers
│   ├── Tool Contributions
│   └── Lifecycle
├── UI
│   ├── UI Manifest
│   ├── TSX Modules
│   └── View Definitions
└── Permissions
```

-   Core 在 Server 侧运行，拥有经授权的能力。
-   UI 在 Desktop 的 NSH Runtime 中运行。
-   UI 不得直接调用 Server 内部实现。
-   UI 通过 `aleph-ui-bridge` 和 `aleph-client` 发起请求。
-   Server 对每次有副作用的操作独立执行授权检查。
-   UI Manifest 的 capability 声明只是需求声明，不构成授权。

## 插件 Core 与 UI 的关联

-   使用稳定 `plugin_id`、插件版本和 UI/Core API 版本关联。
-   UI 必须验证其所依赖的 Core 版本/API。
-   Core 缺失、禁用或版本不兼容时，UI 不得假装操作成功。
-   UI 可在 Core 不可用时展示明确的只读/不可用状态。

## 后果

优点：插件逻辑和界面可独立演进；Server 权限模型不依赖 UI。

成本：需要插件身份、版本兼容、跨进程 UI/Core 绑定和卸载协调。

## 验收条件

-   插件 UI 不能绕过 Server Capability Kernel。
-   Core 不可用时 UI 正确降级。
-   插件卸载时 Core 与 UI 资源均可释放。
-   UI/Core 版本不兼容时拒绝加载或进入明确兼容模式。

# ADR-004：第三方 Rust 插件采用 WASM / 独立进程

-   状态：**Accepted**
-   决策：第三方 Rust 插件不以任意 Rust 动态库形式加载进 Aleph
    Server。支持 WASM 沙箱或独立进程两种隔离运行方式。

## 术语澄清

`wasm_process` 是策略名称，表示"WASM 或
Process"两种可选运行模式，不表示每个插件必须同时运行在 WASM
与独立进程中。

## 插件类型

  类型              运行方式                策略
  ----------------- ----------------------- --------------------
  官方内置能力      静态编译                允许
  第三方 WASM       受限 WASM Runtime       默认优先
  第三方 Process    独立进程 + 受控 IPC     按需求允许
  任意 Rust dylib   Server 进程内动态加载   不作为通用插件机制

## WASM 插件约束

-   只能通过 Host API 访问文件、网络、Browser、Tool 等资源。
-   默认无宿主文件系统和网络访问。
-   通过 Capability Grant 授予精确资源范围。
-   设置内存、执行燃料/时间、并发和句柄限制。
-   Runtime 崩溃或插件 Trap 不得导致 Server 崩溃。
-   WASM Runtime 选型（例如 Wasmtime、WASI/Component Model
    版本）另行验证，不在本 ADR 锁定。

## Process 插件约束

-   独立进程、独立工作目录和受控环境变量。
-   使用受认证 IPC。
-   配置 CPU、内存、进程数、消息大小和超时限制。
-   仅通过 Plugin Host API 请求能力。
-   崩溃重启必须有退避和熔断，不能无限重启。
-   不能因为是独立进程就默认拥有任意用户文件权限。

## API 稳定性

`aleph-plugin-api` 是对外稳定边界；不得暴露 Server 内部 Crate 类型。插件
API 应版本化、可协商，并提供兼容性测试。

## 验收条件

-   插件故障与 Server 故障隔离。
-   未授权资源访问被拒绝。
-   超限插件可被终止且不拖垮 Host。
-   插件升级、禁用、卸载和崩溃恢复可观测、可审计。

# ADR-005：Agent 动态 UI 采用 Restricted TSX

-   状态：**Accepted**
-   决策：允许 Agent 生成受限 TSX UI，但仅在隔离 View Container 和受限
    Runtime 中运行。

## 允许范围

-   在指定容器内创建/更新/销毁 View。
-   使用白名单 Native Components 和受限 TSX 组件。
-   通过有限 UI Bridge 请求数据、提交表单和发起操作。
-   显示任务上下文、结构化结果和交互控件。

## 禁止范围

-   任意 Shell、进程、文件系统和网络访问。
-   任意 Rust Native Component 注册。
-   任意全局窗口创建或 Desktop 全局布局修改。
-   直接访问其他 View 的私有状态。
-   直接授予自身 Capability。
-   修改 Server Policy、审批状态或插件信任等级。
-   通过动态 UI 注入任意 Prompt、Tool Schema 或 Server Event Handler。

## 信任等级

1.  **Trusted UI**：经过信任验证的正式插件 UI；仍受 Host API 权限约束。
2.  **Generated UI**：Agent 生成的临时 UI；最小组件集、最小
    API、严格资源限制。
3.  **Untrusted UI**：来源或完整性无法验证；禁止执行。

## 运行与销毁

每个动态 View 应绑定明确的 owner（Task/Session/Plugin）、生命周期
Scope、资源配额和到期策略。销毁时清理 VM、监听器、定时任务（如 Runtime
支持）、订阅、RPC 和临时资源。

## 安全边界

NSH 的 TSX 沙箱不自动使宿主注册的 Rust Native Components 安全。每个
Native Component 必须自行验证输入、信任等级、权限和资源上限。审批 UI
只能表达用户意图；Server 必须对绑定到具体操作的审批凭据重新验证。

## 验收条件

-   Generated UI 无法访问白名单以外的组件/API。
-   资源耗尽时 View 可被终止。
-   View 销毁后无残留监听器、订阅和后台任务。
-   恶意 TSX 不能通过 Native Component 绕过权限。
-   动态 UI 无权自行批准操作。

# ADR-006：WASM Runtime 选型与适配层

-   状态：**Proposed**
-   建议：先抽象最小 Plugin Runtime Host API，再基于真实插件需求评估
    Wasmtime 与 WASI / Component Model 能力；不提前锁定具体 Runtime。

## 需要验证

-   目标 WASI / Component Model 版本。
-   Rust 插件 SDK 生成和调用体验。
-   Async、网络、文件、时钟和随机数支持。
-   内存、燃料、执行时间和并发限制。
-   启动延迟、吞吐和内存开销。
-   macOS、Windows、Linux 构建与分发。
-   Runtime 升级和组件兼容策略。
-   安全更新、漏洞响应和供应链维护成本。

## 设计约束

-   Server 业务层依赖 `PluginRuntime` 抽象，不依赖具体 Runtime 类型。
-   Host API 必须经过 Capability Kernel。
-   只抽象实际需要的接口，避免为"未来可能的 Runtime"构建过度通用框架。
-   若 Process 插件已经足以满足早期扩展需求，可延后 WASM Runtime 落地。

## 退出条件

只有完成 PoC、威胁模型、跨平台构建和性能评估后，才把具体 Runtime
写入新的 Accepted ADR。

# ADR-007：事件持久化与 Snapshot / Replay

-   状态：**Proposed**
-   建议：优先复用 Aleph 现有持久化技术，新增稳定 Event Log
    接口；不要在没有现状盘点前引入新的数据库或消息中间件。

## 目标语义

-   Session 内事件序号单调递增。
-   Snapshot 携带其覆盖的 `sequence`。
-   Replay 仅发送 Snapshot 之后的事件。
-   Snapshot 与订阅游标建立必须具有一致性边界，避免丢事件。
-   历史已清理时返回 `resync_required`。
-   客户端允许重复投递并按事件 ID/序号去重。
-   关键状态事件必须持久化或可可靠重建。
-   高频 delta 可合并、限流或作为非持久化事件，但必须明确其语义。

## 事件分类建议

-   Durable：Task 创建/终态、审批决策、Tool
    调用生命周期、Session/Message 持久化变更等。
-   Ephemeral：可重建的 UI hint、临时心跳、可合并 token delta 等。

具体分类必须按当前 Agent
执行语义确认，不能把所有事件一律持久化，也不能把关键状态事件当作可丢弃通知。

## 恢复安全

Replay 只恢复状态和观察记录，不自动重新执行外部副作用。Task
恢复需依据持久化执行阶段和副作用记录决定继续、核实、等待用户或失败。

## 验收条件

-   Snapshot 与 Replay 之间无事件缺口。
-   断线重连可确定性恢复。
-   清理历史后客户端收到明确 resync 信号。
-   重复事件不会造成 UI 重复状态变更。
-   恢复流程不会盲目重放非幂等操作。

# ADR-008：插件信任、签名与撤销

-   状态：**Proposed**
-   建议：区分包完整性、发布者身份、用户信任和运行时授权；签名不等于权限。

## 信任模型

-   官方插件：由 Aleph 官方信任根签名。
-   组织插件：由组织配置的信任根签名。
-   用户本地插件：用户显式确认后安装，仍受 Capability Policy 限制。
-   未知/无效签名插件：默认拒绝或进入明确的隔离导入流程，不得静默提升权限。

## 必须区分

1.  **Integrity**：包内容是否被篡改。
2.  **Publisher Identity**：签名者是谁。
3.  **Trust Decision**：当前安装环境是否信任该签名者。
4.  **Authorization**：插件实际可使用哪些 Capability。
5.  **Revocation**：签名密钥或插件版本是否已撤销。

## 建议机制

-   对 Manifest、Core Artifact、UI Artifact
    和资源清单建立可验证的内容摘要。
-   签名覆盖不可变的包清单和全部载荷摘要。
-   信任根和撤销列表独立管理。
-   权限按插件、用户、资源范围和操作类型授予。
-   升级时重新验证签名和权限变化。
-   权限新增不得静默继承；需要重新审批。
-   保留安装来源、版本、签名者、授权变更和撤销审计记录。

## 验收条件

-   修改包内容会导致完整性验证失败。
-   有效签名但未授权的插件仍不能执行未授权操作。
-   撤销后阻止新加载，并按策略处理已运行实例。
-   升级新增权限必须显式确认。

------------------------------------------------------------------------

# ADR-009：动态 UI 包分发、缓存与回滚

-   状态：**Proposed**
-   建议：动态 UI 作为不可变、可校验、可版本化的 Artifact
    分发；运行时加载前完成完整性和兼容性检查。

## 包元数据建议

-   `package_id`
-   `package_version`
-   `ui_api_version`
-   `minimum_host_version`
-   `entry`
-   `content_digest`
-   `signature`
-   `component_requirements`
-   `capability_requirements`
-   `resource_limits`

## 加载策略

1.  获取 Artifact。
2.  校验来源、签名和内容摘要。
3.  校验 Host / UI API 版本。
4.  校验组件与 Capability 需求。
5.  检查资源限制。
6.  在受限 View Container 创建 VM。
7.  记录 Artifact 与 View 的关联。
8.  运行期间监控错误和资源使用。
9.  关闭时销毁 VM 并释放引用。

## 缓存与回滚

-   Artifact 按内容摘要寻址，禁止原地覆盖已加载版本。
-   缓存可清理、可重建。
-   回滚切换到已验证的旧 Artifact，不修改其内容。
-   失败版本应记录原因并避免无限自动重试。
-   UI 包回滚不应自动回滚 Server 数据或插件 Core，除非另有兼容迁移策略。

## 验收条件

-   包损坏或版本不兼容时拒绝加载。
-   加载失败不影响 Desktop 主界面。
-   可回滚到上一个已验证版本。
-   Artifact 缓存清理后可从可信来源恢复。

# 编码 Agent 执行规则

1.  开始前先检查仓库结构、现有 Cargo Workspace、MSRV、edition、异步
    Runtime、持久化和现有 Tauri IPC。
2.  先提交现状盘点和迁移映射，不要直接创建大量空 Crate。
3.  以小步提交实施；每个阶段保持可编译、可测试。
4.  不得同时重写 Server 业务逻辑和 Desktop UI。
5.  不得为了匹配本文目录而无收益搬迁模块。
6.  不得假定 NSH v0.4.0 拥有当前文档中的全部 API；必须对照固定 tag
    的源码和示例验证。
7.  对尚未 Accepted 的
    ADR-006\~009，先做验证和提案；未经确认不得把建议固化为不可逆架构。
8.  不引入未被任务需要的数据库、消息队列、插件 Runtime 或抽象层。
9.  不使用虚构的 API、Cargo feature 或 NSH
    类型；所有依赖和接口必须在锁定版本中核实。
10. 每个任务报告：改动、设计理由、测试命令与结果、未完成事项、风险和兼容性影响。
11. 保持既有外部行为；若必须改变，明确记录迁移方式。
12. 主 Agent 负责规划、边界和验收；适合的子任务可并行委派，但必须由主
    Agent 集成验证。

## 建议实施顺序

1.  NSH v0.4.0 Compatibility Spike（ADR-001 相关）。
2.  现有 Server / Tauri Interface Inventory。
3.  Protocol v1 DTO 与 Frame Codec。
4.  Server Transport + Client。
5.  Snapshot / Replay 与幂等。
6.  Desktop Supervisor。
7.  NSH Host Adapter 与 Native Component Registry。
8.  核心 UI 迁移。
9.  插件 Runtime 与 UI Bridge。
10. Restricted Generated UI。
11. 跨平台发布、升级、回滚。
12. 移除 Tauri。

-   已接受决策的变更必须新增 ADR 或更新对应 ADR 并说明迁移影响。
-   Protocol 的线协议变更必须同步更新
