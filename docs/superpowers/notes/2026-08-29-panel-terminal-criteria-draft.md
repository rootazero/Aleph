## A. 验证纪律（→ 附录 C 候选）

### A.1 一条「调用发生了」的守卫，可能在你写它之前就已经被满足了

**新判据。** 为一条断线写守卫时，自然的第一版是断言「那个调用发生过」。但本轮实测发现：
`build_router()` 已经被三个**互不相干的 webhook 测试**调用，所以
`attach_event_bus → start_flush_loop` **在每一次测试运行里本来就执行了**，零断言。

于是「它被调用了吗」这条守卫**是恒真的，而且是出厂即恒真**——不是写坏了，是它要问的那件事
在这个测试二进制里本来就永远成立。只有断言**效果到达了订阅者**的测试，才可能在线被剪断时变红。

**判据**：写一条断线守卫之前，先问**这条线在测试运行里是不是已经被别的东西驱动了**。
是的话，「调用发生」这个谓词已经死了，守卫必须落在**效果**上。

### A.2 「会不稳」的反对意见通常混同了两种形状，而仓里往往已经裁定过用哪一种

**已有判据的新侧面。** 实施者拒绝写端到端测试，理由是「时序相关会不稳」。那个理由混同了：

- **睡固定时长再断言** —— 真的不稳；
- **最多等待 N 秒直到条件成立** —— 不是。

而本仓在**同一个文件、往上三个测试**的位置已经裁定过：
`session.rs::a_child_write_reaches_the_server_held_screen` 轮询 100×50 ms 而不是固定 sleep。
16 ms 的节拍对 2 秒的界是 **125 倍余量**。

**判据**：听到「这类测试会不稳」时，**先把两种形状分开**，再去看被测代码旁边有没有先例——
先例通常就在同一个文件里。

### A.3 一棵被故意弄坏的树，一旦活得比弄坏它的那个 agent 更久，就不再是实验

**新判据。** 证伪一条守卫要求临时破坏被守护的那一行。这是对的做法。但那个窗口本身就是全部风险：

- 并发的另一个 agent 会看到一次**它无法解释的红**，并去追一个鬼；
- 若破坏它的 agent 在窗口内静默/结束，下一个读到这棵树的人会把那个缺失**当成 bug 修掉**，
  或者绕着它提交——**一次实验就此变成一个没人记得自己引入的缺陷**。

**做法三条**：① 窗口内**一口气做完**（破坏 → 跑 → 恢复 → 跑），不要中途去做别的；
② **并行的每个 agent 都要被告知**会红的**那一个测试名**与症状——并且要写明这条通知**只覆盖那一个**，
不是一张忽略红色的通行证；③ **把窗口连同逐字的恢复代码写进账本**，理由是你可能在窗口开着的时候
被压缩掉。

## B. 多 agent 共享工作树（→ 附录 C 候选）

### B.1 `git add <path>` 暂存的是文件当前内容，不是你的那些编辑

**新判据，本轮真实险情。** 逐文件 `git add` 的纪律**必要但不充分**：它防得住扫进无关目录，
对**两个 agent 在同一个文件里**毫无作用。本轮一次提交落得干净（+8 行）**只是因为**它暂存的那一刻，
另一个 agent 的编辑还没落盘。**那是时机，不是隔离。**

**规则**：① 点名 agent **可以暂存的具体文件**，不是目录；② 两个 agent 共享一个目录时，
后来那个的许可集是**逐路径白名单**，碰到不属于自己的文件必须**停下来上报**；
③ 每次提交前读 `git diff --cached --stat`，纠正用 `git restore --staged <path>`——
**绝不用**裸 `git restore` / `git checkout --`，那会摧毁另一个 agent 在磁盘上的工作。

### B.2 共享工作树里，任何整文件写入都不能用作测试手法

**B.1 的孪生，成因不同。** 为做 RED 而用 git blob **整文件重建**，短暂覆盖了另一条流程的未提交工作
（本轮真实发生，有备份、已恢复、零损失，且是 agent **主动披露**的）。

两次事故同根：**一个以「文件」为单位的操作，用在一棵以「hunk」为所有权单位的树上。**

**规则**：RED 必须由**对被测那一行所能做的最小可逆编辑**产生——精确匹配注释掉、跑、还原。
不许 `git show <blob> > file`、不许凭记忆重写、不许 `git restore`。

⚠️ 两次都**只因为 agent 自己说了出来**才被发现。**任何审查都看不见它们**——每个任务的审查者
只读自己那一段范围。

## C. 计划与编排（→ 附录 D 候选）

### C.1 前置冲突扫描对「中途被改掉的不变量」结构性失明

**新判据。** 派 Task 1 之前的冲突扫描比对的是**任务文本 vs 任务文本**。而一个任务在**实施过程中**
对某个共享不变量做出的（正确的）修正，不存在于任何任务的文本里——于是那些「按旧不变量判定为兼容」
的其余任务**不会被重新核对**。

本轮实例：Task 6 把 `Grid::new` 的 dirty 种子改成空集（孤立地看完全正确），从而让 Task 5 的
备用屏切换在**两个方向上同时**静默失效——进 alt 时 `take_patch()` 报告"什么都没变"而整屏刚被换掉，
出 alt 时恢复的是陈旧脏集。零报错、零红测。

**规则**：**当一个任务改动的是共享不变量（而不只是新增代码）时，派出下一个任务之前，
拿新不变量重扫剩余任务。** 成本是每次偏离跑一次 grep。

### C.2 一个被写成二选一的「未知」，本身就是一个关于「这问题有几个答案」的断言

**已有判据（"先数一遍选项有几个"）的新形态。** brief 写「先查 X 存不存在——存在就用，不存在就降级到 Y」。
本轮两次：两个分支都不该走，代码库里有**第三个**答案，而且是它自己已经在用的那个。

**规则**：读到一个二选一的未知时，**先问代码库对这个问题已经有几个答案**，再决定走哪一支。

### C.3 发给一个「已经提交」的 agent 的指令，会产出无处安放的工作

**新判据，本轮咬了两次。** 第一次是过期的审查区间（我在一个 agent 提交后又给它派活，
于是它的新提交落在审查范围之外）；第二次是一个测试被写出来却**没有提交可以放它**，
在工作树里搁浅，后来被误判了作者。

**规则**：要么在提交前发，要么**明说「作为后续提交落地」**。同族提问：**派下一个任务之前，
确认上一个 agent 手上没有我给的未完成指令**——一条发给"已完成" agent 的补充要求，会让它重新变成未完成。

## D. 承诺与闸（→ 附录 D 候选）

### D.1 一句「无需重启」的声明，必须由它覆盖的每一个字段兑现

**已有判据（"一句关于运行时的承诺必须由每一条到达它的路径执行"）的字段维度。**

`LIVE_SECTIONS` 自己的 doc 已经警告过：把父 section 声明成 live，会为那些没有 live-apply 接线的
字段一并广告「无需重启」。本轮发现同一个失效可以**往下挪一层**——把一个三字段的 **subsection**
声明成 live，而附带的论证只覆盖其中一个字段。

最贵的那种是**字段本身是死的**：加了配置键，而消费它的仍是一个 `const` ⇒ **patch 了什么都不会发生**，
而那张表还在广告它是 live 的。

**规则**：先问**这句话是谁执行的**，再问**是不是每条路径、每个字段都会执行它**——第二问才是这类缺陷的家。

### D.2 问的不是「这件事被闸住了吗」，而是「闸住它的那条规则，是不是一个档位就能放松的」

**已有判据（§5.12）的反向入口。** 一条闸规则可以存在、可以举卡、可以有测试，而在最高档位下**不响**。

本仓的 `is_floor()` 只对两个变体为真，而 "floor" 同时意味着两件事：
① 这条规则举的卡**不许提供持久授权**；② 它是 rung 0，**一条显式配置条目掀不翻它**，即**每个档位都问**。

选错变体的后果因此有两个：**最高档位下卡不响**（而跑在最高档位的人正是最可能一句话就打开危险能力的那个），
以及**卡上出现「始终允许」，点一次就永久授权**。

**规则**：给一个动作接闸时，除了「接了吗」，还要问**它接的是哪一档的闸**。

### D.3 一个被手机端「导航」挡住的模式，并没有被手机端「路由」挡住

**新判据。** 模式清单（`ModeSidebar` / `NavMenu`，`not_phone` 门控）和视图路由（`MainContent`，
**没有**门控）是**两道不同的闸**。一条分享链接穿过的正是缺席的那一道，用户拿到**一块空白**——
读起来像「这个页面坏了」，而不像「这个页面只支持桌面」。

**规则**：把一个界面入口按平台藏起来时，去数**到达那个视图有几条路**，而不是数**有几个按钮指向它**。

## E. 数字与归属（→ 附录 C 候选）

### E.1 一个计数约束的是它测量的那件事，对别的事沉默

**新判据，本轮我自己犯的。** 我用一个测试计数去证明**某个测试是谁写的**：
「Task 6 测得 39，Task 5 报 40 passed / 1 failed，所以 39 + 2 = 41，两个多出来的都是它的。」

**41 同样符合**「树里本来就躺着一个未提交的测试，它加了一个」。
**计数约束的是跑了多少个测试，它对谁写的完全沉默。**

被质疑之后回去核：Task 6 的报告从没提过加那个测试，Task 5 的报告在两处都把它描述成既有的。
最可能的作者是 Task 6，而**起因是我自己在它提交之后发的一条指令**（见 C.3）。

**规则**：拿一个测量当证据之前，说出**它测的是哪个谓词**，再问**我要回答的是不是同一个问题**。

### E.2 一份普查的可靠度，等于那个没人复核的转录步骤的可靠度

**新判据。** 本轮我用 `rg -n 'pty\.output'` 建了一份「这个名字出现在哪些地方」的普查，
交给实施者时报了 **8 处散文**——审查者发现真数是 **9**。

而 `rg` **每一处都找得到**：少掉的那一个是**我转录时丢的**，不是工具丢的。

**规则**：一份由「跑命令 → 人工誊写」两步产出的清单，第二步没有任何东西在校验。
要么让消费者**自己重跑那条命令**（把命令交给他，而不是把结果交给他），要么明说这份誊写没被复核过。

## F. 服务端持有状态（→ 附录 D 候选）

### F.1 一个「服务端持有状态」的架构，全部收益都压在客户端**重新找回**那个状态的那一步上

**新判据，本轮 controller 派单前查实。** 计划把 VT 屏幕搬到服务端（`Screen`/`Grid` 在 Rust core，
客户端只收行级 diff），并为多客户端共享建了 smallest-wins 视口表。这两件事**唯一**可被用户观测到的
方式是**刷新页面之后屏幕还在**，以及**第二个标签页看到同一块屏**。

而挂载路径写的是无条件 `pty.spawn`。于是刷新拿到一个新 shell 的新提示符，第二个标签页拿到第二个
shell——**服务端那半完整、正确、有测试，收益是零**，而两边各自的测试都是绿的：服务端测的是
「屏幕状态对不对」，客户端测的是「帧应用得对不对」，**没有任何一条测试问「刷新之后我还是不是同一个我」**。

同一份任务文本里，Step 4 的两条验收断言的正好是相反的行为（「刷新页面 → 屏幕内容原样恢复」
「第二个标签页 → 两个标签页看到同一块屏」）——**验收清单知道正确答案，实现代码不知道，而两者
写在同一个文件里相距 60 行**。

顺带一个不响的代价：旧会话不会被关闭（断线只释放视口约束，不 `pty.close`），所以每刷新一次泄漏
一个 shell，直到 `MAX_SESSIONS` 的 FIFO 把最老的踢掉。

**规则**：给一个「状态住在服务端」的能力接客户端时，先问**客户端启动时是「找回」还是「新建」**。
答案是新建，那个架构就没有交付；而这一问**不在任何一半的测试范围内**，它只在两半之间。

### F.2 serde 默认忽略未知键，所以一个多发的字段会在 wire 上留下一个看起来在起作用的设计

**已有判据（「同一事实的两份表述」）的 wire 形态。** Task 10 用一段 doc comment 明确否决了
「视口表按调用方自己挑的 `client_id` 键控」，改从 task-local 取真实连接身份。而客户端那半的草稿
仍然发 `client_id`——`ResizeParams` 没有那个字段、也没有 `deny_unknown_fields`，**于是它既不报错
也不生效**，只是在 wire 上把被否决的那个设计重新讲了一遍，等着下一个读 wire 的人把它当成事实。

**规则**：一个字段被服务端**有意**拿掉之后，去 grep 客户端还发不发它——`INVALID_PARAMS` 会告诉你，
而默认的 serde 不会。

### F.3 一条跨越了两个解析根的线，三段都有代码、都有测试，而整条线一格都不通

**新判据，本轮最贵的一次派单前查实。** 计划里的 `[gateway.terminal]` 开关，从配置类型到热应用
到审批闸，三个任务、三段实现，**没有一段是错的**——错的是它们之间那条线跨过了一个边界。

`Config`（`src/config/structs.rs`）**没有 `gateway` 字段，而且是有意的**。`src/config/dead_keys.rs`
里逐字记着这件事：`[gateway]` 由 `src/gateway/config.rs::GatewayConfig` **第二个解析根**读同一个
文件。于是：

- `apply_live_sections(cfg: &Config, ..)` 读不到 `cfg.gateway.*`；
- `LIVE_SUBSECTIONS` 命名的是 `Config` 内的子树；
- `patcher.rs` 把 `Config` 序列化成 JSON、打补丁、反序列化回 `Config` ⇒ 一个 `gateway.*` 补丁被
  **静默丢弃并报成功**。

第三条是关键：热开关的整个故事、以及为它加的那道审批闸，**守的是一条写不进去的路径**。

**为什么读任何一段都发现不了**：每一段单独看都正确且完整——配置类型解析得出来、live 表接得上
census、闸的链上位置也对。缺陷只存在于「这三段说的是同一个 `Config` 吗」这一问里，而**没有任何
一段代码提出这一问**。

**规则**：给一个配置项接运行时机件之前，先问**这个 section 属于哪一个解析根**，再逐个消费者问
**它拿到的是不是那个根**。仓库里有第二个根这件事本身是有记录的、正当的；不正当的是假设只有一个。

⚠️ 顺带一条正向的：**换位置时先问新位置是不是「可用」还是「正确」**。`policies` 不是退路——
`PoliciesConfig` 已经装着 `exec_tier` / `mode` / `spend` / `tool_permissions` / `guardian`，
它就是回答「什么被允许」的那个 section；而 `GATE_DECIDING_CONFIG_PATHS` 现有两项**都在
`policies.` 下**，新条目落在同类旁边，不再需要为「它凭什么和那两个并列」另找说辞。
一个需要额外解释才站得住的位置，通常就是错的位置。
