## A. 验证纪律（→ 附录 C 候选）

### A.1 一条「调用发生了」的守卫，可能在你写它之前就已经被满足了

**新判据。** 为一条断线写守卫时，自然的第一版是断言「那个调用发生过」。但本轮实测发现：
`build_router()` 已经被三个**互不相干的 webhook 测试**调用，所以
`attach_event_bus → start_flush_loop` **在每一次测试运行里本来就执行了**，零断言。

于是「它被调用了吗」这条守卫**是恒真的，而且是出厂即恒真**——不是写坏了，是它要问的那件事
在这个测试二进制里本来就永远成立。只有断言**效果到达了订阅者**的测试，才可能在线被剪断时变红。

**判据**：写一条断线守卫之前，先问**这条线在测试运行里是不是已经被别的东西驱动了**。
是的话，「调用发生」这个谓词已经死了，守卫必须落在**效果**上。

### A.2 「会不稳」的反对意见通常混同了两种形状，而仓里往往已经裁定过用哪一种

**已有判据的新侧面。** 实施者拒绝写端到端测试，理由是「时序相关会不稳」。那个理由混同了：

- **睡固定时长再断言** —— 真的不稳；
- **最多等待 N 秒直到条件成立** —— 不是。

而本仓在**同一个文件、往上三个测试**的位置已经裁定过：
`session.rs::a_child_write_reaches_the_server_held_screen` 轮询 100×50 ms 而不是固定 sleep。
16 ms 的节拍对 2 秒的界是 **125 倍余量**。

**判据**：听到「这类测试会不稳」时，**先把两种形状分开**，再去看被测代码旁边有没有先例——
先例通常就在同一个文件里。

### A.3 一棵被故意弄坏的树，一旦活得比弄坏它的那个 agent 更久，就不再是实验

**新判据。** 证伪一条守卫要求临时破坏被守护的那一行。这是对的做法。但那个窗口本身就是全部风险：

- 并发的另一个 agent 会看到一次**它无法解释的红**，并去追一个鬼；
- 若破坏它的 agent 在窗口内静默/结束，下一个读到这棵树的人会把那个缺失**当成 bug 修掉**，
  或者绕着它提交——**一次实验就此变成一个没人记得自己引入的缺陷**。

**做法三条**：① 窗口内**一口气做完**（破坏 → 跑 → 恢复 → 跑），不要中途去做别的；
② **并行的每个 agent 都要被告知**会红的**那一个测试名**与症状——并且要写明这条通知**只覆盖那一个**，
不是一张忽略红色的通行证；③ **把窗口连同逐字的恢复代码写进账本**，理由是你可能在窗口开着的时候
被压缩掉。

## B. 多 agent 共享工作树（→ 附录 C 候选）

### B.1 `git add <path>` 暂存的是文件当前内容，不是你的那些编辑

**新判据，本轮真实险情。** 逐文件 `git add` 的纪律**必要但不充分**：它防得住扫进无关目录，
对**两个 agent 在同一个文件里**毫无作用。本轮一次提交落得干净（+8 行）**只是因为**它暂存的那一刻，
另一个 agent 的编辑还没落盘。**那是时机，不是隔离。**

**规则**：① 点名 agent **可以暂存的具体文件**，不是目录；② 两个 agent 共享一个目录时，
后来那个的许可集是**逐路径白名单**，碰到不属于自己的文件必须**停下来上报**；
③ 每次提交前读 `git diff --cached --stat`，纠正用 `git restore --staged <path>`——
**绝不用**裸 `git restore` / `git checkout --`，那会摧毁另一个 agent 在磁盘上的工作。

### B.2 共享工作树里，任何整文件写入都不能用作测试手法

**B.1 的孪生，成因不同。** 为做 RED 而用 git blob **整文件重建**，短暂覆盖了另一条流程的未提交工作
（本轮真实发生，有备份、已恢复、零损失，且是 agent **主动披露**的）。

两次事故同根：**一个以「文件」为单位的操作，用在一棵以「hunk」为所有权单位的树上。**

**规则**：RED 必须由**对被测那一行所能做的最小可逆编辑**产生——精确匹配注释掉、跑、还原。
不许 `git show <blob> > file`、不许凭记忆重写、不许 `git restore`。

⚠️ 两次都**只因为 agent 自己说了出来**才被发现。**任何审查都看不见它们**——每个任务的审查者
只读自己那一段范围。

## C. 计划与编排（→ 附录 D 候选）

### C.1 前置冲突扫描对「中途被改掉的不变量」结构性失明

**新判据。** 派 Task 1 之前的冲突扫描比对的是**任务文本 vs 任务文本**。而一个任务在**实施过程中**
对某个共享不变量做出的（正确的）修正，不存在于任何任务的文本里——于是那些「按旧不变量判定为兼容」
的其余任务**不会被重新核对**。

本轮实例：Task 6 把 `Grid::new` 的 dirty 种子改成空集（孤立地看完全正确），从而让 Task 5 的
备用屏切换在**两个方向上同时**静默失效——进 alt 时 `take_patch()` 报告"什么都没变"而整屏刚被换掉，
出 alt 时恢复的是陈旧脏集。零报错、零红测。

**规则**：**当一个任务改动的是共享不变量（而不只是新增代码）时，派出下一个任务之前，
拿新不变量重扫剩余任务。** 成本是每次偏离跑一次 grep。

### C.2 一个被写成二选一的「未知」，本身就是一个关于「这问题有几个答案」的断言

**已有判据（"先数一遍选项有几个"）的新形态。** brief 写「先查 X 存不存在——存在就用，不存在就降级到 Y」。
本轮两次：两个分支都不该走，代码库里有**第三个**答案，而且是它自己已经在用的那个。

**规则**：读到一个二选一的未知时，**先问代码库对这个问题已经有几个答案**，再决定走哪一支。

### C.3 发给一个「已经提交」的 agent 的指令，会产出无处安放的工作

**新判据，本轮咬了两次。** 第一次是过期的审查区间（我在一个 agent 提交后又给它派活，
于是它的新提交落在审查范围之外）；第二次是一个测试被写出来却**没有提交可以放它**，
在工作树里搁浅，后来被误判了作者。

**规则**：要么在提交前发，要么**明说「作为后续提交落地」**。同族提问：**派下一个任务之前，
确认上一个 agent 手上没有我给的未完成指令**——一条发给"已完成" agent 的补充要求，会让它重新变成未完成。

## D. 承诺与闸（→ 附录 D 候选）

### D.1 一句「无需重启」的声明，必须由它覆盖的每一个字段兑现

**已有判据（"一句关于运行时的承诺必须由每一条到达它的路径执行"）的字段维度。**

`LIVE_SECTIONS` 自己的 doc 已经警告过：把父 section 声明成 live，会为那些没有 live-apply 接线的
字段一并广告「无需重启」。本轮发现同一个失效可以**往下挪一层**——把一个三字段的 **subsection**
声明成 live，而附带的论证只覆盖其中一个字段。

最贵的那种是**字段本身是死的**：加了配置键，而消费它的仍是一个 `const` ⇒ **patch 了什么都不会发生**，
而那张表还在广告它是 live 的。

**规则**：先问**这句话是谁执行的**，再问**是不是每条路径、每个字段都会执行它**——第二问才是这类缺陷的家。

### D.2 问的不是「这件事被闸住了吗」，而是「闸住它的那条规则，是不是一个档位就能放松的」

**已有判据（§5.12）的反向入口。** 一条闸规则可以存在、可以举卡、可以有测试，而在最高档位下**不响**。

本仓的 `is_floor()` 只对两个变体为真，而 "floor" 同时意味着两件事：
① 这条规则举的卡**不许提供持久授权**；② 它是 rung 0，**一条显式配置条目掀不翻它**，即**每个档位都问**。

选错变体的后果因此有两个：**最高档位下卡不响**（而跑在最高档位的人正是最可能一句话就打开危险能力的那个），
以及**卡上出现「始终允许」，点一次就永久授权**。

**规则**：给一个动作接闸时，除了「接了吗」，还要问**它接的是哪一档的闸**。

### D.3 一个被手机端「导航」挡住的模式，并没有被手机端「路由」挡住

**新判据。** 模式清单（`ModeSidebar` / `NavMenu`，`not_phone` 门控）和视图路由（`MainContent`，
**没有**门控）是**两道不同的闸**。一条分享链接穿过的正是缺席的那一道，用户拿到**一块空白**——
读起来像「这个页面坏了」，而不像「这个页面只支持桌面」。

**规则**：把一个界面入口按平台藏起来时，去数**到达那个视图有几条路**，而不是数**有几个按钮指向它**。

## E. 数字与归属（→ 附录 C 候选）

### E.1 一个计数约束的是它测量的那件事，对别的事沉默

**新判据，本轮我自己犯的。** 我用一个测试计数去证明**某个测试是谁写的**：
「Task 6 测得 39，Task 5 报 40 passed / 1 failed，所以 39 + 2 = 41，两个多出来的都是它的。」

**41 同样符合**「树里本来就躺着一个未提交的测试，它加了一个」。
**计数约束的是跑了多少个测试，它对谁写的完全沉默。**

被质疑之后回去核：Task 6 的报告从没提过加那个测试，Task 5 的报告在两处都把它描述成既有的。
最可能的作者是 Task 6，而**起因是我自己在它提交之后发的一条指令**（见 C.3）。

**规则**：拿一个测量当证据之前，说出**它测的是哪个谓词**，再问**我要回答的是不是同一个问题**。

### E.2 一份普查的可靠度，等于那个没人复核的转录步骤的可靠度

**新判据。** 本轮我用 `rg -n 'pty\.output'` 建了一份「这个名字出现在哪些地方」的普查，
交给实施者时报了 **8 处散文**——审查者发现真数是 **9**。

而 `rg` **每一处都找得到**：少掉的那一个是**我转录时丢的**，不是工具丢的。

**规则**：一份由「跑命令 → 人工誊写」两步产出的清单，第二步没有任何东西在校验。
要么让消费者**自己重跑那条命令**（把命令交给他，而不是把结果交给他），要么明说这份誊写没被复核过。

## F. 服务端持有状态（→ 附录 D 候选）

### F.1 一个「服务端持有状态」的架构，全部收益都压在客户端**重新找回**那个状态的那一步上

**新判据，本轮 controller 派单前查实。** 计划把 VT 屏幕搬到服务端（`Screen`/`Grid` 在 Rust core，
客户端只收行级 diff），并为多客户端共享建了 smallest-wins 视口表。这两件事**唯一**可被用户观测到的
方式是**刷新页面之后屏幕还在**，以及**第二个标签页看到同一块屏**。

而挂载路径写的是无条件 `pty.spawn`。于是刷新拿到一个新 shell 的新提示符，第二个标签页拿到第二个
shell——**服务端那半完整、正确、有测试，收益是零**，而两边各自的测试都是绿的：服务端测的是
「屏幕状态对不对」，客户端测的是「帧应用得对不对」，**没有任何一条测试问「刷新之后我还是不是同一个我」**。

同一份任务文本里，Step 4 的两条验收断言的正好是相反的行为（「刷新页面 → 屏幕内容原样恢复」
「第二个标签页 → 两个标签页看到同一块屏」）——**验收清单知道正确答案，实现代码不知道，而两者
写在同一个文件里相距 60 行**。

顺带一个不响的代价：旧会话不会被关闭（断线只释放视口约束，不 `pty.close`），所以每刷新一次泄漏
一个 shell，直到 `MAX_SESSIONS` 的 FIFO 把最老的踢掉。

**规则**：给一个「状态住在服务端」的能力接客户端时，先问**客户端启动时是「找回」还是「新建」**。
答案是新建，那个架构就没有交付；而这一问**不在任何一半的测试范围内**，它只在两半之间。

### F.2 serde 默认忽略未知键，所以一个多发的字段会在 wire 上留下一个看起来在起作用的设计

**已有判据（「同一事实的两份表述」）的 wire 形态。** Task 10 用一段 doc comment 明确否决了
「视口表按调用方自己挑的 `client_id` 键控」，改从 task-local 取真实连接身份。而客户端那半的草稿
仍然发 `client_id`——`ResizeParams` 没有那个字段、也没有 `deny_unknown_fields`，**于是它既不报错
也不生效**，只是在 wire 上把被否决的那个设计重新讲了一遍，等着下一个读 wire 的人把它当成事实。

**规则**：一个字段被服务端**有意**拿掉之后，去 grep 客户端还发不发它——`INVALID_PARAMS` 会告诉你，
而默认的 serde 不会。

### F.3 一条跨越了两个解析根的线，三段都有代码、都有测试，而整条线一格都不通

**新判据，本轮最贵的一次派单前查实。** 计划里的 `[gateway.terminal]` 开关，从配置类型到热应用
到审批闸，三个任务、三段实现，**没有一段是错的**——错的是它们之间那条线跨过了一个边界。

`Config`（`src/config/structs.rs`）**没有 `gateway` 字段，而且是有意的**。`src/config/dead_keys.rs`
里逐字记着这件事：`[gateway]` 由 `src/gateway/config.rs::GatewayConfig` **第二个解析根**读同一个
文件。于是：

- `apply_live_sections(cfg: &Config, ..)` 读不到 `cfg.gateway.*`；
- `LIVE_SUBSECTIONS` 命名的是 `Config` 内的子树；
- `patcher.rs` 把 `Config` 序列化成 JSON、打补丁、反序列化回 `Config` ⇒ 一个 `gateway.*` 补丁被
  **静默丢弃并报成功**。

第三条是关键：热开关的整个故事、以及为它加的那道审批闸，**守的是一条写不进去的路径**。

**为什么读任何一段都发现不了**：每一段单独看都正确且完整——配置类型解析得出来、live 表接得上
census、闸的链上位置也对。缺陷只存在于「这三段说的是同一个 `Config` 吗」这一问里，而**没有任何
一段代码提出这一问**。

**规则**：给一个配置项接运行时机件之前，先问**这个 section 属于哪一个解析根**，再逐个消费者问
**它拿到的是不是那个根**。仓库里有第二个根这件事本身是有记录的、正当的；不正当的是假设只有一个。

⚠️ 顺带一条正向的：**换位置时先问新位置是不是「可用」还是「正确」**。`policies` 不是退路——
`PoliciesConfig` 已经装着 `exec_tier` / `mode` / `spend` / `tool_permissions` / `guardian`，
它就是回答「什么被允许」的那个 section；而 `GATE_DECIDING_CONFIG_PATHS` 现有两项**都在
`policies.` 下**，新条目落在同类旁边，不再需要为「它凭什么和那两个并列」另找说辞。
一个需要额外解释才站得住的位置，通常就是错的位置。

## G. 编排与自审（→ 附录 C 候选）

### G.1 一份 brief 拿它自己对照，按构造就是自洽的

**新判据，本轮我自己犯了三次。** 我为还没派单的任务写 brief，然后**重读 brief** 做自审——
三次都没发现问题。三处缺陷全部是**读代码**读出来的：

- Task 13：我断言 `is_floor()` 同时买到两个保证，而那个函数的注释**恰恰在否认这句话**，
  反例（`PlanMode`）就坐在同一个 `match` 里；
- Task 12：我调用了一个**根本不存在**的 `crate::config::current()`；
- Task 19：我写的测试草稿用了 `PtyStyleRun { ..Default::default() }`，而那个类型不 derive
  `Default`；同一份草稿里的夹具还会把整个套件的现存测试静默 resize。

三处都通不过编译或与代码相反，而**重读多少遍 brief 都发现不了**——它内部完全自洽。

**规则**：自审一份 brief 的方式是**去读它引用的每一个符号**，不是重读它。判据一句话：
**这份 brief 里的每一个类型名、函数名、字段名，我刚才是从代码里读到的，还是从记忆里写下的？**

### G.2 前置冲突扫描对「另一半是代码」的冲突结构性失明

**C.1 的实测放大版。** 派单前的冲突扫描比对的是**任务文本 vs 任务文本**。本轮在还没派单的
四个任务里预读出**六处**缺陷，**没有一处**是两份任务文本之间的冲突——每一处的另一半都是
几小时前刚落地的代码：

- Task 17 的 `pty.resize` 带着一个 Task 10 已明确否决的参数；
- Task 17 无条件 spawn，而它自己的验收清单断言相反；
- Task 12 的配置根不存在（`Config` 没有 `gateway` 字段）；
- Task 12 的 live census 证明的是名字不是连线；
- Task 12 调用了不存在的 API；
- Task 18 的验证命令解析不出它自己的包。

**规则**：扫描要跑**两次**——派单前对任务文本跑一次，**每个任务派单前再对当时的代码跑一次**。
第二次才是真正会抓到东西的那一次，而它的成本是读几个符号。

### G.3 一条 idle 通知不携带任何关于「有没有在工作」的信息

**新判据，本轮误判两次。** 两个实现者各自安静了 20–40 分钟并发出 idle 通知，我两次都诊断成
「停住了」，**两次都错**——它们都在等共享 target-dir 上的真实构建（一次 3m06s），其中一个还在
**有意重跑** wasm，因为它依赖的文件在它第一次构建之后又被提交了一次。

**它不是一个需要权衡的弱信号，它根本不是信号。** 三次里每一次真正告诉我情况的都是别的东西：
问一句（换回一份有内容的状态），或者**读它写在盘上的东西**（直接告诉我任务已经完成了，
而任何状态询问都没做到）。

**规则**：agent 安静时，**先读它的工作，再决定要不要问**。并且记住**催问不是免费的**——
它会占掉对方一个回合，而本轮至少有一次 ping 什么都没买到。

### G.4 `grep -c` 数的是行，不是次数

**小而反复的一条。** 本轮两次用 `grep -c` 得出的数字去写脚本的锚点断言，两次都偏低
（26 vs 30、以及另一次 2 vs 1），两次都被断言拦下。**拦下它的不是我，是断言。**

**规则**：凡「我要改 N 处」的脚本，`N` 用 `python` 的 `str.count()` 现算，别用 `grep -c`；
而无论怎么数，**断言都要写**——它拦住的正是你数错的那一次。

### G.5 一份 brief 是计划文本的快照，而没有任何东西把它绑在计划的版本上

`scripts/task-brief` 把任务正文抽成一个文件，实施者读的是**那个文件**。之后计划被修补，
brief 不会知道——它是一份**派生副本，且没有陈旧检测**。这一轮我给计划打了十几次补丁，
五份未派单的 brief 全部是当前版本，但那是**我的习惯凑巧对了**（每次打完补丁顺手重提取），
不是机制保证的。

两条：

1. **重提取要和打补丁在同一笔里**，别留到派单前——派单前你已经在想别的事了。
2. **验证要按内容，不按 mtime。** 本轮 mtime 与提交时间逐秒吻合，读起来像证据，
   而它只是同一个工作流的两个副产品；真正的检查是 grep 修复本身是否在 brief 里。

⚠️ 而这个 grep 有一种必然的假阳性：**裁定文本会保留被否掉的那个写法**。本轮五处非零命中
（`gateway.terminal` ×2、`client_id` ×2、`registry.register("pty` ×1）全部是在解释
「原文这么写，为什么不行」——是**否定**不是设计。所以命中之后必须读上下文，
而不能把「还有命中」直接读成「brief 是旧的」。

### G.6 一个改动共享类型的任务，要去数那个类型在**树上**有几个非定义点，而不是在计划里有几个

Task 19 给 `PtyScreenFrame` 加两个必填字段。计划内部的扫描（哪些任务提到这个类型）是干净的：
只有 Task 17，而且它只反序列化、从不构造。

真正的缺陷在树上：`ClientScreen::write_patch` 有**两个**调用者，而 Task 19 的修复只写进了
其中一个（`apply`）。另一个是 `finish_attach` 的重放循环——它由 Task 15 的复审在
Task 19 被构思**几小时之后**加进来的，直接调 `write_patch`。

于是 attach 期间缓冲的帧（**恰恰是唯一可能带着新几何的那一批**，因为尺寸是 smallest-wins，
别人离开就会把本端撑大而本端什么都没调用过）在重放时写进一个还是快照大小的网格，
`get_mut` 对超出的行返回 `None`、静默丢行、`seq` 照常前进 ⇒ 不 gap ⇒ 永不自愈。
**逐字是这个任务要修的那个缺陷，发生在为修它而新写的代码里。**

而任务自带的两条测试只走 `apply`，全程会绿。

判据三句：

1. 一个任务改共享类型时，**去 grep 那个类型在树上的每一个非定义点**——计划里的引用只是
   其中一个子集，而另一个子集是别的任务几小时前刚提交的代码。
2. 找到多个写入点之后，修法**不是**在每个点重复那条规则，而是**让第二个点不存在**：
   把「resize + write」折成一个必须同时收下几何的私有方法，删掉两个旧的。
   这样顺序从「一条要记住的规则」变成「唯一存在的写法」。
3. 变异要有一次打在**调用点**上而不是打在被调用的函数上——它模拟的正是
   「把修复只写进第一个调用者」这个最自然的错法，而打在函数体上的那次变异看不见它。


### G.7 一个守卫可以既不弱也不错，只是**瞄在另一层**——而那一层不是会变的那层

Task 12 让 `handle_spawn` 调 `spawn_with_scrollback(&opts, lines)`；Task 13 让它改调
`spawn_as(&opts, actor)`——**丢掉 scrollback**。配置里的 `scrollback_lines` 从此到不了任何
真实会话，终端历史退回内置默认值。

而**两个任务的测试都不会红**：

- Task 12 的 `the_configured_scrollback_reaches_the_session_grid` 直接调
  `mgr.spawn_with_scrollback(..)`，**从不经过 handler**；
- Task 13 的 `a_spawn_records_who_asked_for_it` 同样直接调 `spawn_as`。

**一个只调其中之一的 handler，两条测试全过。** 它们守的是两个辅助函数，而会变的是**调用点**。

这不是「守卫要断言效果到达了，不是调用发生了」的重复——那条讲**断言的强度**，这条讲
**断言的位置**：两条测试都在断言真实效果，只是效果被断言在一个不会被改动的层上。判据：

**写完一个守卫之后，问「我下一次会改的那行代码，如果改错了，这条测试会红吗」。**
答案是「不会，因为它没经过那里」时，缺的是一条穿过**接缝**的测试，不是一条更强的单元测试。

### G.8 一次熵减检查如果 grep 的是带引号的标识符，它只看得见代码那一半

`pty.output` 被 CUT 之后，Task 18 的熵减项是 `rg -n '"pty\.output"'` —— **带引号**，
所以它匹配 Rust 字符串字面量。代码侧确实零命中，于是这一项读起来是绿的。

而**三份文档仍在点名它**，其中一份是 `src/gateway/CLAUDE.md` 里那条「一条连接有两个方向」
判据的**经典例子**——一份安全文档，用一个已经不存在的 topic 作为它唯一的实例。

一个被删掉的标识符，它的其余表述住在散文里；而对一份安全文档，**散文正是会被读的那一半**。

⚠️ 修法有个分叉，走错就是伪造记录：那三段记的是**一个真实发生过的缺陷**，把名字改成新的
等于说那个 bug 发生在一个当时还不存在的 topic 上。正确做法是**保住原名 + 补一个指针**
（「这个名字现在叫 X；保留原名是因为缺陷发生在它身上；形状变没变」）。判据一句话：
**历史记录里的标识符是证据不是引用，它跟着事实走，不跟着代码走。**

### G.9 多个 agent 共用一棵工作树时，目录暂存就是 `git add -A`

计划里四个任务的暂存行是目录：`git add src/`（整棵源码树）· `git add src/gateway/` ·
两个 `git add interfaces/webchat/`。这在单人分支上只是懒；在**多个实施者同时写一棵树**时，
它会把别人的在飞工作扫进你的提交，而提交信息会诚实地描述一件它没做的事。

它没造成损失，只是因为 Task 16 的实施者**自己收窄成了四条具名路径**并在提交前核对了
`git diff --cached --stat` —— brief 告诉它的是错的，它做对了。

判据两句：① **暂存行要从任务自己的 Files 块推导**，不要写目录；② **每个提交块都欠一句
`git diff --cached --stat` 的核对**，且核对的期望是「就是上面这几条，多一条都停下来查」。

### G.10 一条会在别的步骤之前中止的 CI 闸，它的红会**遮住**后面那些步骤

这个计划走到第 16 个任务时，**没有一个任务跑过 `cargo fmt`**——十个文件未格式化，
跨 Tasks 2/3/6/8/11/15/16。

代价不是排版：CI 的 fmt 步骤跑在 `bash -e` 下、**排在 clippy 与 `--all-targets` 之前**，
所以一个空白差异会让那两步根本不执行，而它们才是抓真实 lint 回归的地方。fail-fast
再砍掉另外两个平台。**一个红着的闸报不出下一个破坏**。

⚠️ 而修它有两个已知陷阱，本仓各栽过一次以上：
- `cargo fmt -p <crate> -- <file>`：`--` 之后是**传给 rustfmt 的选项**，不是文件过滤器，
  它格式化整个 crate；
- `rustfmt <file>`：会**顺着 `mod` 声明递归进子模块**。

单文件的解法是 `rustfmt --config skip_children=true <file>`，且格式化后**核对一遍
到底哪些文件动了**。

⚠️ 范围也是一次裁定：全树 48 个未格式化文件里 **41 个是既有的**。把它们一起格式化会用一个
巨大的 churn diff 把真实改动埋掉，且不属于这条分支的责任。**只修这个计划碰过的那些。**


### G.11 一份文档**论证**出一条裁定，不等于那条裁定**到达**了会被照抄的那一半

本轮一个会话里同一形状出现**四次**，四次都是：裁定写在散文里，被推翻的那条指令原样留在
**Interfaces 块 / 代码块 / 完成判据**里——也就是实施者真正照着打字的那一半。

| 出处 | 散文里的裁定 | 留在别处的被推翻指令 |
|---|---|---|
| Task 12（首次） | ArcSwap 在这里是 fail-**OPEN** | 紧接着又把 ArcSwap 列为回退，并指向不存在的 `config::current()` |
| Task 13 | `DestructiveArguments` 是错的那条规则（第 3 位，`full` 档不响） | `Consumes:` 逐字点名它 · Step 3 让人去改它 · 两条测试断言它、且都没设档位 |
| Task 18 | 带引号的 grep 结构性看不见散文（三份文档为证） | 完成判据第 3 条原样只写那条带引号的 grep |
| Task 12（再次） | —— | 拒绝语只说现状，而 Task 17 两处断言它说得出出路 |

**为什么散文拦不住**：一份任务书里，散文是**论证**，代码块和 Interfaces 块是**接口**。
实施者按接口干活，把散文当背景。所以「我在上面已经解释过了」对下面那个代码块**不构成约束**——
这和判据清单里「一条只写在散文里的裁定防不住下一个真诚的修复者」是同一条，只是这次的
「下一个人」是同一份文档里下面二十行的自己。

判据两句：
1. **写下一条裁定之后，去 grep 被推翻的那个名字**（谓词名 / 函数名 / 常量名 / 那条命令），
   把每一处命中都改掉或就地标注为已推翻。裁定与它的清理是**同一笔**。
2. **完成判据、Interfaces 块、代码块三处优先于散文**——它们说的话如果和散文冲突，
   坏掉的是它们，不是散文。审这三处比通读全文便宜得多，且这一类缺陷 100% 落在这三处。

### G.12 一条拒绝语有两种错法，方向相反、成因相同

- **点名一个不存在的补救**（Task 11 Minor 2：「register a workspace first」，而根本没有注册
  这一步——那个根是派生配置值，`workspace_roots()` 自己就会创建它）。
- **一个补救都不点名**，而下游有检查断言它点了（Task 12：拒绝语只说 `enabled = false`，
  Task 17 的 Step 3 与真机第 10 条都要求它「说得出怎么打开」）。

两种都读起来像小事，代价不同：前者把被拒的人送去做一件不会起作用的事；后者让每一处
断言"有出路"的下游检查**静默失真**——真机跑到那一条会红在计划自己规定的字符串上。

判据：**写拒绝语时把「被拒的这个人接下来该干什么」写进去，然后去核实那件事真的做得到。**
配套一句边界：**补救要点名那个人够得到的面**。同一条拒绝，回给 Panel 的 operator 该点名
配置文件；把工具名写进去就是在一条拒绝里教一条绕闸路径，而那条写入本来是要举卡的。


### G.13 一次 RED 捕获证明的是「这条测试会红」，不是「它因为你说的那个理由红」

两者在**失败是一次超时或一次缺席**时必然分岔——而「缺席」正是「值错了」和「机制根本没跑到」
共同的长相。

本轮实例：`spawn_with_no_cwd_actually_chdirs_the_child_into_the_first_root` 在被故意破坏的
handler 上红，失败信息逐字写着「must chdir the child into the resolved first workspace root …,
**not the daemon's own process cwd**」。读起来是一份完美的 RED 证据。

**而它红的原因不是那个。** 恢复正确的 handler 之后它**仍然红**——屏幕整个是空的。
`session.rs::spawn_reader` 在子进程 EOF 时调 `manager().remove(&id)`，`sh -c pwd` 毫秒级退出，
于是测试在跟自己的回收器竞速：第一次 `attach_snapshot` 落在读线程喂屏之前，之后每一次都因为
会话已被删而 `Err`。**没有人看见过 daemon 的 cwd 出现在屏幕上**，那句断言点名了一个它从未观测到
的原因。

三句：

1. **RED 只能证伪「这条测试恒绿」。** 要证明它**区分得开**修好与没修好，唯一的做法是在**绿树上**
   做变异——而变异只有在树绿之后才跑得了，所以这一步天然排在 RED 之后，不能用 RED 替代。
   本轮两次变异才建立了区分度：丢掉整个 jail 调用 ⇒ 两条都红；**保留调用、认它的 `Err`、
   只丢弃它的 `Ok`** ⇒ 只有放行那条红。第二次才是这条 Major 点名的那个缺陷形态。
2. **一条断言如果讲的是「屏幕上应该有什么」，它失败时必须把屏幕打出来。** 不打印就是把
   **症状**交给下一个人而不是**证据**。本轮这一改把一个五秒的谜团变成了一次运行的诊断。
3. ⚠️ **改过测试之后，之前那份 RED 就不再覆盖现在这条测试。** 本轮我在采完 RED 之后修了测试
   （让子进程活过断言），那份 RED 从此描述的是另一条测试——所以重新证伪了两次。**「我采过 RED 了」
   是一句有有效期的话，有效期到你下一次动那条测试为止。**

### G.14 一个「会自己被回收」的对象，测试拿到的句柄和产品拿到的句柄可能不是同一种

上一条的成因，单独成条是因为它会以别的形态复发。

先例测试 `session::tests::a_child_write_reaches_the_server_held_screen` 持有的是
`Arc<PtySession>`——读线程从 manager 里删掉那条记录**不影响它手上的 Arc**，所以它一直是绿的。
新测试经 `pty::manager().attach_snapshot(&sid)` **按 id 查表**，于是同一段代码、同一个子进程、
同一个断言，一个恒绿一个恒红，而两者的 doc 都说自己在用「同一个 idiom」。

判据：**照抄一条 idiom 时，去看它握着的是什么**——一个直接句柄，还是一次按 id 的查表。
前者对生命周期免疫，后者要跟回收器竞速。顺带一条产品面的发现：`PtyManager::remove` 是
**删除**不是标记，所以 `SessionInfo.closed` 在「子进程自己退出」这条路上**永远观测不到 true**，
它唯一为真的窗口是 `close_all()` 之后、各读线程还没到 EOF 之前。


### G.15 `tail -N` 是本会话最高产的假缺陷来源——三次，三次都朝同一个方向

同一个会话里栽了三次，**每一次都差点写下一条不存在的缺陷**：

1. `cargo clippy … | tail -40` 之后 grep，得出「我们的文件零命中」。结论碰巧是对的——**而这
   正是它值得重做的理由：一个坏仪器给出的对答案仍然是一个坏仪器。**
2. grep `TerminalView` 的挂载点时把范围限定在 `platform/wide/` 下，零命中，差一步写下
   「没有挂载点」。`app.rs` 在那个目录**之外**，挂载点一直都在。
3. `cargo test -p aleph-protocol pty:: | tail -3` 读到 `0 passed`，差一步写下「Task 18 的验证集
   里有一条永远跑 0 条的命令」。那是**最后一个 target**（一个没有测试的 bin）的结果；lib
   target 上是 **3 passed**，就在上面两行。

三次的共同形状：**输出被截断 / 范围被缩窄之后，「我没看见」和「它不存在」逐字相同**，
而两者的处置相反。判据三句：

1. **凡多 target / 多 target 会各打一行 `test result:` 的命令，别 `tail`**——按
   `grep -E "Running|test result"` 全取，或者干脆全看。`0 filtered out` 是那一行在说
   「这个 target 根本没有测试」，不是「过滤掉了」。
2. **一次搜索的作用域就是它结论的作用域。** 写「X 不存在」之前，先说出你搜过哪几个目录，
   再问「X 会不会住在别处」。
3. **朝哪个方向错也是信息**：这一族的三次全都朝**误报一个不存在的缺陷**错。因为截断和缩窄
   只会让你看见更少，而"更少"的默认解读是"没有"。

### G.16 一次运行分不出「这个说法错了」和「这个测量有噪声」——而噪声可能站在你这边

判据清单里已有这条，本轮以**最难堪的方向**复发：复审报告说那条 refusal 测试在
`--lib -- gateway::pty gateway::handlers::pty` 下 **14/14 全红**。我跑了**一次**，
得到 **68 passed / 0 failed**，并且已经开始怀疑复审说错了。

写脚本跑八次：**8/8 全红。** 我那一次绿是异常值。

补一句这条判据没写全的：**「别人的仪器你重复测量」这半我做到了，「重复」这半没有。**
一次复现失败**不构成**反驳，它只构成「再跑一次」的理由——而竞态的定义就是它不是每次都发生。
凡结论是「这条竞态不存在」，样本量 1 不够；凡结论是「它存在」，样本量 1 就够了。
**这个不对称本身要写进量法**：证伪一条竞态比证实它贵得多。

### G.17 一条测试失败时的措辞，可以指控被测代码干了一件它没干的事

上一条那条竞态的失效**不是**「偶尔红一下」，而是红的时候说：

    a refused spawn must not have created a session, but found new id(s): ["695c5a6f-…"]

那个 id 是**兄弟测试**的会话。于是一条测试在一次纯粹的调度巧合上，**指控 handler 绕过了
cwd jail**——下一个人会去追一个不存在的安全缺陷，而追查的起点是一条听起来非常确定的话。

成因是断言的**主语**选错了：它问「有没有任何会话出现」，而它想问的是「有没有**只有这次调用
才可能产出**的会话出现」。在一个进程级单例上，前者的答案属于整个测试二进制，不属于这次调用。

判据：**一条断言如果要否定「我造成了 X」，它的谓词必须只有"我"能满足。** 全局容器上的
before/after 差集**永远**不满足这一点——它测的是整个进程。修法是给这次调用一个别人产不出的
标记（这里是一个别的测试都不用的程序标签），然后只否定那个标记。

⚠️ 配套：**替代方案本身可能重新引入一个方向相反的竞态**。这里的标记探针如果用一个瞬间退出的
程序（`/bin/echo`），`spawn_reader` 的回收会在你查表之前把它删掉 ⇒ **真的绕闸也会绿**。
所以探针必须长命。**把一个假红换成一个假绿，是这一类修复最常见的失手。**


### G.18 两个写者共用一个文件时，`cp` 备份是**某一刻**的快照，而「恢复」的意思变成「把当时那份写回去」

本轮的险情，事后才被对方的一句话点破：task19 说它在我的 stand-down 落地时**正在跑变异**，
并在那之后才把 mutation 1 撤回。而我做 `cp .good` 备份时如果文件正处于变异态：

- 我的每一次「恢复」都会把**变异体**写回去；
- 我随后的每一次变异都是**从变异体出发**；
- 最后那次恢复 + 提交，交付的就是**倒过来的 `settle`**；
- 而整套测试会是**绿的**——因为我每次都在"变异走开"而不是"变异进去"。

**没有发生，而排除它的证据不在时序里，在运行结果里**：mutation 1 是**把顺序倒过来**。对一个正确
的基线它红；对一个已经倒过来的基线它会把顺序**改回正确**从而**绿**。我拿到的是 3 条红 ⇒ 基线
干净。（`git show <sha>:<path>` 复核了已提交的内容，也是对的。）

判据两句：

1. **共享树上，一个「预期为红」的变异是自校验的，一个「预期为绿」的不是。** 前者的红同时证明了
   「变异生效了」和「基线是我以为的那个」；后者的绿和「我根本没改到东西」「基线本来就坏」逐字
   相同。**能选红的时候别选绿。**
2. **`cp`/`git checkout --`/`git stash` 在多写者的树上都不是「恢复到我的状态」，是「恢复到某个
   状态」。** 同夜另一个 agent 用 `git checkout -- <自己的文件>` 把**自己的成果**回滚掉了，
   因为 HEAD 在它开工后前进过——**危险不在路径归属，在你不拥有那个时间点**。

### G.19 一条断言把两件事焊在一起：变异生效了，而且基线是我以为的那个

上一条的操作面，也是本轮**第二次**被同一个机制救下。

给一棵共享的树打补丁时，锚点计数断言（`assert s.count(old) == 1`）拦下的**不只是**「我改错了
地方」。本轮转置变异的锚点匹配了**两次**，写入被拒绝，而紧接着那次测试运行跑的是**干净树**、
报 56 绿。**没有那条断言，那个绿会被读成「这个变异抓不住」**——一条完全正确的守卫会被我写进
报告说它瞎了。

判据：**每一次「我应用了变异」之后，先证明变异真的在文件里，再去读测试结果。** 最便宜的做法是
让补丁脚本自己断言锚点数并在不匹配时**退出非零**，而不是打印一行警告——警告会和成功的输出混在
一起，而下一行恰好是一个看起来很有说服力的测试结果。


### G.20 一个测试为了证明"真接线"去动进程全局单例——它证明的和它破坏的是两件事，而破坏只在窄命令下可见

Task 12 的 `disabling_the_terminal_live_kills_sessions_through_apply_live_sections` 刻意用
**进程全局**的 `pty::manager()` 而不是新建一个 `PtyManager`，它的 doc 把理由写得完全正确：被测的那
条 arm 里硬编码着 `crate::gateway::pty::manager()`，**局部实例证明不了那条线**。

那句论证对**它证明了什么**是对的，对**它破坏了什么**一个字都没有。`close_all()` 杀掉进程里的
**每一个**会话，而 `gateway::handlers::pty::tests` 的十二条测试全都在同一个单例上 spawn 真实会话
再对它们作断言，libtest 又是并行跑的。

实测（不是推演）：

```
pty handler 模块单跑，6 次              ->  6/6 绿
pty handlers + config::live_apply，6 次 ->  5 次红，每次红的是不同的子集（1,1,3,1,3,0）
同一棵树的全量 --lib，8 次              ->  8/8 干净
```

**全量绿是运气不是安全**：17k 条测试里这一对很少撞上。而 5/6 红的那条命令
（`cargo test -p alephcore --lib -- gateway::handlers::pty config::live_apply`）恰恰是**人在这
个子系统里干活时真会敲的那一条**。

三句：

1. **写一个动进程全局资源的测试时，先问"这个资源上还有谁"**——不是"我会不会污染别人的状态"，
   而是"**别人此刻正握着的东西，我这一下会不会把它拿走**"。
2. **修法不能是点名受害者。** 忘记打标签的失效模式是**别人的**测试变 flaky，不是新写的这条；所以
   要求要**从源码派生**（本轮：`serial_test` 的 `serial`/`parallel` 键 + 一条扫描本模块每个
   test attribute 的 census，自带 `checked >= 12` 自保断言、先剥 `//` 行）。
3. **两半都要单独证伪**：摘掉一个 `parallel` 标签 ⇒ census 按名字红；摘掉 `serial` 键 ⇒ 竞态回来
   （6 次 4 红）。只验其中一半的话，另一半可能从一开始就没在工作。

### G.21 一个 edition 不能从编译器的通用帮助文本里读

`rustfmt --check <file>` 默认 edition 2015，于是对任何 `async fn` 报 E0670，帮助行逐字写着
`pass --edition 2024 to rustc`。我照做了——**那句话是 rustc 在推荐最新 edition，不是在报告这棵树
的 edition**。这棵树是 2021，而 2024 的 import 排序规则不同 ⇒ 量具当场造出满屏假差异，读起来正
像"task12 提交了一堆没格式化的代码"。

判据：**edition 去 `Cargo.toml` 读，别从错误信息里抄。** 同族一句：一个量具在被错误配置时，
输出的不是"错误"，是**一份看起来很具体的、错误的测量**。

顺带记一次**第三次**复发：`cargo fmt -p alephcore -- --check` 报了一个本分支从未碰过的文件
（`src/approval/mod.rs`）。`--` 之后是**传给 rustfmt 的选项**，不是文件过滤器；`-p` 限定的是
crate 不是文件。单文件的唯一安全形式是
`rustfmt --edition <n> --config skip_children=true <file>`，而且格式化之后要**比对
`git status --short` 的前后差集**确认它没碰别的文件——本轮这么做了，差集为空。


### G.22 一个代理谓词有它看不见的方向，而那个方向通常正是"说错了但没说具体"

`GATE_DECIDING_CONFIG_PATHS` 从两项变三项，三份描述它的文本全部过期，而**一条测试都没有**。
补的 census 规则是：**点名了名单里任何一个成员的句子，必须点名全部成员**（成员表从常量派生，
不手抄）。它抓住了两处旧枚举，也抓住了"加第四个成员、不动散文"这个真正的未来失效。

**然后再复审在它扫不到的地方找到了第四份拷贝。** `ExecTier::Full` 的**变体 doc** 说第三条地板是
"一次能**够到审批设置本身**的 `self_config` 写入"——对新成员是假的，而它**一个成员名都不含**，
于是 `named.is_empty()` 直接放行。

实测证明（不是声称）：把那句假措辞装回去，两条守卫**全绿**。

判据三句：

1. **「点名任一就必须点名全部」是一个代理**，它精确的前提是"这句话在泛化描述名单"。对**陈旧的
   枚举**成立，对**陈旧的转述**结构性失明。
2. **发现盲区之后不要加一个"检查正确措辞"的子串检查去糊住它**——那正是第一轮睡过去的那种形状
   （`the_full_tier_prompt_line_names_every_floor` 查四个子串，四个都还在，于是它放过了一次
   把新成员描述成假话的漂移，而它自己的 doc 写着它存在就是为了抓这个）。**一条如实声明的局限，
   胜过一个不会红的守卫。**
3. **声明的局限要能被下一个人行动**，不能读成"我们知道，没事"——那种写法是许可证，会让下一次
   陈旧转述合法化。

**⚠️ 追补（同轮，复审指出我给的判据自己不精确）。** 我一开始把人用的判据写成
「**再加一个成员，这句话会不会变成假的**」。复审指出它**区分不开**该修的那份变体 doc 和不该动的
两条一行回声——我验了，它说得对：变体 doc 那句"够到审批设置本身"**在第三个成员上就已经是假的**，
再加第四个不会让它"变成"假的。

成因是**两种缺陷被我收成了一种**：

- **枚举型**：句子点名成员 ⇒ 名单一长就**不完整**。
- **刻画型**：句子刻画整张名单**是什么** ⇒ 一个不符合该刻画的成员加入，它就**变假**。

覆盖两者的单一判据是：**「以名单今天的样子，这句话对它的每一个成员都还成立吗？」**
逐站点验过：旧 `reason()`（对第三个成员不成立 ⇒ 失败）· 变体 doc（对 `policies.terminal`
不成立 ⇒ 失败）· 新 `reason()`（两类成员都成立 ⇒ 通过）· 两条一行回声（对全部成立 ⇒ 通过）·
SECURITY.md 那条**按主语出局**（它讲某一个成员，不是名单）。

而这也正好说清了机械化的边界：**census 只能机械化「枚举」那一半**（"点名了子集"是可扫描的），
**「刻画」那一半不可机械化**——那就是上面那个盲区，现在它有名字了。**别去写一个自动检查
「这句话对每个成员都成立吗」的守卫**：它不可判定，写出来只会是一个不会红的守卫。

元判据一句：**一条判据如果自己不精确，它会给下一次错误发许可证**——而我这条是写在
census 的 doc 里的，那份 doc 正是下一个人用来判断"新句子归不归我管"的东西。

### G.23 一个扫描器扫哪几个站点，要和"这个仓自己指定的那几个"对账

上一条的成因，而它比"漏了一个"更难看见：census 的 doc 逐字写着它扫描
「`SECURITY.md` 自己那段『三份拷贝』点名的三个站点」。**那句话是假的。**

`SECURITY.md` 点名的三个是：`ExecTier::Full` **变体 doc** · `approval_prompt_line(Full)` ·
`GateRule::GateRemoval::reason`。census 扫的是**后两个 + 常量自己的 doc**——它换掉了一个，
而换进来的那个恰好很有用（正是它抓到了第四成员变异），所以读起来完全合理。

判据：**写下"本扫描器覆盖 X 指定的那一组"之前，去 X 那里把那一组数一遍**。两组不等时，
要么改扫描器，要么在 doc 里说清**为什么不等**——但不能让 doc 继续复述一个它没做到的承诺。
这是"同一事实的两份表述"落在**守卫自己的 doc** 上，也是这条 census 存在要抓的那类缺陷。

顺带一条**处置**判据：多出来的那个站点（常量自己的 doc）**不要删**——它是唯一能抓住
"加第四个成员却不动散文"的那一个。正解是**并集 + 把差异写进 doc**，不是让扫描器去迁就一份
四个月前写下的清单。

### G.24 被拒的变异后面那个绿，和"守卫抓不到"逐字相同（第四次）

本会话第四次被同一个机制拦下，而这次的场景是**验证一条"守卫抓不到 X"的断言**——那种断言的
期望结果本来就是绿，所以"变异没应用"和"结论成立"**读数完全一样**，比平时更危险。

第一版变异按 `floor_asks_for_arguments` 匹配，命中 **2 处**（另一处是别的段落的交叉引用），
`assert count == 1` 触发、写入被拒，而紧跟着那次测试跑报 **2 passed**——**如果没有那条断言，
我会把它当成"盲区证实"写进报告，而当时树是干净的。**

配套一条独立的量具判据：**rust-analyzer 的诊断是增量读数，不是编译器的结论。** 它报
`full_variant_doc_text` 是死代码（"function is never used"），而真实 `--lib --no-run` 里
**没有这条警告**——它捕捉的是"helper 已加、调用点未加"那一瞬。写下"这里有个警告"之前，
用真的构建量一次。本轮同类近失第四次，方向全部是**报一个不存在的缺陷**。


### H. 真机验证暴露的两条（2026-08-30，Panel 终端）

**H.1 一张手写的协议动词表，漏掉的那一个不会有任何测试为它变红——而它很可能正是最常用的那一个。**

`csi_dispatch` 的 `match action` 列了 `H/f A B C D J K`，规格与计划里都没有 `'G'`(CHA)。
实施者一条不漏地做到了被列举的每一条，每一层单测全绿，**而 Panel 终端里敲一个字符会画出三个**
——因为 zsh 每次重绘输入行都发 `ESC[<n>G` 回到列首，这一条被静默丢弃后重绘就变成了追加。

这是「列举法只覆盖立法当天的世界」落在**协议动词表**上的形态，也是目前最难看见的一种：
① 漏掉的动词没有名字出现在任何地方，grep 不到；② 没有编译器替你查；③ 单测按定义只覆盖被列举
的那些；④ 症状（多画几个字符）读起来像渲染毛刺不像协议缺口。

判据：**给一张"我们支持这些"的表写守卫时，守的必须是「表上每一条都真的到达了下游」，不是把表
再抄一遍**。抄一遍的守卫在这个缺陷上恒绿——它比对的两份都缺 `G`。可证伪的形式是**逐条探针 +
一个把终字节改掉的对照**：这个动词若真接线，两次喂食的屏幕必然不同。

⚠️ 配套：这条守卫自己也会退化成列举法（探针表要人手加）。所以它还要**从源码数一遍 match 里
声明了几条臂**，并断言探针数不少于它——加了臂不加探针就红。

**H.2 判断「显示错了还是数据错了」，最强的裁判往往不是显示，而是被测系统里某个只有在数据正确时
才成立的副作用。**

屏幕画出 `xxx`，无法自证是输入重复还是渲染重复——两者在屏幕上逐字节相同。裁判是 **zsh 的历史
补全**：它把缓冲区补成了 `xattr …`，而没有任何历史条目以 `xxx` 开头 ⇒ 缓冲区里只有一个 `x`。

判据：**找一个消费同一份数据、但输出经由另一条路径的消费者**。显示是被怀疑的那一方，它的证词
没有分量；一个"只有值对了才会发生"的行为有。同族：上一步分辨「服务端屏 vs 客户端 diff」用的是
**刷新页面**——它销毁客户端全部状态并从服务端全量快照重建，所以幸存下来的脏数据只可能来自服务端。
而刷新恰好也是清单第 6 条，一个动作同时是诊断和验收。

**H.3（复发第二、三次）「没找到」的读数要先问量具搜的是不是它存储的形态。**

同一轮里犯了两次：① 对一个用 `<canvas>` 渲染的终端读 `innerText`，得到 10 个字符，差点写下
"终端没渲染"；② 从 attach 快照读 `result.rows` 期望拿到行内容，那是**行数**（12），于是六条探针
印出六片空白——**而空白恰好长得像"每个动词都坏了"，正是我当时正在形成的结论**。

判据补一句：**当一个"什么都没有"的读数指向你已经在猜的那个方向时，它最不可信**。停止猜格式，
把一份真实样本原样打印出来——两次都是这一步一秒钟解决的。


**H.4 一个 flex 属性如果它的父盒不是 flex 容器，它就是死的——而退回去的内容尺寸会稳定成一个不动点，看起来像是设计如此。**

CLAUDE.md §7 已有的那条讲**百分比宽度**遇上没声明宽度的父盒；这是同一族的 **flex 版本**，而且
更难看见。实测：`MAIN` 是 `display: block`（它自己带 `flex-1`，但那说的是它在**它**父级里的行为），
所以终端视图的 `flex: 1 1 0%` 完全不起作用 ⇒ 高度退回内容 ⇒ canvas 退回固有宽高比 (1783:892)
⇒ 892 宽给出 446 高，而窗格有 717。**38% 的窗格空着，26 行而不是约 42 行。**

它活过十六个任务和一次真机查看，靠的是三件事叠在一起：

1. **它是不动点**：代码量到 446，把后备存储设成 892（446×dpr），固有比例再从宽度推回 446。
   自洽、稳定、渲染锐利 ⇒ 读起来像"选定的尺寸"而不像 bug。
2. **没有一行代码是错的**——错的地方在一个你不拥有的父盒里。
3. **验收项问的是"在不在"**：清单第 1 条「终端出现，有 shell 提示符」**通过了**。它确实出现了，
   确实有提示符，而窗格空着三分之一。

判据两句：
- **「它出现了」不是「它填满了」**。存在性检查结构上看不见几何缺陷，而几何几乎就是终端的全部。
- **这类缺陷的守卫只能是源码级的规则**（"这个视图不许靠 flex 属性拿高度"），不能是运行时数值
  断言——`rows > 30` 在我的显示器上通过，在笔记本上失败。**一个随观测者变化的断言不是守卫。**


**H.5 一条守卫的名字如果说的是规则、断言检查的却是那条规则的一种实现，它就有能力说假话。**

实测形态：`terminal_view_root_does_not_rely_on_flex_for_its_height` 断言的是「标签里含
`h-full`」。`absolute inset-0` **满足这个名字、却让断言失败**，而失败信息会说"丢了显式高度类"
——那时候高度类明明在。

判据不是"把断言放宽"——放宽意味着**枚举可接受的类名**，那是同一个病升了一层（见 H.1）。正解是
**三者各归其位**：规则写进 doc（那里说得对），断言保持窄而可核，**名字和失败信息改成描述这个断言
实际检查的东西**。

一句话：**断言可以比规则窄，名字不可以比断言宽。** 窄断言只是覆盖不全（安静地漏），宽名字会让
守卫在一个合规的状态上变红并给出一句错误的解释——而本仓已经记过，会误报的守卫比不报的贵，因为
它会被引用为证据。

**H.6（第三次复发，且首次由子代理报上来）恢复或变异只要保留了旧 mtime，cargo 就会跳过重编——两个方向都会骗你。**

task17 用 `mv backup.bak original` 恢复，备份的旧 mtime 被保留 ⇒ cargo 认为无需重编 ⇒ 恢复后的
那次"通过"实际上跑的是**变异体**。我此前从相反方向踩过同一族（`copy2` 保留 mtime）。

通用形式：**变异检查必须在两条边上都 `touch`，不只是恢复那一条。** 只 touch 恢复边的话，"变异
后没变红"读起来像"守卫瞎了"，而真相可能是变异根本没被编译进去。

**H.7 一个会做归一化的测试辅助函数，可能恰好归一化掉了它要测的那一类缺陷——而线上走的是没被归一化的那条路。**

由 Task 20 的实施者在写宽字形修复时自己发现并写进 doc：`Grid::row_text()` **过滤掉 spacer**
（双宽字形后面那个占位单元），所以一次行内移位把双宽字形劈成"孤儿 owner + 孤儿 spacer"之后，
用 `row_text` 写的断言**看不见任何异常**——它把损坏的那一半悄悄滤掉了，读起来完全正常。

而线上发出去的是 `row_cells()`（快照的 `runs` 由它派生），它**不过滤**。

判据：**写断言之前问一句「这个辅助函数把什么东西抹平了，而线上那条路抹不抹」**。同族于本文件
H.3 与仓里那条「量具在用另一种形态搜索」，但这一条更隐蔽：H.3 是量具找错了地方（读数为空），
这一条是量具**读到了内容，而且内容是干净的**——它已经替你把脏东西擦掉了。

一句话：**便利函数的便利，往往正是它替你丢掉的那部分信息。**


**H.8 两个都实测过的端点，不构成对它们之间那句因果的实测——而最危险的情形是，反证的量具已经在你手里了。**

本轮我亲身踩中，且是写下 H.1–H.7 之后踩的。我实测了两件事：① `csi_dispatch` 里没有 `'G'`；
② CHA 被发出时确实被丢弃。然后我把**中间那句**——"zsh 重绘提示符发 `ESC[<n>G`，丢掉它所以重绘
变成追加"——当成第三条实测写进了任务 brief 的标题。**它是推论。**

实测真相（自己在裸 pty 里抓 zsh 对一次按键的输出）：

```
x<BS>\e[1m\e[31mx\e[0m\e[39m<BS>\e[1m\e[31mx\e[0m\e[39m…
CSI final bytes: ['A', 'D', 'J', 'm']      ← 一个 'G' 都没有
```

真凶是 **BS**，不是 CHA。CHA 确实缺失、确实该补，但它**不是那个症状的原因**。

加重的一半：**反证的量具一小时前就在我手里**——我自己的 C0 探针已经打出 `printf 'abc\bZ'` →
`abcZ`（BS 被丢弃）。我把它归档成"同一类的第二个实例"，而没有问"它是不是**那个**原因"。

判据两句：
- **一条实测确认了你的分类，不等于它确认了你的因果。** 新证据落进已有故事时最容易被当成补强，
  而它可能是反证。
- **写下"A 导致 B"之前，去量那条路径上真正流过的东西**（这里是：那个程序到底发了哪些字节），
  而不是去量"A 坏了"和"B 存在"。两个端点各自为真，中间可以是任何东西。

**H.9 一条把范围重述得"看起来完整"的消息，会静默撤销上一条——同一事实的两份表述，发生在我自己的出站消息里。**

> ⚠️ **严重程度更正（实施者推回，我核过树后接受了一半）**：那次追加**只花掉一个来回，没有花掉那个功能**
> ——HT/BS 在**下一个**提交里就落了（`63297417c` 里 `grep -c "pub fn backspace"` 为 0，`d0c9e413f` 里有）。
> 规则本身站得住：实施者**当时**那份报告的原话是 "I did **not** build it — out of the ruled scope"，
> 这是同期证据，比我们两边事后的回忆都强（包括它自己现在说"我读成累加的"）。
> **而"把自己的错误说得过重"本身也是一种错误**——我一小时前刚在 CHA 归因上真错过一次，最省事的
> 做法是此后照单全收每一条更正，那会同样往记录里写下一句假话。两个方向的检查是同一个：
> **回去读当时到底写了什么、树里到底有什么。**

我先发了"把 HT/BS 并进来"，随后发了"**ADD：只加 DECSC/DECRC**"外加一张 DO-NOT-ADD 清单。整体
读起来是一份**完整**的范围声明，于是它撤销了前一条——实施者的理解是对我写下的东西的正确理解，
而**真正能修好症状的那一条因此没有被实现**。

判据：**追加范围时，第二条消息必须显式承接第一条**（"在上一条的基础上再加 X"），不能重新给出
一份读起来自足的清单。凡"清单"就有整体性；一张新清单默认取代旧清单，而不是叠加。


**H.10 一个 brief 引用「照着这里写」时，要确认那个先例调的是不是同一个方法。**

我在 Task 22 的 brief 里点名用 `config.get`，并让实施者去参考 `settings/execution.rs` 的取数模式
——而那一页调的是 `execution_config.get`，一个**专用方法**。「这里有读配置的先例」和「这里有调
**这个 RPC** 的先例」是两个不同的断言，而**前者读起来就是后者**。

结果：Panel 请求 `config.get {"section":"policies.terminal"}`，而**点号路径根本不被支持**
（`"policies"` 可以，返回含默认的生效值；`"policies.terminal"` 恒返回 `{}`）⇒ 覆盖永不发生
⇒ 整个功能是个报成功的 no-op。1166 条 Panel 测试 + 4 条配置测试全绿，**没有一条看得见 RPC 形状**。

**H.11 客户端持有一份"默认值"，就是第二个真源——而它和服务端那份分歧的方向，通常正是让功能失效的那个方向。**

Task 22 的任务本身就是消灭一处双写（`CANVAS_FONT` vs `paint` 里的字面量），而**同一个任务在更高
一层又造了一处**：服务端 `DEFAULT_TERMINAL_FONT_FAMILY`（含 Nerd Font）与客户端
`FALLBACK_FONT_FAMILY`（`'JetBrains Mono', monospace`，一个 Nerd Font 都没有）。两份不一致，
而客户端那份恰好是坏的那一份。

判据：**客户端对"默认值应该是什么"不该有意见。** 兜底常量的职责是"完全没拿到答案"时用一个语法
上保证有效的串，那就该是 `monospace` 这种**显然是降级信号**的值——它不可能冒充默认栈，而一个
以纯等宽渲染的终端本身就在说"有东西没加载上"。

⚠️ **不要靠"把服务端那份抄过来"修**：那让两份**今天**一致，正是这一类复发的方式。

**H.12 一个在成功路径上也会触发的检测器，不是检测器。**

我要求「设完字体读回 `ctx.font()` 比对，不同就回落」。实施者拒绝了，理由是对的：浏览器会
**重新序列化**一个合法的字体串（比如改写引号），所以那个比较**在每一次成功调用上都会误报**。
它改用哨兵——先设一个不可能存在的字体，再设真实请求，然后看哨兵还在不在。

判据：**写下一个比较之前，先把通过路径代进去跑一遍。** 一个在成功时也会喊的检测器，会被下一个
人关掉，而它关掉的时候顺手带走了失败路径。


**H.13 在"规范说的行为有破坏性"与"什么都不做"之间选，判据是**哪一边察觉得到**，不是哪一边动作小。**

我最初把 DECRC（无存档时）做成 no-op 这条裁定记成了「破坏性 vs 惰性 ⇒ 选惰性」。实施者把它收窄成
真正的原则，而收窄之后它才是对的：

> 惰性在**这里**赢，是因为破坏性的那一支**对触发它的程序不可观测**。一个依赖 DECRC-归位的应用
> 拿到的是一个错的光标位置，它在下一次绝对移动时就恢复了；而一个盯着被打乱的屏幕的**用户**恢复
> 不了。反过来，**当规范行为有破坏性、但应用自己察觉得到并能纠正时，惰性可能更糟**——它把一个
> 可恢复的错误变成了一次静默分歧。

一句话：**问的是谁能察觉，不是谁动作少。** 「少做更安全」是个经常会错的启发式；「让察觉得到的
那一方承担错误」才是原则。

**H.14 守卫本身也会被列举法感染：三张分派表各有一条守卫，而"一共有三张表"这句话是会过期的。**

由实施者提出，是 H.1 转向守卫自身的形态。现在每张分派表（`csi_dispatch` / `execute` /
`esc_dispatch`）都有可达性守卫，且每个 `Grid` 动词目前都能在其中某张表里找到调用者——**但没有任何
东西守住这一点**。一个新加的 `Grid` 动词若忘了配分派臂，三条守卫**全都看不见它**（它们枚举的是
表，不是动词），而 `pub fn` 不会被判成死代码。

判据：**给"每个 X 都必须过闸"写守卫之后，再问一次「谁守着 X 的集合本身」**。


**H.15 一次真机验证之前要先看产物时间戳，因为「重建了」和「重建了浏览器实际读的那个」是两件事。**

差点整轮作废：服务器二进制 12:20 重建过，而 `interfaces/webchat/dist/*.wasm` 停在 09:46。
debug 构建下 `rust_embed` **从磁盘读**，所以浏览器拿到的是旧 wasm——不含任何字体改动，也不含
布局修复。那一轮的每一条字体观察都会在测量**不在产物里的代码**，而读数会长成"这些改动什么都没做"。

这是「共享 target 跑的是另一棵树的二进制」换了身衣服：**两个产物、只重建了一个，而没重建的那个
正是对面真正读的那个**。重建服务器是**直觉上的那一半，也是错的那一半**——渲染字体的不是服务器。

判据：**先看时间戳，再开浏览器。** 产物的时间戳必须晚于它所有的源文件；这个检查是免费的，而它
挡住的那一类失败，读起来和"功能没生效"逐字节相同。


**H.16 一个从未到达被测程序的探针，会给出一个干净、自信、完全错误的答案。**

由 task20-csi 记录：它第一次测 `top` 用了 `top -l 3`，那是**日志模式**——420 KB 输出、1336 个 CR、
**零个转义序列**。草草一读，结论是"top 不需要我们缺的任何东西"。

这是本轮同一族的第三个实例（我的两个：对 canvas 读 `innerText`；把行**数**当成行内容），而三次的
共同点是：**空的或干净的读数看起来像结论，而不像故障。**

判据：**一个读数如果异常地干净/空/整齐，先问"我这个探针到达被测对象了吗"**，再问它测出了什么。

**H.17 一次普查最有价值的产出，可能是它证伪了你正要写进下一轮理由里的那句话。**

我正准备把"curses 应用都坏了"当作下一轮的前提。普查测出 **`nano` 什么都不缺**——它用绝对
`CSI H` + `CSI K` 重绘而不是滚动。于是「curses 应用都坏了」这句话太宽，而 nano 成了**回归对照组**：
它今天是对的，改完之后必须还是对的。

判据：**做普查时不要只数"谁坏了"，要数"谁没坏"**——没坏的那些既是范围的边界，也是你改完之后
唯一能证明你没有把好的弄坏的东西。


**H.18 curses 程序读 `ioctl(TIOCGWINSZ)`，不读 `LINES`/`COLUMNS`——所以一个只设了环境变量的夹具，测的是回落路径，而没有回落的程序会直接退出。**

实测：btop 在只设环境变量的 pty 里**跑了 148 字节就退出**，而分类器照常打印了一份普查——那份读
起来是「btop 几乎不碰终端」。补上 `TIOCSWINSZ` 之后，同一次捕获变成 **49,667 字节**。

⚠️ 而这个夹具缺陷**存在于那一轮普查的每一次捕获里**，包括已经上报过的那几个。vim / top / nano
的数字之所以还成立，是因为那几个程序**确实**会回落到环境变量——但这是一件要去核实的事，不是可以
假设的事。**发现夹具缺陷之后回头复核已经交付的结论**，是这一步里最多人跳过的。

判据：**配置"环境"不等于配置"设备"**。凡驱动一个会自适应终端的程序，先问它是从哪里读那个尺寸的。

**H.19 一个类别的名字，如果是从"坏掉的那些例子的共同点"归纳出来的，很可能命名了错误的性质。**

我差一条消息就要把下一轮的范围写成「让 curses 应用能用」。实测推翻了这个命名：**btop 和 nano
今天就是对的**（它们用绝对定位重绘），**vim 和 less 是坏的**（它们滚动）。所以这一包不是
「全屏应用」，是**「会滚动的应用」**。

按错名字写范围，会同时（a）承诺一大堆本来就已经成立的东西，（b）掩盖真正的代价所在。
判据：**给一个类别命名之后，去测一个"按这个名字应该坏、但你怀疑它没坏"的成员。**

**H.20 一条裁定的"理由"可能被后来的测量作废，而结论看起来仍然对——理由变了就要重裁，不要继承。**

我当初把 `?25l`/`?25h`（光标可见性）排除在 Task 20 之外，理由是「快照里没有这个字段，加一个没有
消费者的字段正是 R10 要撤回的」。btop **就是消费者**，每一个全屏应用都是。结论也许仍然成立，
**但那个理由已经不成立了**。

判据：本仓已有「开工修一条在册 gap，第一步是去代码确认它还成立」；这是它的**裁定**形态——
**继承一条裁定时，要继承的是它的理由，而不是它的结论。**

**H.21 一次变异必须打在"正确实现与错误实现给出不同答案"的输入上——只是"这一行跑到了"远远不够。**

已有判据：「变异如果没打在守卫声称的那件事上，绿和瞎长得一样」。这是它的第二半，而这一半更难
察觉：**变异确实打在了那一行上，那一行也确实执行了，但你挑的输入恰好是两种实现都给同一个答案
的那一类。**

同一轮里连续两次（由 task20-csi 报告）：

- 去掉 `repair_row_pairs` 的 `c + 1 == cols` 边界，用例放在 2 行网格的**第 0 行**——那里
  `cells[start + cols]` 只是下一行那个空白首格，**有界和无界给出相同结果**，绿。这个边界
  只在**最后一行**承重（越界读出网格之外）。改到最后一行，当场 panic。
- `cursor_col.min(cols - 1)` 在那个站点是 **no-op**（`9/8+1` 与 `10/8+1` 都得 2）。改成瞄准
  真正可能被写出来的错实现（先结算挂起换行），才把 `(1,8)` 和 `(0,9)` 分开。

判据：**设计变异时先说出"这个变异会让哪一个输入的答案改变"**，然后用那个输入。说不出来，那次
绿证明的只是"我没找到区分点"，不是"守卫弱"，也不是"守卫强"。

⚠️ 而这两次的**表现完全相同**：一次绿。所以看到变异后仍然绿，第一反应不该是"守卫瞎了"，也不该
是"守卫弱"，而是**"我的输入区分得开这两种实现吗"**。

**H.22 一份为了记录"到处都是列举法"而写的普查，本身就是一次列举——而它会在写它的那个文档里复发。**

由实施者自己命名（比我的说法准确）：*"我写了一份普查，数到 `Grid` 的动词就停了，于是它读起来
是完整的，而它少了一个。这就是两轮之前我在自己的 doc comment 里抓到的那次少数一个，只是升了
一层。"* 漏掉的是 `osc_dispatch`——**第四张手写分派表**，恰恰是这个任务的全部主题。

判据：**写完一份"有哪些 X"的清单之后，问一遍"这份清单本身是怎么得来的"**。如果答案是"我把我
想得起来的都写下来了"，那它和它正在批评的那些名单是同一种东西。

**H.19 补正（由 task20-csi 收窄）：要测的不是"随便一个按这个名字应该坏的成员"，是**这个名字预测得最有把握的那个成员**。**

原判据说「给一个类别命名之后，去测一个按这个名字应该坏、但你怀疑它没坏的成员」。这不够——
「全屏应用都坏了」这个名字**扛过了前三个成员**：vim 和 less 证实了它，而 nano 没坏被读成
「nano 太简单了」。名字活下来不是因为它对，是因为反例被解释掉了。

真正推翻它的是 **btop**——进程监视器、仪表、图表，**这份名单上最忙的那一个**，即名字预测它坏得
最厉害的那个成员。它完全正确。

一句话：**一个名字如果在它最有把握的那个例子上是错的，它就是错的；而它在最弱的那个例子上是对的，
什么也没告诉你。** 挑成员时挑前者，别挑后者。

**H.20 配对项：一条裁定只有把理由写在旁边，后来的人才审得动它。**

`?25l`/`?25h` 那条陈旧裁定之所以被发现，是因为它当初连理由一起写下了（"没有消费者，所以 R10"）。
一条只记了**结论**的裁定会被静默继承——继承者读不到任何可以去核实的东西，于是它只能照办。

所以 H.20（继承理由，不继承结论）有一个前置条件：**记录裁定时必须记录理由**。两条合起来才成立：
写的时候把理由写下，读的时候核理由而不是核结论。

**H.21 补正（由 task20-csi 拆分）：变异之后仍然绿，有**两种**成因，修法相反——而第二种更容易被漏掉。**

我原来把它写成一条（"输入区分不开"）。它的两个实例其实不是同一种失败：

**（一）输入区分不开这两种实现。** `repair_row_pairs` 去掉边界之后放在第 0 行——有界和无界在
那里真的给同一个答案。**修法：换输入**（最后一行）。

**（二）你的"错误实现"根本没错。** `cursor_col.min(cols - 1)` 算的是 `9/8 + 1 = 2`，原式算的是
`10/8 + 1 = 2`——同一个制表位、同样钳到 9。**那是一次等价改写**，**没有任何输入区分得开它**，
因为它们之间没有区别。**修法：换变异**（改成语义上真的不同的实现——先结算挂起换行）。

所以变异变绿之后要问的是**两个**问题，且修法不同：

1. **我的输入区分得开这两种实现吗？** 区分不开 → **换输入**。
2. **这两种实现真的不同吗？** 不同不了 → **换变异**。

⚠️ 第二种更容易漏，因为**它看起来完全像你确实变异过了**：diff 是真的、代码编译了、测试跑了，
于是自然的结论是"守卫弱"或"输入不对"——而事实是**你把同一个函数写了两遍**。而且**"看起来不一样"
的算术正是等价改写的藏身处**。

**H.23 「这个二进制是哪棵树编出来的」不由时间戳回答，也不由构建日志回答——由**只有那棵树造得出来的一个值**回答，从产物里 grep 出来。**

本轮实测：worktree 里**根本没有 `target/` 目录**，机器上唯一新鲜的 `aleph-server` 在**主检出**的
target 树里。按时间戳读，它是新的；按目录读，它属于另一棵树——正是那条「共享 target 的第二棵
worktree 跑的是第一棵的二进制」的疤。

判据是把「照妖镜」从**机器身份**推广到**树的身份**：

```
strings target/debug/aleph-server | grep -c "Hack Nerd Font Mono"   →   3
```

`Hack Nerd Font Mono` 只存在于这条分支**未提交的** `terminal.rs` 里——**别的树造不出这个字符串**。
所以它同时是断言和身份证。wasm 那半的对应值是 `render.rs` 里的
`aleph-terminal-font-probe-sentinel`。

三层强度，逐层更贵也逐层更真：

1. **时间戳** —— 只答"它比源文件新吗"，答不了"它是谁"。
2. **产物里的标记字符串** —— 答"这些字节是从哪棵树来的"。两次 grep，挡掉整整一类。
3. **问正在跑的那个进程** —— `config.get {"section":"policies"}` 必须回出那份 Nerd Font 列表。
   **一个二进制可以在磁盘上是对的，而不是正在你端口上监听的那一个。**

判据：做真机验证前，**给每一个参与的产物找一个"只有这棵树造得出来"的值**，并且在开浏览器之前
把它们都 grep 一遍。种一个别处不可能有的值，它同时是断言和身份证。

**H.23 补正（由 task17-panel 加固）：一次标记 grep 需要它的**反向对照**，否则"匹配到了"证明不了那根针有区分力。**

我只要求了两条正向 grep。它跑了四条，补上两条**反向对照**：

```
server  "Hack Nerd Font Mono"                 -> 3   预期存在
server  "aleph-terminal-font-probe-sentinel"  -> 0   预期不存在（Panel 专属）
wasm    "aleph-terminal-font-probe-sentinel"  -> 1   预期存在
wasm    "Hack Nerd Font Mono"                 -> 0   预期不存在（服务端专属）
```

**那两个 0 才让那两个非 0 有意义**：它们证明这两根针**区分得开**。只做正向的标记检查分不出
「产物是对的」和「这根针太常见、匹配什么都命中」，也分不出「针拼错了」和「它真的不在」——
后两者都印 0，而只做正向的人根本不会去看 0。

这与本仓已有的「一条负向断言，先证明它找的那个字符串**有可能**出现在这份 payload 里」是同一条
规则的两半：**正向断言欠一个反向对照，反向断言欠一次锚定。** 两半都做，一次 grep 才是一次测量。

**H.24 一条被明确标注为"预测"的结论，必须真的有人回去测它——否则那个标注只是把它换了个名字继续用。**

**H.23 再补正（两处，由 task20-csi 更正我）：**

**（一）`strings <路径>` 回答的是「这个**文件**是哪棵树造的」，回答不了「这个**进程**在跑哪些字节」。**

macOS 上**替换二进制不会改变一个活着的进程的镜像**。实测两者已经差了一小时：

```
running process pid 79870 started   12:20
binary on disk mtime                13:16
```

所以我对着路径跑的那次 grep，描述的是**那个正在跑的服务器从来没有执行过的字节**。判据保留，但
**把它的主张限定在文件上**，并补上中间那一层：

1. `strings <路径>` → **这个文件出自哪棵树**
2. **进程启动时刻 > 二进制 mtime** → **这个进程跑的是不是那个文件**（最便宜的一层，也是我漏掉的）
3. 问正在跑的那个进程（`config.get`）→ 最终那一层

第 2 层没有 `strings` 版本的答案：文件被替换之后，**进程自己的镜像是唯一的证人，而它在磁盘上没有名字**。

**（二）worktree 里没有 `target/` 是**预期行为**，不是那条疤。** `git worktree` 默认共享父检出的
target 目录。那些构建是真的（`alephcore` 一到三分钟的编译，不是 1.41s 的缓存命中），只是**落进
了共享树**。我记得的那条疤是「**陈旧**的二进制被复用」；这里是「**几棵树写同一个目录**」——
**危害不同：后写者胜出，且无声**。

**H.26 一个产物的文件名是它作者挑的一个标签，不是身份证明——而下游读者分不出这两者。**

实例：Task 20 的复审者从 `task-22-brief.md` 里抄了一段重启服务器的配方，于是日志叫
`aleph-server-task22.log`。下游读者据此把那个服务器归给一个**根本不存在的 agent「task22」**，
并把它写进了一份告警。我差一点原样转发。

判据：**归属要从进程树 / 端口 / 会话 id 去查，别从文件名推。** 反过来，**给临时产物命名时用你
自己的名字**——你省下的那几个字符，会变成下一个人的一次错误归因。

**H.27 一条按"进程名/二进制路径"匹配的 `pkill`，在多 agent 共享一台机器时是一件**共享命名空间
的武器**——它杀的是所有人的，而不是你的那一个。**

实测：`pkill -f 'target/debug/aleph-server'` 匹配的是**二进制**，不是你的日志路径。于是一个只想
重启自己服务器的 agent，顺手杀掉了另一个 agent 正在跑真机验证的服务器；而后者看到的症状是
**端口上什么都没有**，读起来像产品缺陷。

判据：**按 PID 杀，不按模式杀**；重启前先看端口上是谁；per-agent 的日志路径**不构成隔离**（模式
匹配的是二进制）。而共享一个 flock（`~/.aleph/data/aleph.lock`）意味着**先启动的赢**，输的那个
的失败也会读起来像产品缺陷。

**H.26 补正（两层，第二层是我自己犯的）：**

**（一）当一个**标识符**和一个**标签**并排出现在同一个字符串里，读起来有意义的永远是标签——因为
标签本来就是写给人读的，而标识符看起来像噪声。**

由 task20-csi 自陈：那条日志路径它逐字引用过，判据就在它已经拿在手上的那个字符串里——

```
/private/tmp/.../1031521d-a454-4589-b1f6-a597c0b4e6dc/scratchpad/aleph-server-task22.log
                 ^^^^^^^^ 机器分配的会话 id            ^^^^^^^ 人挑的文件名
```

它读了文件名。这与「读二进制路径上的标签而不去问进程」是同一个反射，高了一层：**总是伸手去够
那个人类可读的产物，而不是那个权威的产物。**

**（二）⚠️ 但这条升级有一个尽头，而我一头撞了上去：进程树在 in-process 子代理之间**根本没有
区分力**。**

我据「会话 id 前缀吻合」断定那个服务器是复审者起的，**并把这个推断当成测量报给了两个 agent**。
去查进程树想坐实它——`ps` 一路走到 pid 12660：`claude --dangerously-skip-permissions`，昨天
08:02 起。**整支队伍住在同一个 OS 进程里。** `ps` 认得出**二进制**，认不出**agent**。

于是「别读标签，读标识符」这条升级在 agent 这一层**走到了头**：外部看不到任何权威标识符，
**唯一可靠的来源是那个 agent 自己对它跑过什么的陈述**——而那正是我推翻掉的那份证词。

判据两句：① **能区分机器和树的工具，未必在 agent 这一层有答案**；② **推断和测量的区别，要写在
你转述它的那句话里**——我这次的代价比我刚表扬它抓到的那次大：它错的是一份告警里的一个名字，
我错的是往两个 agent 手里塞了一条假事实。

**H.28 一个出不了阴性结果的仪器，还没有被证明是仪器。**

由 task20-csi 统一命名，把两条判据收成一条：**不可证伪的探针**（只做正向的标记 grep）与**等价
改写的变异**（H.21 第二种），**是同一个错误的两件衣服**。

- 两条正向 grep 只证明那两根针**被找到了**；
- 那两个 0 证明它们**有可能找不到**——这才让前两条有意义。

没有阴性对照，「标记存在」与「这根 grep 对着什么都命中」是同一个读数。没有区分性输入，「变异后
仍绿」与「我把同一个函数写了两遍」是同一个读数。

**H.24 补正（由作者本人收窄）：欠条要在它**离开被标注的那份文档之前**兑现，不是在有人依赖它之前。**

原句是"进入任何裁定的前提之前必须兑现"。它指出为什么那太晚：**警告由散文承载，前提由决定承载**。
标注一直老老实实贴在那句话上，而那句话搬进了另一份文档的前提里——**标注没跟过去，因为决定不
携带散文**。所以 `top` 应该在写下那条 caveat 的当天就测，而不是在一条裁定引用它的时候。

**H.27 补正：重启之后也要看端口，不只是重启之前。** flock 的输家**安静地退出**，所以「我启动了
一个服务器」和「有一个服务器在监听」是两个不同的说法，而两者之间那道缝正是一次假交接的产地。

**H.29 一个标识符可以对**排除**有效，同时对**归属**无效——而这两半读起来是同一次比对。**

由 task20-csi 自陈（它先给了我"去比会话 id"这条建议，然后发现这条建议坏在它真正需要的那一半上）：

- 「这个会话 id 和我的不同」→ **可靠地成立**：**不是我起的**。
- 「这个会话 id 等于某某」→ **不成立**：我拿同一个 id 去和一个 spawn id 做前缀匹配，**得出的归属
  是错的**。

**同一次比对，一半是证据，一半是猜测。** 所以它那条告警本该写成「**一个不是我起的服务器**」然后
就停住——那句话它手上的证据完全支持；再往后的名字与叙事（"task22 跑了 pkill"）在它可及的**任何
一层**都没有支持，而它和有支持的那半在同一口气里说了出来。我随后继承了那个形状。

这是「阴性对照」判据掉转枪口对准自己：**它的仪器只可能读出"不是我的"，而它从一个没有阳性读数的
仪器上读出了一个阳性识别。**

判据：**说出一个归属之前，问"我这件仪器有没有阳性读数？"** 没有，就只报排除，并把句子在那里
截断。

**H.30 当只有证词能归属时，要么去取证词，要么只报排除——不要广播猜测。**

H.26（二）说进程树在 agent 这一层没有区分力，那不是一条注意事项，那是**天花板**：「别读标签、
读标识符」这条升级**在这一层没有下一级可爬**。

于是这一层的规则不是"找一件更好的仪器"，而是：**唯一能归属的东西是那个 agent 自己的陈述。**
而它（和我）**手上都有 SendMessage 通道**——用它去广播了一个猜测，而不是用它去问一句。

判据：**归属不确定时，那条消息应该是一个问句，不是一个断言。**

**H.31 「只读」是**你启动的那个进程**的性质，不是**你打算做的那个操作**的性质。**

我给真机清单画隔离边界时是这么推的：十一条里九条只读、一条写配置，**所以只有第 10 条需要隔离
home**。这条推理**每一步都对，而结论是错的**——因为 `aleph-server` **一启动就重写操作者真实的
`~/.aleph/config.toml`**，与任何一条检查请求它做什么无关。

实测（今天四次重写，文件比 8月27 少了 537 字节）：

```
~/.aleph/config.toml                        13:27, 22461 B
~/.aleph/backups/config.toml.…101510067     8月27 的那份, 22978 B
                 …101611251 · …132723389 · …133259353
```

diff 出来是**一次序列化往返**、功能上惰性：**等于默认值的键被丢掉**（`theme = ""`、整个
`[policies.retry]`、`target_*_ms`、`content_selectors`、`follow_redirects`、`max_redirects`），
`[[agents.list]]` 里被显式写上 `default = false`。没有任何设置改变了取值——文件被**归一化**了，
不是被损坏。而这正是本仓已知的那条（`Config::load()` 在配置缺失时会**写**默认配置），我只是没有
把它带进一份 QA 计划。

判据：**画隔离边界之前，问的不是"我这一步要写什么"，而是"我启动的这个进程会写什么"。** 线要画在
**进程**外面，不是画在**操作**外面。⚠️ 而这一类的隐蔽之处在于**它的推理链是对的**：逐条检查确实
九读一写，错的是把"检查"当成了副作用的边界。

顺带一条：**这次没造成损失，是因为那次重写恰好是幂等的归一化**——如果被丢掉的是"看起来像默认值
但其实是用户显式写下的"那种键（同一个值，但意图是"钉住它"），文本上的丢失就会变成语义上的丢失，
而两者在 diff 里长得一模一样。

**H.32 一个**有损**的可观测量，会把许多种错误实现映射到同一个正确答案上——所以断言落在有损量上时，
输入必须专门挑那些让错误实现落到**不同**输出的那一小撮。**

由 task20-csi 给出 H.21 反复复发的**结构性**原因，而不是数它犯了几次：

> **制表位是一次向下取整的除法，而向下取整是有损的**，所以任何以制表位为可观测量的测试，都有
> 大量错误实现映射到正确答案上。**具备区分力的输入是这个空间里的少数。**

实测的算术：制表位每 8 列。**两个**宽字形 → 正确推进 4、错算 2，`4/8` 与 `2/8` **都向下取整到 0**，
都跳到第 8 位 ⇒ 变异不可见。**四个**宽字形 → 8 与 4，`8/8=1` 跳到 **16**、`4/8=0` 跳到 **8** ⇒ 区分开了。
而 `中文` 比 `中文表格` 更"自然"，所以**自然的选择恰好是错的那个**。

这一条推广到制表位之外：**向下取整 / 钳位 / 饱和 / 取模 / min-max / 哈希**——任何把定义域压缩的
可观测量都有这个性质。判据：**写断言前先问"我这个可观测量是不是有损的"**；是的话，**输入不能随手挑**，
要挑一个让正确实现与错误实现落在不同输出上的。

⚠️ 配套的第二问（因为它在这里差点又出一次）：**把输入换成有区分力的那个之后，这条测试还测不测
得到它当初为之而写的那件事？** 一条为了变得有区分力而改掉输入的测试，可能悄悄不再测原来那件事。

**H.33 跨两次运行去比较一个数字，等于没有测量它——而这一族的症状是「我说不出第七个是谁」。**

由作者自陈，而且他一小时前**刚警告过我同一件事**：他从一次 `cargo test` 读到失败**计数**（7），
从**另一次**读到失败**清单**（6 条），于是那次不一样的输出在他察觉之前已经消失。三次后续**已捕获**
的运行都是 6/17481，算术也对得上（17480+7 与 17481+6 都等于 17487）——但**他说不出第七个是谁**，
所以他把它作为未解释项报了上来，而不是圆成「偶发、无关」。

判据两句：① **一个数字和它的明细必须来自同一次运行**，否则两者之间的差额没有任何证人；
② **一个你解释不了的数字，不该被当成稳定的数字呈现出来**——而「六条是已知的预存失败」这句话，
正是这类第七个最容易藏进去的地方。

**H.34 在多 agent 共享的工作区里，「读那个文件」是一个不可靠的预言机——权威的是 git，不是磁盘。**

刚刚差一步把一次**活的变异**报成生产缺陷。编译器警告 `function run_font is never used` 是**真的**，
我去读 `paint`，读到的是：

```rust
ctx.set_font(&format!("{}px MyCustomFont", m.font_px));   // 工作区当前状态
```

一个硬编码的、不存在的字体族——看起来整个字体功能在 `paint` 里是惰性的，而且那条
`paint_never_states_a_font_family_literal` 守卫**正在放行它自己禁止的那个字面量**。四条并成一条
完美的缺陷叙事。

去查 git：**提交里那一行是 `ctx.set_font(&run_font(&m, run.attrs));`**，完全正确。`MyCustomFont`
是评审者为了检验那条守卫**此刻正在做的变异**。

判据：**一个共享工作区里，另一个 agent 正在变异的文件，其磁盘内容是一个瞬时状态，不是代码。**
写下「这段代码有缺陷」之前，先 `git status`，再从**提交的那个 blob** 读
（`git show <sha>:<path>`）。⚠️ 这与之前五次「rust-analyzer 幻影错误」**不同族**：那五次是量具坏了，
这一次**量具完全正确**——警告是真的、文件内容是真的，**只是它描述的那个世界会在两分钟后消失**。

**H.35 `cmd | tail` 会吞掉退出码——所以「exit code 0」可以和「FAILED」同时出现在同一次运行里。**

后台任务通知报告 `completed (exit code 0)`，而输出里写着：

```
test result: FAILED. 0 passed; 1 failed; 0 ignored; 17503 filtered out
error: test failed, to rerun pass `-p alephcore --lib`
[exited with code 0]
```

管道的退出码是**最后一段**的（`tail` 成功了）。判据：**读输出，别读退出码**——尤其当你为了截断
而加了管道的时候。本仓已记过这条，今天又中一次；**记下一条判据不等于会绕开它**。

**H.34 补正（由 task20-csi 从另一侧独立撞到）：变异窗口的危害是**对称且双向静默**的，而且「这棵树现在是故意坏的」这件事对任何读它的人都不可见。**

我从"读到一个缺陷"那一侧撞到它；它从"读到一个残留"那一侧撞到同一件事——它看到 `grid.rs` 里带着
`// MUTATION M1` 的注释，**差一条消息就要报告"有个变异被遗弃在树里"**，三分钟后 `grid.rs` 已还原、
`perform.rs` 变成修改态。**它抓到的是一个移动的目标，而它差点把一张快照报成一个状态。**

对称的两个方向，**两个都静默**：

- **脏读** → 看起来是一个真缺陷，而且**手里还有一份 diff 可以"证明"它**（我这一侧）
- **净读** → 看起来是一次通过，而它只是**恰好落在两次变异之间的窗口里**（它这一侧）

⚠️ 推论：**在别人跑变异循环期间，你的所有测量都不可按需复现**——不是关于代码的新不确定性，是
**这棵树此刻是别人的仪器**。

约定（与「按 PID 杀，不按模式杀」同族）：**要么变异循环跑在私有 worktree 里，要么宣布窗口的起止。**

**H.36 「永不 `git add -A`」这条规矩，今天挡下的是一次把别人的变异提交进去的事故。**

我在另一个 agent 正在循环变异的**同一分钟**提交了文档。因为逐个文件点名（三个 doc 文件），
`render.rs` 里那句 `MyCustomFont`、`grid.rs` 里那句 `cursor_col += 1` 都留在了工作区。

**换成 `git add -A`，那两句会带着一条读起来完全正当的提交信息进入历史**——而它们的作者当时正
准备把它们还原掉。判据不是"要小心"，是**规矩本身就是那道闸**：逐文件点名让"树此刻是别人的仪器"
这件事**不需要你知道**也伤不到你。

**H.36 补正（由 task20-csi 更正，而它更正的是它自己那次提交）：`git add <file>` 保护的是你**没有**点名的那些文件——它保护不了你点名的那一个。**

我把「逐文件点名」当成了那道闸的全部。它指出只是一半：

- **`git add <file>` 逐个点名** → 保护你**没点名**的文件（我这一半，而它确实起了作用）
- **提交前读 `git diff --cached` 的**内容**** → 唯一能保护你**点了名**的那个文件

而它是拿自己开的刀：`05b7bf266` 按名字暂存了 `perform.rs`，**而复审者的变异循环动的正是那个文件**。
它事后去查提交的 blob——干净的。**但那是运气，不是流程**：它提交前跑的是 `git diff --cached --stat`，
**而 `--stat` 给的是改动的形状，不是改动本身**，所以它结构上看不见一个混进被点名文件**内部**的
外来变异。

⚠️ 缺失那一半的失效形态：**一次读起来完全正当、而作者是错的人的提交。**

判据：在别人的变异窗口里提交，**逐文件点名 + 提交前按内容核对**，两半都要。而 `--numstat` 里
**「零删除」是一个便宜的旁证**（外来变异通常表现为删除+插入成对出现），但它不是内容核对的替代品。

**H.36 再补正（同一位，第三次修同一条规矩）：`--numstat` 的「零删除」旁证，只挡得住外来**替换**，挡不住外来**追加**——而它最弱的地方，正是我用它的那个地方。**

- 一次**变异**通常是替换一行 ⇒ `-1 +1` ⇒ 零删除排除得掉它。
- 一次**追加**是纯插入 ⇒ 与你自己的插入**逐字节同形** ⇒ 零删除对它完全失明。

而我用它的那三个文件是 `CLAUDE.md` / `FEATURE_LOCATOR.md` / 一份判据笔记——**doc 文件，正是别的
agent 的编辑会以「追加」形态出现的地方**。所以在那次提交上，这个启发式处于**最弱**而不是最强。
它强的地方（源码文件、变异循环中、变异是替换）恰恰是我用不上它的地方。

判据：**这与「出不了阴性结果的仪器」同族**——一件只能探测两种到达方式之一的仪器，在另一种上
静默。写下一个旁证时，说出**它探测得到哪一半**，以及**你手上这个案例落在哪一半**。

⚠️ 元观察（由它提出）：这是今天第四次「窄证据、宽陈述」，而且是第一次那个宽陈述不是一个**事实**、
而是**一个启发式的适用范围**。这支持把它读成结构性的：**一个启发式本身就是一句关于测量的话，
而压缩就发生在同一个地方。**

**H.37 一条守卫可以验证「那个正确的东西在场」，而完全不验证「它是唯一的贡献者」——而拼接式的违规
正好落在这条缝里，同时对守卫和编译器不可见。**

`paint_never_states_a_font_family_literal` 的三次实测：

```
'JetBrains Mono', monospace  重新写回              -> FAILED   守卫开火
format!("{}px MyCustomFont", m.font_px)           -> ok       守卫失明（无引号、无 monospace）
format!("{}px {}, ExtraSplicedFallback", m.font_px, m.font_family)
                                                   -> ok       守卫失明（**更危险的那个**）
```

第三种是设计修复时要瞄准的那个：**守卫验的是 `m.font_family` 被引用了，它从不验证
`m.font_family` 是那张字体族清单的唯一贡献者。** 而且拼接**不移除 `run_font` 的调用点**，所以让
第二种露头的那条 `run_font is never used` 警告在这里**也不会响**——**同时对守卫和编译器不可见**。

判据两句：① **「在场」检查不是「唯一」检查**——凡守卫的形式是「必须引用 X」，去问「引用了 X **并且
另外还加了点别的**会怎样」；② 这一族**不可能用更长的黑名单关掉**，只能翻成正向规则（断言那个字符串
的整段**恰好等于**那个合法生成器的输出）——**这是"停止列举"这条判据最干净的一次演示：黑名单在这里
不是弱，是结构上不可能。**
