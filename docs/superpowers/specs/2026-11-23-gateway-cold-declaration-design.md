# Gateway cold channel declarations / Gateway 冷通道声明

**Design at `4f966eaf6`; not a statement of current wiring. / 基于 `4f966eaf6` 的设计，不代表当前生产接线。**

## Intent / 意图

A configured channel must be discoverable before it has a runtime. Today the generic boot loop evaluates `enabled` after vault hydration and factory construction; Signal already owns a `reqwest::Client` at that point. `channel.create` persists `enabled=false` but still tries to construct and start the channel. Make explicit disablement cold at those two boundaries without changing who can start, send to, or manage a channel.

已配置的通道应在没有运行实例时也可发现。当前通用启动循环在从 vault 补齐密钥、调用工厂之后才判断 `enabled`；此时 Signal 已经持有 `reqwest::Client`。`channel.create` 保存 `enabled=false` 后仍尝试构造并启动。首轮让这两个入口尊重显式禁用，但不改变谁有权启动、发送或管理通道。

## Alternatives / 方案选择

| Approach / 方案 | Trade-off / 取舍 |
| --- | --- |
| **Gateway cold declaration (selected) / Gateway 冷声明（已选）** | Reuses Config, Gateway RPCs, and `ChannelRegistry`; fixes real boot/create effects. Does not itself mount a Gateway backend in Zahir. / 复用配置、Gateway RPC 和 `ChannelRegistry`，修复真实的启动和创建副作用；不等于接通 Zahir 的 Gateway backend。 |
| Bound Webhook projection / Bound Webhook 投影 | Advances Capability discovery and generation checks, but its constructor is already HTTP-client cold and the pilot does not fix the wider boot/create path. / 更直接推进统一发现和代际校验，但它的构造本就不创建 HTTP client，试点也不会修复更广的启动和创建路径。 |
| External Terminal artifact / Terminal 独立制品 | Can prove the Core artifact does not link a native implementation; adds IPC and platform packaging work before fixing incumbent channel behavior. / 可验证 Core 制品不链接目标原生实现，但要先承担 IPC 与跨平台打包成本。 |

Pi separates resource selection, module execution, and session loadout; deepseek-harness separates profile selection, loader/Fiber activation, and temporary `define`/`run`. Neither makes ordinary in-process providers unloadable native artifacts. Borrow those phase boundaries, not a second plugin framework or an automatic install step. See Pi `packages/coding-agent/src/core/{resource-loader,agent-session-runtime}.ts` at `4ea883792` and deepseek-harness `vendor/{loader/src/config/entry.ts,cordis/src/fiber.ts}` at `fcc0ad4621`.

Pi 把资源选择、模块求值、会话工具投影分开；deepseek-harness 把 profile 选择、Loader/Fiber 激活和临时扩展 `define` / `run` 分开。普通进程内 provider 并未因此成为能卸载的原生制品。Aleph 借用阶段边界，不引入第二套插件框架或隐式安装机制。

## Behavior and authority / 行为与权威

| Surface / 入口 | Contract / 契约 |
| --- | --- |
| Boot / 启动 | An exact JSON boolean `enabled=false` prevents per-instance vault hydration, runtime factory/constructor, tracker creation, registration, and automatic start. Check before the generic and iMessage/BlueBubbles branches. Missing, true, or non-boolean values follow the pre-existing platform path and validation; do not redefine iMessage's missing-value behavior. Factory registration itself is static metadata/wiring and remains. / JSON 布尔值 `false` 在通用与 iMessage/BlueBubbles 分支之前阻断该实例的 vault 密钥注入、工厂/构造、tracker 建立、运行实例注册和自动启动。缺省、`true`、非布尔值仍走原平台路径及现有校验，不重新定义 iMessage 的缺省语义；静态工厂注册保留。 |
| `channel.create` | Persist a secret-free declaration first. If explicitly disabled, return `{id, type, status: "disabled"}` without vault hydration, construction, registration, or start. Deliberately supplied secrets may still be **written** via existing vault storage; disabled read paths do not fetch them. Reject an existing ID whether live or config-only, including two creates of one cold ID; check config membership under the config write lock before processing secrets. Existing entries are edited through the existing settings flow, not overwritten by create. Preserve enabled/default response shapes and failure behavior. / 先持久化不含密钥的声明。显式禁用返回 `{id, type, status: "disabled"}`，不注入密钥、不构造、不注册、不启动；请求主动提交的密钥仍可通过现有 vault **写入**，冷读路径不读取。存在同 ID 的运行实例或配置均拒绝；写锁内在处理密钥前检查配置，覆盖同一冷 ID 的并发 create。已有配置通过现有设置流程编辑，不能用 create 覆盖。已启用/缺省的响应结构及失败行为不变。 |
| `channels.list` / `channels.status` | Registry status wins for an existing runtime entry. Otherwise project an explicitly disabled declaration directly from current Config as `disabled` with no claimed runtime capabilities; resolve type using the same rules as boot. Unknown IDs keep `channels.status` not-found; other uninstantiated entries keep existing pending-list and status behavior. Count projected disabled rows once in list `total`/`disabled`; preserve legacy pending-row counting and other summary fields. No factory, vault, owner transition, or network work on reads. / 有运行条目时以 registry 状态为准；否则直接从当前 Config 投影显式禁用声明，返回 `disabled`，不宣称有运行能力；类型与启动共用解析规则。未知 ID 仍返回 not-found；其他未构造条目保留原 pending 列表及 status 行为。列表总数和禁用数对禁用投影只计一次，既有 pending 计数及其他汇总语义不变。读取不调工厂、不碰 vault、不推进 owner、不走网络。 |
| `channel.start` | Keep the existing authorized explicit start for factory-supported adapters, including Signal. It may activate a declaration without flipping `enabled` on disk. If the ID has config but no registered instance, parse its effective inbound policy and prepare its transport from the **same latest Config snapshot**, even if `enabled` was edited since boot. Invalid policy rejects the start without publishing a runtime or opening ingress. Apply valid policy under the requested, factory-confirmed instance ID before the first inbound event can be forwarded; do not inherit another instance's policy or fall back to starting another ID. Preserve incumbent restart behavior and the current iMessage/BlueBubbles factory limitations. / 工厂已支持的平台（含 Signal）继续通过现有授权的显式 start 激活，不修改落盘的 `enabled`。目标有配置、无运行实例时，从**同一份最新配置快照**解析入站策略并准备 transport，即使 `enabled` 在启动后已被改过。策略无效则拒绝启动，不发布运行实例、不开放入站。有效策略必须在首条入站消息可转发前按工厂确认的请求实例 ID 生效；不借用其他实例的策略、不回退启动其他 ID。保留已有运行实例的重启行为和 iMessage/BlueBubbles 的现有工厂限制。 |
| Stop, send and delete / 停止、发送与删除 | A cold declaration does not become callable by being visible. Send, pairing, and stop keep their runtime-only behavior; delete already accepts config-only IDs and must not instantiate one. Disabled config is not a command to stop a running channel. An explicitly started adapter uses incumbent stop/restart semantics; this slice does not promise it becomes cold again after stop. / 可见不等于可调用；发送、配对和停止仍只操作运行条目。现有删除入口支持只在配置中的 ID，不应制造实例。禁用配置不是对运行中实例的停止指令；显式启动后沿用现有 stop/restart，不承诺停止后重新变冷。 |

`Config` owns declarations; `ChannelRegistry` owns instantiated channels and effects. A read-side union is not stored and creates no new state owner. Keep existing authorization and wire method names. Emit no new notifications and do not imply cold entries are subscribed through Zahir or represented as live entries in existing registry subscriptions.

`Config` 管声明，`ChannelRegistry` 管运行实例及实际 effects；读侧合并不持久化，不引入新 owner。保留现有授权和 RPC 名称；不新发通知，也不声称冷条目已纳入 Zahir 订阅或 registry 的运行条目订阅。

## Wiring and cleanup / 连线与清理

1. Reuse the type-resolution rule in `src/config/structs.rs::Config::resolved_channels` for individual declarations, and derive the explicit-disable predicate once for boot/create/read rather than copying `enabled` checks into each handler. Keep established list behavior for other config rows. / 复用配置的类型解析，按 ID 也能取得同样的声明；显式禁用判据只保留一份，不在各入口重复；其他配置项沿用列表既有表现。
2. Move the automatic activation decision ahead of effects in `src/bin/aleph-server/commands/start/builder/subsystems.rs::initialize_channels` and `src/gateway/handlers/channel.rs::handle_create`; delete the superseded post-construction decision. Keep public registry boot behavior that still serves bound/compatibility callers and preserve enabled platform setup, including Telegram catalog and offset wiring. / 将自动激活判据移到副作用之前，删除构造后才读取的旧判据；保留仍有调用者的 registry API 和启用平台原有装配，包括 Telegram catalog 和 offset。
3. Split boot policy projection from live activation. At boot, a cold row projects its existing credential-free common policy fields under its declared ID, preserving valid tool denies for resume/goal-wake continuations. It does **not** need transport policy: skip the Telegram/Feishu boot branches that hydrate secrets for that policy, and do not pick a live sibling's ID for a cold row. Leave enabled boot behavior intact. / 区分启动时的策略投影和运行实例激活：冷声明按自身 ID 投影已有的无凭证通用策略字段，保留 resume/goal-wake 所需的有效工具拒绝规则；冷时**不需要** transport 策略，跳过为此读取 Telegram/Feishu 密钥的启动分支，不把冷声明的策略写到另一运行实例上。已启用平台的启动行为不变。
4. For a config-only explicit start, reuse the existing policy parsers and reducers (including Telegram legacy/V2, Feishu access, common slash/tier/workspace/busy/tool settings, and pair-loop overrides where configured). Validate instead of defaulting malformed policy to permissive values. Publish through the existing Gateway policy path before ingress; permission checks, slash commands, execution identity, and system continuations must not use stale or independently maintained policy for this activated ID. This requires wiring the existing read-side policy projection to the start RPC, not creating another authority. Reuse the existing lifecycle publication boundary so a refused registration cannot apply policy to an incumbent or start it as a fallback. / 冷声明显式启动时，复用现有策略解析和推导（包括 Telegram 旧版/V2、Feishu access、通用 slash/权限层级/workspace/busy/tool 配置，以及已设置的 pair-loop override）。校验失败不能退回宽松默认值。入站前通过现有 Gateway 策略链路发布；权限、slash 命令、执行身份和系统续跑不能对该 ID 继续读旧策略或独立维护的副本。这需要把现有策略投影接给 start RPC，不引入新权威；复用已有生命周期发布边界，注册被拒时不能把策略写给原实例或回退启动它。
5. Reuse one config-only response shape in list/status; wire the existing Config handle into `channels.status` registration in `src/bin/aleph-server/commands/start/builder/handlers/session.rs`. Current references go in `docs/reference/{FEATURE_LOCATOR,GATEWAY}.md`; this dated design remains evidence. / list/status 复用配置条目的响应形状；为 `channels.status` 注册连上既有 Config handle。现状写入 `FEATURE_LOCATOR.md` 与 `GATEWAY.md`，本设计只作为时点证据。

The security boundary is activation, not configuration discovery: a malformed declaration remains visible and repairable, but cannot open ingress. The builder chooses how to share the existing policy projection and observe factory calls in tests. This design adds wiring between activation and policy publication; it does not introduce hot reconfiguration for already-running instances. No new dependencies, capability kind, runtime/supervisor, transport, or UI work. Do not redesign general concurrent start/delete or reconnection.

安全边界在激活，不在发现：配置错误的声明仍可见、可修复，但不能开放入站。由实施者决定怎样共享现有策略投影、怎样在测试中观察工厂调用。本方案增加激活与策略发布之间的连线，不实现运行中实例的热更新。不加依赖、不加 capability kind 或 supervisor、不引入新传输、不改 UI，不重构通用 start/delete 并发模型或重连。

## Verification / 验收

- Exercise real composition/RPC and the real Signal factory against a disposable, isolated config and local service. Show boot/create of a valid disabled Signal do **not** cross the constructor boundary, publish a registry instance, or contact upstream; `list/status` report `disabled`, and `send` does not activate it. No network requests alone is insufficient: the Signal constructor already allocates a client without sending. / 用隔离配置、本地服务、真实装配/RPC 和 Signal 工厂验证：禁用的有效 Signal 在 boot/create 不跨过构造边界、不发布实例、不触达上游；list/status 可见，send 不激活。只有零网络请求不够，因为构造 HTTP client 本就不要求发请求。
- Run the positive control: omission/`true` still reaches the previous boot/create start path. An authorized explicit Signal start from boot- or RPC-created cold state constructs the right ID, attempts its normal transport work, and does not persist `enabled=true`. Exercise duplicate create, invalid/unknown status, and deletion of a config-only row. / 验证缺省/`true` 仍走原路径；对启动或 RPC 创建的冷 Signal，授权 start 真正构造目标 ID 并执行正常 transport 工作，不写回 `enabled=true`。覆盖重复创建、非法或未知 status 请求和删除冷声明。
- Verify that cold Telegram/Feishu boot does not hydrate secrets and valid continuation tool denies remain in effect. Test both a disabled declaration created after boot and a boot declaration whose policy was tightened after boot: their first inbound event must see the latest policy, including settings not overridden by Telegram's per-account routing. Invalid policy must return a start error with no runtime publication or ingress; a cold alias must not alter a live sibling. Exercise the enabled boot control and explicitly disabled iMessage gate; don't present a gate test as cross-platform transport QA. / 验证冷 Telegram/Feishu 启动不注入密钥，且续跑仍保留有效的工具拒绝规则。分别验证启动后创建的禁用声明，以及启动后收紧过策略的冷声明：首条入站必须看到最新策略，包括 Telegram 按账号路由不会覆盖的字段。无效策略必须令 start 返回错误、不发布实例、不开放入站；冷别名不能改变同平台已有运行实例的策略。验证已启用启动对照和显式禁用 iMessage 的启动闸门，不以闸门测试冒充跨平台传输 QA。
- Run targeted Cargo tests, build the server, and use the repository wiring/doc checks. Record the actual runtime and unrun checks, not just source-order assertions. / 执行定向 Cargo 测试、构建 server，运行仓库接线和文档守卫。记录实际运行结果与未跑项，不能只靠源码顺序断言。

All edits and commits stay on the isolated worktree branch; no main changes, merge, or push.

**不做：** 不接 Gateway → Zahir 生产挂载，不绕过 Feishu NO-GO，不承诺外部重放、RSS 降低、Signal monitor join 或停止后回收资源，不移动或卸载原生制品，不重构其他 provider，不做 Tauri、WASM 或 NSH 优化。修改与提交只落独立 worktree 分支，不改 main、不合并、不推送。
