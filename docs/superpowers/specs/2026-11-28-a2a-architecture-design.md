# Aleph A2A architecture / Aleph A2A 架构设计

2026-11-28 · `a2a-architecture`

## Intent / 意图

让外部 Agent 通过标准 A2A 客户端调用 Aleph 并可靠地观察与取消任务，也让 Aleph 通过已注册的远程 Agent 执行受策略约束的委派。任务状态、任务可见性与实际 Core 运行要一致。用户选择在同一分支交付两个阶段，先修运行链，再打通标准协议与 Agent Capability。

External agents can invoke Aleph and reliably observe or cancel their tasks through standard A2A clients. Aleph can delegate to registered remote agents within its existing policy boundaries. Task state, task visibility, and Core execution must agree. The two stages share a branch and land in lifecycle-first order.

## Approaches / 方案比较

| 方案 / Approach | 取舍 / Trade-off |
|---|---|
| 两阶段交付 / Two stages | **已选 / Selected.** 先用现有入口证明任务行为，再用标准客户端验证协议与 Capability。保留现有 Aleph 对接需要额外的兼容测试，但能让升级与生命周期修复独立验收。 Prove task behavior through existing routes, then validate the standard binding and Capability integration. Existing Aleph peers add compatibility tests and can be verified separately. |
| 仅生命周期 / Lifecycle first as the entire release | 能更快验证安全和取消效果。标准客户端互操作和远程 Agent 的 Capability 查找将进入后续交付。 Faster path to validating task isolation and cancellation. Standard client interoperability and Capability discovery move to a later release. |

## Stage 1 — Task identity and execution / 任务归属与执行

- `TieredAuthenticator` 从已验证凭据导出不透明的机器主体。同一凭据在不同认证入口得到同一主体，两个不同 token 的任务范围独立。显式开启的无凭据本地入口是单独的共享主体。携带凭据的请求先验证凭据。每个任务及上下文在创建时绑定主体。在任务读写、继续发送、列表、订阅和 push 配置入口统一检查归属。未知和不可见使用同一协议错误及同样的副作用约束。凭据和主体内部标识均保留在服务端。
- `TieredAuthenticator` derives an opaque machine principal from verified credentials. A credential identifies the same principal across entry points. Distinct tokens have distinct task scopes. Opt-in credential-free loopback access has its own shared principal. Requests carrying credentials validate them first. Bind identity at task and context creation, and apply it to reads, writes, follow-up sends, listings, subscription admission, and push configuration. Unknown and invisible tasks share an error shape and have no effects. Keep credentials and internal principal identifiers on the server.
- 合并 `request_processor.rs`、`routes.rs` 和 `bridge.rs` 的同步与 SSE 发送路径。`TaskStore` 每个任务同时只允许一次有效领取。领取时绑定本次 Core `run_id`、会话准入和取消句柄。`InputRequired` 保留由原主体重新领取的能力，每次重新领取分配独立 `run_id`。阶段内其余暂停状态通过版本映射明确拒绝续跑。复用已有的 Core 执行和取消入口，让 Core 结算一次，按顺序发布产物和终态。取消在登记前也能生效。调用方在最多五秒内观察结算，Core 确认后才返回 `Canceled`，完成获胜时返回不可取消。到时仍未结算时返回 JSON-RPC `-32603`，并在错误 `data.reason` 中注明 `cancellation_pending`。取消意图保持有效，重复的在途请求观察同一运行，客户端可查询最终状态。对已经进入终态后才发出的新取消请求返回不可取消。等待期间不持有存储锁。
- Converge blocking and SSE sends in `request_processor.rs`, `routes.rs`, and `bridge.rs`. Admit one active run per task and bind its Core `run_id`, session admission, and cancellation handle at claim. An owner may resume `InputRequired` using a new `run_id`. Other paused states reject resumption in this scope. Reuse Core execution and cancellation. Settle once, publish artifacts before terminal status, and cover cancellation before registration. Wait for settlement for up to five seconds. Report `Canceled` once Core confirms it, or non-cancelable when completion wins. If settlement is pending at the deadline, return JSON-RPC `-32603` with `data.reason` set to `cancellation_pending`. Keep the cancellation intent active. Concurrent pending requests observe the same run, and clients can query the outcome. Fresh cancellation requests after terminal settlement return non-cancelable. Release storage locks before waiting.
- 保留现有无人值守工具策略和 `NotificationService` 的 SSRF 边界。兼容入口允许旧客户端为自己选择任务 ID，在调用方范围内解析该 ID。每一任务实例另有服务器分配的内部 ID，作用域、Core 会话、流和回调均绑定内部实例。终态快照沿用有界回收，回收后兼容 ID 可复用，旧订阅和旧 push 配置不会关联到新实例。外部查询只保证在快照保留期间可用。非法请求在注册 push 和启动 Core 前结束。任务运行由服务端持有，HTTP 等待者离开后仍可查询任务结果。
- Preserve unattended tool policy and the `NotificationService` SSRF boundary. The legacy binding resolves client-selected task IDs within the caller's scope. Each task instance also has a server-allocated internal ID for binding execution, streams, and webhooks. Keep bounded terminal snapshot eviction. An alias can be reused after eviction, with fresh internal identity, subscriptions, and push configuration. External queries are available while the snapshot is retained. Rejected requests stop before push registration and Core execution. The server owns execution across HTTP waiter disconnects.
- `StreamHub` 只负责实时观察。状态及产物先落入任务快照。订阅的授权、当前快照和后续事件订阅以同一次协调完成。已经终止的任务立即返回可识别结果。缓冲区溢出时结束落后的流并给出可恢复的错误，客户端可重新查询快照。终态发布一次，观察者和工作句柄可回收。后台刷新及健康监控交给 `StartupResources`，支持取消和等待回收。
- `StreamHub` delivers live observations. Commit status and artifacts to the task snapshot before publication. Coordinate subscription authorization, snapshot, and receiver attachment. Terminal resubscription returns promptly. A slow receiver gets a recoverable error and can fetch the task snapshot. Publish one terminal state and release observers and worker handles. `StartupResources` owns and joins card refresh and health workers.

## Stage 2 — Interoperability and Capability / 互操作与 Capability

- 保留 `/a2a` 和 `/a2a/stream` 的 Aleph 兼容入口。标准 JSON-RPC 接口 `/a2a/rpc` 供同端点普通响应与 SSE，卡片明确公布该地址。`A2A-Version` 按规范匹配 major/minor，缺省为 0.3。0.3 和 1.0 使用独立 wire DTO 和错误映射，共用阶段一的操作。协议表包含卡片发现、发送、发送流、查询、取消及重订阅，1.0 另支持作用域内列表和分页。测试 1.0 `returnImmediately` 与 0.3 `blocking` 的明确行为。1.0 流首项为 `Task`，错误与终态沿 wire 约定处理。
- Keep the Aleph compatibility routes at `/a2a` and `/a2a/stream`. The card-advertised JSON-RPC endpoint `/a2a/rpc` supports both unary responses and SSE. `A2A-Version` matches major/minor and defaults to 0.3. Use typed wire conversion and version-specific errors around the same operations. Cover discovery, send, streaming send, get, cancel, and resubscribe, plus scoped pagination in 1.0. Verify 1.0 `returnImmediately` and 0.3 `blocking`. The 1.0 task stream begins with `Task` and follows the version's error and terminal rules.
- 标准新任务由服务器分配 ID。消息内的 `taskId`、`contextId` 和支持的任务引用只解析到当前主体可访问的资源。复用 Core 会话，将标准上下文绑定到服务器分配的会话键。同一上下文有运行时，第二条发送立即返回可重试的忙错误 `-32603`（`data.reason` 为 `context_busy`），在任务创建、push 注册或改变当前运行前结束。其余上下文仍可并发。收到终态任务的继续请求返回相应错误。文本是本轮公布的输入与输出模式，文件和结构化 Parts 可按协议解码和验证，运行适配器对不支持的输入明确返回协议错误。
- The server assigns new standard task IDs. Message task IDs, context IDs, and supported references resolve within the authenticated scope. Bind a standard context to a server-assigned Core session key. A second send to an active context returns retryable JSON-RPC `-32603` with `data.reason` set to `context_busy`, before creating a task, registering push, or changing the running turn. Other contexts can run concurrently. Reject continuation of terminal tasks using the appropriate protocol error. Advertise text input and output. Decode and validate file and structured parts at the binding, with a protocol error where the run adapter cannot consume them.
- 从同一张卡片事实生成发现表示。默认 `/.well-known/agent-card.json` 给出 0.3 发现字段和 1.0 `supportedInterfaces`。用两个固定版本 SDK 无额外发现请求头解析并调用。旧 Aleph 卡片提供独立发现路径 `/a2a/legacy/.well-known/agent-card.json`，因为旧 `security` 元素与 0.3 同名字段结构不同。旧版 Aleph 对接如果需要读取旧卡片，将基础地址改为以 `/a2a/legacy` 结尾。该前缀也提供兼容的执行路径，原执行地址继续可用。反代暴露地址可由 operator 配置，直接部署沿用 Gateway 监听地址。出站沿用 `CardRegistry`、`A2AClientPool` 和 `A2ASubAgent`，统一解析配置根地址、发现地址、协议版本和被选中的 JSON-RPC endpoint。保留已配置 Aleph 对端的兼容模式。检查新 endpoint 的 URL、传输和现有网络策略。同源是发现后携带凭据的默认边界，跨源由 operator 显式配置。流式与一元调用在发消息前选择。投递结果不明时向调用方保留不确定性，避免重发。
- Derive discovery representations from one local card. The default `/.well-known/agent-card.json` carries the 0.3 discovery fields and 1.0 `supportedInterfaces`. Both pinned SDKs must discover and invoke with ordinary discovery headers. The old Aleph card is available at `/a2a/legacy/.well-known/agent-card.json` because its `security` elements differ from the 0.3 field of the same name. Older Aleph integrations that read the old card can use the `/a2a/legacy` base path. Serve legacy execution routes under this prefix and keep their existing URLs available. An operator can configure the advertised reverse-proxy address. Direct deployments derive it from the Gateway listener. Reuse `CardRegistry`, `A2AClientPool`, and `A2ASubAgent` to select discovery, protocol version, and JSON-RPC endpoint. Keep compatibility for configured Aleph peers. Recheck the selected endpoint against URL, transport, and network policy. Forward credentials to the discovery origin by default, with explicit operator configuration for another origin. Select streaming or unary before sending. Report ambiguous delivery as such and avoid resending.
- `CardRegistry` 持有远程 Agent 的配置与卡片。通过 `CapabilityKind::Agent` 把它接入 `ZahirFacade` 的发现、解析及更新流。沿用 `OwnershipTree` 的可见性与 lease 判定，`a2a_delegate` 从同一份已验证的注册记录解析调用，`a2a_agents` 继续作为工具入口。请求构造和客户端池等待完成后，在首次向 HTTP 客户端交付请求之前，由同一个源更新同步边界执行最终代次检查和请求准入。先发生撤回、替换或关闭时，旧端点预期收到零次 POST。先完成准入的调用允许收尾，并可能产生远程效果。健康变化可更新描述，影响实际调用的变更更新调用代次。客户端及内存记录复用现有实现。
- `CardRegistry` owns configured remote agents and their cards. Expose it through `CapabilityKind::Agent` for `ZahirFacade` discovery, resolution, and change delivery. Use `OwnershipTree` visibility and lease validation. `a2a_delegate` resolves the same authoritative registry entry, and `a2a_agents` remains the tool entry point. Once request construction and client lookup are complete, serialize final generation validation and dispatch admission with source mutations just before handing the request to the HTTP client. If removal, replacement, or shutdown wins, expect zero POSTs to the old endpoint. A call that wins admission can finish and can have remote effects. Publish health changes and rotate the invocation generation on changes that affect invocation. Reuse the existing client and memory capture.

## Cleanup and acceptance / 清理与验收

- 清理重复发送协调、仅写状态的取消、以固定地址和失败重发作为常规委派路径的逻辑，保留实际有调用方的兼容适配。单独核对旧接口调用点和无用实现。先对照规范 fixtures，再走实际 Gateway 路由和真实 Core 取消。验收至少覆盖双主体与租户参数拒绝、取消前后竞态、终态和滞后订阅、流分块 UTF-8、断线后查询、一次远程 POST、声明地址、Capability 查找和移除。用固定的两版官方 `a2a-python` 客户端通过默认卡片发现调用 Aleph，再用固定 SDK 或按规范实现的 JSON-RPC 对端验证 Aleph 出站行为。`ra2a` 作为固定的 Rust 对照，用通过的互操作用例记录证据。
- Remove duplicate send orchestration, status-only cancellation, and ordinary delegation through guessed paths and retry-on-stream-error. Verify remaining callers and compatibility adapters. Test spec fixtures, then the Gateway routes and actual Core cancellation. Exercise two principals, unauthorized tenant parameters, cancellation races, terminal and lagged streams, split UTF-8, reconnect by query, a single remote POST, discovered URLs, and Capability discovery and withdrawal. Require inbound discovery and invocation with both pinned official Python SDKs. Validate Aleph outbound calls against the pinned SDKs or spec-conforming raw JSON-RPC peers. Record any passing `ra2a` interoperability cases as evidence.
- 两阶段的验收针对文本 JSON-RPC/SSE 和现有 Aleph push。标准 push 扩展、REST/gRPC、跨重启任务恢复、多租户身份服务以及文件执行属于独立范围。协议卡片只公布有生产接线的能力。校对 `FEATURE_LOCATOR.md` 和相关 reference 的双语入口、配置、支持矩阵及验收记录，按阶段提交到 `a2a-architecture`。
- Acceptance covers text JSON-RPC/SSE and existing Aleph push. Standard push extensions, REST/gRPC, restart recovery, multi-tenant identity services, and file execution are separate scopes. Cards advertise capabilities with production wiring. Update the bilingual locator and relevant references with route, configuration, support, and verification details, then commit to `a2a-architecture`.
