# VESR v1.1 Enrichment — Design Spec

> 状态: DESIGN (approved 2026-06-29). 续 VESR v1 (`docs/superpowers/specs/2026-06-29-verified-experience-self-routing-design.md`, merged to local main `d47f4f7fe`). docs/* 受 .gitignore 管控，本地优先不提交（与 v1 spec 同）。

## 摘要 (Abstract)

VESR v1 只记录顶层 run、把成本/上下文字段留空、按任务 kNN 邻居召回。v1.1 补三项被显式延后的"信息富化"，全部是给已有 VESR 骨架补数据，**零新红线、零 harness 改动**：

1. **(c) USD 成本富化** — observer 在记录前用已有的 `pricing::estimate()` 把 token 折算成 USD，写进早已存在的 `estimated_cost` 列。
2. **(b) 子代理经验捕获** — 在 spawn seam 给子 run 的 trace sink 包一个它自己的 `OutcomeObserver`，按 `child_agent_id` 入库（顶层路径今天完全绕过子代理）。
3. **(a) per-agent 按模型聚合** — run-start 召回块新增一段"本 agent 各模型终身画像"（原始聚合事实，非排行榜）。**投放面是 `RoutingRecall` 召回块，不是 `list_models` 工具**（见 §2 决策）。

`list_models.rs` / `select_model.rs` / `src/harness/`（含 `trace.rs`）在 v1.1 仍**字节不变**（N1/N2/N3 全部续守）。

实现顺序 **(c) → (b) → (a)**：(c) 一处改动同时覆盖顶层与子代理（两者共用 `OutcomeObserver`）；(b) 让子代理也产出数据；(a) 把这些数据聚合呈现。

## 1. 背景与不变量 (Inherited Constraints)

v1.1 继承 v1 plan 的 Global Constraints，逐条仍然成立：

- **R3 (Core Minimalism)**: 复用单一 `Arc<dyn EmbeddingProvider>`（`RoutingExperienceStore` 已持有，经 `embed_task` 暴露）。仅 sqlite + sqlite-vec，无第二向量库、无第二 async runtime。`pricing.rs` 是已有的内联静态价表（无 HTTP、无 config）。
- **R7 (LLM Sovereignty)**: 存储/observer/recall 零裁决。新增的聚合**只暴露原始聚合事实**——`N`、各 `terminate_reason` 变体原始计数、平均迭代/工具错误/token/USD、最近使用时间。**禁** `success_rate` / 0-1 评分 / argmax / 跨模型排名 / `best_for`。USD 折算是确定性数据富化（tokens × 单价），非路由判断。
- **R10 (Thin Harness)**: `src/harness/`（12 文件）+ `trace.rs` **字节零改**(N1)。observer 包裹全部 harness-external（顶层在 `orchestrator/harness_bridge/`，子代理在 `agents/subagent_spawner/`）。召回 run-start once-per-run，**绝不**进 `think.rs` / `prompt.rs` 每轮循环（源级守卫 `build_prompt_path_never_references_routing_recall` 仍然有效）。
- **N2**: `select_model.rs` 字节不变。
- **N3**: `list_models.rs` 字节不变 —— v1.1 选择把聚合投到召回块（§2），所以这条**在 v1.1 依然成立**，不是被打破。
- **Per-agent 隔离**: `agent_id` 是 record / recall / aggregate 的隔离键。子代理按 `child_agent_id` 入库；聚合按调用方 agent 分组。
- **Crate paths**: lib `crate::`，binary `alephcore::`。

## 2. 锁定决策 (Locked Decisions)

| # | 决策 | 来源 |
|---|------|------|
| D1 | (a) 聚合粒度 = **按调用方 agent**（非全局跨 agent）。守 per-agent 隔离不变量。 | 用户 AskUserQuestion #1 |

## 3. Item (c) — USD 成本富化

### 现状
- `routing_experiences` 表早有 `estimated_cost REAL`（nullable）列；`RoutingOutcome.estimated_cost: Option<f64>`；`record()` 已把它写进行（`experience_store.rs:69`）。
- `outcome_from_session_completed()` 硬编码 `estimated_cost: None`（`observer.rs:36`）。
- `pricing::estimate(provider: &str, model: &str, breakdown: &TokenBreakdown) -> CostEstimate { usd: f64, status: CostStatus, .. }` 已存在（`pricing.rs:779`）。`CostStatus = { Complete, PartialMissingPrice, Unknown }`，未知 provider/model → `Unknown`（best-effort，永不报错）。
- `TokenBreakdown` 在 observer 捕获点就拿得到（`observer.rs:89` 从 `SessionCompleted` 解包）。
- observer 已持有 v1 修复后的**真实** `self.provider_id` + `self.model_id`（构造期注入，非 `FailoverProvider.name()` 的 `"failover"`）。

### 设计
单点改动：`OutcomeObserver::on_trace`（`observer.rs:87-110`）。在拿到 `outcome` 后、`tokio::spawn(record_to_store)` 前，折算成本：

```rust
let mut outcome = outcome_from_session_completed(/* ... */);
let est = crate::pricing::estimate(&self.provider_id, &self.model_id, &outcome.token_breakdown);
outcome.estimated_cost = match est.status {
    crate::pricing::CostStatus::Complete
    | crate::pricing::CostStatus::PartialMissingPrice => Some(est.usd),
    crate::pricing::CostStatus::Unknown => None, // "(dynamic)"/""/未知模型 → 优雅降级
};
```

### 关键性质
- **mapper 保持纯粹**：`outcome_from_session_completed` 仍返回 `None`，成本在 `on_trace` 里覆盖。`mapper_never_fabricates_or_reads_judgment_signals`（`observer.rs:166`）测试不受影响。
- **顶层 + 子代理一处覆盖**：两者共用同一个 `OutcomeObserver`。在 `on_trace` 折算 → (b) 接好子代理 observer 后，子代理成本**免费**得到。
- **优雅降级**：`(dynamic)` / `""` / 未在价表的模型 → `Unknown` → 存 `None`，不报错（与 `runner_impl.rs:594` 既有 FlowOutcome 算法一致）。
- **R7**：tokens × 单价 = USD 是确定性数据富化，非路由裁决。LLM 解读成本，代码不按成本排序。

## 4. Item (b) — 子代理经验捕获

### 现状（为什么 v1 没捕获）
子代理走**独立路径**，**完全绕过**顶层 observer 包裹点（`runner_impl.rs:294-306`）：

```
SubagentTool::execute → AgentRuntime::run → subagent_spawner::spawn
  → 构造 HarnessDeps { trace_sink: base.trace_sink.clone() (裸 sink) }  // mod.rs:362
  → AgentHarness::run(...)  // mod.rs:418，直接跑，不回 runner_impl
```

但子 run **照常** emit `LoopTraceEvent::SessionCompleted`（全 payload：iterations / tool_calls_made / terminate_reason / token_breakdown / duration_ms / tool_timeline）进它的 sink——今天流到裸 sink 无人观测。

`parent_and_child_attribution_isolated`（`routing/mod.rs:135-162`）已在单测层证明：两个独立构造的 `OutcomeObserver`（各冻结自己的 model+agent+attribution）写同一 store 不同 `agent_id`，互不串。(b) 就是把这个**已验证的模式接到 spawn seam**。

### 设计
**a) routing_store 接到 spawn seam**（这是 (b) 唯一的 threading 工作）。子代理的 trace_sink 来自 `gateway/execution_engine/run_loop/inner.rs:760`（gateway run loop 传入的**裸 sink**——观测包裹是 runner_impl 在顶层 run 内部才施加的，所以子代理拿到的是裸 sink，与 v1 "subagents hold the raw sink" 一致），经 `SubagentTool → AgentRuntime → SpawnerBase` 的 `with_*` 链下传。

`routing_store` 在该构造点**可达**：`inner.rs:730-784` 的 `orchestrator.harness`（= `AgentHarnessRunner`，持 `routing_store` @`harness_bridge/mod.rs:225`）就在 scope 内（`orchestrator.harness.guardrails()` 已在 `inner.rs:767` 被调）。新增 `routing_store()` accessor（镜像 `guardrails()`）即可。threading 链（全部镜像 `guardrails`/`trace_sink` 的既有 `with_*` 惯例）：

```
inner.rs:760ish  t.with_routing_store(orchestrator.harness.routing_store())
  → SubagentTool.routing_store (新 field + builder, subagent_tool/{mod,spawn}.rs)
  → build_runtime → AgentRuntime.with_routing_store (新 field + builder, runtime.rs)
  → spawn_subagent (runtime.rs:438) → SpawnerBase.routing_store (新 field)
```

> **父 routing 归因不可达**：父 run 的 `routing_model_id`/`provider_id` 在 `runner_impl.rs` 运行**内部**才算出，在 `inner.rs` 构造 SubagentTool 时尚不存在。故子代理**不继承父归因**，只取 spawn-seam directives（见 b）——这也是为什么 v1.1 不 thread 父归因（避免大改）。

**b) `spawn()` 内（`subagent_spawner/mod.rs`），当 `base.routing_store.is_some()`**：

1. 子模型 = `req.model.or(agent_def.model_hint).unwrap_or("(dynamic)")`。
2. 子 provider = `agent_def.provider_hint.clone().unwrap_or("(dynamic)")`（`AgentDef.provider_hint`/`model_hint` @`types.rs:124,131`；provider_hint 正是 `AgentRuntime.provider_overrides` Phase-3 映射的键，即子代理真实 provider 身份）。**避开 `FailoverProvider.name()` 的 `"failover"` 坑**——直接取 directive，不问被包裹的 provider。
3. embed `effective_task`（`mod.rs:253` 构造，clone 一份在 move 进 `UserMessage` 之前）→ 子 `task_emb`（`store.embed_task` 异步，**在 run 之前**完成，无竞态）。
4. 构造子 `RoutingAttribution::new(child_id)`，`set(task_emb)`。
5. 构造子 `OutcomeObserver::new(base.trace_sink, routing_store, child_attribution, child_model, child_provider, agent_def.id)`。
6. `HarnessDeps.trace_sink`（`mod.rs:362`）= `Arc::new(child_observer)`，替代 `base.trace_sink.clone()`。

**`base.routing_store.is_none()` 时**：`trace_sink` = `base.trace_sink.clone()`（**今天行为，零改动**，routing 未装时完全不变）。

> **归因精度边界（诚实标注）**：带显式 model 选择的子代理（`req.model` 或 `agent_def.model_hint`——正是"LLM 把任务路由给某模型"的高价值场景）精确归因；全继承父模型的子代理（两者皆 None）落 `model="(dynamic)"`/`provider="(dynamic)"`。这是**有意的 KISS 选择**：避免把父归因 thread 穿三层。"(dynamic)" 桶诚实（= 未做显式模型选择的 run）、availability gate fail-open 不误标、pricing 降级 None。v1.1 **记录全部**子 run（不按是否显式选择跳过），数据从优。

### 关键性质
- **入库键 = `agent_def.id`**（child_agent_id），per-agent 隔离，与召回一致。
- **MeteringProvider 不动**：它向 `base.trace_sink` emit `ProviderUsage`，与 observer 关心的 `SessionCompleted`（来自 harness 循环、流入 `deps.trace_sink`）正交。只需 `deps.trace_sink` 换成包裹后的 sink。
- **R10 安全**：包裹发生在 `subagent_spawner`（agents/orchestrator 层），**不碰** `src/harness/`。子 run 仍跑 `AgentHarness::run` 不变；`trace.rs` 字节不变。
- **D4**：无 parent-linkage 列。
- 更新 `runner_impl.rs:291-293` 注释（"v1: top-level only" → "v1.1: 顶层与子代理各自 seam 捕获"）。

## 5. Item (a) — per-agent 按模型聚合

### 设计：纯读侧，零 DDL 改动
聚合是对 `routing_experiences` 关系表的只读 `GROUP BY`，不碰 vec 表、不加列。`ddl_has_no_judgment_columns`（`routing_experience.rs:320`）保持绿。

**a) 新存储方法** `SqliteMemoryBackend::aggregate_routing_experiences_by_model(agent_id) -> Result<Vec<ModelAggregate>, AlephError>`（`routing_experience.rs` 新增，镜像现有 `record/recall/prune` 错误处理与锁惯例）。

**b) 新 facade** `RoutingExperienceStore::aggregate_by_model(agent_id) -> Result<Vec<ModelAggregate>, AlephError>`。

**c) 新类型 `ModelAggregate`**（每个 (model, provider) 一行，**全部原始事实**）：

```rust
pub struct ModelAggregate {
    pub model_id: String,
    pub provider_id: String,
    pub n_runs: u32,
    /// terminate_reason 变体原始计数分布（变体名 = v1 逐字存的 "kind" 判别值）。
    /// 例: [("completed", 38), ("max_iterations", 3), ("verifier_veto", 1)]
    pub terminate_reason_counts: Vec<(String, u32)>,
    pub avg_iterations: f64,
    pub avg_tool_errors: f64,
    pub avg_total_tokens: f64,
    pub avg_cost: Option<f64>, // 仅对已知成本的行求平均（NULL 忽略）
    pub last_used_unix: i64,
}
```

R7 红线（结构性测试守卫）：**无** `success_rate` / `score` / `rank` / `best_for` 字段。`terminate_reason_counts` 是原始变体分布——`completed` 计数不是"成功率"，是 v1 已逐字存的原始判别值的分布，由 LLM 解读。

**d) 聚合查询**：按 `agent_id` 过滤、按 `(model_id, provider_id)` 分组。数值均值/计数走 SQL `AVG`/`COUNT`；`terminate_reason` 变体分布通过提取 JSON `kind` 字段（`json_extract(terminate_reason,'$.kind')` 分组，或拉取 `(model,provider,terminate_reason)` 投影后 Rust 内折叠——plan 定，二者皆可，≤5000 行/agent 有界）。`avg_cost = AVG(estimated_cost)`（SQLite 忽略 NULL → 已知成本行的均值）。`last_used = MAX(created_at)`。

**e) 投放：`RoutingRecall::build_routing_experience_message`（`recall.rs:80-101`）**

新增 `render_aggregates(&[ModelAggregate], &availability) -> String`（镜像 `render_neighbors`，复用同一 availability gate：`Deconfigured` 标 `[UNAVAILABLE]`，`Unknown` fail-open 不标）。聚合段追加在 kNN 邻居之后，独立子标题明确区分：

> "Lifetime per-model track record for THIS agent (raw aggregates across ALL past tasks, NOT a ranking — weigh them yourself):"

**聚合段的真正价值 = 与邻居并列多一层终身画像**：normal case 下 neighbors 与 aggregates 同有同无（kNN 无距离阈值——有行必返回最近邻；neighbors 空 ⟺ cold-start 无行 ⟺ aggregates 也空）。所以这不是"无邻居时才出现"——而是**有历史时，聚合段追加在 task-specific 邻居之后**，让 LLM 既看"像这种任务上各模型的表现[邻居]"、又看"每个模型的总体战绩[聚合]"。发射条件改为 **neighbors 或 aggregates 任一非空**（早返回 `None` 改为两者皆空时）属正确性兜底——覆盖 embedder 换维度的边缘（旧维度 kNN 表查不到 → neighbors 空，但关系表聚合仍返回）。`build_routing_experience_message` 仍照常 embed query + backfill `task_emb`（observer record 对称性需要）。中性顺序按 `last_used_unix` 倒序，**绝不**按结果指标排序（D5）。

### 关键性质
- `list_models.rs` / `select_model.rs` **字节不变**（N3/N2）。
- 聚合是 read-side，无 DDL 改动、无 vec 表参与。
- per-agent 隔离：聚合按 `agent_id` 过滤（与 recall 同键）。

## 6. 明确排除 (Out of Scope)

- **`context_tokens` / `context_window` 回填**（今为 0）—— 非这三项；需另接 `SessionCompleted` 的 context_usage。不做。
- **O11 子代理召回投放**（子 run 收到召回块）—— (b) 是捕获不是投放（D3）。子 run 走不同路径、今天本无召回块；保持不变。
- **list_models 全局聚合 / 跨 agent 排行榜**（D1/D2 已否决）。
- **list_models.rs / select_model.rs / src/harness/ 任何改动**（N1/N2/N3）。
- **parent-linkage 列**（D4）。

### 已知消费缺口（D3 的诚实标注）
(b) 捕获的子代理数据，只有当该 agent 也作为**顶层 run** 跑时才会经召回块 (a) 被看到（双模式 agent 常见），或等未来 O11。纯子代理型 agent 的画像在 v1.1 先"沉淀但暂无即时消费者"——这是 capture-only 的有意边界，非缺陷。

## 8. Plan 阶段待定的实现细节 (Open Implementation Points)

1. **(b) routing_store threading 的精确触点**：spec §4a 已给出完整链（`inner.rs` → SubagentTool → AgentRuntime → SpawnerBase + `AgentHarnessRunner::routing_store()` accessor）。plan 落地各 `with_*` builder 与 accessor 的确切签名（镜像 `guardrails`）；注意 `orchestrator.harness` 若为 trait object，accessor 加在 trait 上。**background subagent 路径**（`subagent_tool/spawn.rs:113-124` 的 `spawn_background`，用 `ForwardingTraceSink`）也走 `build_runtime`，自动继承 routing_store——plan 确认其 trace_sink 包裹不与子 observer 冲突（两者关心不同事件，正交）。

3. **(c) `PartialMissingPrice` 落库**：spec 选择存 `Some(usd)`（已知下界、best-effort）；plan 确认与 §3 一致。
