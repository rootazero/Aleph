## 1. 桶 A — 连线 / 错误修复

### A1 · 闭合 MCP → ToolCatalog（旗舰连线，价值 H）

**根因（已核实仍开）**：`register_mcp_tools`（`src/tools/handlers/registration.rs:62,105-110`）已把 `tool_catalog: Option<&Arc<ToolCatalog>>` 全程穿过，但**只**用来挂 `McpServerProbe` 健康探针，从不调 `register_with_conflict_resolution` → 没有任何 MCP `UnifiedTool` 进入 `ToolCatalog`。Boot 聚合（`src/bin/aleph-server/commands/start/builder/agent_init/tool_catalog_init.rs:38-218`）注册 builtin/executor-builtin/custom/skills/plugin，**无 MCP 分支**。

**爆炸半径**：`commands.list`（`gateway/handlers/commands.rs:244-264,491-509`）、`tools.catalog`/`tools.effective`（`gateway/handlers/tools_visibility.rs:59-116,135-187`）永不见 MCP；`mcp:<server>` 分组 + `mcp:*` 过滤已完整实现且有测试，但生产中恒空。`command.execute → resolve_command` 对 MCP 名返回 `None` → 落 "Unknown command"。MCP 仅经专用 `mcp.tools` RPC 可见、经 `ToolHandlerRegistry→mcp_adapter→LoopToolRegistry` 可执行。

**修复（连线优先，复用既有基建）**：
- **Add 侧**：在 `register_mcp_tools` 挂探针处（`registration.rs:105-110`），追加一次
  `disp.register_with_conflict_resolution(UnifiedTool::new(format!("mcp:{server_id}:{name}"), <cmd_name>, <desc>, ToolSource::Mcp{ server }))`。
  这是每个其它来源都走的 R8 同源路径；`ConflictResolver`（`tool_metadata/registry/conflict.rs:155`）已处理 `ToolSource::Mcp` 优先级/改名；`extract_source`/`group_tools`/`filter_by_source("mcp:*")` 已能渲染。
- **Remove 侧**：在 `unregister_mcp_tools`（`registration.rs:130-149`）追加 `tool_catalog.remove_by_mcp_server(server_id)`——复活已存在但死的方法（`tool_metadata/registry/state.rs:117`），使 catalog 与 server 断连/`ToolsChanged` 保持锁步。

**命名决策**：catalog 命令名用**裸 MCP 工具名**（`/slack_post`），不用 provider-safe 的 `server__tool`（作斜杠命令太丑）；`ToolSource::Mcp{server}` 携带 server 供分组。

**顺带**：修 `tool_metadata/.../health.rs:23-25` 过期注释（描述了不存在的 `RegistryChange` 订阅）。

**收益**：一次连线同时 (a) 恢复 `commands.list`/`tools.catalog`/`tools.effective` 的 MCP 可见性，(b) 让 MCP 斜杠命令可解析（不再死于 "Unknown command"），(c) 救活死的 removal 方法。零 harness 增长。

### A2 · 修 glob `pattern` 越权（价值 M，安全）

**根因**：`file_ops` 的 `search`（`src/builtin_tools/file_ops/search.rs:34-56`）与 `batch_move`（`batch.rs:48-89`）只对 base dir（及 dest）过 `check_and_resolve_path`，glob 匹配结果用 `canonical.join(pattern)` **原样使用**。绝对 pattern（如 `/etc/*`）经 `Path::join` **替换** base；含 `..` 的 pattern **逃逸** base → 可 list/move workspace 外文件（含凭据黑名单目录），`batch_move` 还会真的 `fs::rename`（变更）。

**修复**：
- 入口拒绝**绝对路径 pattern** 与含 `..` 组件的 pattern。
- 每个 glob 匹配结果回过 `check_and_resolve_path`（拒绝落在 deny 名单 / FsScope 外的项）；正常相对 glob 仍工作。

### A3 · 修 web_fetch 结果预算 + 删死适配器（价值 M，含熵减）

**根因**：per-tool `max_result_tokens` 的"经 trait 声明"重构（删掉 `result_processing.rs:55-63` 的 `bash`/`web_fetch` 名表 arm）假设了一个 forwarding 适配器。但生产路径全走 `RegistryToolAdapter`（`src/tools/adapters/registry_adapter.rs:195-315`），它**不覆写** `LoopTool::max_result_tokens` → 恒 `None` → 回落 `result_processing.rs:28` 的 `DEFAULT=8_000`。唯一 forward trait 值的 `BuiltinToolAdapter` 是**死代码**（`src/tools/adapters/builtin_adapter.rs`，仅 `#[cfg(test)]` 构造）。净效果：`web_fetch` 声明 10k（`web_fetch/mod.rs:378`）被静默截到 8k（`bash` 恰好 8k==默认，无影响）。

**修复（连线优先 + 顺带熵减）**：
- 删死代码 `BuiltinToolAdapter`（`builtin_adapter.rs` + `adapters/mod.rs:8` 的 `pub use`）。
- 给 `RegistryToolAdapter` 补 `max_result_tokens` 覆写，从 registry metadata / `UnifiedTool` 转发工具声明值。

## 3. C1 — tool_search 三档延迟（旗舰功能增强）

### 3.1 分档模型（用户已选：三层，保留 + 新增）

| 档 | 行为 | 归属（默认） |
|---|---|---|
| **Direct** | 全 schema 常驻模型列表 | config `core_tools` 集 |
| **Collapsed**（现有） | name+desc 可见，`input_schema` 折叠为 `{additionalProperties:true}` + hint，经 `get_tool_schema` 加载 | builtin 非核心 |
| **Deferred**（新） | **整个移出模型列表**，仅经 `tool_search` 发现 | MCP + plugin（开启后） |

**非破坏性 / 默认 OFF**：deferral 默认关闭（opt-in），镜像现有 `ProgressiveDisclosureRewriter` 的 escape-hatch 纪律（`core` 空 / `["*"]` → 特性全关、工具面字节等同 pre-feature、保 prompt-cache 连续性）。未开启时行为与今天完全一致。

### 3.2 组件（全部落在工具呈现 / 注册层）

1. **`ToolExposure` 分类**：纯函数 `exposure_of(tool, config) -> Direct | Collapsed | Deferred`。config 驱动、静态分区（不看消息内容 → R10/R7 安全）。新增 `[tools]` 配置项（如 `deferred_sources = ["mcp", "plugin"]` 或 `tool_search = true`），默认空 = OFF。
2. **Deferral 过滤器**：在 `src/tools/scoped/mod.rs` 的 `list()`（`126-133`）/ `metadata_schema()`（`342-360`）——即 `ProgressiveDisclosureRewriter` 应用的同层——加一个过滤，把 Deferred 工具**从模型列表移除**。关键不变量：Deferred 工具**仍在 `loop_registry` 可执行**、**仍在语料快照可搜**，只是不进模型 prompt 列表。
3. **`ToolSearchTool` 元工具**：镜像 `SchemaLookupTool` 的注册（`src/gateway/execution_engine/run_loop/inner.rs:607-634` 同处），闭包持有**全量语料快照** `name → { desc, schema, source }`（含 Deferred）。注册守卫同 `get_tool_schema`：仅当 deferral 启用时注册 + 挤进 non-empty allow-set。

### 3.3 tool_search 返回什么（决策：top-K 带 schema）

返回 top-K（默认 5，可配）排序结果，每条 `{ name, description, schema }` → 模型可**直接调用**，无需二次 `get_tool_schema` 往返。`get_tool_schema` 保留服务 Collapsed 档（已知名字、只缺 schema 的场景）。

### 3.4 排序（决策：自研轻量 BM25，零新依赖）

对 `(name + description)` 分词建 in-memory 语料，BM25 打分。语料小（几十~低几百工具、短 query），~60–80 行手写 scorer 即可，**不引入 `bm25` crate**（R3 核心轻量化；codex 用该 crate 因其目录/架构不同）。机械词法排序、模型发起查询 → R7 干净（非意图分类，是模型显式检索）。

### 3.5 A1 × C1 关系（互补，不同层）

- **A1** 把 MCP 放进 **ToolCatalog** = 人 / RPC 发现 + 斜杠命令解析层。
- **C1** 把 MCP 移出 **模型 prompt 工具列表** = 呈现层。

两者正交：catalog 变大不污染 prompt；prompt 变瘦不损发现性（斜杠命令 / RPC 仍能列出 MCP）。

## 5. 排序、风险、分支

**实施顺序**（先连线后扩展，先低风险后高风险）：
1. B4 文档修正（零风险）
2. A3 + B1（web_fetch 预算 + 删死适配器 + 折叠并发双 API，顺带熵减）

- B3 删 `CommandNode` 前**必须**核对 panel / TS bindings 无消费者。

- cargo 调用**极度节制**（按内存约定：默认不跑全量测试；至多一次 `cargo check --lib` 收尾；Windows 全量验证排除 `aleph-desktop-macos`/`linux` crate）。

**分支纪律**：实施在**新建 worktree 分支**（不碰 main）。当前 `feat-multisession-parallel-v2` worktree 仅用于本次 brainstorm 读分析，不在其中实施。
