### B10-001 [P1] Per-instance channel policies are registered under an ID the runtime does not use
- Location: /home/zou/data/workspace/Aleph-wt-review/src/bin/aleph-server/commands/start/builder/subsystems.rs:1147 (initialize_inbound_router)
- Failure mode: Configure a non-dedicated channel instance with an ID different from its channel type and set slash-command or permission policy; inbound messages carry the factory channel type ID, so the router misses the policy and applies defaults, allowing commands or capabilities that the operator configured out.
- Evidence: `inbound_router.register_channel_config(&inst.id, channel_config);` while the surrounding channel factories use fixed runtime IDs such as `"webhook"` and `"discord"`, and policy lookup uses the message `channel_id`.
- Suggested fix: Register by the actual runtime channel ID, or thread `inst.id` through channel construction and emitted message IDs; preserve distinct IDs for multi-instance channels.
- Confidence: 0.99

### B10-002 [P2] Config watcher has no shutdown path and survives server teardown
- Location: /home/zou/data/workspace/Aleph-wt-review/src/bin/aleph-server/commands/start/builder/handlers/config.rs:73-137 (setup_config_watcher)
- Failure mode: Start the gateway with an existing config, stop it, and start it again in the same process; the detached watcher task retains its `Arc<ConfigWatcher>` and continues watching and publishing events after the first gateway has shut down, so repeated starts accumulate file watchers and duplicate reload/event processing.
- Evidence: `tokio::spawn(async move { ... let watcher_handle = watcher_for_watch.clone().start_watching(); ... while let Ok(event) = config_rx.recv().await { ... } ... watcher_handle.await });` has no cancellation or shutdown signal. The caller stores the returned `Arc` in `_config_watcher` at `/home/zou/data/workspace/Aleph-wt-review/src/bin/aleph-server/commands/start/mod.rs:3854`, then drops it after `run_until_shutdown` without aborting or joining the task. `ConfigWatcher::start_watching` starts `watch_loop`, whose `rx.recv()` loop has no stop condition other than task cancellation.
- Suggested fix: Return and retain an owned shutdown handle/JoinHandle and cancel and join it during the existing server teardown; ensure the watcher task and its file debouncer are stopped before the next in-process start.
- Confidence: 0.94

### B10-003 [P2] Separate WebChat server is detached from gateway shutdown
- Location: /home/zou/data/workspace/Aleph-wt-review/src/bin/aleph-server/commands/start/builder/handlers/config.rs:194-205 (start_webchat_server)
- Failure mode: Run with `--webchat-port` different from the gateway port, stop the gateway, then restart it in the same process; the detached `serve_webchat` task keeps the old TCP listener alive, so the replacement WebChat server cannot bind the configured port and the restarted instance loses its WebChat endpoint.
- Evidence: `tokio::spawn(async move { if let Err(e) = serve_webchat(webchat_addr, webchat_path_clone).await { ... } });` discards the `JoinHandle`; no shutdown receiver or task ownership is returned to `/home/zou/data/workspace/Aleph-wt-review/src/bin/aleph-server/commands/start/mod.rs:3863`, which only awaits `start_webchat_server` and later tears down gateway resources.
- Suggested fix: Return the task handle plus a cancellation path from `start_webchat_server`, and stop/join it on every `run_until_shutdown` exit before allowing a new server start; preserve the current behavior when WebChat shares the gateway port.
- Confidence: 0.92
