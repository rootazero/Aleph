### B6-001 [P2] Bootstrap token hides database open failures as “no token”
- Location: src/bin/aleph-server/commands/bootstrap_token.rs:21 (read_token_from_db)
- Failure mode: When `security.db` cannot be opened because of permissions, locking, corruption, or an I/O failure, `SecurityStore::open(db_path).ok()?` converts the error to `None`; the command then exits 64 and tells the operator that no token has been provisioned, masking the actual storage failure and sending troubleshooting in the wrong direction.
- Evidence: `let store = Arc::new(SecurityStore::open(db_path).ok()?);`
- Suggested fix: Return a `Result<Option<String>, ...>` from the helper and propagate an open/read error distinctly from the valid empty-database case; preserve the existing EX_USAGE result only for `Ok(None)`.
- Confidence: 0.94

### B6-002 [P2] Identity commands misreport vault/database failures as a missing token
- Location: src/bin/aleph-server/commands/identity.rs:45 (open_ledger)
- Failure mode: If the existing security database cannot read the token because of an I/O, lock, corruption, or HMAC-validation failure, `try_load_token_from_db()` returns `None`; `identity list`, `ledger`, `export`, and local `verify` then report “No vault master token found. Start the server” even though the installation may already be provisioned, hiding the real storage/integrity failure and directing the operator toward an unsafe or irrelevant restart.
- Evidence: `if vault.try_load_token_from_db().is_none() { return Err("No vault master token found. Start the server at least once.".into()); }`
- Suggested fix: Preserve the underlying read/validation error through a result-returning load path, and distinguish an empty first-run database from a failed recovery without weakening the existing requirement that the vault token be present.
- Confidence: 0.91

### B6-003 [P2] Export size cap is defeated by a file replacement race
- Location: src/bin/aleph-server/commands/identity.rs:80-91 (verify_exported_file)
- Failure mode: An attacker or concurrent process can replace the path after `metadata(path)` reports a small regular file and before `read_to_string(path)`; the 256 MiB guard is then bypassed and the CLI may allocate the replacement's entire contents, causing excessive memory use or a process abort while verifying an untrusted export path.
- Evidence: `let meta = std::fs::metadata(path)?;` followed later by `let body = std::fs::read_to_string(path)?;`
- Suggested fix: Open the file once, inspect the opened handle's metadata, and read through that same handle with a bounded reader; retain the cap for the actual bytes consumed and preserve normal symlink/path behavior required by this CLI.
- Confidence: 0.88

### B6-004 [P2] Hook review can hang or exhaust memory on untrusted command output
- Location: src/bin/aleph-server/commands/hooks.rs:324,381,431 (run_skill_inline_command, run_inline_command, run_command_with_payload)
- Failure mode: A pending hook can be `yes`/an infinite-output command or a command that never exits; after the operator confirms the test, `.output()` or `wait_with_output()` captures output without a size limit and waits without a timeout, so `aleph-server hooks test` can grow memory indefinitely or hang until forcibly killed.
- Evidence: `command.as_std_mut().stdout(Stdio::piped()).stderr(Stdio::piped()).output()?` and `child.wait_with_output()?`; the file comments also state this review path has no production timeout or output cap.
- Suggested fix: Apply the same bounded output capture and deadline used by production hook execution, terminate the child on timeout, and report truncation/timeout while preserving the existing explicit confirmation and shell-metacharacter checks.
- Confidence: 0.97
