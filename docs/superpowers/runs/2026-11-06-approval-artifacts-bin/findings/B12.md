## P1 Findings

### B12-P1-01 [P1] Memory extension registry panic on duplicate registration
- Location: mod.rs:332-336 (inside `register_agent_handlers`, memory_ext_registry construction)
- Failure mode: If two plugins or future code paths attempt to register the same extension type with the same ID, the `.expect("first registration...")` call panics the entire server process during startup, preventing daemon boot.
- Evidence:
  ```rust
  reg.register(std::sync::Arc::new(EnvelopeRelevanceFloorExtension::new(0.0)))
      .expect("first registration into a fresh registry cannot collide");
  ```
- Suggested fix: Change to `.unwrap_or_else(|e| { tracing::error!("memory extension registration failed: {e}"); })` or gracefully skip the duplicate, preserving the invariant that startup completes. If collision is a configuration error, fail boot explicitly with a descriptive error before reaching this point.
- Confidence: 0.85

### B12-P1-02 [P1] Tool health probe registration without existence check
- Location: tool_catalog_init.rs:135-142 (`browser_*` family probe registration loop)
- Failure mode: If `BUILTIN_TOOL_DEFINITIONS` is modified to remove or rename a `browser_*` tool, the probe registration loop still fires for the old name, silently registering a probe for a non-existent tool. The LLM never sees the tool (no schema), but the probe keeps running on every request TTL boundary, wasting cycles and memory. Under load this accumulates orphan probes.
- Evidence:
  ```rust
  for def in BUILTIN_TOOL_DEFINITIONS {
      if def.name.starts_with("browser_") {
          tool_catalog.register_health_probe(def.name, browser_probe.clone());
      }
  }
  ```
  The loop trusts `BUILTIN_TOOL_DEFINITIONS` as the single source of truth, but the conditional registration logic in `optional_tools` (referenced in the comment at line 149) can skip actual tool registration while this loop still fires.
- Suggested fix: Before registering a probe, verify the tool exists in `tool_catalog` or `tool_registry`. Alternatively, make probe registration happen inside the conditional block that registers the tool itself (in `BuiltinToolRegistry::with_config`), not in a separate loop over a static list.
- Confidence: 0.75

## P2 Findings

### B12-P2-01 [P2] Unvalidated API key hydration from vault
- Location: generation_init.rs:28-33 (hydrate_key_and_gate function), provider_registry.rs:32-38 (vault_lookup closure)
- Failure mode: When `vault.get_secret()` succeeds but returns `Some(secret)`, the code calls `secret.expose().to_string()` and trusts the result as a valid API key. If the vault stores a malformed or empty secret (e.g., user error, key rotation race, vault corruption), the provider is registered with an invalid key. Every request to that provider fails with authentication errors, and the user sees confusing "provider configured but unusable" symptoms rather than a clear boot-time validation error. The `is_empty()` check at line 31/37 only gates registration, it does not validate the exposed string's format.
- Evidence (generation_init.rs:28-33):
  ```rust
  if provider_cfg.api_key.as_ref().is_none_or(std::string::String::is_empty) {
      if let Ok(Some(secret)) = vault.get_secret(&format!("gen:{name}")) {
          provider_cfg.api_key = Some(secret.expose().to_string());
      }
  }
  ```
- Suggested fix: After hydration, validate the exposed key against provider-specific requirements (minimum length, prefix format like `sk-`, or a lightweight test request). If invalid, log a clear warning and skip registration, or attempt the next fallback.
- Confidence: 0.70

### B12-P2-02 [P2] Race between extension load and tool registration
- Location: mod.rs:351-359 (extension manager handle installation), tool_catalog_init.rs:174-195 (ensure_loaded loop for plugin tools)
- Failure mode: The extension manager handles (MCP, memory registry, tool catalog, canonical tools) are installed at mod.rs:351-359, followed by a synchronous `.ensure_loaded()` at mod.rs:361. Later, `init_tool_catalog` runs its own `ensure_loaded()` loop at tool_catalog_init.rs:174. If a plugin's activation is slow (network MCP handshake, disk I/O), the first `ensure_loaded` might return while the plugin is still `Pending`, and the tool registration loop sees an incomplete plugin list. The activation gate at mod.rs:644-694 is spawned asynchronously and only reports status; it does not block tool registration. Result: tools from slow-activating plugins are missing from the LLM tool list until a restart or manual reload, even though the plugin eventually activates.
- Evidence:
  ```rust
  // mod.rs:361
  if let Err(e) = ext_manager.ensure_loaded().await { ... }
  // tool_catalog_init.rs:174-195
  if let Err(e) = ext_manager.ensure_loaded().await { ... }
  let registry = ext_manager.get_plugin_registry().await;
  for plugin in registry.list_plugins() {
      if !plugin.status.is_active() { continue; }
  ```
  The second `ensure_loaded` does not wait for the activation gate to settle.
- Suggested fix: Await the activation gate's `activation_settled()` before running `init_tool_catalog`, or make `get_plugin_registry().list_plugins()` block on activation completion. Alternatively, subscribe to plugin activation events and incrementally register tools as plugins activate (deferred improvement, not critical for correctness).
- Confidence: 0.65

### B12-P2-03 [P2] Leaked spawned tasks on early return
- Location: mod.rs:1385-1392 (goal wake service spawn), mod.rs:1464-1509 (autonomous team dispatcher spawn), mod.rs:1531-1550 (deadlock sweeper spawn), mod.rs:1585-1618 (wake-on-transition subscription spawn)
- Failure mode: Four background tasks are spawned via `tokio::spawn` without storing their `JoinHandle`. If `register_agent_handlers` returns early due to an error after spawning these tasks (e.g., migration failure, store init failure, or a future validation step), the tasks continue running indefinitely, holding references to `Arc<...>` resources (goal_deps, dispatcher, coord_store, dispatch_signal). The resources are never dropped, consuming memory and potentially interfering with cleanup or a retry attempt.
- Evidence:
  ```rust
  tokio::spawn(async move { goal_wake_boot.rearm_parked_goals().await; });
  dispatcher.spawn_loop(); // internally spawns
  tokio::spawn(async move { /* deadlock sweeper loop */ });
  tokio::spawn(async move { /* wake-on-transition subscription */ });
  ```
  No `JoinHandle` is captured; no cleanup is performed on error paths.
- Suggested fix: Capture `JoinHandle`s in a `Vec<JoinHandle<()>>` at function scope, and on any early `Err(...)` return, call `.abort()` on each handle (or `join()` with a timeout if graceful shutdown is required). Alternatively, scope the spawns under a `tokio::task::JoinSet` and drop it on error, aborting all child tasks.
- Confidence: 0.75

### B12-P2-04 [P2] Blocking SQLite operations in async context
- Location: coord_stores.rs:44-47 (open_sqlite_safe call), coord_stores.rs:135-137, coord_stores.rs:176-271 (all `open_sqlite_safe` calls)
- Failure mode: `open_sqlite_safe(&db_path)` performs synchronous filesystem I/O (open, flock, read) in an async function. On a slow filesystem (NFS, networked storage, or under heavy load), this blocks the tokio executor thread for tens to hundreds of milliseconds per call. With multiple stores opened sequentially (coord.db, teams.db × 5 connections), the cumulative stall delays startup and can starve other async tasks. Under high concurrency, this contributes to degraded responsiveness.
- Evidence:
  ```rust
  let conn = match alephcore::utils::sqlite_open::open_sqlite_safe(&db_path) {
      Ok(c) => c,
      Err(e) => { ... return (None, None); }
  };
  ```
  The calls are in async functions but use blocking syscalls.
- Suggested fix: Wrap each `open_sqlite_safe` call in `tokio::task::spawn_blocking(move || open_sqlite_safe(&db_path))` and `.await` the result. This offloads the blocking I/O to a dedicated blocking threadpool, keeping the async executor responsive.
- Confidence: 0.80

### B12-P3-01 [P3] Duplicate default-provider selection logic
- Location: provider_registry.rs:30-45 (default_name resolution), provider_registry.rs:78-93 (same logic in else branch)
- Failure mode: The logic to determine `default_name` from config or by sorting providers and picking the first enabled+keyed one is duplicated in two branches (env-provider vs config-only). If the sorting/filtering rule changes (e.g., to prefer a specific provider type, or to honor a "priority" field), both copies must be updated. This has already drifted slightly: the env-provider branch (lines 78-93) has a stale comment and does not filter by `has_key` before sorting. Future maintainers will update one copy and miss the other, causing inconsistent default-provider selection depending on whether an env key is present.
- Evidence:
  ```rust
  // Lines 30-45
  let default_name = app_config.general.default_provider.clone().or_else(|| {
      let mut candidates: Vec<(&String, &alephcore::ProviderConfig)> = app_config.providers.iter().collect();
      candidates.sort_by(|a, b| a.0.cmp(b.0));
      candidates.into_iter().find(|(name, cfg)| cfg.enabled && has_key(name, cfg)).map(|(name, _)| name.clone())
  });
  // Lines 78-93 (inside if let Some((env_name, env_prov)) = env_provider)
  // Comment says "honor it" but does not re-sort or re-filter
  ```
- Suggested fix: Extract the default-provider-selection logic into a helper function `fn resolve_default_provider(app_config, providers, has_key) -> Option<String>`, and call it once at the top of `build_multi_provider_registry`. Use the result in both branches.
- Confidence: 0.70
