### B9-01 [P1] Invalid default config is replaced by defaults instead of failing startup
- Location: src/bin/aleph-server/commands/start/helpers.rs:198-207 (`load_gateway_config`)
- Failure mode: An existing default `config.toml` that is unreadable, malformed, or fails validation causes the server to boot with `FullGatewayConfig::default()`. The operator's bind, TLS, origin, authentication-adjacent, and agent settings are silently discarded; in daemon mode even the warning is suppressed, so the service can come up on a different, less restrictive configuration than configured.
- Evidence: `Err(e) => { if !args.daemon { eprintln!("Warning: {e}, using defaults"); } FullGatewayConfig::default() }`; `FullGatewayConfig::load_default()` returns an error whenever an existing file fails `load`, including parse and validation errors.
- Suggested fix: Preserve the no-config-file default inside `load_default`, but propagate every error from an existing default file from `load_gateway_config`, just as the explicit `--config` branch already does. Do not change the behavior when no config file exists.
- Confidence: 0.98

### B9-02 [P1] Unknown session-store backend silently selects SQLite
- Location: src/bin/aleph-server/commands/start/helpers.rs:232-318 (`initialize_session_store`)
- Failure mode: A typo or obsolete value such as `session_store_backend = "files"` takes the catch-all SQLite branch. Startup reports success against a different database instead of rejecting the configuration, making existing file-backed sessions appear lost and splitting new history into the wrong store.
- Evidence: `if backend == "file" { ... } else { // SQLite default ... SessionManager::with_defaults() ... }` accepts every non-`file` string as SQLite.
- Suggested fix: Match explicitly on `"file"` and the supported SQLite spelling(s), and return an error naming the invalid value for every other string. Keep the configured shipped default unchanged.
- Confidence: 0.95

### B9-03 [P2] Runtime warmup performs unbounded blocking subprocess and file I/O on a Tokio worker
- Location: src/bin/aleph-server/commands/start/runtime_warmup.rs:26-62 (`runtime_startup_warmup`; spawned at src/bin/aleph-server/commands/start/mod.rs:174)
- Failure mode: A runtime executable that hangs on `--version`, or blocking filesystem access on a slow/frozen home filesystem, blocks the Tokio worker running this spawned task indefinitely. The detached warmup never finishes or persists its ledger, and enough such blocking startup work can delay unrelated server tasks on the same runtime.
- Evidence: The async function directly calls synchronous `migrate_from_legacy`, `runtimes::probe::probe`, and `CapabilityLedger::persist`. `probe` reaches `std::process::Command::output()` in `src/runtimes/probe.rs:128,444`, which waits for process exit with no timeout; ledger load/persist use `std::fs` in `src/runtimes/ledger.rs:124,330-348`.
- Suggested fix: Move the synchronous ledger operations and each probe to `tokio::task::spawn_blocking` (and await their results), and bound subprocess version probes with a timeout. Preserve best-effort warmup semantics by logging probe/join failures and continuing to the remaining specs.
- Confidence: 0.99
