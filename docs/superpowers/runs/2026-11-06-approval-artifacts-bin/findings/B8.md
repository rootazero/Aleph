### B8-01 [P2] Channel-pairing credential store falls back to a predictable, world-readable `/tmp` path

**Location:** `src/bin/aleph-server/commands/start/mod.rs:859-866` (path fallback at :861-862)

```rust
let pairing_store_path = alephcore::utils::paths::get_pairing_db_path()
    .unwrap_or_else(|_| PathBuf::from("/tmp/aleph_pairing.db"));
let store = SqlitePairingStore::new(&pairing_store_path)
```

**Failure mode:** `get_pairing_db_path()` → `get_data_dir()` (`src/utils/paths.rs:413-415` → `:380-389`) fails when `HOME`/`USERPROFILE` is unset **or** when `create_dir_all(<data_dir>)` fails (read-only home, service account without a writable home). The fallback is a *fixed* path: `/tmp/aleph_pairing.db`. Two consequences on a shared host:
1. **Cross-tenant mixing** — two daemons whose data dir is unresolvable open the *same* file, so user A's `approved_senders` allowlist authorizes user B's channel (and B's pairing requests are visible to A).
2. **Local disclosure** — the file is created by `rusqlite::Connection::open` (`src/utils/sqlite_open.rs:23`) with the default umask (0644) and no permission hardening, so the pairing `code` values and the approved-sender allowlist (`src/gateway/pairing_store.rs:194-210`) are readable by any local user; the `-wal`/`-shm` sidecars inherit the same mode.

**Evidence:** `get_data_dir()` returns `Err` for an undeterminable home (`src/utils/paths.rs:381-385`) *and* for a `create_dir_all` failure (`:386-387`) — the second case is realistic for a system service with a non-writable home. `open_sqlite_safe` performs no `chmod`/`set_permissions` (`src/utils/sqlite_open.rs:12-31`).

**Suggested fix:** don't fall back to a fixed world path for a credential store. Either fail boot with the real reason, or use a per-process private path (`std::env::temp_dir().join(format!("aleph-pairing-{}.db", std::process::id()))`) with `OpenFlags`/0600 permissions, and `log::warn` with the resolved path.

**Confidence:** 0.6

### B8-02 [P2] Pairing store silently degrades to in-memory: durable credentials are lost while the RPCs keep answering

**Location:** `src/bin/aleph-server/commands/start/mod.rs:863-869`

```rust
let store = SqlitePairingStore::new(&pairing_store_path)
    .or_else(|e| {
        eprintln!("Warning: Failed to create pairing store: {e}. Using in-memory.");
        SqlitePairingStore::in_memory()
    })
    .map_err(|e| format!("Failed to create pairing store: {e}"))?;
```

**Failure mode:** the on-disk pairing DB exists but is unreadable/corrupt (schema migration error, disk I/O error, wrong permissions after a home-directory move). `SqlitePairingStore::new` fails → the store silently becomes `in_memory()`. The failure is announced only on **stderr** (`eprintln!`), never through `tracing`, so in daemon mode (stdout/stderr redirected to `server.log`, and the tracing console layer dropped when stdout is not a TTY) the operator sees nothing in the log stream that is actually consulted. Consequences:
- Every previously issued pairing credential is **gone** (the old file is not read) — every paired channel must be re-paired, with no error surfaced on the channel that asks for it.
- Newly approved pairings are written to RAM and vanish on the next restart, so a channel appears approved in the UI and is rejected after a restart — the approval looks durable but is not.
- `channel.pairing.*` RPCs keep answering `200 OK` from the in-memory store, so nothing in the API surface distinguishes "paired" from "paired, but only until the next restart".

**Evidence:** the `or_else` arm swallows the open error entirely (no `tracing::warn!`, unlike every other degraded arm in this file, e.g. the MCP manager at :366-372 and the hub catalog at :1433-1446). `SqlitePairingStore::in_memory()` is documented as "for testing" (`src/gateway/pairing_store.rs:168-169`) yet is now the production fallback.

**Suggested fix:** treat a failed pairing-store open as fatal (or as an explicit degraded state surfaced on the capability roster, like `install_degraded_users_store` does for the users table at :628-636). At minimum log through `tracing::warn!` with the path, and expose "pairing state is not durable" to `channel.pairing.list`.

**Confidence:** 0.55

### B8-03 [P3] A2A tools stay registered but permanently dead when the execution adapter is missing; the error names the wrong cause and daemon mode logs nothing

**Location:** `src/bin/aleph-server/commands/start/mod.rs:1417-1419` (handle creation), `:1498` (handed to the agent/tool registry), `:2607-2615` (deps stored **only** inside the exec-adapter branch), `:2649-2651` (the `else if !args.daemon` arm)

```rust
if let (Some(exec_adapter), Some(registry)) = (execution_adapter, agent_registry) {
    …
    if let Some(ref handle) = a2a_tool_handle {
        handle.store(Some(Arc::new(A2AToolDeps { … })));   // :2608
    } else {
        tracing::warn!("A2A enabled but tool handle missing — a2a_* tools unavailable");
    }
} else if !args.daemon {
    println!("A2A: skipping server (no execution adapter available)");
}
```

**Failure mode:** `[a2a] enabled = true` but the boot has no execution adapter (no provider API key → the agent stack is not constructed) and/or no agent registry. The `a2a_delegate` / `a2a_agents` builtin tools are still registered in the tool registry, but `handle.store(...)` never runs, so every call returns the uniform tool error `"A2A subsystem is not available. Enable it with `[a2a] enabled = true` in the Aleph config and restart."` (`src/builtin_tools/a2a_tools.rs:63-70`) — advice that is wrong, because the operator already enabled A2A. In daemon mode the `else` arm prints nothing at all (it is gated on `!args.daemon`), and the `tracing::warn!` inside the taken branch is unreachable in this scenario → **zero diagnostics**: the A2A HTTP endpoints (`/a2a`, `/a2a/stream`, `/.well-known/agent-card.json`) are silently absent and the LLM is told a config knob is wrong.

**Evidence:** `a2a_tool_handle` is created unconditionally when the section is enabled (:1417-1419) and passed into `register_agent_handlers` (:1498) — i.e. the tools are registered *before* the branch that decides whether they can ever work; the only diagnostic for the missing-adapter case is a `println!` behind `!args.daemon` (:2650).

**Suggested fix:** in the missing-adapter branch, (a) log through `tracing::warn!` unconditionally, and (b) make the tool error name the real cause (or decline/remove the tools). Move the "did the A2A server come up" decision before the tools are registered so the tool surface matches reality.

**Confidence:** 0.6

### B8-04 [P2] The spend ledger's durability guarantee is false when the security store fell back to memory

**Location:** `src/bin/aleph-server/commands/start/mod.rs:606-620` (install), vs. `src/bin/aleph-server/commands/start/builder/subsystems.rs:174-232` (`initialize_vault` fallback)

```rust
// Install the durable per-principal spend ledger on the same
// `SecurityStore` every other durable consumer shares … so no request or
// LLM call ever sees the process fall back to `spend::InMemorySpendLedger`,
// whose rows do not survive a restart.
alephcore::spend::install_ledger(Arc::new(alephcore::spend::sqlite::SqliteSpendLedger::new(
    auth_bundle.security_store.clone(),
)));
```

**Failure mode:** `initialize_vault` falls back to `SecurityStore::in_memory()` when the on-disk security store cannot be opened, and reports that through `auth_bundle.security_store_fallback = Some(reason)`. The code *does* branch on that flag for the users table (`match auth_bundle.security_store_fallback.clone() { None => install_users_store(…), Some(reason) => install_degraded_users_store(…) }`, :628-636) — but the spend ledger is installed **unconditionally** on top of that same, possibly in-memory, store. `SqliteSpendLedger` owns no connection of its own; its rows live in the `SecurityStore`'s `spend_ledger` table (`src/spend/sqlite.rs:1-12, 77-87`). So in the degraded case the "durable" ledger is backed by RAM: every restart zeroes the per-principal, per-period totals, and the admission check that reads it (`src/spend/mod.rs:785` → `check_with(principal, now_ms, &policy, &*global_ledger())`) sees a fresh budget. The configured per-user/per-machine USD ceiling can therefore be bypassed simply by restarting the daemon — exactly the outcome the comment claims cannot happen.

**Evidence:** `SqliteSpendLedger::new(store)` takes the shared store and its module doc states the ledger's rows are a table *inside that store* (`src/spend/sqlite.rs:1-12`); `SecurityStore::in_memory()` is not file-backed (`src/bin/aleph-server/commands/start/builder/subsystems.rs:174-232`).

**Suggested fix:** branch on `auth_bundle.security_store_fallback` for the ledger too — refuse to install a ledger that claims durability over an in-memory store (or install it with an explicit "degraded / non-durable" marker surfaced on the capability roster and in `spend.query`), and correct the comment so it does not assert a guarantee the code does not provide.

**Confidence:** 0.55

### B8-05 [P2] Provider build errors are swallowed: the provider's models silently vanish from the OpenAI-compatible routing table

**Location:** `src/bin/aleph-server/commands/start/mod.rs:1794-1812`

```rust
for (name, config) in &app_cfg.providers {
    provider_configs.push((name.clone(), config.clone()));
    if let Ok(http_provider) = build_http_provider(name, config) {   // :1801 — Err dropped
        let provider = Arc::new(http_provider);
        for model in &config.models {
            provider_map.entry(model.clone()).or_insert_with(|| provider.clone());
        }
    }
}
server.openai_provider_map = Arc::new(provider_map);
```

**Failure mode:** `build_http_provider` returns `Err` for an unknown `protocol` (`src/bin/aleph-server/commands/start/helpers.rs:549-551`) or for an invalid provider config (`:553`). The `Err` is discarded with no `tracing::warn!`, so the provider contributes **no** models to `server.openai_provider_map` — the routing table used by the OpenAI-compatible surface (`src/gateway/server/mod.rs:1006` → `src/gateway/openai_api/completions/passthrough.rs:152-156` and `src/gateway/openai_api/responses/mod.rs:79-83`). A client calling `POST /v1/chat/completions` with that model gets `404 Model '<name>' not found`, i.e. a *model* error for a *provider configuration* error. The operator's only symptom is a 404 that names the wrong thing; the log contains nothing about the provider that failed to build.

**Evidence:** no `tracing::warn!`/`eprintln!` on the `Err` arm; the sibling degraded paths in the same function all log (e.g. :366-372 MCP manager, :1433-1446 hub catalog, :1770-1772 background journal).

**Suggested fix:** log the provider name and the error (`tracing::warn!(provider = %name, error = %e, "provider failed to build; its models are unavailable")`) and keep the provider in `provider_configs` with a "not ready" marker so `providers.list` can show *why* its models are unroutable.

**Confidence:** 0.7

### B8-06 [P2] Duplicate model names across providers bind to a random provider (HashMap iteration order)

**Location:** `src/bin/aleph-server/commands/start/mod.rs:1797-1807` (same block as B8-05)

```rust
provider_map.entry(model.clone()).or_insert_with(|| provider.clone());
```

**Failure mode:** `Config.providers` is a `HashMap<String, ProviderConfig>` (`src/config/structs.rs:64`), so the iteration order at :1799 is randomized per process. When two providers advertise the same model name (an official vendor entry plus a proxy entry, or the same vendor configured under two names), `or_insert_with` keeps the **first** one seen — which changes from boot to boot. The OpenAI-compatible surface therefore routes the same model to a different provider after each restart, with no log line: requests may start failing with an auth error from the provider that was silently demoted, or (worse) may be billed to the other account.

**Evidence:** `pub providers: HashMap<String, ProviderConfig>` (`src/config/structs.rs:64`); Rust's `HashMap` iteration order is not stable across processes; the map is the sole model→provider lookup for `/v1/*` (`src/gateway/openai_api/state.rs:26`, `completions/passthrough.rs:152-156`, `responses/mod.rs:79-83`).

**Suggested fix:** make the binding deterministic — sort the providers by name before building the map (and log a warning when a model is claimed by more than one provider, naming both), so a duplicate is an explicit, visible configuration conflict rather than a per-boot coin flip.

**Confidence:** 0.55

### B8-07 [P3] Boot prints "Task reaper: started" even when the reaper was disabled and never spawned

**Location:** `src/bin/aleph-server/commands/start/mod.rs:3053-3057`

```rust
let _ = alephcore::tasks::shared::reaper::spawn_task_reaper(reaper_cfg, subs, rx);
if !args.daemon {
    println!("Task reaper: started");
}
```

**Failure mode:** `spawn_task_reaper` returns `None` when `!config.enabled` (`src/tasks/shared/reaper.rs:136-139`) or when a reaper is already running (`:140-143`). `reaper_cfg` comes straight from the user config (`app_cfg.tasks_reaper.clone()`, :3011-3017), so `[tasks_reaper] enabled = false` is a supported operator setting — and the boot output still claims "Task reaper: started". The operator believes history rows (`cron_job_runs`, `heartbeat_runs`) are being pruned; they are not, and the tables grow unbounded. The `let _ =` also discards the `JoinHandle`, so there is no way to tell "disabled" from "spawned" after the fact.

**Evidence:** `spawn_task_reaper` returns `Option<JoinHandle<()>>` and returns `None` in exactly the two cases above; the return value is dropped at :3053.

**Suggested fix:** branch on the returned `Option` and print "skipped (disabled via config)" / "already running" accordingly; keep the `JoinHandle` so the reaper can be joined during the teardown funnel (:3941+) instead of being abandoned to runtime teardown.

**Confidence:** 0.7

## Checked and deliberately NOT reported (hypotheses that did not survive verification)

- **`config.reload` drops the vault-hydrated provider `api_key`.** `handle_reload_with_subsystems` replaces the whole config (`src/gateway/handlers/config.rs:96-98`) without re-hydrating from the vault, so the live config's `api_key` becomes `None`. Verified as harmless: the live targets are `behavior`/`execution`/`search`/`policies.*` only (`src/config/reload_impact.rs:84,119`), no provider is rebuilt after boot (`build_http_provider` is called only at `start/mod.rs:1801`), and every runtime consumer re-resolves its own secret from the vault (`src/gateway/health_prober.rs:176-179`, `src/gateway/codex_token_refresher.rs:172-174`, `src/gateway/voice/format.rs:126`, `src/search/handle.rs:124-146`).
- **Two `CatalogCache` instances over one `hub_catalog.db`.** The cache is a thin SQLite wrapper with no in-memory copy (`src/hub/cache.rs:141-159`) and `busy_timeout=5000`, so the two connections see each other's committed writes; the code documents the intent (`start/mod.rs:1425-1428`).
- **Memory runtime mounted before it is started.** `ProjectionHost::mount_with_memory` only registers a provider handle (`src/capability/zahir_facade.rs:137-152`); the runtime state is propagated through `provider.transition(...)` when `start()` runs (`src/memory/runtime/mod.rs:221-253`), and `MemoryRuntime::stop()` on a never-started runtime returns immediately instead of hanging (`src/memory/runtime/mod.rs:255-289`).
- **Detached tasks leaking when a later phase fails.** Every fatal `?` in the boot path propagates out of `start_server` → `main.rs:424` → the process exits, so detached tasks cannot outlive the failed boot; `StartupResources::finish` covers memory + projection host (`builder/startup_resources.rs:36-60`).
- **`let _team_sub = GlobalBus::global().subscribe_async(...)` unsubscribes.** `subscribe_async` returns a plain `SubscriptionId` with no `Drop` guard (`src/event/global_bus.rs:319`), so dropping the binding does not cancel the subscription.
- **`let _event_tx = acp::manager::wire_persistence(&manager)` closes the ACP event channel.** The manager hook holds an `Arc` clone of the sender, so the channel stays open after the local binding is dropped.
- **Port binding happens ~3700 lines after the bind probe.** The probe (`helpers.rs:62-69`) releases the socket, so the real bind at `run_until_shutdown` can still fail — but the failure surfaces as `run_result?` *after* the full teardown funnel has run (`start/mod.rs:3900-4205`), so no half-initialized state survives.
