### B13-01 [P1] Re-indexing an existing database retains sessions absent from the source
- Location: src/bin/aleph-migrate/index.rs:23,127-225 (`run_index`, `index_sessions`, `index_single_session`)
- Failure mode: Run `index` against an existing `metadata.db` after removing or renaming a Markdown session; the old session/agent/workspace rows are never deleted, so the resulting index reports and serves data that is not in the migration source.
- Evidence: `Connection::open(&output_db)` is followed only by `INSERT OR IGNORE` / `INSERT OR REPLACE`; there is no reconciliation or staging-table replacement for rows not visited in `session_paths`.
- Suggested fix: Build the complete index in a fresh temporary database and atomically replace the target, or reconcile all existing keys in one transaction; do not delete the only good target before the replacement is known valid.
- Confidence: 0.98

### B13-02 [P1] A mid-index error commits a partially updated target
- Location: src/bin/aleph-migrate/index.rs:23-34,127-225 (`run_index`, `index_sessions`, `index_single_session`)
- Failure mode: A malformed later `metadata.json` or attachment manifest returns an error after earlier sessions have already been inserted/replaced; the failed command nevertheless leaves an existing target database partially migrated, with no automatic rollback to its pre-run state.
- Evidence: `index_single_session` performs several independent `conn.execute` calls and `index_sessions` simply propagates `?`; no transaction or temporary target surrounds the batch.
- Suggested fix: Index into a fresh temporary file (preferred for rebuild semantics) or use one transaction covering session, attachment, and FTS updates; preserve the previous database on every error.
- Confidence: 0.98

### B13-03 [P1] Removing a transcript leaves its old FTS content searchable
- Location: src/bin/aleph-migrate/index.rs:307-339 (`build_fts5_index`)
- Failure mode: Index a session with a transcript, delete that transcript, then run `index` without `--rebuild-fts`; the early `continue` skips the delete for that session and the old full transcript remains in `session_transcripts_fts`.
- Evidence: `if !transcript_path.exists() { continue; }` occurs before `DELETE FROM session_transcripts_fts WHERE session_id = ?1`.
- Suggested fix: Delete the session's old FTS rows before testing/reading the transcript, then insert only when the file exists.
- Confidence: 1.0

### B13-04 [P1] Attachment metadata lookup errors are exported as “no attachments”
- Location: src/bin/aleph-migrate/export.rs:315-323 (`load_attachments`)
- Failure mode: If `PRAGMA table_info(attachments)` fails because of an SQLite I/O/schema error rather than a genuinely absent table, export silently writes every session with an empty attachment list and exits successfully, producing an incomplete migration artifact.
- Evidence: `let columns = match table_columns(conn, "attachments") { Ok(columns) => columns, Err(_) => return Ok(vec![]), };` discards every error kind.
- Suggested fix: Distinguish a verified absent table from query/prepare failures; return absent only for the former and propagate the latter with context.
- Confidence: 0.96

### B13-05 [P1] Failed JSON serialization can destroy the previous export and leave a truncated artifact
- Location: src/bin/aleph-migrate/export.rs:210-212 (`run_export`)
- Failure mode: With `--force`, a disk-full/write/serialization failure after `File::create` truncates the prior good export and leaves a partial JSON file; even on a new path, a failed run leaves a corrupt artifact that looks like the requested output.
- Evidence: `std::fs::File::create(&output_path)` writes directly to the destination followed by `serde_json::to_writer_pretty(file, &export_data)?`.
- Suggested fix: Serialize to a uniquely named temporary file in the destination directory, flush/close it successfully, then atomically rename it over the destination; clean up the temporary file on failure.
- Confidence: 0.99

### B13-06 [P1] Overwrite failures corrupt previously transformed sessions
- Location: src/bin/aleph-migrate/transform.rs:105-150,211,262,290 (`transform_session`, `write_transcript`, `write_tool_outputs`, `write_metadata`)
- Failure mode: With `--overwrite`, an attachment decode/write failure or disk-full error after one of the direct file writes leaves the pre-existing session with a mixture of new and old files (and potentially truncated JSON/Markdown); the cleanup path explicitly skips every directory that existed before the run.
- Evidence: Existing directories are written in place, while `if result.is_err() && !existed { let _ = fs::remove_dir_all(&session_dir); }` preserves the partially overwritten directory on error.
- Suggested fix: Build each replacement session in a temporary sibling directory and swap only after every file and attachment succeeds, retaining/restoring a backup of the old directory on failure.
- Confidence: 0.99

### B13-07 [P1] A failed attachment write is later trusted as a complete deduplicated file
- Location: src/bin/aleph-migrate/transform.rs:350-384 (`store_attachment`)
- Failure mode: If `write_all` fails (for example, disk full), the truncated content-addressed file remains. A retry sees `target_path.exists()` and, without checking length or digest, emits a successful manifest pointing to those corrupt bytes.
- Evidence: The create/write branch returns the write error without removing the new file; the existing-file branch checks only canonical path containment.
- Suggested fix: Write to a temporary file in the target directory, verify size/hash, then atomically rename with no-clobber semantics; on every failure remove only the temporary file, and validate existing deduplicated files before referencing them.
- Confidence: 0.99

### B13-08 [P1] A valid relative output directory with no parent component is rejected
- Location: src/bin/aleph-migrate/transform.rs:31-36,154-166 (`run_transform`, `migration_root`)
- Failure mode: Run `aleph-migrate transform --input export.json --output sessions --attachments-dir ...`; `Path::parent()` yields an empty path for bare `sessions`, and canonicalizing that empty migration root fails before any sessions can be transformed.
- Evidence: `output_dir.parent()` is accepted as the root, then `fs::canonicalize(&migration_root)?` is called without converting an empty parent to `.` or first absolutizing the output path.
- Suggested fix: Normalize relative paths against `current_dir` before deriving the migration root, or map an empty parent to `.`; preserve the existing `raw/sessions` special case.
- Confidence: 0.95

### B13-09 [P2] Out-of-range timestamps are silently replaced with the current time
- Location: src/bin/aleph-migrate/transform.rs:425-429 (`format_timestamp`)
- Failure mode: An export containing an invalid/out-of-range `started_at` or message timestamp produces plausible Markdown stamped with the operator's current time instead of reporting bad source data, silently falsifying migrated history and making results nondeterministic.
- Evidence: `DateTime::from_timestamp(ts, 0).unwrap_or_else(Utc::now)` substitutes `Utc::now()` on conversion failure.
- Suggested fix: Return a validation error identifying the session/message timestamp, or preserve an explicit invalid-timestamp marker without inventing a date.
- Confidence: 0.97

### B13-10 [P1] Filesystem-only sessions can still produce a successful verification
- Location: src/bin/aleph-migrate/verify.rs:56-59,104-127,137-190 (`run_verify`, `check_session_count`, `check_session_files`)
- Failure mode: A valid attachment-free session directory is present on disk but missing from `metadata.db`; without `--original-db`, verification records only a count warning. All per-session checks iterate database IDs, so the command prints `Migration Status: SUCCESS` and exits 0 despite the unindexed session.
- Evidence: The database/filesystem count branch only executes `report.warnings.push(...)`; `run_verify` fails solely on `report.errors > 0`, and `check_session_files` obtains IDs with `SELECT session_id FROM sessions`.
- Suggested fix: Treat database/filesystem session-key mismatches as errors and explicitly enumerate/reconcile both directions, rather than relying only on directory counts.
- Confidence: 1.0

### B13-11 [P1] FTS verification does not check transcript coverage or stale rows
- Location: src/bin/aleph-migrate/verify.rs:644-679 (`check_fts5_index`)
- Failure mode: If every transcript is absent from the FTS table, verification emits only `FTS5 index is empty` and can still return success; if one unrelated row exists, any nonempty index that accepts a test query passes without checking missing or stale session IDs/content.
- Evidence: `Ok(0) => { report.warnings.push("FTS5 index is empty".to_string()); }`; the nonempty branch checks only whether `MATCH 'session'` returns an error.
- Suggested fix: Compare FTS session IDs and content against every filesystem transcript and reject unexpected IDs; an empty index with nonempty transcripts must be an error.
- Confidence: 1.0

### B13-12 [P0] Orphan cleanup deletes attachments owned by sessions whose directories are missing
- Location: src/bin/aleph-migrate/verify.rs:341-375,594-606 (`check_attachments`)
- Failure mode: With `--remove-orphans`, if a database session owns an attachment but its session directory is absent, no manifest contributes that hash to `referenced_hashes` and `manifests_complete` remains true. Verification then deletes the still-referenced attachment file, even though the earlier missing-files check has already recorded an error.
- Evidence: References are collected only by walking existing session directories, while deletion is `if !referenced_hashes.contains(&hash) && remove_orphans && manifests_complete { fs::remove_file(&path)?; }`; there is no guard for missing database sessions or prior verification errors.
- Suggested fix: Never sweep unless database and filesystem session sets fully reconcile and all checks needed to establish ownership pass; also protect every hash/path referenced by the database. Fail closed before any deletion.
- Confidence: 0.99

### B13-13 [P1] Identical bytes with different MIME types cannot be represented by the attachment index
- Location: src/bin/aleph-migrate/index.rs:99-108,274-292 (`init_schema`, `index_attachments`); src/bin/aleph-migrate/transform.rs:327-348 (`store_attachment`)
- Failure mode: Two attachments contain the same bytes but have different MIME types, producing valid paths such as `images/<hash>.png` and `documents/<hash>.bin`. Both manifests use the same full SHA-256 key, so the second `INSERT OR REPLACE` overwrites the first database row; indexing loses one path/MIME association and verification then reports a metadata mismatch.
- Evidence: The schema declares `content_hash TEXT PRIMARY KEY`, while each transform manifest carries its own `file_path` and `mime_type`; attachment insertion uses `INSERT OR REPLACE INTO attachments` keyed only by that hash.
- Suggested fix: Key attachment references by attachment ID (with a separate content-blob table keyed by hash), or include path/MIME identity in the reference schema; preserve byte-level deduplication without conflating distinct logical attachments.
- Confidence: 0.98

### B13-14 [P1] “Metadata consistency” accepts values that disagree with the database
- Location: src/bin/aleph-migrate/verify.rs:191-292 (`check_metadata_consistency`, `validate_metadata`)
- Failure mode: Edit a transformed `metadata.json` so `agent_id` or `started_at` differs from the corresponding row in `metadata.db` while retaining valid JSON types. Verification checks only field presence/types and the session ID, so it reports success despite contradictory migrated records.
- Evidence: `check_metadata_consistency` selects only `session_id` and calls `validate_metadata(&metadata, &session_id)`; no database fields are selected or compared.
- Suggested fix: Select the indexed metadata fields and compare each one with the JSON value, reporting every mismatch; auto-fix only when the database is explicitly designated as the source of truth.
- Confidence: 1.0

### B13-15 [P1] Metadata auto-fix splits legal tags containing commas
- Location: src/bin/aleph-migrate/index.rs:166-171 (`index_single_session`); src/bin/aleph-migrate/verify.rs:683-710 (`regenerate_metadata`)
- Failure mode: A session has a tag such as `foo,bar`, which is accepted in the export JSON. Indexing flattens it to the same string as two tags; if metadata is later missing/invalid and `verify --fix` regenerates it, the single tag becomes `["foo", "bar"]`, silently changing user data.
- Evidence: Indexing uses `.collect::<Vec<_>>().join(",")`, and regeneration reverses it with `s.split(',')`, which is not an invertible encoding for arbitrary accepted tag strings.
- Suggested fix: Store tags as a JSON array in the database and deserialize that array during repair; if compatibility requires comma text, reject commas at the input boundary instead of lossy round-tripping.
- Confidence: 0.98

### B13-16 [P1] Export succeeds after dropping source rows with null timestamps
- Location: src/bin/aleph-migrate/export.rs:161-172 (`run_export` row loop)
- Failure mode: A legacy session contains both timestamped rows and rows with a null timestamp. Export drops every null-timestamp row's content but still emits that session and exits successfully; comparing only distinct session counts during verification does not detect the missing messages.
- Evidence: `let Some(created_at) = created_at else { log::warn!("Skipping raw memory row without timestamp"); continue; };` discards the entire source row rather than failing or preserving its content with explicit timestamp semantics.
- Suggested fix: Fail the export with row/session context by default, or define a lossless fallback that preserves the row and marks its missing timestamp; never silently reduce message content in a successful full export.
- Confidence: 0.99

### B13-17 [P2] Missing attachment counts silently disable attachment indexing
- Location: src/bin/aleph-migrate/index.rs:173-175,249-253 (`index_single_session`, `index_attachments`)
- Failure mode: If `metadata.json` lacks `attachment_count` or stores it with the wrong type but still has a valid nonempty `attachments.json`, indexing defaults the count to zero and returns before reading the manifest; the command reports success with all of that session's attachments absent from the database.
- Evidence: `let attachment_count = metadata["attachment_count"].as_i64().unwrap_or(0);` is followed by `if attachment_count == 0 { return Ok(()); }`.
- Suggested fix: Require a nonnegative integer count whenever indexing, and reject a missing/zero count when a nonempty manifest exists; apply the same validation to message/tool counts to avoid false zero metadata.
- Confidence: 0.99
