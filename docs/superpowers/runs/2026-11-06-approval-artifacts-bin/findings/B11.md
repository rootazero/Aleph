### B11-01 [P2] One fleet-wide `StreamRegistry` + mint-time TTL turns a per-caller voice stream into a cross-user liveness kill

- Location: `src/bin/aleph-server/commands/start/builder/handlers/settings.rs:690` (`stream_registry`), mechanism at `src/gateway/voice/streaming/relay.rs:27`, `relay.rs:61-71`, `relay.rs:86`
- Failure mode:
  1. *Eviction ignores ownership.* `settings.rs:690` creates **one** `StreamRegistry` shared by every connection, and `voice.stream.start` / `.audio` / `.stop` are member-reachable (`method_census.rs:472-475`, `Class::Open`). `insert` then enforces a single global cap by evicting the globally oldest entry:
     `while guard.len() >= MAX_ACTIVE_STREAMS { let oldest = guard.iter().min_by_key(|(_, e)| e.opened) ... guard.remove(&k) }` (`relay.rs:69-79`). Any member opening 8 concurrent streams therefore terminates another user's in-flight dictation — the sender drop closes that user's backend WS mid-utterance.
  2. *TTL is measured from mint, not from activity.* `opened: Instant::now()` is written once (`relay.rs:86`) and never refreshed, while reaping is `guard.retain(|_, e| e.opened.elapsed() < STREAM_TTL)` with `STREAM_TTL = Duration::from_secs(10 * 60)` (`relay.rs:32`, `relay.rs:68`). A *healthy* continuous dictation/meeting transcript older than 10 minutes is destroyed the next time **any** client starts any stream — no cap message is logged for that path (`tracing::warn!` only fires inside the `while` loop).
- Evidence:
  - `const MAX_ACTIVE_STREAMS: usize = 8;` / `const STREAM_TTL: Duration = Duration::from_secs(10 * 60);` (`relay.rs:27`, `relay.rs:32`)
  - `guard.retain(|_, e| e.opened.elapsed() < STREAM_TTL);` (`relay.rs:68`) with `opened: Instant` set only at `relay.rs:86`
  - `let stream_registry = Arc::new(alephcore::gateway::voice::streaming::StreamRegistry::default());` (`settings.rs:690`)
- Scope note: liveness/DoS only — per-stream *ownership* is correctly enforced (`caller_may_act_on_known_id` / `caller_may_use` over `StreamEntry.owner`, `relay.rs:37-49`), so no audio is disclosed to another caller.
- Suggested fix: enforce the cap per owner (count entries by `owner`, keep the global 8 as a hard ceiling) at the `insert` boundary; refresh the entry's activity stamp from `stream.audio` frames and reap on *idle* time (`last_frame`) rather than `opened`.
- Confidence: 0.6

### B11-02 [P3] Dead duplicate memory-context factories; the live path already diverges, and config docs point at the dead one

- Location: `memory.rs:157` (`init_memory_context_provider`), `memory.rs:190` (`init_memory_context_provider_with_extensions`)
- Failure mode: neither function has a call site anywhere in the repo (grep hits are the definitions plus prose). Production builds the provider in `src/memory/runtime/services.rs:102-131`. Because the dead bodies are maintained in parallel, they have already drifted: the dead pair omits `with_curated_root(inputs.curated_root)` and `with_open_loop_injection(...)`, uses `new`/`with_provider` instead of `assemble_at`, and has no `memory.profile.enabled` gate — whereas `services.rs` has all four. `src/config/types/memory/ingest.rs:121-128` documents the curated-ingest wiring by *naming* `init_memory_context_provider_with_extensions`, so a maintainer "fixing" that knob edits a function that never runs — exactly the failure `memory.rs:150-156`'s own doc says already shipped once. If someone re-wires the dead pair instead, curated notes silently resolve against the default root (not `inputs.curated_root`) and open-loop injection config stops applying.
- Evidence:
  - `pub(in crate::commands::start) fn init_memory_context_provider(` (`memory.rs:157`) — zero callers
  - dead body: `.with_curated_config(curated)` (`memory.rs:227`) with no `.with_curated_root(..)` anywhere in the file
  - live body: `.with_curated_config(memory.curated.clone().into()).with_curated_root(inputs.curated_root.clone())` (`src/memory/runtime/services.rs:102-131`)
- Suggested fix: delete both functions (and repoint `src/config/types/memory/ingest.rs:121` and `src/thinker/memory_context_provider/constructor.rs:502` at `MemoryRuntimeServices`), or make the dead pair a thin delegation to the live builder so there is exactly one body.
- Confidence: 0.9 (deadness), 0.6 (drift harm)

### B11-03 [P3] Absent optional subsystems answer `-32601` instead of the codebase's typed `SERVICE_UNAVAILABLE` contract

- Location: `settings.rs:693-712` (`voice.stream.*`), `settings.rs:1030-1040` (`voice.synthesize`), `settings.rs:435-520` region (`providers.*` arms) — same shape inside `register_config_handlers`
- Failure mode: `voice.synthesize` is registered only inside `if let Some(gen_reg) = generation_registry` (`settings.rs:1030`), and `acp.*` only when the ACP adapter is present; there is **no** placeholder for these in `HandlerRegistry::new()` (`src/gateway/handlers/mod.rs` has no `acp.` / `voice.synthesize` / `voice.stream.*` entries). So on a deployment without TTS/ACP the Panel's request returns `-32601 MethodNotFound`, while the same file's `memory.curated.*` verbs answer the intended shape (`SERVICE_UNAVAILABLE` + `"memory_unavailable"`, `memory.rs:114-148`, asserted by `memory_lifecycle_tests.rs:59-100`). A client that switches on the error code (as the Panel does for `admin_refusal` / service-unavailable) cannot distinguish "feature disabled on this deployment" from "server built wrong".
- Evidence:
  - `if let Some(gen_reg) = generation_registry { register_handler!(server, "voice.synthesize", ...) }` (`settings.rs:1030-1040`)
  - registered-but-unavailable precedent: `memory.curated.*` closures at `memory.rs:114-148`
- Suggested fix: always register these methods and let the handler answer `SERVICE_UNAVAILABLE` when the optional context is `None` (the `sessions`/daemon registrations in the sibling files already do this with `Option` + `None`-aware handlers).
- Confidence: 0.45 (may be a deliberate "absent = not advertised" choice; flagging because the file applies two different encodings for the same situation)

### B11-04 [P3] Five parallel hot/cold `providers.*` arms make provider semantics depend on which arm a verb was added to

- Location: `settings.rs:435`, `settings.rs:457`, `settings.rs:477`, `settings.rs:500` (`if let Some(ref registry) = multi_registry` blocks) inside `register_config_handlers` (`settings.rs:338`, 8 parameters)
- Failure mode: each provider verb is written twice — once with the hot registry, once without — and the cold twin is a *different* handler with different semantics (`providers.setDefault` cold → `handle_set_default_config_only`, which never hot-swaps the live instance nor injects a vault key, unlike the hot arm). Adding a new provider verb, or fixing only the hot arm, yields a deployment-dependent behaviour (dev/test/cold = config-only no-op reported as success; production = live swap and `ConfigChanged` broadcast) with no compile-time or test-level signal. Drift is silent because both arms answer `success`.
- Evidence:
  - `if let Some(ref registry) = multi_registry { ... }` repeated at `settings.rs:435/457/477/500`
  - `handle_set_default_config_only` path (cold) vs populated-registry path (hot) in the `providers.setDefault` registration
- Suggested fix: register once per verb and let the handler accept `Option<Arc<..>>` (as `handle_set_default` already does via `run_registry: Option<..>`), so there is one registration site and the config-only fallback is an explicit branch inside the handler that the tests can target.
- Confidence: 0.4 (maintainability hazard with a concrete divergence; not currently a live bug)
