## Findings by severity

### F-01 [P1] Synchronous blocking file I/O inside async function (node.rs)
- Location: src/bin/aleph-server/commands/node.rs:193 (persist_identity → write_identity)
- Failure mode: `persist_identity(path, id)` calls `write_identity(path, id)` which executes `std::fs::write(path, json)` — synchronous, blocking I/O. This is invoked from the `on_identity` closure (line 191-201) called during `run_session` (line 401-415), which is an async function. If `persist_identity` blocks while writing the identity file to disk, it stalls the tokio executor. A slow filesystem, network mount, or heavily-contended I/O can cause the entire connection event loop to freeze, blocking other spawned tasks from running.
- Evidence: Line 101 in `write_identity`: `std::fs::write(path, json)?;`. Called from line 197 in `persist_identity`. Invoked from line 199 in `on_identity` closure (synchronously called at line 404).
- Suggested fix: Wrap the `persist_identity` call in `tokio::task::spawn_blocking` to move the I/O work to a dedicated thread pool, allowing the async executor to continue. Alternatively, use `tokio::fs::write` instead of `std::fs::write` and mark `write_identity` as async.
- Confidence: 0.9

### F-02 [P1] Privilege escalation in plugins.rs: unvalidated symlink in uninstall path
- Location: src/bin/aleph-server/commands/plugins.rs:209-220 (handle_plugins_uninstall function)
- Failure mode: The uninstall function validates the plugin name with `is_safe_plugin_dir_name` (line 206), which rejects path separators, `.`, and `..` to prevent escape from the plugins root. However, after this check, it inspects the path with `std::fs::symlink_metadata` (line 215) and refuses to follow symlinks (line 219). The issue: if a user (or attacker with local access) creates a symlink **inside** the plugins directory with a safe name (e.g., `plugins/legit` → `../../sensitive`), the `symlink_metadata` check catches it. However, the code then calls `tokio::fs::remove_dir_all(&plugin_path).await` (line 233) on the validated path. If the symlink is followed by the async fs op (which depends on Tokio's underlying platform behavior), it could delete files outside the plugins directory.
- Evidence: Line 206 validates name with `is_safe_plugin_dir_name`. Line 215 checks `symlink_metadata`. Line 219 guards against symlinks. Line 233 removes `plugin_path` recursively. The guard at line 219 exists, so the actual risk is if `tokio::fs::remove_dir_all` follows symlinks despite the check (platform-dependent behavior).
- Suggested fix: The guard is correct and catches this. However, document that `remove_dir_all` on a symlink is a no-op (removes the link itself, not its target). The code is currently safe due to the check at line 219.
- Confidence: 0.3 (retract: code is defensively correct)

### F-03 [P1] Process::exit called on error paths in plugins.rs without cleanup
- Location: src/bin/aleph-server/commands/plugins.rs (13 process::exit call sites per brief)
- Failure mode: The file calls `std::process::exit(1)` on multiple error paths (lines ~110, 127, 131, 139, 163, 188, 206, 245, 324, 334, 439, 449, 504). Each call terminates the process immediately without running Drop implementations or async cleanup. If any resource (temp files, open database handles, spawned tasks) is held at the time of the exit, it will leak. The brief specifically asks: "check that an exit skips required cleanup (temp files, open db)". Examining the handlers: `handle_plugins_install` (line 87-170) does clone git repositories. If git clone fails and calls `std::process::exit(1)` at line 127, any partially-cloned repository is left behind.
- Evidence: Line 110: `std::process::exit(1);` after failed repo name derivation. Line 127: `std::process::exit(1);` after symlink/traversal check fails. Line 139: `std::process::exit(1);` after plugin already exists. Line 163: `std::process::exit(1);` after clone fails — at this point git has already created `dest_path_clone` and begun cloning; the exit will leave a partial repo.
- Suggested fix: Replace `std::process::exit(1)` with `return Err(...)` to allow proper cleanup, or ensure all critical resources are cleaned up before the exit (e.g., remove the partial clone directory before exiting). Use explicit try-finally or RAII guards to ensure cleanup always happens.
- Confidence: 0.7

### F-04 [P2] Implicit panic on path construction in resume.rs
- Location: src/bin/aleph-server/commands/resume.rs:18-19 (handle_resume_command function)
- Failure mode: The function constructs a data directory path and passes it to `run_no_lock(|| forward_to_server(&data_dir, ...))`. If `paths::get_data_dir()` fails, the error is immediately returned (which is correct). However, if forward_to_server (or downstream IPC code) expects a valid, writable directory and encounters a filesystem error, there is no defensive handling. More specifically: line 19 passes `&data_dir` to `run_no_lock`, which wraps it in a closure. If the data directory does not exist or is unreadable, the error is propagated as a Box<dyn Error>. This is correct behavior and not a defect.
- Evidence: Line 18: `paths::get_data_dir()` can return Err, which is propagated. Line 19: `run_no_lock(|| ...)` closure captures `&data_dir` and passes it to `forward_to_server`.
- Suggested fix: None; error handling is correct.
- Confidence: 0.0 (retract as false positive)

### F-05 [P2] Race condition: plugin discovery reads disk after enable/disable writes
- Location: src/bin/aleph-server/commands/plugins.rs:277-296 (set_enabled_locally function)
- Failure mode: The function calls `manager.discovered_plugin_ids()?` to verify a plugin name exists (line 283), then writes the preference to disk with `manager.set_plugin_enabled(name, enabled).await?` (line 287). Between these two operations, another process could delete the plugin directory or rename it, causing the write to succeed but target a non-existent plugin. However, the write targets `<data_dir>/plugins.toml`, not the plugin directory itself, so the TOCTOU window does not cause data loss or incorrect behavior — the preference is stored, and the daemon will later discover it refers to a missing plugin and simply skip it.
- Evidence: Line 283 reads `discovered_plugin_ids()`. Line 287 writes to plugins.toml. No filesystem operation directly mutates the plugin directory between these lines.
- Suggested fix: None; the operation is idempotent and safe. Recording a preference for a missing plugin is not an error.
- Confidence: 0.2 (retract: not a real defect)

### F-06 [P3] Dead code: #[allow(dead_code)] suppresses cross-platform warnings
- Location: src/bin/aleph-server/commands/service/descriptors.rs:22, 48, 80 (launchd_plist, systemd_unit, scheduled_task_xml)
- Failure mode: Three descriptor generators are marked `#[allow(dead_code)]` with a comment stating each is "used in production on one OS and tested on all". This suppression hides the warning on dev machines where only one platform is active. If a function is accidentally deleted or never actually called on its target platform, no warning will alert the developer. The cross-platform test suite catches this, but only if tests are run. Single-platform dev machines will silently compile even if a function is unused.
- Evidence: Lines 22, 48, 80 all have `#[allow(dead_code)]` with identical explanation.
- Suggested fix: Use `#[cfg_attr(target_os = "macos", allow(dead_code))]` etc. to suppress the warning only on the irrelevant platforms. This preserves the warning on platforms where the function is actually used, catching accidental deletions. Alternatively, wrap the functions in `#[cfg(test)]` (if they are only tested, not used in production), or verify at compile time that each function is called via conditional compilation.
- Confidence: 0.6
