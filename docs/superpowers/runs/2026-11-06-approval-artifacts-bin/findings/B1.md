### B1-01 [P1] The approval cascade resolves sibling cards whose originator never consented — the group-chat approval gate protects only the clicked id
- Location: src/approval/callback_sink.rs:59-79 (`ManagerCallbackSink::handle_callback`) → src/exec/manager.rs:772-782 (`resolve_by_id`) → src/exec/manager.rs:915-924 (`cascade_to_identical_cards`)
- Failure mode: In a group chat, two members of the same conversation each trigger the SAME tool call with the SAME input (grant_key is a fingerprint of tool name + input, so both cards carry an identical `grant_key`; the group conversation maps to one `session_key`). Both cards are live at once — "two concurrent runs in one conversation" is an explicitly supported scenario in this codebase (src/gateway/inbound_router/mod.rs:1433). Member A clicks **Allow (session)** on A's card: the originator gate at callback_sink.rs:59-66 passes (A is A's card's originator), then `resolve_for_channel` → `resolve_by_id(.., owner_only=true)` resolves A's card **and cascades** the same `AllowSession` to member B's card, because the cascade filter compares only `session_key` + `grant_key` and never `originator_user_id`. B's action is approved by someone else; B never saw or clicked anything, and the sibling card is stamped `resolved_by = A`. The mirror case is worse for a refusal: A tapping **Deny** cancels B's pending action. The `owner_only=true` flag that encodes the channel gate is applied to the addressed entry only and is not propagated to the cascaded siblings, so the cascade re-opens exactly the group-chat approval bypass the gate was added to close.
- Evidence:
  ```rust
  // src/approval/callback_sink.rs:59-66 — gate covers ONE id
  if let Some(originator) = self.manager.record_originator(&id) {
      if originator != user_id { return Some(ApprovalCallbackResult { resolved: false, ... }); }
  }
  ```
  ```rust
  // src/exec/manager.rs:917-922 — cascade filter has no originator comparison
  .filter(|(id, e)| {
      id.as_str() != resolved_id && e.is_live()
          && e.record.session_key == session_key
          && e.record.grant_key.as_deref() == Some(key)
  })
  ```
  (`record_originator_user_id` IS present on the record — src/exec/manager.rs:201 — so the information needed to close this exists.)
- Suggested fix: In `cascade_to_identical_cards`, skip any sibling whose `record.originator_user_id` differs from the resolving user's (compare `Option<&str>` against `resolved_by`), so a decision by A can only reach cards A originated. Must not break the intended concurrent-sibling release: siblings raised by the SAME originator must still cascade, and records with no originator must keep their current behaviour (or be excluded explicitly — decide one and pin it with a test).
- Confidence: 0.65

### B1-02 [P2] The originator gate fails open for any approval record that carries no originator
- Location: src/approval/callback_sink.rs:59-66 (`ManagerCallbackSink::handle_callback`) + src/exec/manager.rs:974-980 (`record_originator`)
- Failure mode: `record_originator` returns `None` for a live record whose `originator_user_id` is unset, and the gate's `if let Some(originator)` therefore skips the check entirely. A channel-delivered record with no originator is then resolvable by **any** member of the destination conversation, not only the requester. The channel bridge stamps the originator from `crate::tools::turn_context::current_originator()` (src/approval/adapters.rs:190-200), which is unset for runs that are not gateway turns; such a run still gets a channel route through the `SESSION_ID` fallback (src/approval/adapters.rs:98-106 → `channel_route`), so the card is delivered into a group conversation with no originator recorded. Trigger: a legacy/background run resumed under a group session key raises a privileged action; member B (not the requester) taps Allow and the action proceeds, and `resolved_by` is stamped with B.
- Evidence:
  ```rust
  // src/exec/manager.rs:974-980 — None means "no originator", not "operator authorized"
  pending.get(id)
      .filter(|entry| entry.is_live() && !entry.is_operator_only())
      .and_then(|entry| entry.record.originator_user_id.clone())
  ```
  ```rust
  // src/approval/callback_sink.rs:59 — the gate no-ops on None
  if let Some(originator) = self.manager.record_originator(&id) { ... }
  ```
- Suggested fix: Make the no-originator case explicit rather than implicit: a channel-resolved record with no originator should either be refused ("this approval cannot be answered from this conversation") or routed to the operator path, never accepted from an arbitrary channel member. Must not break the operator path — operator cards are already refused earlier in `handle_callback` (callback_sink.rs:36-45) and `resolve_by_id` also rejects `owner_only && entry.is_operator_only()`.
- Confidence: 0.45

### B1-03 [P2] `ActionType::inherited_from` is honoured by the defaults map but NOT by the allowlist/blocklist rule lookup
- Location: src/approval/types.rs:173-197 (`ActionType::inherited_from`, the documented contract) — consumed at src/approval/config.rs:484-487 and 501-504 (out of this batch, quoted as the consumer)
- Failure mode: The doc on `inherited_from` promises that "an operator with `"browser_cookies_write": "deny"` was denying header/user-agent overrides and storage-state moves too" — but the inheritance is only consulted for the DEFAULTS map (`self.config.defaults.get(action).or_else(|| … get(parent))`, src/approval/config.rs:521-525). The blocklist (config.rs:484-487) and allowlist (config.rs:501-504) are looked up by the EXACT action only. Trigger: an operator expresses "never write credentials" as a blocklist RULE (`{"action": "browser_cookies_write", "pattern": "..."}`) instead of a default; `browser_identity_override` and `browser_session_state` (both `inherited_from() == BrowserCookiesWrite`) are not matched by that rule and fall through to the Ask default instead of being denied. The same operator intent therefore produces two different security outcomes depending on which policy syntax was used — and the deny-by-default-map path is the one that keeps the documented promise.
- Evidence:
  ```rust
  // src/approval/types.rs:189-196 — the documented inheritance
  Self::BrowserIdentityOverride | Self::BrowserSessionState => Some(Self::BrowserCookiesWrite),
  Self::BrowserSwitchEngine => Some(Self::BrowserOpen),
  ```
  ```rust
  // src/approval/config.rs:484-487 — list rules ignore the inheritance
  self.blocklist_by_type.get(action).and_then(|r| first_match(r, target))
  ```
- Suggested fix: Apply the same inheritance to the list lookups (try the exact action, then `action.inherited_from()`), so one operator intent has one outcome regardless of policy syntax. Must not break the blocklist's fail-closed compile behaviour (a broken rule must never degrade to "weaker than the operator wrote") and must not widen a rule to actions the operator did not name — the inherited parent is the documented rename pair, not a taxonomy.
- Confidence: 0.5

### B1-04 [P3] `audit_identity` collapses a subagent's agent id to the parent agent's, so two different subagents produce identical audit identities
- Location: src/approval/audit.rs:33-38 (`audit_identity`) — the collapse happens in src/routing/session_key.rs:338 (`SessionKey::agent_id`)
- Failure mode: `audit_identity` derives the audit identity from `turn.session_key.agent_id()`, and `SessionKey::agent_id()` returns the PARENT's agent id for a `Subagent` key (`Self::Subagent { parent_key, .. } => parent_key.agent_id()`). Trigger: two subagents of the same agent each perform a gated action (e.g. `browser_cookies_write`); both approval records carry the SAME `agent_id` and the same context string, so the audit trail cannot say which subagent performed the privileged action, and a subagent's action is filed under the parent agent's name. The subagent identity (`SessionKey::Subagent`'s own id) is dropped from the audit identity entirely.
- Evidence:
  ```rust
  // src/approval/audit.rs:33-38
  let agent_id = turn.session_key.agent_id().to_string();
  let context = if turn.is_channel_routable() { format!("{base} via {}/{}", ...) } else { base };
  ```
  ```rust
  // src/routing/session_key.rs:338 — the parent id is what comes back
  Self::Subagent { parent_key, .. } => parent_key.agent_id(),
  ```
- Suggested fix: Include the subagent's own id in the audit identity (e.g. `agent_id` = parent agent id, plus the subagent id in the context string), so a privileged action by a subagent is attributable. Must not break the "main" fallback for turns with no `TURN_CONTEXT` (audit.rs:30-32) nor the channel-routable context format the record consumers already parse.
- Confidence: 0.55

### B1-05 [P3] `ApprovalPolicy::check`'s doc says the decision is not audited, but the only implementation audits the `Ask` inside `check`
- Location: src/approval/policy.rs:19-23 (`ApprovalPolicy::check`) vs policy.rs:28-36 (`ApprovalPolicy::record`)
- Failure mode: `ApprovalPolicy` is a public, implementable trait (`pub mod approval;` → `pub use policy::ApprovalPolicy;` in src/approval/mod.rs:67). The `check` doc states "A decision is NOT audited by this call: the caller decides what to do with it and then records the FINAL decision through `Self::record`", while the `record` doc states the opposite — that an `Ask` IS recorded by the producing implementation INSIDE `check`, because "the refusal path records no final decision at all". The production implementation follows the second statement (src/approval/config.rs:559-565 records the Ask inside `check`); an implementor who follows the first statement's wording ships an implementation where an ask that never became an `Allow`/`Deny` leaves NO trace — exactly the audit hole the second paragraph exists to prevent.
- Evidence:
  ```rust
  // src/approval/policy.rs:20-22
  /// The returned decision is the one the caller acts on. A decision is NOT
  /// audited by this call: the caller decides what to do with it and then
  /// records the FINAL decision through [`Self::record`].
  ```
  ```rust
  // src/approval/policy.rs:33-36 — the same file says the opposite
  /// An `Ask` decision is recorded by the policy implementation that
  /// PRODUCED it, inside [`Self::check`]: ...
  ```
- Suggested fix: Make the `check` doc state the actual contract in one sentence (the implementation MUST audit an `Ask` it produces inside `check`; the caller records only the final `Allow`/`Deny`), so a second implementation cannot silently ship a missing ask-audit. Doc-only change — no behaviour, no public signature.
- Confidence: 0.7
