### B4-01 [P0] Concurrent eviction can delete another successful `put`
- Location: src/artifacts/store.rs:136 and src/artifacts/store.rs:283-330 (`put`, `evict_overflow`)
- Failure mode: With 200 deliverables already stored, concurrently put two non-deliverables A and B. If A's eviction snapshot includes both and B sorts before A, A excludes only itself and selects B as a victim. A removes B's sidecar; B's subsequent eviction can see no overflow and return, so B's `put` returns `Ok(record)` but `read(session, &record.id)` immediately returns `NotFound`.
- Evidence: `evict_overflow(&dir, Some(record.id.as_str())).await;` protects only the calling record; victims are selected from a shared directory snapshot and removed without rechecking whether they are another in-flight put.
- Suggested fix: Serialize publication plus eviction per session across all store instances (or introduce equivalent in-flight victim protection and recheck before deletion). Preserve the invariant that every `Ok` put remains readable and the session cap still holds after concurrent writers finish.
- Confidence: 0.94

### B4-02 [P1] Acknowledged writes are not crash-durable
- Location: src/artifacts/store.rs:337-349 (`write_atomic`)
- Failure mode: After `put` returns success, an OS crash or power loss can lose the blob, sidecar, or rename because neither file contents nor the containing directory are synced; a supposedly durable artifact can therefore disappear or leave an unreferenced blob after restart.
- Evidence: `fs::write(&tmp, bytes).await?;` followed directly by `fs::rename(&tmp, path).await` closes the file but performs no `sync_all`/`sync_data`, and the directory is never synced after rename.
- Suggested fix: Open the temp file explicitly, write and `sync_all` it before rename, then sync the parent directory where supported; map failures instead of acknowledging the put. Preserve temp-plus-rename atomic visibility.
- Confidence: 0.90

### B4-03 [P2] Failed writes and eviction leave untracked blobs that bypass the cap
- Location: src/artifacts/store.rs:129-131, src/artifacts/store.rs:315-330, and src/artifacts/store.rs:342 (`put`, `evict_overflow`, `write_atomic`)
- Failure mode: If the blob write succeeds but sidecar creation fails (for example, disk full or a transient permission error), `put` returns early and leaves the UUID `.bin` forever. A failed temp write similarly leaves `.tmp`; a crash or blob-deletion failure after sidecar deletion leaves another orphan. These files are invisible to `read_records`, so later evictions never retry or count them, and repeated failures can fill the data disk despite the 200-artifact cap.
- Evidence: The two writes use `?` with no blob cleanup; eviction deletes the sidecar first and only logs `fs::remove_file(&bin)` failure; `fs::write(&tmp, bytes).await?` returns without removing a partial temp file.
- Suggested fix: Best-effort clean up the blob/temp on every failed put, and add orphan reconciliation (or retain retryable deletion state) for files left by crashes and failed eviction. Preserve sidecar-last publication and sidecar-first eviction.
- Confidence: 0.97

### B4-04 [P2] Reads allocate the whole on-disk file before enforcing any bound
- Location: src/artifacts/store.rs:177-189 and src/artifacts/store.rs:241 (`read`, `read_records`)
- Failure mode: If an artifact blob or `.json` sidecar is replaced by a much larger file (filesystem corruption, manual/legacy content, or another local writer), `fs::read` allocates its entire size. `read` checks only equality with sidecar `size` after allocation and never enforces `MAX_ARTIFACT_BYTES`, so a sufficiently large file can OOM the process instead of returning a controlled error; listing has the same issue for sidecars.
- Evidence: `let bytes = read_or_not_found(...).await?;` precedes `if bytes.len() as u64 != record.size`, and sidecars use unrestricted `fs::read(&path).await`.
- Suggested fix: Validate declared record size, inspect file metadata, and read with explicit small sidecar and `MAX_ARTIFACT_BYTES` limits (including a race-safe limited reader rather than relying only on metadata). Preserve normal round trips and `NotFound` behavior.
- Confidence: 0.88

### B4-05 [P2] Session encoding leaves Windows device names unchanged
- Location: src/artifacts/mod.rs:75-81 (`encode_session_key`)
- Failure mode: On Windows, a valid raw session key such as `CON`, `NUL`, `COM1`, or `LPT1` is returned unchanged and joined as the session directory. Win32 treats that component as a device rather than a normal directory, so `put` fails during directory creation (or addresses a device) and that session cannot store artifacts.
- Evidence: `utf8_percent_encode` preserves all alphanumerics and the function returns nonempty `encoded` directly; unlike the filename sanitizer, it never applies the repository's `is_windows_reserved_name` guard.
- Suggested fix: On Windows, map reserved encoded components to an unreachable safe spelling (for example, prefix `%`, which normal encoding never emits), leaving all other existing directory names unchanged. Preserve injectivity and keep artifact/media-cache paths aligned through this shared function.
- Confidence: 0.93
