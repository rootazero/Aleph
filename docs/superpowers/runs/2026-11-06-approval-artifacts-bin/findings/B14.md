## F-01 [P1] `revoke_exact` aborts the whole helper on any resolve error other than `device_not_found`

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:700` (`control_loop`, `revoke_exact` branch);
error origins `main.rs:897` (`unknown_device`) and `main.rs:916` (`ambiguous_device`).

**Failure mode:** The driver contract for `revokeExact` is *ack | error `already_revoked`*
(`qa/native_ipc/native_project_native_io.mjs:319`, 8 s timeout). The cleanup step iterates over device
labels (`qa/native_ipc/native_project_cleanup.mjs:31`: `for (const device of devices) requireResult(await helper.revokeExact(device), ...)`).
If a label was never issued by `issue_pairing` (`resolve_device` → `unknown_device`), or if two panel
devices match the binding (`ambiguous_device`), the branch does `Err(error) => return Err(error)` → the
control loop aborts → `run()` returns `Err` → `main` prints `{"ok":false,"code":"internal"}` and exits 1.
The driver sees `helper_closed`/`helper_timeout` instead of the contract's `already_revoked` → the cleanup
step throws → the *later* cleanup steps (credential deletion, owned-root removal) never run → the disposable
root that holds the credential stays on disk and the run outcome degrades to AMBIGUOUS/FAIL.

**Evidence:**
```rust
let actual = match resolve_device(&mut fixture, device) {
    Ok(actual) => actual,
    Err(error) if error.to_string() == "device_not_found" => { /* writes already_revoked */ }
    Err(error) => return Err(error),          // main.rs:700 — kills the helper on unknown/ambiguous
};
```

**Suggested fix:** Never `return Err` from a command branch. Map the remaining resolve failures to a
structured `ErrorMessage` (`already_revoked` for `unknown_device`/`device_not_found`, `bad_state` for
`ambiguous_device`) and `continue`.
Invariant: every command the helper accepts must be answered with a protocol message; the helper stays alive
until stdin closes.

**Confidence:** 0.9

## F-02 [P1] `main()` discards the error, so every failure looks identical

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:249-257` (`main`).

**Failure mode:** Any startup or loop failure — missing panel build (`main.rs:274-278`), malformed nonce
(`main.rs:1007`), qa-root refusal (`main.rs:262-269`), SQLite/project-store errors, a stdout write error —
is reported as the single fixed string `{"ok":false,"code":"internal"}` on stderr plus exit code 1. The
operator (and the run ledger) cannot distinguish "the `--panel-root` pointed at a non-panel directory" from
"the nonce was not 32 hex chars" from "the project store could not be opened"; the native QA run fails with
no actionable cause and the evidence record keeps only a generic reason.

**Evidence:**
```rust
Err(_error) => {
    eprintln!("{}", r#"{"ok":false,"code":"internal"}"#);
    std::process::ExitCode::from(1)
}
```

**Suggested fix:** Keep the machine-readable line, but also print the error chain to stderr
(`eprintln!("helper failed: {error:#}")`). The driver's parser reads stdout lines only, so stderr is free.
Invariant: the JSON contract on stdout must not change.

**Confidence:** 0.85

## F-03 [P2] `shutdown` waits for the HTTP server without a timeout → a parked asset request hangs the helper forever

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:774` (`control_loop`, `shutdown` branch;
same pattern at `main.rs:804`).

**Failure mode:** The hold gate parks a `/tabs/project-a/...` request on a `Notify`
(`main.rs:874-890`). If a request is still parked when `shutdown` arrives, the branch awaits
`server.await??` — the graceful shutdown of the listener waits for that in-flight request, and the request can
only be woken by `release_response`, a command the control loop can no longer process because it is blocked
inside the shutdown branch. The helper therefore never emits `stopped` → the driver's `stop()` times out after
10 s (`qa/native_ipc/native_project_native_io.mjs:304`) → the cleanup step `helper_stopped` fails → the
credential-deletion and owned-root-removal steps that follow it never run → leftovers on disk.

**Evidence:**
```rust
if let Some(server) = server.take() {
    server.await??;                 // main.rs:774 — unbounded wait on an in-flight request
}
```

**Suggested fix:** Release the gate before awaiting the server (notify it unconditionally) and bound the wait
(e.g. `tokio::time::timeout`). Invariant: `shutdown` must always answer with `stopped` inside the driver's
10 s budget, whatever the HTTP layer is doing.

**Confidence:** 0.6 (today's driver sequences terminate the native shell before stopping the helper, which
drops the parked request; the hazard is reachable whenever the client connection stays open)

## F-04 [P2] `hold_response` swaps the `Notify` instance → a parked waiter is orphaned (lost wakeup)

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:619` (`hold_response`), `main.rs:652-654`
(`release_response`), `main.rs:876-882` (the park).

**Failure mode:** `hold_response` replaces `state.asset_a_notify` with a brand-new `Notify`. A request that
already parked on the previous instance is waiting on an object nobody will ever notify again;
`release_response` notifies the *current* instance only. The parked request therefore never completes → the
driver's fetch hangs until its own timeout, and the server can no longer shut down (see F-03).
Trigger: a second `hold_response` while a request is parked (a retried or repeated gate command).

**Evidence:**
```rust
state.asset_a_held = true;
state.asset_a_notify = Arc::new(Notify::new());   // main.rs:619 — replaces the instance waiters registered on
...
let notify = { ... state.asset_a_notify.clone() };  // main.rs:652
notify.notify_one();                                // main.rs:654 — wakes the new instance only
```

**Suggested fix:** Allocate one `Notify` per gate for the process lifetime and never replace it; express the
gate with a boolean/permit instead of swapping the notifier.
Invariant: a waiter parked on the gate must be woken by the next `release_response` for that gate.

**Confidence:** 0.7

## F-05 [P2] The `fixture` mutex is held across the stdout write → the HTTP middleware stalls behind it

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:481` + `main.rs:512-525` (`issue_pairing`),
`main.rs:684` + `main.rs:690-698` (`revoke_exact`), consumer at `main.rs:824` (middleware).

**Failure mode:** `issue_pairing` and `revoke_exact` take `fixture.lock().await` and keep the guard alive
while awaiting `write_json(...).await?` on stdout. If stdout blocks (reader stalled → pipe full), the write
never completes and the guard is never released, so every `/tabs/...` request blocks on
`state.fixture.lock().await` → the whole asset surface stalls, and the control loop cannot process the next
command meanwhile.

**Evidence:**
```rust
let mut fixture = fixture.lock().await;                    // main.rs:481 (and 684)
...
write_json(&mut output, &Pairing { ... }).await?;            // main.rs:512 — await while the guard is held
```

**Suggested fix:** Copy the data needed for the reply out of the guard's scope and drop the guard before
awaiting the write. Invariant: never hold a `tokio::sync::Mutex` guard across an `.await` on I/O.

**Confidence:** 0.7

## F-06 [P2] A `release_response` that lands before the request parks silently disables the gate — the case the gate exists to prove is never exercised, yet the run still reports PASS

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:651-654` (`release_response`),
`main.rs:874-890` (the gate is evaluated only *after* the response was produced).

**Failure mode:** The gate decision is taken after `next.run(request).await` returns. `release_response`
clears `asset_a_held` and notifies. If the release lands in the window between the request entering the
middleware and the gate check, the request does not park at all: it returns immediately, the "delayed A
response" the driver asserts on (`qa/native_ipc/native_project_gateway_smoke_test.mjs:221`) was never
delayed, and the late-body / identity-fencing property the gate exists to prove is skipped — the smoke test
still passes (`status === 200`). A green QA run therefore does not prove the fencing property it advertises.

**Evidence:**
```rust
// main.rs:651-654 (release)                  // main.rs:876-882 (park, after the response)
state.asset_a_held = false;                    if state.asset_a_held {
state.asset_a_notify.clone()                       state.asset_a_held = false;
notify.notify_one();                             Some(state.asset_a_notify.clone().notified_owned())
                                                } else { None }
```

**Suggested fix:** Make the gate an explicit state machine (`Armed` / `Held` / `Released`) and have the
driver observe it (e.g. echo the gate state in the ack) so a release-before-park is detected instead of
silently no-op'ing.
Invariant: an ack must not report success for an effect that did not happen.

**Confidence:** 0.55

## F-07 [P2] No bound on the stdin line length (the protocol declares 16 KiB) → unbounded allocation

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:423` (`input.next_line()`),
`main.rs:437` (`serde_json::from_str(&line)`).

**Failure mode:** `tokio::io::Lines::next_line` returns an unbounded `String`, and `serde_json::from_str`
then parses it into a `Command`. A peer that writes one oversized line (the protocol's `MAX_LINE_BYTES` is
16384 — `qa/native_ipc/native_project_protocol.mjs`) makes the helper allocate the whole line and its parse
tree before it can even answer `bad_command` — an unbounded allocation driven by the peer's input, where the
protocol already declares a maximum that only the helper could enforce.

**Evidence:**
```rust
let mut input = BufReader::new(tokio::io::stdin()).lines();
while let Some(line) = input.next_line().await? {
    let command: Command = match serde_json::from_str(&line) { ... }
```

**Suggested fix:** Reject lines longer than the protocol's `MAX_LINE_BYTES` (16384) with `bad_command`
before parsing. Invariant: a single line must never drive an allocation larger than the protocol bound.

**Confidence:** 0.75

## F-09 [P2] The `stopped` message reports `fixtureClosed: true` while the fixture is open and the helper keeps serving commands

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:776-785` (`Stopped`), `main.rs:786`
(the loop `continue`s after the shutdown branch).

**Failure mode:** After `shutdown` the control loop writes `stopped { listenerClosed: true,
fixtureClosed: true }` and then keeps looping: the fixture (project store, device-token store, SQLite
connections) is still open and the helper still answers commands — the smoke test relies on exactly that
(`qa/native_ipc/native_project_gateway_smoke_test.mjs:243` sends `revoke_exact` *after* `stopped` and
asserts the ack). So the run ledger records "the fixture is closed" while the process is alive with an open
database that can still be mutated, and the operator reads a teardown claim that never happened.

**Evidence:**
```rust
write_json(&mut output, &Stopped { v: 1, r#type: "stopped", run: &run,
    listener_closed: true, fixture_closed: true, }).await?;   // main.rs:776-785 — the fixture is not closed
continue;                                                       // main.rs:786 — commands are still served
```

**Suggested fix:** Either close the fixture before emitting `stopped` and stop accepting commands, or report
what actually happened (e.g. `listenerClosed` + `commandsClosed`) and update the driver contract in the same
change. Invariant: a lifecycle message must not assert a state the running process contradicts.

**Confidence:** 0.7

## F-10 [P3] An unknown command is reported as `bad_state` instead of `bad_command`

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:789-799` (dispatch fall-through), versus the
`bad_command` paths at `main.rs:441`, `main.rs:455`, `main.rs:471`.

**Failure mode:** The dispatch is an if-chain whose fall-through answers `bad_state`. A command name the
helper does not implement (a typo, or a command added to the protocol but not to this binary) is reported as
an illegal-state error, so the driver/operator diagnoses a fixture-state problem instead of an unsupported
command and looks in the wrong place. The driver's own validator (`native_project_protocol.mjs`,
`HELPER_COMMANDS`) rejects unknown names before sending, so today the branch is only reachable through the
raw-socket path — but the helper is the contract boundary.

**Evidence:**
```rust
write_json(&mut output, &ErrorMessage { v: 1, r#type: "error", run: &run,
    code: "bad_state", }).await?;   // main.rs:789-798 — fall-through for an unknown command name
```

**Suggested fix:** Make the fall-through answer `bad_command` (malformed/unsupported) and reserve `bad_state`
for a known command used in the wrong state.
Invariant: the error code must describe the actual fault.

**Confidence:** 0.8

## F-11 [P3] `control_loop` is a 392-line if-chain with nine copy-pasted reply shapes

**Location:** `src/bin/aleph-panel-native-qa-gateway/main.rs:416-808` (`control_loop`).

**Failure mode:** Every command repeats the same "validate → error message → continue → mutate → ack" shape:
14 `ErrorMessage` literals and 5 `Ack` literals are duplicated across the branches. The drift is already
visible — `revoke_exact` (F-01) is the only branch that ends the loop instead of writing an error message,
and `hold_response`/`release_response` duplicate the same gate-argument check. The next command added to the
protocol will be copy-pasted again, and a guard forgotten in one branch (e.g. echoing the command `id`) yields
a message the driver cannot match.

**Evidence:** nine `if command.command == "..."` branches (`main.rs:465-799`), each carrying its own
`ErrorMessage{...}` / `Ack{...}` literal.

**Suggested fix:** Dispatch with `match command.command { ... }` and extract two helpers
(`fn error(run, code)` / `fn ack(run, id, command)`) so the reply shape exists exactly once.
Invariant: all branches must emit the same message shape.

**Confidence:** 0.8

## Mandatory checklist coverage

1. **Panic risk** — `.expect("binding exists")` (`main.rs:920`) is guarded by the `get_mut` on a key read from
   the same map with no mutation in between; `candidates[0]` (`main.rs:921-922`) is guarded by
   `ensure!(!candidates.is_empty())` above it; the std-mutex `.expect(...)` calls (`main.rs:167`, `173`,
   `211`, `234`, `237`, `749`, `841`) can only be poisoned by a panic inside the guarded body (a `Vec` push /
   a map insert); `receipts.len() as u32 + 1` is bounded by the 512 cap, so no overflow; an out-of-range
   `id` fails deserialization into `bad_command`, not a panic.
2. **Error handling** — F-01 (command branch aborts the process), F-02 (error discarded), F-09 (lifecycle
   message overstates the state). The `.ok()` at `main.rs:827` only turns a failed token validation into
   "no identity", i.e. a refusal, never a success. `let _ = shutdown.send(())` (`main.rs:771`, `801`) is
   intentional: the receiver may already be gone.
3. **Concurrency** — F-03, F-04, F-05. Lock order is `gateway_state` → `fixture` everywhere
   (`main.rs:823-824` vs `481`, `532`, `572`, `684`) and there is no `fixture` → `gateway_state` nesting, so
   no deadlock; the std `receipts` mutex is always the innermost lock and is never held across an `.await`
   except for `panel_ui_capability_revision()` (a publication `RwLock` read), so there is no lock inversion.
4. **Security** — F-07 (unbounded allocation from a peer-controlled line). The static fallback
   `ServeDir::new(&args.panel_root)` (`main.rs:390`) is tower-http's sanitizing implementation (no `..`
   escape) and the panel root is operator-supplied; the bootstrap ticket is written only to the protocol
   channel on stdout (`main.rs:506`, `512`), never logged; device tokens are never echoed into messages or
   error text.
5. **State machine** — F-06, F-09, F-10. The hold/release gate has three states but is modelled by one
   boolean plus a swappable notifier; `release_response` reports success for a gate that was never armed.
6. **Blocking I/O inside async fn** — the `std::fs` and SQLite calls in `run()` (`main.rs:270-300`) all
   execute *before* the listener is spawned, with only idle tokio workers alive, so nothing stalls the
   executor; the synchronous device-token calls inside the async control loop (`main.rs:502`, `506`, `702`)
   block one worker for a single millisecond-scale query in a single-user QA harness — acceptable, not
   reported.
7. **Resource lifetime** — the server task and the shutdown oneshot are owned by the control loop and joined
   on both exit paths (`main.rs:771-775`, `801-805`); on the early-error path of F-01 the server task is
   dropped together with the process, so no orphan process survives the helper's exit; the SQLite stores are
   process-local and the owned root is owned by the driver, not by this binary.
8. **Numeric / logic** — receipt sequences start at 1 and the 512 cap matches the protocol's `MAX_RECEIPTS`;
   the bootstrap ticket uses the manager's default 5-minute TTL; the nonce is validated as 32..=128 lowercase
   hex bytes (`main.rs:1007`) while `qa_root` accepts 16..=128 either case, so the helper is consistently the
   stricter side; the asset receipt's `project` is derived from the first path segment after `/tabs/`
   (`main.rs:848-856`).
9. **Wiring** — `issue_pairing`, `confirm_pairing`, `set_fixture`, `hold_response`, `release_response`,
   `revoke_exact`, `receipt_since` and `shutdown` are all reachable from the command dispatch and all appear
   in the protocol's `HELPER_COMMANDS`; `apply_fixture_action`'s `revoke_device_a` (`main.rs:947`) is not
   issued by the current driver (which uses `revoke_exact`) but is consistent with it; `NativeQaObserver` is
   registered through `set_native_qa_observer` and its receipts are consumed by `receipt_since`.
