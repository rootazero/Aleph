### B2-001 [P0] Renamed actions bypass blocklist and allowlist rules
- Location: src/approval/config.rs:483-525 (ConfigApprovalPolicy::decide)
- Failure mode: An existing policy with `browser_cookies_write` default `allow` and a `browser_cookies_write` blocklist rule formerly denied a matching credential write; after the split, the equivalent `browser_identity_override` or `browser_session_state` request skips the old blocklist, inherits the old `allow` default at lines 520-525, and executes without approval. `browser_switch_engine` has the same problem relative to `browser_open`.
- Evidence: Rule lookup uses only `.get(action)` for both lists, while only the default lookup falls back to `action.inherited_from()`; thus the inheritance intended to preserve old policy files does not cover their security rules.
- Suggested fix: Resolve inherited action types consistently for blocklist, allowlist, and defaults (or duplicate inherited rules when compiling), keeping blocklist-before-allowlist priority and ensuring an explicit child entry cannot discard a parent blocklist rule.
- Confidence: 0.98

### B2-002 [P1] Home-directory failure loads policy from an untrusted working directory
- Location: src/approval/config.rs:368-379 (ConfigApprovalPolicy::config_path)
- Failure mode: Start the service without a resolvable home directory (a common service-manager misconfiguration) from a directory containing attacker-supplied `.aleph/approval-policy.json`; startup reads that file and its `allow` defaults/allowlist replace the operator policy, silently authorizing gated actions. If `current_dir` also fails, the fixed `/tmp/.aleph/approval-policy.json` fallback is another cross-user path.
- Evidence: `get_config_dir()` failure is converted to `current_dir().unwrap_or_else(|_| temp_dir()).join(".aleph").join("approval-policy.json")`, and `load()` subsequently parses that path as authoritative instead of failing closed.
- Suggested fix: Make policy loading return/use `safe_default()` when the canonical config directory cannot be determined; do not substitute CWD or a shared temp directory. Preserve the existing missing-file versus broken-file behavior for the canonical path.
- Confidence: 0.94

### B2-003 [P2] Policy patterns leak secrets into debug and error logs
- Location: src/approval/config.rs:124-128, 489-510 (cached_glob_regex, ConfigApprovalPolicy::decide)
- Failure mode: An operator blocks a credential-bearing URL, script, PIM body, or token by putting its literal text in a glob; every matching request writes that secret verbatim to the `pattern` log field even though the corresponding `target` is redacted. Invalid oversized patterns likewise log their full contents at error level.
- Evidence: Both match arms use `pattern = %rule.pattern` beside `target = %redact_target(target)`; the compile-error path uses `pattern = %pattern`. Existing redaction tests construct patterns containing secrets but inspect only the `target` field.
- Suggested fix: Redact/hash patterns in logs just as targets are redacted (and cap diagnostic length), while retaining the original pattern internally for matching. Do not change the decision text contract unless its consumers are audited separately.
- Confidence: 0.96

### B2-004 [P2] Audit logging copies an unbounded raw target into the log pipeline
- Location: src/approval/config.rs:575-578 (ConfigApprovalPolicy::record)
- Failure mode: A tool request with a very large target (for example a large typed/script/PIM payload) causes `audit_identity` to embed that entire target in `request.context`; every final audit record then allocates and emits the whole masked context, allowing a single request to produce a comparably huge log event and exhaust log storage or stall logging.
- Evidence: `context = %masker.mask(&request.context)` has no length cap, unlike the adjacent Ask prompt path, which explicitly truncates to 256 bytes. `src/approval/audit.rs:25` builds context as `format!("{domain}.{action} ({target})")`.
- Suggested fix: Apply the existing UTF-8-safe bounded truncation helper to masked context (and other free-form audit fields) before logging, preserving enough prefix for diagnosis without changing the approval decision.
- Confidence: 0.93

### B2-005 [P2] Policy loading reads an unbounded file into memory
- Location: src/approval/config.rs:331-336 (ConfigApprovalPolicy::load_from)
- Failure mode: A corrupted, accidental, or attacker-placed multi-gigabyte `approval-policy.json` is read in full during registry construction, causing a matching allocation plus JSON parsing overhead and potentially OOM-ing the process before the approval system starts.
- Evidence: `std::fs::read_to_string(&path)` has no metadata/size check or bounded reader; the later bounded regex compiler does not bound the initial file allocation.
- Suggested fix: Enforce a small explicit maximum policy-file size before reading (or use a bounded reader) and route oversize files through `safe_default()` with an error log, preserving normal valid-file behavior.
- Confidence: 0.90

### B2-006 [P0] URL case variation bypasses navigation blocklists
- Location: src/approval/config.rs:241-256, 483-492 (compile_rules_grouped, ConfigApprovalPolicy::decide)
- Failure mode: A policy blocks `*://malicious.com/*` while navigation remains allowed by default; a request for `HTTPS://MALICIOUS.COM/payload` does not match the case-sensitive regex, falls through to `Allow`, and the browser resolves the same scheme/host. Any upper/mixed-case DNS hostname or URL scheme similarly evades an operator's deny rule.
- Evidence: `RegexBuilder::new(&glob_to_regex_str(pattern))` never enables case folding and `decide` matches the raw target. Browser callers pass the original URL string as the approval target; there is no URL canonicalization before this comparison. Existing tests exercise only lowercase URLs.
- Suggested fix: Canonicalize URL scheme and host for browser URL actions before both rule construction/matching (or use URL-aware rule matching) while leaving path and non-URL action targets case-sensitive. Add mixed-case scheme/host deny tests that assert `Deny`.
- Confidence: 0.96

### B2-007 [P1] Long-target redaction emits the secret-bearing prefix verbatim
- Location: src/approval/config.rs:54-66 (redact_target)
- Failure mode: A target longer than 120 characters, such as `https://user:password@example.com/<long-path>` or a URL whose first query parameter contains a token, is logged with its first 60 characters unchanged; those credentials therefore appear in blocklist/allowlist match logs despite the helper's promise that secrets never reach logs.
- Evidence: The long-target branch returns `format!("{}:sha256:{:016x}", prefix, hash)` where `prefix` is the first 60 raw characters. No masking or URL credential removal is applied before this formatting.
- Suggested fix: Emit only a keyed/deterministic digest and length for long targets, or sanitize with `SecretMasker` and remove URL userinfo/query before taking any prefix. Add tests with credentials within the first 60 bytes of a >120-character target.
- Confidence: 0.98
