## New findings

### B5-S2-01 [P1] Daemon parent reports success before daemon setup succeeds
- Location: `src/bin/aleph-server/daemon.rs:437-464`
- Failure mode: `fork()` succeeds but the child later fails `setsid()`, the second `fork()`, `chdir("/")`, log redirection, or another post-fork setup step -> the intermediate parent has already called `std::process::exit(0)`, so the invoking shell/service records a successful start although the daemon never becomes available.
- Evidence: `match unsafe { libc::fork() } { ... _ => { std::process::exit(0); } }` followed by `if unsafe { libc::setsid() } == -1 { return Err("setsid failed".into()); }`, and the second fork has the same parent-side `std::process::exit(0)` before setup continues.
- Suggested fix: use a parent-child readiness/error handshake (pipe/socketpair) and have the original parent wait for the final daemon to complete PID/log/initialization setup, returning a non-zero error on setup failure; retain `exit(0)` only after readiness is acknowledged.
- Confidence: 0.98

### B5-S2-02 [P2] Requested WebChat listener failure is detached and startup still succeeds
- Location: `src/bin/aleph-server/commands/start/builder/handlers/config.rs:187-199`
- Failure mode: `--webchat-port` is occupied or the listener cannot bind -> the spawned task logs `WebChat server error` and terminates, while `start_webchat_server` returns successfully and the main gateway continues, so the CLI/user receives a successful startup and printed WebChat URL for an unavailable UI.
- Evidence: `tokio::spawn(async move { if let Err(e) = serve_webchat(webchat_addr, webchat_path_clone).await { tracing::error!("WebChat server error: {}", e); } });` has no join/readiness handshake and no error propagation.
- Suggested fix: bind the WebChat listener before declaring startup successful, or return/await a readiness result from the spawned task and fail startup (or explicitly report degraded startup) when the requested listener cannot bind.
- Confidence: 0.96

### B5-S2-03 [P2] Failed installer launch leaks downloaded update files
- Location: `src/bin/aleph-server/commands/update.rs:294-300`
- Failure mode: `bash`/PowerShell cannot be launched or process creation fails after the private temp installer is written -> `.status().map_err(...)?` returns before the cleanup call, leaving the installer and directory under the system temp directory; repeated failures accumulate downloaded release scripts.
- Evidence: `let status = ... .status().map_err(|e| format!("failed to launch the installer: {e}"))?;` is followed only afterward by `let _ = std::fs::remove_dir_all(&temp_dir);`.
- Suggested fix: put cleanup in a scope guard/RAII drop guard so all return paths after temp-directory creation remove the directory, while preserving the installer exit status for the caller.
- Confidence: 0.98
