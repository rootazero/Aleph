# B10 — second pass (adversarial) — builder/{subsystems,startup_resources,mod} + handlers/{agents,canvas,config,core,extensions,mcp,mod,session,system}

Scope: `src/bin/aleph-server/commands/start/builder/subsystems.rs` (1626 lines, incl. in-file tests),
`startup_resources.rs`, `builder/mod.rs`, `handlers/{agents,canvas,config,core,extensions,mcp,mod,session,system}.rs`.
All 12 in-scope files were read end-to-end. Out of scope and not read: `handlers/memory.rs`, `handlers/settings.rs`.
No hotspot file was supplied (`.review/rd-2026-11-06-approval-artifacts-bin/hotspots/B10.txt` does not exist), so the
brief's pattern classes were swept manually rather than line-anchored.

First-pass `findings/B10.md` header claims `P0=0 P1=1 P2=2 P3=0`; the dispatch note ("only ONE finding for ~3700 lines")
understates the first pass. Three findings exist; all three are downgraded below, and seven new findings follow.

## Verdict on first-pass findings

- **B10-001 [P1] → DOWNGRADED to P2.** The failure mode is real but narrower than stated: `initialize_channels`
  rebuilds the telegram / qq / whatsapp / webhook channels from config with `&inst.id`, and imessage has its own path, so
  runtime id == `inst.id` for those. Only the nine "plain" channels (discord, slack, matrix, mattermost, signal, irc,
  nostr, xmpp, email) keep the factory-hardcoded id, because `register_plain_channel!`
  (`src/gateway/interfaces/mod.rs:91-101`) takes `_config: ChannelConfig` and discards it. The code already documents this
  exact defect at `subsystems.rs:1105-1127` ("This is NOT always the channel's runtime id … silently revert to defaults …
  deliberately left as a decision rather than done in passing", after 2026-08-11 QA verification): a known, documented
  deferral rather than a missed defect.
- **B10-002 [P2] → DOWNGRADED to P3.** Confirmed there is no shutdown path (`handlers/config.rs:80-137`: `let
  watcher_handle = watcher_for_watch.clone().start_watching(); while let Ok(event) = config_rx.recv().await { … }
  watcher_handle.await` holds an `Arc`, so the receiver never closes), but production runs one `start()` per process, so
  the leak is bounded by process exit. It only accumulates on in-process restart. The genuinely broken thing in that same
  loop is the `Lagged` handling — see B10-S2-01.
- **B10-003 [P2] → DOWNGRADED to P3.** `tokio::spawn(async move { if let Err(e) = serve_webchat(..).await {
  tracing::error!(..) } })` (`handlers/config.rs:196-200`) discards the handle, but the error *is* logged, and a second
  in-process gateway start would surface EADDRINUSE loudly. Blast radius is one RPC-surface daemon task, not
  password-hash durability as the first pass suggested.

## Hotspot triage

No hotspots were supplied for B10. Pattern classes swept and their result:

- *startup ordering*: `initialize_*` sequence in `start/mod.rs` (state db → memory → vault → router → channels →
  projections) has no dependency inversion visible in this batch; `initialize_inbound_router` correctly requires the
  channel registry and the runtime. Clean, except B10-S2-04 (`enabled` flag).
- *shutdown/cleanup ordering*: `StartupResources::{push, cleanup}` stops Memory then awaits `ProjectionHost` — correct
  order, idempotent, but invoked twice on the success path (B10-S2-05) and owns none of the spawned tasks (B10-S2-07).
- *fail-open defaults*: B10-S2-06 (`/tmp` fallbacks for security db + data dir), B10-S2-04 (`enabled=false` ignored).
- *swallowed init errors*: B10-S2-02 (config RPCs vanish with no daemon-mode log), B10-S2-01 (hot reload dies silently).
- *panics/unwraps reachable at runtime*: none new. `initialize_vault`'s `.expect("Fatal: in-memory security store
  fallback failed …")` is documented design-by-contract (only reachable on allocation/fd exhaustion), `eprintln!`s and
  `lock().unwrap_or_else(PoisonError::into_inner)` are all safe.
- *handler contracts / wrong error codes*: no mismatches found. All registered method names exist in the handler
  dispatch tables and every "capture-handle" handler (teams, config, artifacts) only skips registration when its store is
  genuinely absent at boot; `register_graph_handlers` binding six methods to `runtime::handle_graph` is intentional —
  that handler dispatches on `request.method` (`src/gateway/handlers/memory/runtime.rs:123-148`).

## New findings

### B10-S2-01 [P2] Config hot-reload consumer exits permanently on a single `broadcast::RecvError::Lagged`
- **Location**: `src/bin/aleph-server/commands/start/builder/handlers/config.rs:84` (`while let Ok(event) =
  config_rx.recv().await`), against `channel_capacity: 16` at `handlers/config.rs:30` and `pub fn subscribe(&self) ->
  broadcast::Receiver<ConfigEvent>` at `src/gateway/hot_reload.rs:118`.
- **Failure mode**: `tokio::sync::broadcast::Receiver::recv()` returns `Err(Lagged(n))` when more than 16 events were
  published while the consumer was busy. That is recoverable (the next `recv()` resumes at the oldest retained event),
  but `while let Ok(..)` treats it as terminal. The task then falls through to `watcher_handle.await`, which never
  resolves because the consumer holds an `Arc` to the watcher. No log, no metric, no restart.
- **Impact**: after one event storm (editor save-loops, `git checkout` over `config.toml`, or a reload burst while
  `event_bus.publish_json` blocks on a slow subscriber) hot reload, `PiiEngine::reload`, and the `config.reloaded` /
  `config.error` topic events are silently dead for the rest of the process lifetime. An operator who edits the config
  sees "saved" and gets nothing, with no error anywhere.
- **Evidence**: the only `Err` arm in the loop is the explicit `match event` on `ConfigEvent::FileError`
  (`handlers/config.rs:85-95`); the `Result` from `recv()` is discarded by the `while let` pattern. No `Lagged` handling
  appears anywhere in the file (`grep -n "Lagged" handlers/config.rs` → none).
- **Suggested fix**: `loop { match config_rx.recv().await { Ok(event) => handle(event), Err(broadcast::error::RecvError::
  Lagged(n)) => { tracing::warn!(skipped = n, "config hot-reload lagged"); } Err(Closed) => break } }`.
- **Confidence**: 0.90 (code shape certain; the trigger requires a 16-event backlog, which the 500 ms debounce makes
  uncommon but not impossible).

### B10-S2-02 [P2] `config.reload` / `config.validate` / `config.path` are unregistered whenever the watcher cannot be
created — and daemon mode never says why
- **Location**: `handlers/config.rs:11-24` (early `let path = config_path?;`, `if !path.exists() { … return None }`,
  `Err(error) => { if !daemon_mode { eprintln!("  ✗ Config watcher failed: {error}") } return None }`) versus the
  registration block that exists only inside that `Ok` path.
- **Failure mode**: RPC registration is conditioned on a runtime object (`ConfigWatcher`) rather than on "the gateway is
  up". A gateway started without a `config.toml` on disk (bare `aleph-server start`, container image whose config is
  mounted later, or config path that disappears) boots fine but exposes no `config.*` methods at all. The Panel's Config
  page then sees *method not found* — indistinguishable from a client/server version skew — and in daemon mode
  (`daemon_mode == true`) the only diagnostic is suppressed entirely.
- **Evidence**: `grep -rn "config.reload" src/` shows a single registration site; `src/gateway/method_census.rs:148-152`
  only classifies the methods, never registers them. The `eprintln!` calls at `handlers/config.rs:199-209` are all
  `if !daemon_mode`-gated, while the unregisterable-RPC consequence is not.
- **Suggested fix**: register `config.reload` / `config.validate` / `config.path` unconditionally, resolving the watcher
  through the captured `Option` and returning `INTERNAL_ERROR` ("config watcher unavailable: {reason}") instead of
  disappearing; log the creation failure with `tracing::warn!` in every mode.
- **Confidence**: 0.95.

### B10-S2-03 [P3] Dead note-maintenance lifecycle wrappers, kept alive only by tests that prove nothing about production
- **Location**: `subsystems.rs:35-165` — `drain_note_vault_watcher`, `spawn_note_orientation_bootstrap`,
  `spawn_note_index_rebuild`, `NoteMaintenanceOwner::{new, …}`, `drain_note_maintenance`; tests at
  `subsystems.rs:1300-1626`.
- **Failure mode**: these six "production" helpers have zero callers anywhere in `src/` (grep for each name outside
  `subsystems.rs` returns only `src/memory/notes/watcher/lifecycle_tests.rs` and `src/memory/notes/watcher.rs:154`, both
  for the *core* `spawn_note_vault_watcher`, not these wrappers). Note-vault ownership moved into core in commit
  `6745cdc21` ("feat(memory): add source-owned lifecycle runtime"; `src/memory/runtime/bundle.rs:17` holds
  `watcher: tokio::sync::Mutex<Option<NoteVaultWatcher>>`, `:52` `prepare_owned_note_vault_watcher(..)`), but the
  binary-side copy was left behind and then *invested in* by `4bba875ac` ("fix(memory): await note watcher during
  shutdown") and `ff5989abd` ("test(memory): strengthen note maintenance lifecycle evidence").
- **Why it matters**: the tests at `subsystems.rs:1330-1626` assert shutdown/error-propagation semantics of code the
  binary never runs — a twin subsystem (shape #16/#3). Any real regression in `MemoryRuntime`'s note lifecycle passes this
  suite. If the wrappers are kept deliberately (as a future re-wiring seam), they need a `#[allow(dead_code)]` plus a
  comment naming the owner and the intended call site; otherwise delete them and move the lifecycle assertions to
  `src/memory/runtime/service_lifecycle_tests.rs`.
- **Suggested fix**: delete `subsystems.rs:35-165` and its tests, or mark them clearly as an unused seam and add a test
  that the *binary* path (`MemoryRuntime` boot) starts and drains the watcher.
- **Confidence**: 0.95 (dead-ness grep-verified; "was this intentional" 0.5 — either way the tests are misleading).

### B10-S2-04 [P2] `enabled = false` is honoured at boot only for `feishu`
- **Location**: `subsystems.rs` (`initialize_channels`, ~`let boot_enabled = if inst.channel_type == "feishu" { … } else
  { true };` then `channel_registry.register_for_boot(channel, boot_enabled)`), with `resolved_channels()` at
  `src/config/structs.rs:350-380` (no enabled filter) and `start_all()` at `src/gateway/channel_registry.rs:1322-1338`
  (starts every `DesiredChannelState::Enabled`).
- **Failure mode**: an operator who writes `[channels.telegram] enabled = false` (or any non-feishu channel) still gets
  that channel registered and started at boot: the JSON `enabled` flag is read only in the feishu branch, and the plain
  channel factory throws its `ChannelConfig` away (`src/gateway/interfaces/mod.rs:91-101`), so the adapter cannot even see
  the flag. The same key means "registered but not started" on feishu and "fully live" everywhere else (shape #9).
- **Impact**: consent/least-exposure violation — a disabled channel keeps a live socket to an external platform and keeps
  accepting inbound messages; the Panel meanwhile renders it as disabled.
- **Not verified**: whether `telegram`/`discord` adapters re-check their own typed `enabled` field at `start()`
  (`src/gateway/interfaces/discord/config.rs:63` defines one; I did not trace `DiscordChannel::start`).
- **Suggested fix**: derive `boot_enabled` from `inst` for every channel type (a shared `ChannelInstanceConfig::enabled()`
  accessor), and have `register_plain_channel!` pass the config instead of dropping it.
- **Confidence**: 0.65 (code shape verified; impact depends on per-adapter re-checks).

### B10-S2-05 [P3] `StartupResources::cleanup` runs twice on the success path and the second failure is swallowed
- **Location**: `start/mod.rs:3931` (`if let Err(error) = startup_resources.cleanup().await { warn!(..) }` inside
  `start_server_body`) plus `start/mod.rs:91-93` (`let result = start_server_body(..).await;
  startup_resources.finish(result).await`) where `finish` calls `self.cleanup()` again and discards its error
  (`startup_resources.rs:65-73`, `tracing::warn!(%error, "Startup resource cleanup failed")`).
- **Failure mode**: today harmless — `MemoryRuntime::stop` (`src/memory/runtime/mod.rs:255-279`) re-returns the cached
  `first_error` and `ProjectionHost::close_and_await` (`src/capability/projection_host.rs:818-835`) re-returns the cached
  `completion.outcome`, so the second pass is a no-op (with a duplicated warning line). It is a trap for the next
  resource added to `cleanup()`: any non-idempotent step (flush, socket close, lease release, `fsync`) runs twice, and
  the second, swallowed error is exactly the one that would report the real failure. Also: the success-path cleanup
  result is only logged at `warn`, so a Memory-stop failure can never affect the process exit code.
- **Suggested fix**: pick one owner — delete the in-body `cleanup()` and let `finish()` do it, or make `cleanup()`
  itself take `&mut self`/a `cleaned` flag and return early; surface the failure to the exit code on the graceful path.
- **Confidence**: 0.9 (double call verified; severity is preventive).

### B10-S2-06 [P2] Security artifacts fall back to predictable `/tmp` paths
- **Location**: `subsystems.rs` (`initialize_vault`, ~200-255):
  `paths::get_security_db_path().unwrap_or_else(|_| PathBuf::from("/tmp/aleph_security.db"))` and
  `alephcore::utils::paths::get_data_dir().unwrap_or_else(|_| PathBuf::from("/tmp/.aleph/data"))` →
  `secrets.vault` and user rows land under `/tmp/.aleph/data`.
- **Failure mode**: `get_data_dir()` fails only when `HOME`/`USERPROFILE` is unset (`src/utils/paths.rs:380-389`), i.e. in
  systemd units without `Environment=HOME=`, cron, or a container with a stripped environment — configurations that do
  occur in production. In that state the gateway silently writes its credential vault and security DB into a
  world-writable, predictable location instead of refusing to start.
- **Impact**: pre-creation/symlink hijack is possible on a multi-user host (attacker plants `/tmp/.aleph/data` as a
  symlink to a path they control, or plants `/tmp/aleph_security.db` with a pre-seeded admin user). Even without an
  attacker, credentials land somewhere every `/tmp` cleaner deletes.
- **Suggested fix**: fail closed (`return Err(...)` with a clear "set HOME or ALEPH_HOME" message) instead of inventing a
  path; if a fallback is required for tests, gate it behind `cfg(test)`/an explicit env opt-in.
- **Confidence**: 0.7 on exploitability, 0.95 on the code shape.

### B10-S2-07 [P3] Gateway teardown owns none of the background tasks it spawns
- **Location**: `subsystems.rs` — `spawn_drain(channel_registry.clone(), store)` (delivery-queue replay),
  `let _inbound_router_handle = inbound_router.clone().start().await;` (handle immediately dropped), plus the config
  watcher task (`handlers/config.rs:80`) and the webchat task (`handlers/config.rs:196`). Process-global slots
  (`set_channel_registry`, `channel_policy::set_channel_config_snapshot`) are never cleared.
- **Failure mode**: nothing ties these tasks to `StartupResources`, so shutdown cannot await or cancel them, and a
  failure inside `inbound_router`'s task is unobservable (the `JoinHandle` is `_`-named). A second in-process start
  duplicates every task (two drain loops racing on the same queue) and leaves the first registry reachable through the
  process-global slot.
- **Suggested fix**: register each spawned task with `StartupResources` (abort/await on cleanup) and log the
  `JoinHandle`'s completion at `warn!` if it ends while the gateway is Up.
- **Confidence**: 0.9 (shape verified; blast radius is in-process restart, so P3).
