- Location: `/home/zou/data/workspace/Aleph-wt-review/src/approval/node_requester.rs:124`
- Failure mode: `run_node_approval` publishes `ApprovalRequested` with only `if let Err(e)` check. ## Not verified

### Cross-transport semantic divergence for undelivered notifications
Operator and node requesters fail closed when the initial `ApprovalRequested` cannot be delivered (APPROVAL-R3-003 / APPROVAL-R4-01 contract), but they encode the outcome differently: operator_requester returns `ApprovalOutcome::Unavailable` (a distinct fail-closed outcome introduced to prevent the ledger from treating undeliverable approvals as user refusals), while node_requester—after B3-S2-01 is fixed—would return the wire string `"unavailable"` (mapped from `ApprovalOutcome::Unavailable` by `outcome_to_wire`). The mapping itself is correct (node_requester.rs:54), but the first pass noted "node approvals currently diverge by accepting `publish_frame(Ok(0))`". With B3-S2-01 fixed, this divergence is closed; both transports now return the same semantic outcome (`Unavailable`) for the same trigger (zero subscribers at publish).

### Guardian judge prompt cache lifetime
`GuardianApprovalRequester.system_blocks` is built once at construction (guardian_requester.rs:210-214) and reused across all judge calls. The Anthropic provider's prompt cache is keyed on the exact text of the cached block; if `GUARDIAN_SYSTEM` is updated (e.g., risk taxonomy refined or an instruction clarified), existing `GuardianApprovalRequester` instances continue sending the old cached rubric until the process restarts. New instances use the new rubric, so a rolling deploy would mix old and new guardian verdicts for the same action. This is not a defect (the rubric is code—restart to update is standard), but it is a cross-request state artifact that survives prompt edits during development. Production impact: zero (prompt changes are code changes, deploy = restart). Development footgun: moderate (a running dev server's guardian keeps the stale rubric until restart).

### Breaker cooldown observes wall-clock time, not monotonic time
`GuardianBreaker.opened_at: Option<Instant>` (guardian_requester.rs:80) uses `std::time::Instant`, which is monotonic and unaffected by system clock adjustments. The cooldown check at :103 (`t.elapsed() >= GUARDIAN_BREAKER_COOLDOWN`) is therefore correct and immune to NTP jumps or manual clock changes. Not a defect.

### Operator `request_operator_once` applies explicit deadline on top of record expiry
`request_operator_once` (operator_requester.rs:120-157) computes a deadline at :133 (clamped to 60s), checks it at :135 before registration, at :172 before notification, at :192 during the select, and at :207 and :219 after resolution. The registered record's `expires_at_ms` (set at :164-169) is a separate expiry enforced by the manager. Both are checked; the tighter one wins. The explicit deadline ensures the caller's `CancellationToken` or wall-clock timeout dominates even if the manager's expiry is wider. This is intentional and documented (operator_requester.rs:131-132: "zero means deny, NOT the manager's no-expiry sentinel"). Not a defect.

### Unbounded reminder schedule
`remind_until_answered` (operator_requester.rs:281-327) is an endless loop that sleeps, publishes a reminder, and continues. The comment at :318-321 says "dead code—reachable only if a future caller hands in a finite iterator", and :322 awaits `pending()` to make returning impossible. The caller (operator_requester.rs:478-490) passes `reminder_schedule(timeout)`, which yields an endless iterator (mod.rs:217-231). The loop is dropped when the wait future wins the `select!`, which is the only documented exit. This is intentional design (reminders continue until the card is answered or the process dies). Not a defect.
