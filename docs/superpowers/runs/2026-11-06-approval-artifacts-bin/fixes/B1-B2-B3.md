## B1-01 [P1] A member's answer released another member's approval card
- verdict: fixed
- files: src/exec/manager.rs:413 (new `CascadeOriginScope`), src/exec/manager.rs:757-806 (`resolve_by_id` cascade scope), src/exec/manager.rs:933-968 (`cascade_to_identical_cards` filter), src/exec/manager.rs:1166-1180 (`resolve_for_session`), src/exec/manager.rs:2427-2495 (new test `a_member_answer_does_not_release_another_origins_card`)
- change: The cascade that releases "identical" cards now carries the authority of the answer: a new private `CascadeOriginScope` is `Any` for the operator path and `Originator(..)` for the member/channel paths. In `Originator` scope a sibling card is released only when its `originator_user_id` equals the addressed card's originator, so a member's click on their own card in a group chat can no longer resolve a card another member raised. Cards raised by the same originator still go together, and the operator path (`exec.approval.resolve`, `owner_only == false`) keeps the unrestricted cascade, so an operator's answer still stands for the session.
- risk: A member answering a card of an action whose sibling card was raised by somebody else now leaves that sibling pending instead of resolving it — intended, but it changes a group-chat behaviour. `resolve_for_session` (the text `/approve` path) is now originator-scoped for the same reason. The operator path and every single-card flow are unaffected. No public signature changed (`cascade_to_identical_cards` is a private helper).
- skipped-reason: n/a
