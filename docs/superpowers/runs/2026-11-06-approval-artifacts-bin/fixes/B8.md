## B8-01 [P2] Channel-pairing credential store falls back to a predictable, world-readable `/tmp` path

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:862-871`
- **change:** Removed the `/tmp/aleph_pairing.db` fallback. Changed `get_pairing_db_path().unwrap_or_else(|_| PathBuf::from("/tmp/aleph_pairing.db"))` to `get_pairing_db_path().map_err(|e| format!("Failed to resolve pairing store path: {e}"))?`. When the data dir cannot be resolved or created, boot now fails fast with the real reason instead of silently falling back to a fixed world-readable path that leaks credentials across tenants.
- **risk:** Boot will now fail when `HOME`/`USERPROFILE` is unset or the data directory is unwritable (e.g., service account with read-only home). This is the intended behavior: the previous fallback created a security vulnerability. Operators must ensure the data directory is writable or the daemon will refuse to start. No callers affected (the store is constructed in-place at startup).

## B8-02 [P2] Pairing store silently degrades to in-memory: durable credentials are lost while the RPCs keep answering

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:864-870`
- **change:** Removed the silent in-memory fallback. Changed `SqlitePairingStore::new(&pairing_store_path).or_else(|e| { eprintln!(...); SqlitePairingStore::in_memory() })` to `SqlitePairingStore::new(&pairing_store_path).map_err(|e| format!("Failed to create pairing store at {}: {e}", pairing_store_path.display()))?`. When the on-disk pairing DB cannot be opened (corrupt, wrong permissions, I/O error), boot now fails fast instead of silently degrading to an in-memory store that loses all existing pairings and makes new pairings non-durable.
- **risk:** Boot will now fail when the pairing DB file exists but is unreadable/corrupt. This is the intended behavior: the previous silent fallback created data-loss and misleading durability guarantees. Operators must fix the DB permissions/corruption or delete the file to force a fresh start. No callers affected (the store is constructed in-place at startup).

## B8-03 [P3] A2A tools stay registered but permanently dead when the execution adapter is missing; the error names the wrong cause and daemon mode logs nothing

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:2672-2689`
- **change:** Added `tracing::warn!` logging and improved user-facing message when A2A is enabled but dependencies are unavailable. Replaced the conditional `println!` with a match that determines the specific missing dependency (`(false, false)` → no adapter or registry; `(false, true)` → no adapter; `(true, false)` → no registry; `(true, true)` → unavailable for other reasons), logs unconditionally via `tracing::warn!(reason = %reason, "A2A is enabled but unavailable; the A2A server cannot start and outbound tools cannot be wired")`, and prints the reason in non-daemon mode. The tool error message still points to the config knob (that text lives in `src/builtin_tools/a2a_tools.rs` and was not changed per the minimal-fix rule), but operators now have a log line naming the real cause.
- **risk:** The A2A tools are still registered before we know whether they can work (the handle is created unconditionally at :1417-1419 and passed into `register_agent_handlers` at :1498, before the adapter-availability branch at :2607-2689). Moving the decision earlier would require restructuring tool registration, which was out of scope for this batch. Operators now have visibility into the failure mode, but the tools remain "registered but dead" when the adapter is missing. No behaviour change for the success case. No callers affected (the A2A subsystem is initialized in-place at startup).

## B8-04 [P2] The spend ledger's durability guarantee is false when the security store fell back to memory

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:603-605`
- **change:** Added a fail-fast check for security store fallback before installing the spend ledger. Immediately after `initialize_vault`, added `if let Some(reason) = auth_bundle.security_store_fallback.as_deref() { return Err(format!("Cannot start with non-durable security store: {reason}").into()); }`. When the security store falls back to in-memory (on-disk store cannot be opened), boot now fails instead of installing a "durable" spend ledger on top of RAM-backed storage. This prevents the scenario where per-principal spend limits can be bypassed by restarting the daemon.
- **risk:** Boot will now fail when the on-disk security store cannot be opened. This is the intended behavior: the previous silent fallback created a false durability guarantee. Operators must fix the security store path/permissions or the daemon will refuse to start. The users table already had a degraded-install arm for this case (`:628-636`), but the spend ledger did not. No callers affected (the ledger is installed in-place at startup before any request handler runs).

## B8-05 [P2] Provider build errors are swallowed: the provider's models silently vanish from the OpenAI-compatible routing table

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:1808-1831`
- **change:** Changed `if let Ok(http_provider) = build_http_provider(name, config)` to `match build_http_provider(name, config)` with an explicit `Err(error)` arm that logs `tracing::warn!(provider = %name, error = %error, "provider failed to build; its models are unavailable")`. When a provider fails to build (unknown protocol, invalid config), the error is now logged with the provider name and reason, so operators know why its models are missing from the routing table.
- **risk:** The provider is still dropped (its models are not added to `provider_map`), so clients calling `/v1/chat/completions` with those models still get `404 Model '<name>' not found`. The provider also still appears in `provider_configs` with no "not ready" marker, so `providers.list` does not distinguish "configured but failed" from "configured and working". Adding a "not ready" marker would require changing the `provider_configs` schema, which was out of scope for this batch. Operators now have visibility into the failure, but must infer the broken provider from the log line and the missing models. No callers affected (the provider map is built in-place at startup).

## B8-06 [P2] Duplicate model names across providers bind to a random provider (HashMap iteration order)

- **verdict:** fixed
- **files:** `src/bin/aleph-server/commands/start/mod.rs:1801-1802, 1803-1821`
- **change:** Sorted providers by name before building the map, and added duplicate-model tracking. Changed `for (name, config) in &app_cfg.providers` to `let mut providers = app_cfg.providers.iter().collect::<Vec<_>>(); providers.sort_by(|(left, _), (right, _)| left.cmp(right)); for (name, config) in providers`. Added `let mut provider_owners = std::collections::HashMap::new();` and a check inside the model loop: `if let Some(existing) = provider_owners.get(model) { tracing::warn!(model = %model, first_provider = %existing, duplicate_provider = %name, "multiple providers claim the same model; using the first provider"); continue; }`. The binding is now deterministic (alphabetically first provider wins), and duplicate claims are logged.
- **risk:** The deterministic sort is by provider name, not by any operator-specified priority. If two providers advertise the same model and the operator intended the second (alphabetically) to win, they must rename it to sort earlier or remove the duplicate from the other provider. The log line names both providers, so operators can see the conflict and fix it. No behaviour change for non-duplicate models. No callers affected (the provider map is built in-place at startup).
