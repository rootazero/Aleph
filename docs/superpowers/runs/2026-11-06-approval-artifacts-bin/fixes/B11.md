## B11-01 [P2] Fleet-wide stream registry + mint-time TTL makes a per-caller stream shared
- verdict: fixed
- files: `src/gateway/voice/streaming/relay.rs:34` (new `MAX_STREAMS_PER_OWNER`),
  `src/gateway/voice/streaming/relay.rs:45-48` (`StreamEntry.opened` → `last_activity`),
  `src/gateway/voice/streaming/relay.rs:87-140` (`insert`: per-owner cap before the global
  ceiling), `src/gateway/voice/streaming/relay.rs:213-219` (`audio_sender` refreshes the stamp)
- change: The single `StreamRegistry` stays fleet-wide (one registry per server is the existing
  design; the ownership predicates already scope who may act on an id), but capacity and lifetime
  are now per caller. `insert` resolves the owner first and, when the caller already holds
  `MAX_STREAMS_PER_OWNER`, evicts that caller's own least-recently-active entry before the
  pre-existing global ceiling runs — so a member opening streams can no longer evict another
  caller's in-flight dictation. The TTL now measures idle time rather than open time: every audio
  frame handed out by `audio_sender` refreshes `last_activity`, so a healthy dictation longer than
  10 minutes is no longer reaped by an unrelated `insert`. Unattributed entries (`owner == None`:
  cron, internal, pre-identity loopback) keep the old global-only behaviour, which is what
  `cap_evicts_oldest_entry` exercises.
- risk: A caller with three concurrent devices/tabs loses its own oldest stream at the third open
  (`MAX_STREAMS_PER_OWNER = 2`); that is a deliberate per-caller share of the existing global 8.
  The evicted stream still gets the normal terminal `{closed:true}` delta, so the Panel falls back
  to batch as it does for any cap eviction. No signature change; `StreamEntry` is private to the
  module and no other file names the field. Global ceiling, `STREAM_TTL` value and all ownership
  predicates are unchanged.

## B11-03 [P3] Absent optional subsystems answer -32601 instead of the typed service-unavailable
- verdict: fixed
- files:
  `src/bin/aleph-server/commands/start/builder/handlers/settings.rs:363-364` and
  `settings.rs:1001-1002` (`JsonRpcRequest` / `JsonRpcResponse` / `SERVICE_UNAVAILABLE` imports),
  `settings.rs:914-983` (ACP block), `settings.rs:1061-1083` (`voice.synthesize`)
- change: `acp.presets` / `acp.presets_meta` are stateless and are now registered unconditionally;
  the manager-dependent ACP verbs (10 methods) and `voice.synthesize` are registered on both
  branches, and the absent branch answers the codebase's typed contract instead of leaving the
  method unregistered: `JsonRpcResponse::error(id, SERVICE_UNAVAILABLE, "acp_unavailable" |
  "voice_synthesize_unavailable")`, matching the `memory.curated.*` precedent
  (`memory.rs:114-148`, asserted in `memory_lifecycle_tests.rs:59-100`). A client that switches on
  the error code can therefore distinguish "feature disabled on this deployment" from "server
  does not know this method". The `register_handler!` macro cannot carry an `Option` context, so
  the absent branch registers a plain closure on `handlers_mut().register(...)`, the same shape
  `session.rs` uses for conditionally-constructed handlers.
- risk: `acp.*` and `voice.synthesize` now appear in the handler map even when the subsystem is
  off, so a client that enumerates methods sees them; the answers are error responses, never
  success. `generation_registry` is `Some` at every current production construction site, so the
  `voice.synthesize` unavailable arm is defence-in-depth today rather than a live behaviour change;
  the ACP arm is live whenever `[acp] enabled = false`. Handler registration count changes for
  tests that assert method lists, if any.
