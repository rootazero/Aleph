## B10-001 [P1] Per-instance channel policies are registered under an ID the runtime does not use
- verdict: fixed
- files:
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1027-1032` (feishu arm: config guard released before the await)
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1054-1067` (feishu arm registers under the runtime id)
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1107-1110` (generic tiering arm: config guard released before the await)
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1153-1167` (generic tiering arm registers under the runtime id)
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1332-1350` (new `runtime_channel_id` helper)
  - `src/bin/aleph-server/commands/start/builder/subsystems.rs:1084-1104` (the stale ⚠️ comment rewritten)
- change: The executor resolves a channel policy by the id the *channel* reports
  (`channel_run_identity(&self.channel_configs, ctx.message.channel_id.as_str())`,
  `src/gateway/inbound_router/executor.rs:313`), which is the channel **type** for every factory that
  hardcodes it (`discord`, `slack`, `feishu`, `imessage`, …) and the **config instance id** only for the
  channels the builder rebuilds with it (`telegram`, `qq`, `whatsapp`, `webhook`). The feishu arm and the
  generic slash/tier arm registered the policy under the config instance id, so an instance whose id
  differs from its type keyed a policy nothing reads (tier / workspace / busy-input mode /
  tool-permission overrides all reverted to the defaults). Both arms now ask the channel registry which id
  the live channel reports (`runtime_channel_id`: the instance id when it is a registered channel id,
  otherwise the single registered channel id of that type, otherwise the instance id) and register under
  that id. The registry — not a re-derived rule — is the authority, so multi-instance channels
  (`telegram`/`qq`/`whatsapp`/`webhook`, rebuilt with the instance id) keep their distinct ids.
- risk: The key of the `channel_configs` map (and of the boot snapshot published to
  `alephcore::gateway::channel_policy`) changes from the config instance id to the runtime channel id for
  channels whose factory hardcodes the type. Every consumer of that map already looks it up by the runtime
  id (`src/gateway/inbound_router/mod.rs:1004`, `src/gateway/inbound_router/permission.rs:71-76`,
  `src/gateway/inbound_router/executor.rs:313`, `src/gateway/channel_policy.rs:176`), so this aligns the
  writer with the readers instead of changing a contract. Two instances of the same hardcoded-id type now
  share one key — but they already shared one *channel* (the registry's map is keyed by the runtime id, so
  the second registration already replaced the first); the surviving channel is the one the last-configured
  instance created, and the last registration now wins for the policy too (both loops iterate
  `resolved_channels()` in the same order). A channel whose creation failed is not in the registry, so the
  instance id is kept — the same key the policy used before. `initialize_channels` /
  `initialize_inbound_router` are unchanged as public functions (no signature change).

  failure surface, not a different outcome. No behaviour change on the current path: the registration
  succeeds and the registry is built exactly as before. `register_agent_handlers` already returns
  `alephcore::Result<AgentHandlersResult>`, so no signature change and no caller change.

## B12-P2-01 [P2] Unvalidated API key hydration from vault
- verdict: fixed
- files:
  - `src/bin/aleph-server/commands/start/builder/agent_init/provider_registry.rs:31-41` (`vault_lookup` treats a blank vault entry as "no key")
  - `src/bin/aleph-server/commands/start/builder/agent_init/generation_init.rs:31-47` (a blank vault secret is no longer installed as the provider key)
  - `src/bin/aleph-server/commands/start/builder/agent_init/generation_init.rs:66-73` (boot skip is logged)
  - `src/bin/aleph-server/commands/start/builder/agent_init/generation_init.rs:124-131` (reload skip is logged)
- change: The real defect behind the finding was an *empty* vault secret: `provider_registry.rs`'s
  `vault_lookup` returned `Some("")` for a blank entry, so `has_key` reported the provider as keyed while
  `hydrate` installed `Some("")` — a provider registered with an empty credential whose every request fails
  authentication. `vault_lookup` now returns `None` for a blank secret, and `generation_init.rs`'s
  `hydrate_key_and_gate` refuses to install a blank vault secret (it warns and leaves the key unset, so the
  existing gate drops the provider). Both provider-skip sites now warn with the provider name, so "provider
  configured but unusable" is diagnosable at boot instead of silent.
- risk: A provider whose vault entry is an empty string is now skipped instead of registered with an empty
  key — that is the fix (the old registration could only fail at request time). Provider-specific key
  *format* validation (prefix/length) was deliberately **not** added: key shapes differ per provider and
  custom OpenAI-compatible endpoints accept arbitrary strings, so a fixed rule would reject valid keys.
  `vault_lookup`/`has_key` are local closures; no public signature changed.

  until every MCP server-start watcher settles — up to 60 s per step
  (`src/extension/lifecycle.rs:348-353`) — while the gate was deliberately spawned non-blocking
