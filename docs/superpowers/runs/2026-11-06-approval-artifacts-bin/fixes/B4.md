## B4-01 [P0] Concurrent eviction deletes another `put`'s successful artifact

- verdict: fixed
- files: `src/artifacts/store.rs:262-289` (`PublicationLocks`, `publication_lock`), `src/artifacts/store.rs:141` (lock in `put`)
- change: Publication and eviction are now one critical section per session directory. A
  process-local registry (`std::sync::Mutex<HashMap<PathBuf, Weak<tokio::sync::Mutex<()>>>>`,
  pruned at 128 entries by dropping dead `Weak`s, same shape as `src/gateway/btw/seed/gate.rs`)
  hands out a `tokio::sync::Mutex<()>`; `put` acquires `lock_owned()` after `create_dir_all` and
  holds the guard (`let _publishing`) across `publish`, `evict_overflow`, and reconciliation. The
  victim snapshot of one `put` therefore can no longer contain a record another `put` is about to
  acknowledge, so `Ok(record)` always names a readable artifact.
- risk: (1) The lock is keyed by the *resolved* session directory, so two stores in one process
  serialise correctly; two separate processes writing the same session are still unsynchronised
  (the previous behaviour, and cross-process locking would need a file lock — out of scope and
  a new failure mode on NFS). (2) `put` now serialises per session, so concurrent puts into one
  session queue instead of interleaving: a throughput change, not a correctness one, and the only
  caller path publishes one artifact per tool call. (3) `purge_session` does not take the lock, so
  a purge racing a `put` can still delete a just-published artifact — unchanged from before and
  outside this finding's stated scope (it is a deliberate session-level delete, not eviction).

## B4-02 [P1] Acknowledged writes are not crash-durable

- verdict: fixed
- files: `src/artifacts/store.rs:531-547` (`write_atomic`), `src/artifacts/store.rs:549-562` (`write_synced`), `src/artifacts/store.rs:564-584` (`sync_parent_dir`)
- change: `write_atomic` no longer uses `fs::write` + `rename`. It creates the temp file,
  `write_all`s, `sync_all()`s it (data + metadata of the temp inode before the rename that makes
  it visible), then renames, then calls `sync_parent_dir`. On unix `sync_parent_dir` opens the
  parent directory and `sync_all()`s it so the rename itself is durable; on other targets it is a
  no-op. Both fsync failures on the temp file propagate as `?` — a write we cannot make durable is
  reported instead of acknowledged. The directory sync only warns: by then the rename has already
  succeeded, there is nothing to roll back, and macOS/network filesystems legitimately reject
  directory fsync.
- risk: One extra fsync per artifact (crash durability is not free) and one extra directory
  fsync per publish/evict. The directory fsync is best-effort by design, so on a filesystem that
  refuses it the temp-file durability is still guaranteed but the rename may not be — documented
  in the function comment rather than silently swallowed.

## B4-03 [P2] Failed writes and failed eviction leave untracked blobs outside the cap

- verdict: fixed
- files: `src/artifacts/store.rs:154-176` (`put` publication + `reconcile_orphans`), `src/artifacts/store.rs:291-308` (`publish`), `src/artifacts/store.rs:460-526` (`reconcile_orphans`, `is_stale`), `src/artifacts/store.rs:588-598` (`remove_quietly`)
- change: Two layers. (a) `put` now undoes its own partial work: if `publish` fails at any step
  (blob sync, blob rename, sidecar serialisation, sidecar write), it best-effort removes both the
  blob and the sidecar before returning the error, so a failed put leaves no `.bin` that `list`
  cannot see. (b) Every successful `put` then reconciles the directory: any `.bin` whose sidecar
  is absent, and any `*.tmp` leftover, is deleted only once it has been untouched for
  `ORPHAN_GRACE` (1 hour), so a concurrent in-process writer (or another process) is never raced
  and a crash-interrupted temp is eventually reclaimed. An unreadable mtime keeps the file.
- risk: Reconciliation runs on the `put` path (one extra `read_dir` per put — same cost class as
  the existing `read_records` snapshot in `evict_overflow`) and is bounded by the freshness test,
  so garbage younger than an hour survives until a later put. A `.bin` orphan therefore still
  consumes space for up to an hour after a crash; it is bounded garbage, not permanent garbage.
  Orphans younger than the grace period are also invisible to the cap for that window.

## B4-04 [P2] Reads allocate the whole file before enforcing any bound

- verdict: fixed
- files: `src/artifacts/store.rs:310-334` (`read_bounded`), `src/artifacts/store.rs:204-237` (`read`), `src/artifacts/store.rs:346-375` (`read_records`), `src/artifacts/store.rs:41` (`MAX_SIDECAR_BYTES`)
- change: `read_or_not_found` is replaced by `read_bounded(path, id, limit)`: it stats the file
  first and returns `ArtifactError::TooLarge` when `metadata.len()` exceeds `limit`, then reads
  through `file.take(limit + 1)` + `read_to_end` and returns `TooLarge` again if the stream still
  exceeds `limit` (the file grew between stat and read). `read` uses `MAX_SIDECAR_BYTES` (64 KiB)
  for the sidecar and `record.size.min(MAX_ARTIFACT_BYTES)` for the blob, keeping the existing
  size-disagreement check, so a blob can no longer be read past what the record and the global cap
  allow. `read_records` bounds sidecars the same way instead of `fs::read`.
- risk: `read` gained a new error shape (`TooLarge`) for blobs/sidecars that exceed the bound; the
  HTTP handler in `src/gateway/handlers/artifacts.rs:215` maps it to `INTERNAL_ERROR` (controlled
  string, not a panic). A sidecar larger than 64 KiB is now skipped by `read_records` with a
  warning (it was previously loaded whole) — a record with such a sidecar becomes invisible to
  `list` but its blob still occupies the cap; that is unreachable for records this store writes
  (a sidecar is a few hundred bytes). The stat-then-read race is handled by the second check, so a
  growing file still cannot overrun the limit.

## B4-05 [P2] Session encoding leaves Windows device names unchanged

- verdict: fixed
- files: `src/artifacts/mod.rs:40` (import), `src/artifacts/mod.rs:77-93` (`encode_session_key`), `src/artifacts/mod.rs:210-229` (test)
- change: `encode_session_key` now reuses the existing `crate::utils::paths::is_windows_reserved_name`
  guard (the same predicate `sanitize_filename` already applies) and prefixes the encoded form with
  `%` when it collides with a device name. `%` is unreachable in the normal encoding (every literal
  `%` is escaped to `%25`), so the mapping stays injective, and names outside the reserved set keep
  their previous spelling. The empty key still maps to `EMPTY_SESSION_DIR`.
- risk: Session directories for the handful of keys that are device names change name, so an
  existing artifact directory for such a session is orphaned on upgrade — but on Windows those keys
  could never create a directory in the first place (that was the bug), and on unix the old spelling
  still worked. `encode_session_key` is also used by the media cache, which now shares the fixed
  spelling (intended: both caches must agree on one directory name).
