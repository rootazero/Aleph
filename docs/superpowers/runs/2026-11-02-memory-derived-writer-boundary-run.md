## Evidence method / 证据方法

The census searched by behavior rather than only by type names: `tokio::spawn`, `spawn_blocking`, `JoinSet`, `MemoryOperation`, `dispatch_*`, raw insert calls, provider/cache construction, runtime propagation, and production constructors. The relevant source modules and the approved lifecycle design, plans, and prior run record were read before this record was created.

清查按行为检索，而不是只按类型名称检索：`tokio::spawn`、`spawn_blocking`、`JoinSet`、`MemoryOperation`、`dispatch_*`、raw insert、provider/cache 构造、runtime 传播与生产构造链。在写入本记录前，已读取相关源码模块、已批准的生命周期设计、计划、旧运行记录和本次边界计划。

Classification used in the ledger:

- **Owned / source-admitted**: the production path obtains or inherits a matching operation before the derived effect, and the owner retains the task or drains the child work.
- **Raw-only**: the path writes raw archival/telemetry/search data and intentionally remains available while derived Memory is Off; it does not mutate derived Memory state.
- **Pure synchronous / CPU**: the path performs computation or reads only, with no independent Memory effect or retained asynchronous child requiring lifecycle admission.
- **Standalone/test-only**: the public compatibility path or test path has no production runtime obligation; changing it would remove standalone compatibility or expand scope.
- **Candidate / RED required**: source evidence is incomplete or semantics are ambiguous. It is not a confirmed defect until a real temporary Markdown/SQLite test with a `Notify` or semaphore distinguishes the behavior.

清查中的分类含义：

- **Owned / source-admitted**：生产路径在派生效果前获取或继承匹配 operation，且 owner 保留任务或排空子任务。
- **Raw-only**：只写 raw 归档/遥测/搜索数据，并有意在派生 Memory Off 时继续可用；不修改派生 Memory 状态。
- **Pure synchronous / CPU**：只做计算或读取，没有独立 Memory effect，也没有需要生命周期准入的保留异步子任务。
- **Standalone/test-only**：公共兼容路径或测试路径没有生产 runtime 义务；修改它会破坏独立构造兼容性或扩大范围。
- **Candidate / RED required**：源码证据还不完整或语义存在歧义。除非真实临时 Markdown/SQLite 测试配合 `Notify` 或 semaphore 区分出行为，否则不认定为缺陷。

## Census conclusion before implementation / 实施前清查结论

The current source evidence confirms the main production derived boundaries are already source-admitted and retained: runtime startup roots, compression, Dream, producer, reconciler, note rebuild, SQLite blocking access, Memory RPC, capture dispatch, and delegation callbacks. The remaining direct raw writes are deliberately raw-only or are invoked from the retained session-end owner. The apparent plain `tokio::spawn` sites in legacy APIs and summary concurrency tests are not production bypasses based on current callsite searches.

当前源码证据确认：生产派生边界已经由 source-admitted 与 retained 机制覆盖，包括 runtime startup roots、compression、Dream、producer、reconciler、note rebuild、SQLite blocking access、Memory RPC、capture dispatch 与 delegation callback。剩余 direct raw write 要么明确是 raw-only，要么由保留的 session-end owner 调用。当前调用点搜索没有发现 legacy API 与 summary 并发测试中的 plain `tokio::spawn` 是生产绕过。

The provider/cache comparison also found no separate Memory-owned cache or provider task outside the runtime bundle. `MemoryServices::initialize` creates one activation snapshot; provider and embedding handles are captured by services, while SQLite-derived effects re-enter through the backend's matching `MemoryOperation`. The reflector's recall-signal closure writes through that same runtime-bound backend. This supports the narrower claim that the census found no provider/cache boundary requiring new propagation; it does not claim that all application providers or caches are Memory-owned.

provider/cache 比对同样没有发现 runtime bundle 之外另有一套 Memory-owned cache 或 provider task。`MemoryServices::initialize` 创建单次 activation snapshot；provider 与 embedding handle 由 services 持有，而 SQLite 派生效果通过 backend 的 matching `MemoryOperation` 重新进入。reflector 的 recall-signal closure 也通过同一个 runtime-bound backend 写入。因此可以提出较窄的结论：清查没有发现需要新增传播的 provider/cache 边界；这不等于所有应用 provider 或 cache 都由 Memory 所有。

At this point there is **no confirmed missing derived boundary** that justifies a production edit. The provider/cache and callback construction comparison is complete for the production paths identified by the census, so no RED test is being added: adding a RED without a source-proven production defect would test a newly invented contract and could incorrectly convert raw archival into derived lifecycle work. The bounded implementation result is therefore a documented no-change outcome; any future candidate must first produce a real-store RED with a `Notify` or semaphore handshake.

截至目前，**没有确认的派生边界缺口**足以支持生产代码修改。本次清查识别出的生产 provider/cache 与 callback 构造链源码比对已经完成，因此不添加 RED：在没有源码证明生产缺陷时添加 RED，会测试新编造的契约，并可能错误地把 raw 归档纳入派生生命周期。本次有界实施结果是“记录后不改代码”；未来候选必须先用 `Notify` 或 semaphore handshake 产生真实存储 RED。
