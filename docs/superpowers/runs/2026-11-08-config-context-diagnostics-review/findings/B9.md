### B9-01 [P0] `merge_sections` destroys `[security.ssrf]` configuration when saving `security` section
- Location: `src/config/save.rs:228-235` (`merge_sections`)
- Failure mode: When `Config::save_incremental` or `ConfigPatcher::apply` updates any path under the `security` section (e.g. `security.custom_patterns`), `merge_sections` processes `section = "security"`. In this case, `parts = ["security"]`, so `path_parts` is empty and `target` remains `existing` (the root TOML table). At line 228, `if section == "security"` checks `t.get("ssrf")` on the root table `t` rather than `t.get("security").and_then(|s| s.get("ssrf"))`. In all standard configurations, `ssrf` is a subsection of `[security]`, so `t.get("ssrf")` returns `None`. When line 235 executes `t.insert("security", value)`, `existing["security"]` is overwritten with `value` (which only contains serialized `ShellSecurityConfig` without `ssrf`). This permanently deletes the user's `[security.ssrf]` section on disk, erasing all allowed/blocked hosts, private network settings, and redirect limits upon the next server restart.
- Evidence:
```rust
if section == "security" {
    if let Some(ssrf) = t.get("ssrf").cloned() {
        if let toml::Value::Table(ref mut value_table) = value {
            value_table.entry("ssrf".to_string()).or_insert(ssrf);
        }
    }
}
t.insert(leaf_key.to_string(), value);
```
- Suggested fix: Inspect the existing `security` table before insertion, matching `preserve_external_sections` in the same file:
```rust
if section == "security" {
    if let Some(ssrf) = t.get("security").and_then(|s| s.get("ssrf")).cloned() {
        if let toml::Value::Table(ref mut value_table) = value {
            value_table.entry("ssrf".to_string()).or_insert(ssrf);
        }
    }
}
t.insert(leaf_key.to_string(), value);
```

### B9-02 [P1] `preserve_external_sections` resurrects omitted `Config` sections, breaking section deletion and rollback
- Location: `src/config/save.rs:257-266` (`preserve_external_sections`)
- Failure mode: `preserve_external_sections` is designed to protect foreign sections like `[gateway]` during full `save_to_file`. However, it treats any key in `existing` that is absent in `current` as an external section: `if !current.contains_key(key) { current.insert(...); }`. In `Config`, 16 fields (such as `profiles`, `search`, `fetch`, `unified_tools`, `guardrails`, `stability`, `fallback_provider`, `personas`, `bindings`, `stop_hooks`, etc.) use `#[serde(skip_serializing_if)]`. When an operator clears one of these sections (setting it to `None` or empty), `current` omits the key. `preserve_external_sections` copies the section back from `existing` and writes it to disk. Consequently:
  1. An operator can never clear or delete any `Option` or `Vec` section with `skip_serializing_if` using `save_to_file`.
  2. In `ConfigPatcher::rollback`, restoring a snapshot that lacked these sections updates `self.config` in memory to `None`, but `save_to_file` writes the old section back to disk, causing in-memory config and on-disk config to silently diverge.
- Evidence:
```rust
for (key, value) in existing {
    if !current.contains_key(key) {
        current.insert(key.clone(), value.clone());
    }
}
```
- Suggested fix: Distinguish known `Config` fields from foreign-owned sections (e.g. using an explicit allowlist of foreign sections such as `["gateway"]`, or checking against a list of known `Config` section names). Only copy keys that do not correspond to schema-defined `Config` fields.
- Confidence: 1.0

### B9-03 [P1] `ConfigPatcher` holds `RwLock` read guard across async `apply_live_sections`, creating deadlocks and high lock contention
- Location: `src/config/patcher.rs:383-391` and `src/config/patcher.rs:682-690` (`ConfigPatcher::apply`, `ConfigPatcher::rollback`)
- Failure mode: In both `apply` and `rollback`, `let cfg = self.config.read().await;` binds an `RwLockReadGuard<'_, Config>`. While holding this read lock, it calls `.await` on `apply_live_sections`. `apply_live_sections` performs async operations, including awaiting PTY manager deactivation under a 5-second timeout (`Duration::from_secs(5)`). Under Tokio's fair `RwLock`, if any concurrent task requests `self.config.write().await`, all subsequent read requests are blocked behind the waiting writer. If any event listener, PTY cleanup hook, or background task triggered during `apply_live_sections` attempts to read `self.config`, it deadlocks. Even without re-entrancy, all configuration readers and writers across the gateway are stalled for up to 5 seconds.
- Evidence:
```rust
let live_applied = {
    let cfg = self.config.read().await;
    crate::config::live_apply::apply_live_sections(
        &cfg,
        &[top_section.as_str()],
        self.event_bus.as_ref(),
    )
    .await
};
```
- Suggested fix: Release the `RwLockReadGuard` before entering `apply_live_sections` by cloning the configuration:
```rust
let (cfg_clone, event_bus) = {
    let cfg = self.config.read().await;
    (cfg.clone(), self.event_bus.clone())
};
let live_applied = crate::config::live_apply::apply_live_sections(
    &cfg_clone,
    &[top_section.as_str()],
    event_bus.as_ref(),
)
.await;
```
- Confidence: 1.0

### B9-04 [P1] `commit_patch` runs synchronous file I/O, OS locks, and fsyncs on Tokio worker thread while holding `RwLock` write lock
- Location: `src/config/patcher.rs:440-465` (`ConfigPatcher::commit_patch`)
- Failure mode: Inside `commit_patch`, `let mut config = self.config.write().await;` acquires an exclusive in-memory write lock. While holding this lock, it invokes `config.save_incremental_to_file(...)`. This synchronous function acquires an OS advisory file lock (`fs2`), performs multiple blocking file reads and metadata queries, writes a temp file, calls `sync_all` on the file and `sync_all` on the parent directory, renames the file, and adjusts file permissions. Running multiple synchronous blocking `fsync` syscalls directly on the Tokio async executor thread starves the Tokio worker and blocks all readers of `self.config` until the disk write and sync finish.
- Evidence:
```rust
let mut config = self.config.write().await;
...
if let Err(e) = config.save_incremental_to_file(&self.config_path, &[top_section]) {
    *config = previous;
    return Err(e);
}
```
- Suggested fix: Perform file serialization and blocking disk I/O in a separate helper off the critical write lock path, or offload the file write and directory sync to `tokio::task::spawn_blocking`.
- Confidence: 0.95

### B9-06 [P1] `deep_merge` fails to prune `null` keys on newly inserted objects, causing deserialization failure
- Location: `src/config/patcher.rs:846-848` (`deep_merge`) and `src/config/patcher.rs:814-820` (`set_nested_value`)
- Failure mode: In `deep_merge`, when `source_obj` contains a key absent in `target_obj`, line 846 initializes `let mut new_val = serde_json::Value::Null;` and calls `deep_merge(&mut new_val, source_val)`. Because `new_val` is `Null`, `target.as_object_mut()` is `None`, falling into the `_ => *target = source.clone()` branch. Any nested `null` values inside `source_val` (intended to delete keys per JSON Merge Patch semantics) remain intact in `new_val`. In `set_nested_value`, a similar failure occurs if the leaf key does not exist yet: it clones `patch` without calling `deep_merge`. When `validate_candidate` subsequently deserializes the candidate via `serde_json::from_value`, any non-`Option` field assigned `null` fails with `invalid type: null`, causing valid patches to be rejected.
- Evidence:
```rust
let mut new_val = serde_json::Value::Null;
deep_merge(&mut new_val, source_val);
target_obj.insert(key.clone(), new_val);
```
- Suggested fix: If `source_val.is_object()`, initialize `new_val` as `serde_json::Value::Object(serde_json::Map::new())` so `deep_merge` recurses into the object and strips null keys. In `set_nested_value`, ensure object patches always pass through `deep_merge`.
- Confidence: 1.0
