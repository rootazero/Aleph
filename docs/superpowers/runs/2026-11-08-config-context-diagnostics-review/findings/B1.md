### B1-01 [P1] `duplicate_instance` check unconditionally disabled when running `aleph-server doctor`
- Location: `src/diagnostics/checks/duplicate_instance.rs:33` (`count_other_instances`)
- Failure mode: Whenever `aleph-server doctor` (the CLI command meant to run diagnostics) is executed, `std::env::args().any(|arg| arg == "doctor")` checks the current process's command line and returns `true`, causing `count_other_instances()` to return `0` immediately without inspecting `sysinfo` processes. The command always falsely reports `[ok] Single instance (No other aleph-server processes detected.)`, even if multiple `aleph-server` daemons are running and racing the vault/database, completely defeating duplicate instance detection in the CLI doctor tool.
- Evidence:
  ```rust
  if std::env::args().any(|arg| arg == "doctor") {
      return 0;
  }
  ```
- Suggested fix: Remove the early return checking current process arguments. In the `sys.processes().values().filter(...)` predicate, filter out other processes whose command line contains `"doctor"` (e.g. `!p.cmd().iter().any(|arg| arg == "doctor")`), so that other doctor invocations are ignored while live daemon instances are properly detected.
- Confidence: 1.0

### B1-02 [P1] Blocking `statvfs` syscall inside async check without `spawn_blocking` in `disk_space`
- Location: `src/diagnostics/checks/disk_space.rs:93` (`DiskSpaceCheck::run`)
- Failure mode: `fs2::available_space(anchor)` executes a synchronous `statvfs` libc call (or `GetDiskFreeSpaceExW` on Windows) directly on the Tokio worker thread inside `async fn run`. When the data directory or its mount point is on a slow, unresponsive, or hanging network share (NFS, SMB, FUSE), the Tokio worker thread is stalled. Because `statvfs` does not yield to Tokio, `run_bounded`'s `tokio::time::timeout` cannot preempt or cancel the hung task, causing the entire diagnostics suite to hang.
- Evidence:
  ```rust
  let available = match fs2::available_space(anchor) {
      Ok(available) => available,
  ```
- Suggested fix: Wrap `fs2::available_space` (and the preceding ancestor directory `Presence::of` loop) in `tokio::task::spawn_blocking`.
- Confidence: 0.95

### B1-03 [P1] `discord_channel_health` violates engine severity contract by emitting `Severity::Info` on read failures
- Location: `src/diagnostics/checks/discord_channel_health.rs:226-240` (`findings_for`)
- Failure mode: `DiscordVerdict::Unknown` is rendered as `Finding::problem(CHECK_ID, Severity::Info, "Discord channel config status unknown", ...)`. In the diagnostics engine (`mod.rs`), `Severity::Info` is treated as a passing check: `render_human` renders it as `[ok]` and suppresses the detail line, `report.ok()` evaluates to `true`, and CI exit code is 0. An unreadable configuration file or permission error is thus disguised as a clean pass, breaking the core invariant established in `check.rs` and `mod.rs` where "unknown must never read as healthy".
- Evidence:
  ```rust
  DiscordVerdict::Unknown(reason) => vec![Finding::problem(
      CHECK_ID,
      Severity::Info,
      "Discord channel config status unknown",
  ```
- Suggested fix: Change `DiscordVerdict::Unknown` finding severity to `Severity::Warning` (consistent with `unknown_finding`), ensuring unreadable files and permission errors fail the health check and surface visibly.
- Confidence: 1.0

### B1-04 [P2] `discord_channel_health` falsely reports missing default `config.toml` as read failure
- Location: `src/diagnostics/checks/discord_channel_health.rs:251-254` (`probe`)
- Failure mode: On a clean/fresh installation running with default settings, `config.toml` does not exist on disk. `tokio::fs::read(path)` fails with `ErrorKind::NotFound`. `probe()` treats this as `DiscordVerdict::Unknown("read failed: No such file or directory...")` instead of recognizing that absence of `config.toml` is normal and simply means no Discord channel is configured. This emits an alarming read failure finding under `[ok]` on fresh installs.
- Evidence:
  ```rust
  let bytes = match tokio::fs::read(path).await {
      Ok(b) => b,
      Err(e) => return DiscordVerdict::Unknown(format!("read failed: {e}")),
  };
  ```
- Suggested fix: Probe presence with `Presence::of(CHECK_ID, "Discord channel config", path)` before reading. If `Presence::Absent`, return `DiscordVerdict::Ok` (no Discord channel configured). Only when `Presence::Present` does it attempt to read the file.
- Confidence: 0.95

### B1-05 [P2] Blocking `std::fs` operations inside `async fn run` in `hooks_consent`
- Location: `src/diagnostics/checks/hooks_consent.rs:41, 93, 265-268` (`HooksConsentCheck::run`)
- Failure mode: `HooksConsentCheck::run` calls `self.diagnose()` directly on the async executor thread. `self.diagnose()` performs synchronous `std::fs::read(path)` and calls `self.consent.entries()`, which internally performs another synchronous `std::fs::read_to_string` and JSON parse. If the file is on a network mount or I/O is slow, this stalls the Tokio worker thread.
- Evidence:
  ```rust
  async fn run(&self, _posture: Posture) -> Vec<Finding> {
      // Consent is never auto-repaired — approval is a human decision.
      self.diagnose()
  }
  ```
- Suggested fix: Offload `self.diagnose()` onto the blocking thread pool using `tokio::task::spawn_blocking`.
- Confidence: 0.95
