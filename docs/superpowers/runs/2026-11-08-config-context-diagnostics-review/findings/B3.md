### B3-01 [P1] drop_pre_scope_tables drops FTS tables on any transient database error instead of verifying missing column
- Location: `src/context/retrieval/content_index.rs:499-509` (`drop_pre_scope_tables`)
- Failure mode: During initialization in `ContentIndex::from_conn`, `drop_pre_scope_tables` checks if virtual tables need schema upgrade by calling `conn.prepare("SELECT session_id FROM {table} LIMIT 0")`. If `prepare` returns `Err` for any reason (e.g. transient `SQLITE_BUSY` lock contention, disk I/O glitch, or corrupted temporary table handle), `.is_err()` evaluates to `true`, and the function executes `DROP TABLE chunks` and `DROP TABLE chunks_tri`. This completely deletes the entire persistent FTS5 retrieval index for all sessions on disk, rather than only handling the intended legacy missing column case.
- Evidence:
```rust
        if conn
            .prepare(&format!("SELECT session_id FROM {table} LIMIT 0"))
            .is_err()
        {
            tracing::warn!(...);
            conn.execute_batch(&format!("DROP TABLE {table};"))?;
        }
```
- Suggested fix: Inspect the exact `rusqlite::Error` returned by `prepare`. Only drop the table when the error specifically indicates `no such column: session_id` (or query `PRAGMA table_info` to verify column existence). Propagate all other errors (such as `SQLITE_BUSY` or I/O errors) up to the caller without dropping tables.
- Confidence: 0.95

### B3-02 [P1] HistoricalUserImageStrippingStage unconditionally targets newest image without checking tool_results filter, stripping user images when tool results contain images
- Location: `src/context/budget/cheap_passes/image_stripping.rs:68-81` (`strip_history`)
- Failure mode: `HistoricalUserImageStrippingStage` runs when `clears_tool_results_server_side == true` (with `tool_results = false`) to strip older user images while leaving tool results for the server to handle. However, `strip_history` locates `newest_image_idx` via `messages.iter().enumerate().rev().find(|(_, m)| message_has_image(m))` without filtering out `ToolResult` messages. If the newest image in history was produced by a tool result (e.g., screenshot tool output), `newest_image_idx` points to that tool result. All user images preceding it are therefore treated as older than the newest image and get stripped to placeholders. When the provider's server-side tool result clearing later deletes the tool result image, the conversation is left with zero images—the latest user-supplied image was stripped unnecessarily.
- Evidence:
```rust
    let newest_image_idx = messages
        .iter()
        .enumerate()
        .rev()
        .find(|(_, m)| message_has_image(m))
        .map(|(i, _)| i);
```
- Suggested fix: Respect the `tool_results` filter when finding `newest_image_idx`. When `tool_results == false`, ignore `UnifiedMessage::ToolResult` messages when searching for the newest image so that the newest user image remains intact:
```rust
    let newest_image_idx = messages
        .iter()
        .enumerate()
        .rev()
        .find(|(_, m)| (tool_results || !matches!(m, UnifiedMessage::ToolResult { .. })) && message_has_image(m))
        .map(|(i, _)| i);
```
- Confidence: 0.95

### B3-03 [P1] accept_external_candidate serializes message slices to JSON strings, corrupting token estimates and massively overcounting image blocks
- Location: `src/context/budget/preflight.rs:300-307` (`accept_external_candidate`)
- Failure mode: `accept_external_candidate` evaluates token savings of external compaction candidates by calling `serde_json::to_string(before)` and `serde_json::to_string(&candidate)` and running `estimate_tokens_aware` on the serialized JSON strings. This breaks the budget token accounting contract:
  1. For `ContentBlock::Image`, the serialized JSON contains megabytes of raw base64 data, estimating hundreds of thousands of tokens at 2.5 chars/token, whereas the budget sensor and preflight stages charge a flat `IMAGE_TOKENS_ESTIMATE` (1,500 tokens). Stripping or adding an image distorts the token diff by 500x.
  2. For text messages, JSON formatting syntax (`{"role":"user","content":...}`) and string escape sequences are counted as prompt tokens, violating the invariant documented on line 158 ("otherwise the 'how many tokens did this candidate free?' question is answered with a different yardstick than the one the budget enforces").
  3. Every call allocates two massive JSON `String` copies of the conversation history on the heap.
- Evidence:
```rust
        let before_tokens = crate::context::budget::pressure::estimate_tokens_aware(
            &serde_json::to_string(before).unwrap_or_default(),
            self.token_estimate_ratio,
        );
        let after_tokens = crate::context::budget::pressure::estimate_tokens_aware(
            &serde_json::to_string(&candidate).unwrap_or_default(),
            self.token_estimate_ratio,
        );
```
- Suggested fix: Directly sum message token estimates using `estimate_message_tokens_aware(msg, self.token_estimate_ratio)` over `before` and `candidate`. This avoids JSON serialization allocations and maintains consistent token accounting for text, structured, and image blocks:
```rust
        let before_tokens: usize = before
            .iter()
            .map(|m| crate::context::budget::pressure::estimate_message_tokens_aware(m, self.token_estimate_ratio))
            .sum();
        let after_tokens: usize = candidate
            .iter()
            .map(|m| crate::context::budget::pressure::estimate_message_tokens_aware(m, self.token_estimate_ratio))
            .sum();
```
- Confidence: 0.95

### B3-05 [P2] ContentIndex::open bypasses standard open_sqlite_safe hardening, omitting WAL mode and busy_timeout
- Location: `src/context/retrieval/content_index.rs:126-129` (`open`)
- Failure mode: `ContentIndex::open` calls `rusqlite::Connection::open(db_path)` directly instead of `crate::utils::sqlite_open::open_sqlite_safe`. By default, SQLite connections open without WAL mode and with a `busy_timeout` of 0ms. If another thread or process accesses `index.db` concurrently (e.g. background TTL cleanup, inspection, or another subsystem query), any lock contention immediately errors out with `SQLITE_BUSY` (`database is locked`), causing indexing or search to fail intermittently.
- Evidence:
```rust

        Self::from_conn(conn)
    }
```
- Suggested fix: Use `crate::utils::sqlite_open::open_sqlite_safe(db_path)` to ensure standard WAL mode and `busy_timeout = 5000` are configured:
```rust
    pub fn open(db_path: &Path) -> Result<Self, IndexError> {
        let conn = crate::utils::sqlite_open::open_sqlite_safe(db_path)?;
        Self::from_conn(conn)
    }
```

### B3-06 [P2] Non-atomic deletion in ContentIndex::clear can leave chunks and chunks_tri tables desynchronized
- Location: `src/context/retrieval/content_index.rs:462-473` (`clear`)
- Failure mode: `ContentIndex::clear` issues two separate `conn.execute` statements against `chunks` and `chunks_tri` without enclosing them in a transaction. If the connection fails or an error interrupts execution between the two statements, the session's rows are deleted from `chunks` but remain present in `chunks_tri`. Subsequent searches and session listings will observe inconsistent results between the porter and trigram indices.
- Evidence:
```rust
        conn.execute(
            "DELETE FROM chunks WHERE session_id = ?1",
            params![session_id],
        )?;
        conn.execute(
            "DELETE FROM chunks_tri WHERE session_id = ?1",
            params![session_id],
        )?;
```
- Suggested fix: Wrap the two statements in a transaction:
```rust
        let tx = conn.transaction()?;
        tx.execute("DELETE FROM chunks WHERE session_id = ?1", params![session_id])?;
        tx.execute("DELETE FROM chunks_tri WHERE session_id = ?1", params![session_id])?;
        tx.commit()?;
```
- Confidence: 0.95

### B3-07 [P2] ContentIndex lacks eviction mechanism when MAX_SESSION_INDEX_BYTES quota is reached, permanently blocking further indexing in long sessions
- Location: `src/context/retrieval/content_index.rs:233-238` (`index_text`)
- Failure mode: `ContentIndex::index_text` enforces a hard quota of `MAX_SESSION_INDEX_BYTES` (16MB across both tables) per session. However, `ContentIndex` provides no FIFO or LRU eviction mechanism to prune earlier indexed sources when the quota is reached. Once a session accumulates 16MB of indexed data, all subsequent tool outputs fail indexing with `SessionQuotaExceeded` for the remainder of the session, permanently disabling search retrieval for newer outputs.
- Evidence:
```rust
        let retained_bytes = existing_session_bytes.saturating_sub(existing_source_bytes);
        if retained_bytes.saturating_add(new_bytes).saturating_mul(2) > MAX_SESSION_INDEX_BYTES {
            return Err(IndexError::SessionQuotaExceeded {
                limit: MAX_SESSION_INDEX_BYTES,
            });
        }
```
- Suggested fix: When `retained_bytes + new_bytes` exceeds the quota, evict the oldest indexed sources within the session (e.g. by querying earliest `source` entries and deleting them) until enough quota is freed, or expose a `prune_oldest_sources` method for `ToolResultStore` to invoke.
- Confidence: 0.85
