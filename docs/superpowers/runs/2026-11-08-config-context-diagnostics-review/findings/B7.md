### B7-01 [P1] `AcpAdapterEntry::hydrate_from_preset` wipes out user overrides due to uninitialized `#[serde(skip)] presence`
- Location: `src/config/types/acp.rs:575` (`AcpAdapterEntry::hydrate_from_preset`)
- Failure mode: `AcpAdapterEntry` marks its `presence: AcpAdapterEntryPresence` field with `#[serde(skip)]`. Whenever an `AcpAdapterEntry` is deserialized outside `deserialize_adapters_with_presets` (e.g. from JSON-RPC, gateway handlers, or cloned runtime objects), `presence` defaults to all `false`. When `hydrate_from_preset` is called (e.g. during runtime sync in `src/gateway/handlers/acp_config.rs:172`), all fields with `!presence.<field>` are treated as absent and overwritten by the preset's defaults. An operator's configured `trust_level = Disabled`, custom `executable`, or custom `args` are clobbered back to the preset's values (`TrustLevel::Full`, preset binary, preset args).
- Evidence:
```rust

    let presence = self.presence;
    self.hydrate_from_preset_with_presence(preset, &presence);
}
```
- Suggested fix: In `hydrate_from_preset`, check whether `self.presence` is active; if uninitialized, derive presence using `AcpAdapterEntryPresence::from_entry(self)` before calling `hydrate_from_preset_with_presence`.
- Confidence: 0.95

- Suggested fix: Either add `native_acp_args: Option<Vec<String>>` to `AcpAdapterEntry` or have `from_entry` populate `native_acp_args` from `entry.args` when `default_mode == AdapterModeSerde::NativeAcp`.
- Confidence: 0.95

### B7-03 [P1] `TeamDispatcherConfigToml` accepts zero values without clamping, leading to deadlocks and CPU starvation
- Location: `src/config/types/dispatcher/core.rs:42` (`TeamDispatcherConfigToml`)
- Failure mode: `TeamDispatcherConfigToml` fields (`max_concurrent`, `lock_ttl_secs`, `task_timeout_secs`, `fallback_tick_secs`) lack validation and boundary clamping. Unlike `TeamBroadcastConfigToml` and `TeamMessagesConfigToml`, which clamp `0` to default (`.filter(|&v| v > 0)`), `TeamDispatcherConfigToml` accepts `0` verbatim. If `max_concurrent: Some(0)` is configured, the dispatcher can never execute any tasks (permanent deadlock). If `fallback_tick_secs: Some(0)` is configured, `src/teams/dispatcher/mod.rs:280` executes `tokio::time::sleep(Duration::from_secs(0))` in a tight loop, causing 100% CPU thread starvation. If `task_timeout_secs: Some(0)`, every dispatched task immediately times out.
- Evidence:
```rust
pub max_concurrent: Option<usize>,
pub lock_ttl_secs: Option<u64>,
pub task_timeout_secs: Option<u64>,
pub fallback_tick_secs: Option<u64>,
```
- Suggested fix: Clamp zero values to their respective `DispatcherConfig::default()` values during mapping via `.filter(|&v| v > 0)` (mirroring the P7 boundary clamps used in `TeamBroadcastConfigToml` and `TeamMessagesConfigToml`).
- Confidence: 0.95

### B7-06 [P2] Inverted deduplication thresholds (`noop < similarity`) cause silent data loss of new facts
- Location: `src/config/types/memory/ingest.rs:35` (`CompoundIngestConfig`)
- Failure mode: `CompoundIngestConfig` defines `dedup_similarity_threshold` (default 0.92) and `dedup_noop_threshold` (default 0.985). The system contract requires `noop_threshold >= similarity_threshold`. If configured inverted (e.g. `noop: 0.90, sim: 0.95`), the ingest gate evaluates the noop threshold first and drops incoming note writes whose similarity falls between 0.90 and 0.95 as no-ops instead of appending them, causing silent data loss of valid facts.
- Evidence:
```rust
pub dedup_similarity_threshold: f32,
pub dedup_noop_threshold: f32,
```
- Suggested fix: Add validation ensuring `dedup_noop_threshold >= dedup_similarity_threshold` and that both values reside in `(0.0..=1.0)`.
- Confidence: 0.90
