### B5-01 [P1] `strip_tagged_block` and `unwrap_tagged_block` search closing tag from string start instead of after opening tag
- Location: `src/context/compact/summary_utils.rs:116` (`strip_tagged_block`), `src/context/compact/summary_utils.rs:144` (`unwrap_tagged_block`)
- Failure mode: When the model response contains a closing tag (e.g. `</analysis>` or `</summary>`) before the opening tag (such as in markdown commentary, code blocks, or an analysis mentioning `</summary>`), `text.find(close.as_str())` matches that preceding closing tag. For `strip_tagged_block`, `end > start` is false, so `<analysis>` scratchpad thoughts fail to be stripped and leak verbatim into the context summary. For `unwrap_tagged_block`, `end < inner_start` evaluates to true and returns `None`, failing to extract `<summary>...</summary>` and returning unstripped tags or falling back to truncation.
- Evidence:
```rust
let start = text.find(open.as_str())?;
let inner_start = start + open.len();
let end = text.find(close.as_str())?;
if end < inner_start {
    return None;
}
```
- Suggested fix: Search for `close` starting after `inner_start` (or `start + open.len()`):
```rust
let end = text[inner_start..].find(close.as_str()).map(|offset| inner_start + offset)?;
```
- Confidence: 1.0

### B5-04 [P2] Inverted fallback ratio in `ToolAwareChunker::new` causes 16x token count explosion

```rust

    token_ratio
} else {
```
- Suggested fix: Change `DEFAULT_RATIO` to `crate::context::budget::pressure::DEFAULT_PROSE_RATIO` (or `4.0`).
- Confidence: 1.0

### B5-05 [P2] Lossy head-elision in `file_carry` corrupts ledger round-tripping and breaks deduplication
- Location: `src/context/compact/file_carry.rs:185, 206-216` (`elide_path`), `src/context/compact/file_carry.rs:157-168` (`parse`)
- Failure mode: When a file path exceeds `MAX_PATH_CHARS` (120 chars), `render()` truncates its prefix to `…<tail>`. In subsequent compaction cycles, `parse()` parses this lossy string back as a real file path and places it into `prior.modified`. If the file is modified again in the new window, `ledger.modified.contains(&path)` fails to match the real full path against the elided `…` string. This causes duplicate entries for the same file, consumes slots in `MAX_LISTED_PATHS` (40 paths), and exposes non-existent paths starting with `…` to the model.
- Evidence:
```rust
lines.push(format!("{MODIFIED_PREFIX}{}", elide_path(path)));
...
let tail: String = path.chars().skip(count - MAX_PATH_CHARS).collect::<String>();
format!("…{tail}")
```
- Suggested fix: Either preserve full paths in the carry message (e.g., in a comment or structured form) or re-emit bytes verbatim / do not elide paths in the parseable ledger lines, or in `parse` filter out / normalize paths that begin with `…` so they don't corrupt deduplication.
- Confidence: 0.95
