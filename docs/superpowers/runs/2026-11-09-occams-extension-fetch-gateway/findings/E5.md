### E5-01 [P0] Workspace prefix check is bypassed by an in-root symlink

- **Location**: `src/extension/runtime/wasm/host_functions.rs:50` (`host_workspace_read`)
- **Failure mode**: A plugin granted only `docs/` requests `docs/link/key.pem`, where `docs/link -> ../secrets` points to `secrets/` inside the workspace → the lexical prefix check accepts `docs/link`, the canonical root check accepts the target, and the guest receives a file outside the granted prefix.
- **Evidence**: `"if let Err(e) = state.kernel.check_workspace_read(&path) {"`; `"if !canonical.starts_with(&root) {"`; `"match std::fs::read_to_string(&canonical) {"`
- **Suggested fix**: After canonicalization, apply the same allowed-prefix boundary check to the canonical path relative to the canonical workspace root (and reject if it is not under an allowed prefix) before reading. Preserve the existing default-deny lexical traversal checks, whole-workspace confinement, and JSON error contract.
- **Confidence**: 0.98

### E5-02 [P1] Workspace reads can block indefinitely and exceed the advertised byte cap

- **Location**: `src/extension/runtime/wasm/host_functions.rs:72` (`host_workspace_read`)
- **Failure mode**: An authorized prefix contains a FIFO, or a regular file changes after metadata is read → `metadata().len()` reports zero or an old small size, then `read_to_string` blocks waiting for a writer/EOF or allocates more than 1 MiB into host memory, stalling the host call and bypassing the cap.
- **Evidence**: `"let file_len = match std::fs::metadata(&canonical) {"`; `"if file_len > MAX_WORKSPACE_READ_BYTES {"`; `"match std::fs::read_to_string(&canonical) {"`
- **Suggested fix**: Require `metadata.is_file()` and read through a bounded reader with `take(MAX_WORKSPACE_READ_BYTES + 1)`, rejecting when the bounded read exceeds the cap. Preserve the existing prefix/root checks, UTF-8 behavior, and structured error responses.
- **Confidence**: 0.96

### E5-03 [P0] URL-path credential injection can move the request outside the validated allowlist

- **Location**: `src/extension/runtime/wasm/credential_injector.rs:173` (`inject_credential`)
- **Failure mode**: A `UrlPath` binding with placeholder `api` targets `https://api.example.com/v1/data`; after the binding resolves, a secret value such as `evil` produces `https://evil.example.com/v1/data` (or a placeholder in another URL component changes the scheme/authority) → the request is sent to a target that was never allowlist-checked, potentially disclosing the secret to the wrong host.
- **Evidence**: `"let modified = url.replace(placeholder, &encoded);"`; `"Ok(Some(modified))"`; the only pre-injection gate is `".check_http_request(&method, &req.url)"` in `src/extension/runtime/wasm/host_functions.rs:170-172`, while the final `egress_url` is sent at `:296`.
- **Suggested fix**: Restrict `UrlPath` replacement to a parsed path segment (reject placeholders not wholly within the path), then re-run the existing method/HTTPS/host/path allowlist check on the final URL immediately before sending. Preserve host-pattern matching, header/query injection, rate/call limits, and redirect prohibition.
- **Confidence**: 0.97

### E5-04 [P0] Request errors can return injected URL secrets to the guest

- **Location**: `src/extension/runtime/wasm/host_functions.rs:303` (`try_http_fetch`)
- **Failure mode**: A credential is injected into a query URL, then DNS, TLS, timeout, or connection failure occurs → reqwest formats the URL containing the secret into the error, `do_http_fetch` serializes that message, and the untrusted WASM guest receives the plaintext credential.
- **Evidence**: `"serializer.append_pair(param_name, secret_value);"` in `src/extension/runtime/wasm/credential_injector.rs:146`; `"let resp = builder.send().map_err(|e| format!(\"request failed: {e}\"))?;"`; `"Err(msg) => serde_json::json!({ \"error\": msg }).to_string(),"`
- **Suggested fix**: Strip the URL from reqwest errors with `without_url()` before formatting, and apply the same redaction to any response-read/client-build error that can carry the request URL. Preserve the host-facing error shape while ensuring no resolved secret can enter guest-visible diagnostics.
- **Confidence**: 0.93

### E5-05 [P1] Per-execution resource counters are never reset between plugin calls

- **Location**: `src/extension/runtime/wasm/capability_kernel.rs:210` (`WasmCapabilityKernel::check_http_limit`)
- **Failure mode**: A loaded plugin makes one HTTP call in each of 51 otherwise independent tool invocations → the first 50 consume the kernel's lifetime counter and every later invocation is permanently rejected until the plugin is reloaded, contrary to the documented per-execution limit; log entries have the same lifetime behavior.
- **Evidence**: `"/// Per-execution security kernel for WASM plugins"`; `"let prev = self.http_call_count.fetch_add(1, Ordering::SeqCst);"`; `"if prev >= self.limits.max_http_calls {"`. The kernel is constructed once at `src/extension/runtime/wasm/mod.rs:300-303`, while calls reuse the loaded instance at `:636-645`.
- **Suggested fix**: Retain the existing kernel Arc on the loaded instance and reset its HTTP and log counters under the plugin execution mutex immediately before each guest call, while retaining the sliding-window timestamp vector for the declared rate limit. Preserve the existing atomic admission behavior, per-call limits, and reload/unmount identity semantics.
- **Confidence**: 0.95

### E5-06 [P1] Re-registering a skill or agent leaves two different registrations for one identity

- **Location**: `src/extension/registry/plugin_registry/mod.rs:341` (`PluginRegistry::register_skill`; also `register_agent` at `:389`)
- **Failure mode**: Register skill `p:s` with prompt/allowed-tools A, then register the same plugin/name with updated values B → the namespaced entry becomes B but the short-key entry remains A. `get_skill("p:s")` always returns B, while `get_skill("s")` and `list_skills()` select either clone depending on HashMap iteration order. Agents have the same defect, so changed prompts, model settings, or permissions can remain stale on short-name resolution despite successful re-registration.
- **Evidence**: `".or_insert_with(|| skill.clone());"`; `"self.skills.insert(namespaced_key, skill);"`; `"self.agents.insert(namespaced_key, agent);"`
- **Suggested fix**: Apply the existing `register_tool` same-owner refresh rule to the skill and agent short keys: replace the short entry if absent or owned by the registering plugin, while retaining another plugin's incumbent short alias. Preserve namespaced lookup, active-plugin filtering, collision behavior across different owners, and public registration/serialization contracts. This removes the stale duplicate without introducing a second ownership map.
- **Confidence**: 0.98
