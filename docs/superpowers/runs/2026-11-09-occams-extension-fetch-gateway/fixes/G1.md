### G1-01 [P0] A concurrent ownership-cache fill can undo a completed rescope invalidation
- VERDICT: DOWNGRADE | ROUTE: FIX-NOW | claimed severity: P0
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/event_visibility.rs:1171` (`EventVisibilityIndex::session_admits`; cache insertion at 1212 and invalidation at 1330)
- **Failure mode**: An event's cache miss reads a personal session's old metadata, then pauses before inserting it. `projects.channel.bind` commits the move into a project room and calls `forget_session`; because the miss has not inserted anything, that invalidation removes nothing. The suspended miss then inserts the old personal ownership. Subsequent room frames keep using that stale personal scope until FIFO eviction/process restart: room members are denied, and the former personal owner continues to be admitted even if not in the room's current roster. This is persistent authorization-cache poisoning, not merely one frame already in flight during the bind. The rescope/invalidation contract and the distinction between personal-owner and room-roster decisions are documented in this same file at 776–788 and 1147–1156.
- **Evidence**: `Some(key) => match store.get_metadata(&key).await {` (1171); `self.cache_ownership(session_key.to_string(), ownership.clone())` (1212); `forget(order, map, session_key);` (1333).
- **Suggested fix**: Fence miss fills against invalidation: capture an invalidation generation before the metadata read, increment it under the cache lock in `forget_session`, and check it under that same lock before inserting or accepting the loaded ownership. If it changed, reload rather than publishing/using that stale value. A single cache-wide generation is sufficient; no second ownership map is needed. Preserve the bounded cache, the session store as ownership authority, fail-closed store errors, and per-frame live roster evaluation. The trade-off is an occasional extra metadata read when an unrelated session is rescoped.
- **Confidence**: 0.98

### G1-02 [P1] Stop followed by start installs a second persistent inbound forwarder
- VERDICT: UPHELD | ROUTE: FIX-NOW | claimed severity: P1
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/channel_registry.rs:1257` (`ChannelRegistry::start_channel_inner`; `start_message_forwarder` at 1921)
- **Failure mode**: Start a Legacy channel, stop it successfully, then start the same registration again. Every successful start spawns a forwarder, but stop only stops the adapter/unmounts its webhook; it does not stop the existing forwarder. The registration's persistent inbound broadcast survives stop/start, so both receivers forward each subsequent inbound message to `inbound_tx`. A single user message therefore reaches routing twice and can drive duplicate agent executions/replies. Each repetition adds another receiver. This is not a claim about Bound lifecycle: the file itself explains the persistent-broadcast behavior at 2095–2103 and avoids the duplicate only in `restart_channel_inner`.
- **Evidence**: `self.start_message_forwarder(channel_id.clone(), channel_arc.clone())` (1257); `tokio::spawn(async move {` (1924); `if let Err(e) = inbound_tx.send(message) {` (1950).
- **Suggested fix**: Track the Legacy forwarder's task in its registration entry and only install it when no live forwarder exists. Reuse it across ordinary stop/start, as restart already does; replace a completed task when needed. Preserve one inbound stream per registration, health stamping, broadcast lag recovery, existing adapter stop/start semantics, and the documented unregister return-value contract. Do not introduce a separate registry of channel capability ownership.
- **Confidence**: 1.0

### G1-03 [P1] Cancelling a Legacy lifecycle future permanently leaves its operation marker busy
- VERDICT: UPHELD | ROUTE: FIX-NOW | claimed severity: P1
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/channel_registry.rs:1232` (`begin_legacy_operation` and the Legacy lifecycle callers; also 1289, 2126, 694, and 456)
- **Failure mode**: Hold the exposed Legacy channel handle's write lock, start `start_channel`, and cancel/drop that future after admission while it waits for the channel lock. No adapter operation has run, but `runtime.operation` remains `Some`. After releasing the channel lock, every later start/stop/restart for that registration returns `Busy`; replacement and unregister also fail because `stop_outgoing_channel` uses the same admission check. Cleanup is only normal control flow after an await, so a caller timeout can strand an otherwise healthy channel until the registry is recreated. Cancellation during factory creation or adapter I/O has the same marker leak.
- **Evidence**: `runtime.operation = Some(marker.clone());` (1098); `let result = self.start_channel_inner(channel_id, &entry).await;` (1233); `self.finish_legacy_operation(&entry, &marker).await;` (1234).
- **Suggested fix**: Return an operation guard that owns the entry and marker and clears only its matching marker synchronously under the existing runtime mutex on drop; use it at every Legacy admission call site instead of relying on an awaited finish call. This closes the proven cancellation-before-I/O case without a new lock/map. Preserve per-entry mutual exclusion, marker identity fencing, stale-entry rejection, poison handling, and current adapter cancellation behavior; it does not imply rollback of adapter side effects from a partially completed operation.
- **Confidence**: 1.0

### G1-04 [P1] In-flight stamps do not prevent same-process replay of an interrupted or already delivered send
- VERDICT: UPHELD | ROUTE: FIX-NOW | claimed severity: P1
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/delivery_queue.rs:1408` (`DeliveryStore::begin_replay`; claim queries at 1219/1267 and settlement at 2038)
- **Failure mode**: An inline backlog flush stamps a queued row and sends it. The transport succeeds, but the caller is cancelled before settlement—for example while `send_on` awaits its post-send observer—or `mark_delivered` fails with a transient SQLite write error. The drain gate is subsequently released, but the still-due row retains its stamp. Both claim queries select stamped rows, and `begin_replay` overwrites an existing stamp rather than refusing it, so the next background tick sends that same message again. Startup-only `reconcile_inflight` does not protect a still-running process. Additionally, `spawn_drain` starts the drainer even when startup reconciliation fails. These paths violate the module's explicit rule that ambiguous sends become `UnknownOutcome`, never automatic retries.
- **Evidence**: `WHERE next_attempt_at <= ?1` (1219); `"UPDATE outbound_deliveries SET inflight_since = ?1 WHERE id = ?2 AND channel_id = ?3",` (1408); `warn!(id = rec.id, error = %e, "delivery queue: mark_delivered failed");` (2039).
- **Suggested fix**: While holding `drain_gate`, reconcile residual in-flight rows before each new drain/inline claim pass, not only at startup; no previous send can still own that gate, so these stamps represent unsettled attempts. If reconciliation fails, refuse that replay pass, including startup, rather than proceeding. This also covers failed settlement without adding a second outcome store. Preserve `UnknownOutcome` retention, explicit operator recovery rules, single-drainer/gate ownership, explicit-only policy fences, existing safe transient retry budgets, and per-conversation ordering. The trade-off is an additional reconciliation transaction per claim pass.
- **Confidence**: 0.99

### G1-05 [P1] Authority refusal closes a fabricated run instead of the interrupted run
- VERDICT: UPHELD | ROUTE: FIX-NOW | claimed severity: P1
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/resume_coordinator.rs:2401` (`ResumeCoordinator::settle_refused`; interrupted caller at 1880)
- **Failure mode**: Resume a recent interrupted run whose provenance is valid but whose owner now fails authority preflight, such as a deactivated principal. The interrupted path has already reduced and retained its real open run ID, but routes through `settle_refused`, which always calls `abandon` with `None`. The resulting `RunFinished { Abandoned }` names a new `abandoned-<uuid>` rather than the actual opener. The report calls the candidate closed, while by-ID consumers retain the original open run and see an unmatched terminal marker. Age/cap abandonment correctly passes the real ID, and `abandon` explicitly documents this pairing invariant at 2421–2425. This finding is about the stored by-ID contract, not a claim that the current last-finish disposition reducer necessarily re-resumes it.
- **Evidence**: `self.settle_refused(session_id, Abandoned::InterruptedRun, reason, report)` (1880); `self.abandon(session_id, what, None, &notice).await;` (2401); `|| format!("abandoned-{}", uuid::Uuid::new_v4()),` (2435).
- **Suggested fix**: Carry an optional `closes` ID through `settle_refused`; pass `reduction.open_run.as_ref().map(|o| o.run_id.as_str())` from the interrupted arm and `None` from the unanswered-message arm. Preserve no attempt spent on refusal, the privacy-safe public notice, full operator refusal details, goal handling, and the deliberately synthetic closer for an unanswered message with no open run.
- **Confidence**: 0.99

### G1-06 [P2] The oversized-payload rejection persists the entire oversized payload in the same database
- VERDICT: UPHELD | ROUTE: FIX-CAREFULLY | claimed severity: P2
- **Location**: `/home/zou/data/workspace/Aleph/src/gateway/delivery_queue.rs:966` (`DeliveryStore::enqueue_on`; `insert_dead_letter` at 1091)
- **Failure mode**: Send a large user-controlled inline attachment/text payload to a disconnected automatic channel. The serialized body exceeds `max_payload_bytes`, so the enqueue reports `TooLarge`, yet writes the full body to `dead_letters` in `delivery.db`. That table only limits row count. A handful of large media pushes can therefore still grow the database by hundreds of megabytes with single-digit row counts—the exact CWE-400 scenario the byte-limit documentation at 88–98 claims to prevent. Moving the bytes to another table does not bound disk use or the subsequent dead-letter payload reads.
- **Evidence**: `if payload.len() > self.config.max_payload_bytes {` (966); `payload: &payload,` (974); `let len: i64 = conn.query_row("SELECT COUNT(*) FROM dead_letters", [], |r| r.get(0))?;` (1096).
- **Suggested fix**: For `PayloadTooLarge` only, store a bounded, valid serialized diagnostic message without inline attachment bytes or unbounded text, retaining channel/conversation identity and original byte size in the error metadata. Keep the original `TooLarge { bytes }` result and non-redrivable reason; this preserves operator visibility without pretending the oversized body was durably retained. Leave ordinary, replayable dead-letter payloads unchanged. The explicit trade-off is that the rejected body cannot be inspected in full from the outbox.
- **Confidence**: 1.0
