### G3-01 [P1] 容量回收使用新请求的窗口，提前抹掉其他 scope 的有效计数
- VERDICT: UPHELD | ROUTE: FIX-NOW | claimed severity: P1
- **Location**: `src/gateway/rate_limiter.rs:431` (`RateLimiter::check_and_record`, `RateLimiter::prune_stale`)
- **Failure mode**: 配置不同长度的 scope 窗口，并触及 `max_entries` → 短窗口的新键触发全表回收，把长窗口内仍有效的记录删掉，从而允许原本应拒绝的请求。例如 `max_entries=1`、auth 限制为 60 秒内 1 次、rpc_default 窗口为 1 秒、非 loopback：t=0 接受一次 auth；t=2 首次 rpc_default 请求用 1 秒作为回收年龄，删除 auth 记录并进入；t=4 再次 auth 删除已过期的 rpc_default 记录后获准。两次 auth 只隔 4 秒，却均通过 60 秒限额。此例没有先触发 lockout，故保留活动 lockout 的分支不能阻止它。`RateLimitConfig` 明确支持独立的 per-scope `window_secs` 与 `max_entries`，不是必须修改内部状态才能构造的情形。
- **Evidence**:
  > `self.prune_stale(window_dur);` (line 431)
  > `self.windows.retain(|_key, sw| {` (line 511)
  > `Some(&last) => now.saturating_duration_since(last) < max_age,` (line 520)
- **Suggested fix**: 在 `prune_stale` 的 retain 闭包中使用条目的 `key.scope`，将保留期限取为 `max_age.max(Duration::from_secs(self.config.config_for(&key.scope).window_secs))`；继续先保留活动 lockout。这样任何调用者传入的短回收年龄都不会清除仍在所属 scope 窗口内的记录，同时保留现有公共签名、较长的显式保留期限、容量满时拒绝新键、loopback 豁免和各 scope 的限流/lockout 语义。

### G3-03 [P2] 父进程探针超时后只 kill 不 wait，遗留僵尸子进程
- VERDICT: UPHELD | ROUTE: FIX-CAREFULLY | claimed severity: P2
- **Location**: `src/gateway/shutdown_forensics.rs:195` (`read_parent_command`)
- **Failure mode**: Unix 上启用父命令探测，`ps` 在 250 ms 期限内没有退出 → 超时分支发送 kill 后直接返回并丢弃 `std::process::Child`。`kill()` 不回收退出状态，`Child` 的 Drop 也不会 wait，因此被杀的 `ps` 成为未回收的 zombie，持续到 gateway 退出或另有进程回收机制介入。该问题不需要 `kill()` 失败；成功发送信号的正常超时清理路径本身就遗漏了 reap。
- **Evidence**:
  > `if Instant::now() >= deadline {` (line 195)
  > `let _ = child.kill();` (line 196)
  > `return None;` (line 197)
- **Suggested fix**: 超时终止后显式回收子进程：在 kill 成功时调用 `child.wait()`，再返回 `None`；kill 失败时不得无条件阻塞等待仍活着的进程。保留 Unix 条件编译、探针结果 best-effort 的 `Option<String>` 契约及 250 ms 的探测等待期限；正常 kill/reap 会额外花费少量清理时间，不应继续把它描述成涵盖清理阶段的严格总时限。
- **Confidence**: 0.98
