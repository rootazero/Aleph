### B2-01 [P1] Lock inversion between `TargetControl::serial` and `LiveProfileOwner::mutations` causes 250ms timeout failure
- Location: `src/browser/live/control.rs:494`, `src/browser/live/mod.rs:508`, `src/browser/live/mod.rs:852` (`TargetControl::dispatch`, `LiveProfileOwner::mutate`, `LiveProfileOwner::dispatch_human_input_with_route`)
- Failure mode: Concurrent execution of an agent mutation (`LiveProfileOwner::mutate`) and a human input dispatch (`TargetControl::dispatch`) -> Thread A (`mutate`) acquires `owner.mutations.lock()` and awaits `control.agent_permit()` which tries to acquire `control.serial`. Concurrently, Thread B (`dispatch`) already holds `control.serial` and inside its dispatch closure awaits `dispatch_routed_human_input` which tries to acquire `owner.mutations.lock()`. Both operations stall for 250ms (`DISPATCH_BUDGET`) and fail with `BrowserError::ActionFailed("browser mutation permit delayed over 250ms")`.
- Evidence:
```rust
// mod.rs:508
let _mutation = tokio::time::timeout_at(deadline, self.mutations.lock()).await...;
permits.push(tokio::time::timeout_at(deadline, control.agent_permit()).await...);
// control.rs:494 & mod.rs:852
let Ok(_serial) = tokio::time::timeout_at(queued.deadline, self.serial.clone().lock_owned()).await;
...
let _mutation = tokio::time::timeout(Duration::from_millis(250), self.mutations.lock()).await...;
```
- Suggested fix: Do not acquire `owner.mutations` under `control.serial` in human input dispatch (or establish a consistent acquisition order where `owner.mutations` is always acquired prior to `control.serial`). Since human input already holds `control.serial` which fences out agent permits, re-acquiring `mutations` under `control.serial` is redundant.
- Confidence: 0.95

### B2-07 [P3] Fragile `yield_now().await` workaround to avoid lock self-deadlock in `declare_boundary_off_control_lock`
- Location: `src/browser/live/mod.rs:1456-1459`, `src/browser/live/control.rs:505-545`, `src/browser/live/control.rs:697-710`
- Failure mode: `TargetControl::dispatch` and `run_agent` poll their inner async future once while holding a non-reentrant `std::sync::MutexGuard`. Because navigation actions synchronously declare a document boundary which revokes grants and attempts to re-acquire `control.state.lock()`, `declare_boundary_off_control_lock` uses `tokio::task::yield_now().await` to defer boundary declaration to the second poll when the mutex guard is dropped. This relies heavily on runtime cooperative scheduling semantics; if polling order or waker behavior differs, an immediate non-reentrant deadlock occurs.
- Evidence:
```rust
    async fn declare_boundary_off_control_lock(&self, scope: BoundaryScope, cause: BoundaryCause) {
        tokio::task::yield_now().await;
        self.declare_boundary(scope, cause);
    }
```
- Suggested fix: Drop the synchronous state lock in `dispatch` and `run_agent` before calling `future.as_mut().poll(cx)`, removing the need for `yield_now().await` and eliminating the reentrant lock hazard at its architectural source.
- Confidence: 0.85
