### B7-01 [P1] Panic on `NaN` in `screenshot` quality argument via `f64::clamp`
- Location: `src/builtin_tools/desktop/native.rs:1094` (`call_via_platform`)
- Failure mode: When a caller or model passes a non-finite `quality` float (such as `NaN`) in `{"action": "screenshot", "format": "jpeg", "quality": NaN}`, `quality.unwrap_or(0.9)` evaluates to `NaN`. Calling `.clamp(0.0, 1.0)` on `NaN` panics in Rust's standard library (`"NaN passed to clamp"`). While coordinates, regions, durations, and deltas are checked with `finite_f64` / `is_finite()`, `quality` was omitted from validation, crashing the async worker task.
- Evidence:
```rust
let quality_u8 = (quality.unwrap_or(0.9).clamp(0.0, 1.0) * 100.0) as u8;
```
- Suggested fix: Validate `quality` with `finite_f64(quality, "quality")?` or filter with `.filter(|q| q.is_finite())` before calling `.clamp()`.
- Confidence: 0.95

### B7-02 [P1] Read-only batch operations misclassified as mutating `DesktopClick` causing false-positive approval gate or denial
- Location: `src/builtin_tools/desktop/mod.rs:579` (`classify_approval`)
- Failure mode: `classify_approval` maps `"batch"` unconditionally to `Some((ActionType::DesktopClick, "batch operation".into()))`. If an agent issues a batch containing only read-only actions (such as `screenshot`, `window_list`, or `wait_visual`), or if a UI-TARS action script containing only `wait()` is parsed into a batch, `classify_approval` misclassifies the entire batch as an intrusive `DesktopClick`. Under an interactive approval policy, this prompts the user for click confirmation (or denies execution) for a completely read-only request. Furthermore, for mutating batches, each sub-action is re-evaluated by `classify_approval` inside the loop, creating a redundant double-approval gate.
- Evidence:
```rust
"batch" => Some((ActionType::DesktopClick, "batch operation".into())),
```
- Suggested fix: Do not unconditionally classify `"batch"` as `DesktopClick`. Either inspect the batch's sub-actions to see if any requires approval, or omit `"batch"` from `classify_approval` and let each sub-action be gated individually during sequential dispatch in `execute_batch` (mirroring `check_hard_block` and `check_blocked_app`).
- Confidence: 0.95

### B7-04 [P2] TOCTOU race in file-based session lock acquisition and deletion across processes
- Location: `src/builtin_tools/desktop/session_lock.rs:79-113` (`acquire`) and `src/builtin_tools/desktop/session_lock.rs:180` (`write_lock_file`)
- Failure mode: `ComputerUseLock::acquire()` checks `self.lock_path.exists()` and `self.read_lock_file()`, and subsequently calls `self.write_lock_file()`. `write_lock_file()` calls `fs::write(&self.lock_path, content)`, which uses `create(true).truncate(true)` instead of atomic `create_new(true)`. If two Aleph server instances attempt to acquire the lock concurrently when no lock exists or when the prior lock PID is dead, both pass the check and both write the file with `fs::write`, leaving both handles with `self.held = true`. Furthermore, on release, process A can delete the lock file after process B has just acquired it.
- Evidence:
```rust
if self.lock_path.exists() {
    match self.read_lock_file() { ... }
}
self.write_lock_file()?;
self.held = true;
```
- Suggested fix: Use atomic file creation (`std::fs::OpenOptions::new().write(true).create_new(true)`) or an OS-level file lock (`fs4::FileExt::try_lock_exclusive`) to eliminate the check-then-write race window.
- Confidence: 0.90

### B7-05 [P2] Blocking synchronous filesystem I/O executed directly on Tokio worker thread in `session_lock`
- Location: `src/builtin_tools/desktop/session_lock.rs:160, 167, 180, 142` (`acquire`, `release`, `Drop`)
- Failure mode: `DesktopTool::call` runs in the Tokio async runtime thread. Step 4 acquires `_session_guard` by calling `acquire_for_session`, which synchronously performs `fs::read_to_string`, `fs::create_dir_all`, and `fs::write` on `computer-use.lock`. On drop, `fs::remove_file` is executed synchronously. Under slow disk or networked storage conditions, synchronous file I/O blocks the Tokio executor thread.
- Evidence:
```rust
let content = fs::read_to_string(&self.lock_path).ok()?;
...
fs::write(&self.lock_path, content)
...
fs::remove_file(&self.lock_path)
```
- Suggested fix: Offload filesystem access in `session_lock` to `tokio::task::spawn_blocking` or use `tokio::fs`.
- Confidence: 0.90
