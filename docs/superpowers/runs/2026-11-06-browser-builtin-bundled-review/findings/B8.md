### B8-1 [P1] `stats.rs` sorts after premature truncation, discarding top-ranking files
- Location: `src/builtin_tools/file_ops/stats.rs:141-150` (`execute_stats`)
- Failure mode: When `execute_stats` runs with `limit` (e.g. `limit = 10`) and `sort_by = Some(StatsSort::Size)` or `StatsSort::Lines`, it stops accumulating matching file entries into `files` as soon as `files.len() == cap` during the walk (`if files.len() < cap { files.push(info); }`). Subsequent files visited by `glob::glob` are ignored for the per-file rows, even if they have much larger byte sizes or line counts. Then `sort_files` sorts only the first `cap` items yielded by the filesystem. This directly violates the documented invariant in `types.rs:55-56` and `stats.rs:28-30` ("`size` / `lines` sort descending (largest first) so the cap retains the *biggest* matches — typical 'show me the top offenders' intent"), causing the tool to return arbitrary first files rather than the actual top offenders.
- Evidence:
  ```rust
  total_files += 1;
  if files.len() < cap {
      let mut info = FileInfo::with_path(&path);
      info.size = size;
      info.lines = lines;
      info.mtime = mtime;
      files.push(info);
  }
  ```
  Followed immediately by `sort_files(&mut files, sort_by.unwrap_or(StatsSort::Name));`
- Suggested fix: Collect matching `FileInfo` rows and sort before truncating with `files.truncate(cap)` (consistent with `execute_list` in `ops.rs:89-91`), or maintain a bounded top-K heap during iteration if memory bounding is required.
- Confidence: 1.0

### B8-3 [P1] Synchronous 40,000-file directory traversal in async `find` and `grep` stalls Tokio executor

- Evidence:
  In `find.rs:127`:
  ```rust
  let (root, report) = walk(&WalkRequest {
      path,
      glob: Some(args.pattern.as_str()),

  })?;
  ```

  ```rust
      respect_ignore: respected_ignore,
      denied_paths: &self.denied_paths,
      output_dir: output_dir.as_deref(),

  ```
- Suggested fix: Wrap the `walk(...)` call in `tokio::task::spawn_blocking` in both `FindTool::run` and `GrepTool::run`.

### B8-5 [P2] Dead `..` component handler and premature abort in `safe_normalize`
- Location: `src/builtin_tools/file_ops/path_utils.rs:1230-1250` (`safe_normalize`)
- Failure mode: In `safe_normalize`, the loop peels non-existent components using `if let Some(file_name) = existing.file_name()`. In Rust stdlib, `Path::file_name()` returns `None` if the final component is `..` or `.`. If a non-existent path has `..` in its non-existent portion (e.g. `/tmp/nonexistent/../sub`), `file_name()` returns `None`, causing the loop to `break` prematurely with `..` still attached to `existing`. Then `existing.canonicalize()` is called on `/tmp/nonexistent/..`, which fails with `NotFound` and returns an execution error. Furthermore, lines 1246-1250 checking `if component == ".."` are completely dead code because `remaining` was populated exclusively from `file_name()`, which can never return `".."` or `"."`.
- Evidence:
  In `path_utils.rs:1230-1237`:
  ```rust
  while !existing.exists() {
      if let Some(file_name) = existing.file_name() {
          remaining.push(file_name.to_owned());
          existing.pop();
      } else {
          break;
      }
  }
  ```
  And lines 1246-1250:
  ```rust
  for component in remaining.into_iter().rev() {
      if component == ".." {
          result.pop();
      } else if component != "." {
          result.push(component);
      }
  }
  ```
- Suggested fix: Inspect `existing.components().next_back()` to properly pop `ParentDir` (`..`) and `CurDir` (`.`) components from `existing` into `remaining`, so `..` can be resolved as intended instead of hitting the `break` branch.
- Confidence: 0.95

### B8-8 [P2] Unescaped root path causes `glob::glob` failure when directory name contains brackets
- Location: `src/builtin_tools/file_ops/search.rs:38` (`execute_search`), `src/builtin_tools/file_ops/stats.rs:61` (`execute_stats`), `src/builtin_tools/file_ops/batch.rs:89` (`execute_batch_move`)
- Failure mode: `full_pattern = canonical.join(pattern)` joins the caller-supplied pattern with the canonicalized base directory. If the base directory path contains glob metacharacters (e.g. `/home/user/project [v1]/`), `glob::glob` parses `[v1]` as a glob character class instead of literal directory characters. The search then looks for directories matching `v` or `1` and fails to find any files in `/home/user/project [v1]/`.
- Evidence:
  In `search.rs:38-39`:
  ```rust
  let full_pattern = canonical.join(pattern);
  let pattern_str = full_pattern.to_string_lossy();
  ```
  Passed directly to `glob::glob(&pattern_str)`.
- Suggested fix: Escape the root path prefix using `glob::Pattern::escape(&canonical.to_string_lossy())` before joining with `pattern`, or scope the search to the directory without passing the absolute base path into the glob parser.
- Confidence: 0.90

- Suggested fix: Update the check to `if expanded_str.starts_with("~/") || expanded_str.starts_with("~\\") || expanded_str.as_os_str() == "~"`.
