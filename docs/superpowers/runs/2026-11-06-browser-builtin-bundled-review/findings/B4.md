### B4-01 [P1] Blocking recursive filesystem directory walk in async `playwright_managed`
- Location: `src/browser/chromium_resolve.rs:554` (`playwright_managed`)
- Failure mode: In the async function `playwright_managed` (executed on the Tokio worker thread during binary resolution), `files_under(&dir, WALK_MAX_DEPTH)` and `scan_sibling_installs(&dir)` synchronously invoke `std::fs::read_dir` to walk up to 5 directory levels deep. The file's own documentation notes this enumerates `.app` bundles containing thousands of entries. Under slower disks, network filesystems (NFS), or high I/O load, this blocks the Tokio executor thread for tens to hundreds of milliseconds, starving other concurrent asynchronous tasks.
- Evidence:
```rust
if let Some(exe) = executable_among(&files_under(&dir, WALK_MAX_DEPTH)) {
    return Ok(exe);
}
let (seen_revisions, sibling_exe) = scan_sibling_installs(&dir);
```
- Suggested fix: Wrap the directory walk in `tokio::task::spawn_blocking` (matching the pattern used for `find_chromium_preferred` and `managed_cli_path` earlier in the same file), or offload the entire post-dry-run parsing and filesystem resolution to a blocking task before returning the resolved path.
- Confidence: 0.95

### B4-02 [P1] Synchronous `/proc` filesystem read inside async `ensure_chrome_running`
- Location: `src/browser/chrome_mcp.rs:594` (`ChromeMcpDriver::ensure_chrome_running`)
- Failure mode: Inside `ensure_chrome_running` (an async function on the Tokio worker thread), `read_proc_starttime(pid)` performs a synchronous `std::fs::read_to_string(&format!("/proc/{pid}/stat"))`. Under containerized/virtualized environments or high system load where `/proc` reads contend on kernel task locks, performing synchronous filesystem I/O on the Tokio thread violates async runtime safety and risks stalling other tasks on that worker.
- Evidence:
```rust
#[cfg(target_os = "linux")]
let starttime = read_proc_starttime(pid).ok();
```
where `read_proc_starttime` at line 316 calls:
```rust
let stat = std::fs::read_to_string(&path)?;
```
- Suggested fix: Use `tokio::fs::read_to_string(&path).await` or wrap the invocation in `tokio::task::spawn_blocking(move || read_proc_starttime(pid)).await.unwrap_or(Err(...))`.
- Confidence: 0.95

### B4-03 [P2] Unbounded `per_session_locks` memory leak across dynamic session keys
- Location: `src/browser/playwright_cli.rs:185` (`PlaywrightCliDriver::session_lock`)
- Failure mode: When session locks are requested via `session_lock(session_key)`, new entries are inserted into `per_session_locks: RwLock<HashMap<String, Arc<Mutex<()>>>>`. While `ChromeMcpDriver` explicitly cleans up its session locks in `destroy_session` (documented under BROWSER-R4-06 to avoid leaking heap across dynamic profile names), `PlaywrightCliDriver` never removes entries from `per_session_locks` during `shutdown_chromium`, `shutdown_all_chromium`, or tab disposal. In long-running daemons with multi-tenant materialized profiles (`default__u-alice`, etc.) or ephemeral profile names, `per_session_locks` grows monotonically without bound.
- Evidence:
```rust
fn session_lock(&self, session_key: &str) -> Arc<Mutex<()>> {
    let mut map = self.per_session_locks.write().unwrap_or_else(|e| e.into_inner());
    map.entry(session_key.to_string())
        .or_insert_with(|| Arc::new(Mutex::new(())))
        .clone()
}
```
- Suggested fix: Add `self.per_session_locks.write().unwrap_or_else(|e| e.into_inner()).remove(session_key);` in `PlaywrightCliDriver::shutdown_chromium`, and drain `per_session_locks` in `PlaywrightCliDriver::shutdown_all_chromium`, mirroring BROWSER-R4-06 in `ChromeMcpDriver`.
- Confidence: 0.95

### B4-05 [P3] Duplicate function body in `ChromeMcpBackend::type_text` instead of delegating to `fill`

The function's own docstring states that it "Delegates to fill", yet it duplicates the logic instead of making the call `self.fill(tab_id, target, text).await`. - Suggested fix: Replace the body with `self.fill(tab_id, target, text).await` or remove the override and rely on the trait default implementation in `BrowserBackend`.
