### B1-01 [P1] Synchronous blocking filesystem calls inside async `RecordingRegistry::start`
- Location: `src/browser/cdp_backend/recording.rs:478` (`RecordingRegistry::start`)
- Failure mode: In `RecordingRegistry::start` (an async function running on the Tokio worker thread), multiple blocking synchronous filesystem operations (`std::fs::create_dir_all`, `probe_writable` via `std::fs::write` and `std::fs::remove_file`, and `fs2::available_space` syscall) execute directly without `tokio::task::spawn_blocking` or `tokio::fs`. If the recording target directory resides on a slow, spinning, or network-mounted filesystem (NFS/CIFS) or under high I/O saturation, these synchronous calls block the Tokio runtime thread, delaying event handling and stalling concurrent async tasks across the browser module.
- Evidence:
```rust
if managed {
    if let Some(parent) = raw.parent() {
        std::fs::create_dir_all(parent)?;
    }
}
...
probe_writable(&parent)
    .map_err(|_| RecordStartError::PathNotWritable { path: path.clone() })?;

// 3. The disk floor (spec §3: <500MB 拒录).
if let Ok(available) = fs2::available_space(&parent) {
```
- Suggested fix: Replace `std::fs::create_dir_all` with `tokio::fs::create_dir_all(parent).await?`, make `probe_writable` async using `tokio::fs::write` and `tokio::fs::remove_file`, and wrap `fs2::available_space` in `tokio::task::spawn_blocking`.
- Confidence: 1.0

### B1-02 [P2] Unhandled panic risk on `child.stdin.take().expect(...)` in spawned task
- Location: `src/browser/cdp_backend/recording.rs:721` (`run_recording`)
- Failure mode: In `run_recording` (a background task spawned via `tokio::spawn`), `child.stdin.take().expect("ffmpeg stdin is piped")` calls `.expect()` on the child process stdin handle. If `child.stdin` is `None` (for instance, if `spawn_ffmpeg` process configuration is modified or if stdin handle was already consumed), the spawned task panics immediately. This aborts supervisor execution before the live owner tap is cleanly released and before receipts are finalized in the registry.
- Evidence:
```rust
let child_stdin = child.stdin.take().expect("ffmpeg stdin is piped");
```
- Suggested fix: Safely unwrap `child.stdin.take()` with `let Some(child_stdin) = child.stdin.take() else { ... }`, returning an appropriate error / `Break::WriterDied` to allow normal supervisor finalize and receipt generation without panicking.
- Confidence: 0.95

### B1-03 [P2] Case-sensitive cookie domain matching violates RFC 6265
- Location: `src/browser/cdp_backend/cookies.rs:102` (`cookies`)
- Failure mode: In `CookieOp::List { domain, path }`, filtering matches domains using case-sensitive equality `c.domain.trim_start_matches('.') == d.trim_start_matches('.')`. Per RFC 6265 §5.1.3, domain names are ASCII case-insensitive. If an engine returns a domain with uppercase letters or a caller queries with mixed/uppercase domain names (e.g. `domain: Some("Example.com")`), valid cookies are erroneously discarded and the caller receives `"no cookies match"`.
- Evidence:
```rust
domain.as_ref().is_none_or(|d| {
    c.domain.trim_start_matches('.') == d.trim_start_matches('.')
})
```
- Suggested fix: Use case-insensitive comparison `eq_ignore_ascii_case`:
```rust
domain.as_ref().is_none_or(|d| {
    c.domain.trim_start_matches('.').eq_ignore_ascii_case(d.trim_start_matches('.'))
})
```
- Confidence: 0.95

### B1-04 [P3] Expect panic risk on Enter key resolution in `type_text`
- Location: `src/browser/cdp_backend/actions.rs:1394` (`type_text`)
- Failure mode: In `type_text`, `let (down, up) = press_key_event("Enter").expect("Enter is in the table");` uses `.expect()` on a production dispatch path. Although `"Enter"` is present in the current `KEY_TABLE`, `press_key_event` returns `Option<(KeyEvent, KeyEvent)>`. Any future refactoring of key mapping or dynamic key resolution could turn this into a runtime panic.
- Evidence:
```rust

```
- Suggested fix: Handle the `Option` safely using `let Some((down, up)) = press_key_event("Enter") else { ... };` and return a `BrowserError::ActionFailed` or continue cleanly.
- Confidence: 0.90

### B1-05 [P3] Gratuitous vector clone on every `Runtime.consoleAPICalled` event
- Location: `src/browser/cdp_backend/events.rs:102` (`apply_event`)
- Failure mode: When folding `Runtime.consoleAPICalled` events, `ev.params["args"].as_array().cloned().unwrap_or_default()` clones the entire `Vec<Value>` of arguments into an owned vector before calling `args.iter().map(render_arg)`. On web pages that generate frequent or verbose console messages, this triggers redundant heap allocations and copies on the event pump thread.
- Evidence:
```rust
let args = ev.params["args"].as_array().cloned().unwrap_or_default();
let text = args.iter().map(render_arg).collect::<Vec<_>>().join(" ");
```
- Suggested fix: Operate on the borrowed array slice without `.cloned()`:
```rust
let text = ev.params["args"]
    .as_array()
    .map(|args| args.iter().map(render_arg).collect::<Vec<_>>().join(" "))
    .unwrap_or_default();
```
- Confidence: 0.95

### B1-07 [P3] Redundant `metadata` call in Unix executable permission probe
- Location: `src/browser/cdp_backend/recording.rs:197-200` (`is_executable`)
- Failure mode: `is_executable` calls `p.is_file()` followed immediately by `std::fs::metadata(p)`. `p.is_file()` internally issues a `metadata(p)` syscall. Consequently, every candidate file probed during PATH traversal triggers two consecutive `stat` syscalls instead of one.
- Evidence:
```rust
p.is_file()
    && std::fs::metadata(p)
        .map(|m| m.permissions().mode() & 0o111 != 0)
        .unwrap_or(false)
```
- Suggested fix: Call `std::fs::metadata(p)` once and verify both `m.is_file()` and `m.permissions().mode() & 0o111 != 0`.
- Confidence: 0.95

### B1-08 [P3] Infallible expect on string JSON serialization in `import_local_storage_js`
- Location: `src/browser/cdp_backend/migration.rs:239` (`import_local_storage_js`)
- Failure mode: `serde_json::to_string(origin).expect("origin is serializable")` invokes `.expect()` on serializing a `&str`, which is statically infallible in `serde_json`. While it never fails at runtime, using `.expect()` in production code trips zero-expect linting rules and creates unnecessary noise.
- Evidence:
```rust
let origin = serde_json::to_string(origin).expect("origin is serializable");
```
- Suggested fix: Avoid `expect()` by using `serde_json::to_string(origin).unwrap_or_else(|_| format!("\"{origin}\""))`.
- Confidence: 0.90
