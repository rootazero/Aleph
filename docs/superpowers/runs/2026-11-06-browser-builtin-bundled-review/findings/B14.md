### B14-01 [P0] POSIX `rename` atomically overwrites existing destination in `node_file` pull mode, bypassing `overwrite: false` check
- Location: `src/builtin_tools/node_file.rs:285-313` (`NodeFileTool::call`)
- Failure mode: In `node_file`'s `direction == "pull"` branch when `overwrite == false`, the implementation writes the incoming payload to a temporary file `tmp_path` and then calls `tokio::fs::rename(&tmp_path, &local).await` under the erroneous assumption that POSIX `rename(2)` will fail with `io::ErrorKind::AlreadyExists` if `local` already exists. Under POSIX/Linux semantics, `rename(old, new)` atomically replaces an existing destination file without returning `EEXIST`. As a result, the `rename` succeeds without entering the error handler at line 298, and the existing destination file is silently truncated and overwritten, causing data loss and violating the tool's core contract.
- Evidence:
```rust
if !args.overwrite {
    if let Err(e) = tokio::fs::rename(&tmp_path, &local).await {
        let _ = tokio::fs::remove_file(&tmp_path).await;
        if e.kind() == std::io::ErrorKind::AlreadyExists {
            return Err(AlephError::tool("local target exists (set overwrite)".to_string()));
        }
        return Err(AlephError::tool(format!("rename tmp to local '{}': {e}", local.display())));
    }
}
```
- Suggested fix: When `!args.overwrite`, check if the destination file exists before renaming (e.g. via `tokio::fs::symlink_metadata(&local)`), or use an atomic non-replacing syscall such as `std::fs::hard_link(&tmp_path, &local)` followed by removing `tmp_path`. If `local` exists, immediately return `AlephError::tool("local target exists (set overwrite)")`.
- Confidence: 1.0

### B14-02 [P1] Index out-of-bounds panic in `user_profile::scan_ssn` when profile ends with numeric patterns
- Location: `src/builtin_tools/user_profile.rs:234-266` (`scan_ssn`)
- Failure mode: `scan_ssn` scans `chars` for SSN-like patterns (`DDD-DD-DDDD`). At line 234, it only checks `if start + 2 >= chars.len() { return None; }`. If the input ends with a 3-digit sequence (e.g., `"Account 123"` where `start = 8` and `chars.len() = 11`), `start + 2 == 10 < 11`, so the check passes. Line 244 then unconditionally accesses `chars[start + 3]`, which is `chars[11]`, panicking with index out of bounds. The same flaw occurs at line 255 (`chars[start + 6]` when `chars.len() == start + 6`), and at line 263 (`chars[start + 10]` is accessed when only `start + 9 >= chars.len()` is guarded). Any profile text ending with numbers will crash the runtime task.
- Evidence:
```rust
    if start + 2 >= chars.len() {
        return None;
    }
    if !chars[start].is_ascii_digit()
        || !chars[start + 1].is_ascii_digit()
        || !chars[start + 2].is_ascii_digit()
    {
        return None;
    }
    // Separator.
    if !matches!(chars[start + 3], '-' | ' ') {
        return None;
    }
```
- Suggested fix: At the entry of `scan_ssn`, enforce that `chars` has at least 11 characters starting from `start` before evaluating any offsets: `if start + 11 > chars.len() { return None; }`.
- Confidence: 1.0

### B14-03 [P1] String slice panic on non-padded hex hash in `scratchpad::derive_namespaced_project_id`
- Location: `src/builtin_tools/scratchpad.rs:1074` (`derive_namespaced_project_id`)
- Failure mode: When `slug.chars().all(|c| c == '-')`, the function generates an 8-character disambiguator by hashing `actor` and slicing the formatted hex string with `[..8]`. Because `"{:x}"` formats integers without zero padding, any hash value with leading zeros or whose integer value is `<= 0x0FFF_FFFF` produces a hex string of length <= 7. Slicing with `[..8]` triggers an unhandled `byte index 8 is out of bounds of string of length N` panic.
- Evidence:
```rust
    use std::hash::{Hash, Hasher};
    let mut h = std::collections::hash_map::DefaultHasher::new();
    actor.hash(&mut h);
    format!("{:x}", h.finish())[..8].to_string()
```
- Suggested fix: Format with 16-character zero-padding (`format!("{:016x}", h.finish())[..8].to_string()`), or take up to 8 characters using character iterator (`format!("{:x}", h.finish()).chars().take(8).collect::<String>()`).
- Confidence: 1.0

### B14-04 [P2] `try_read()` lock contention drops `session_id` in async `SessionCompleteTool::current_session_id`
- Location: `src/builtin_tools/session_complete.rs:105-112` (`SessionCompleteTool::current_session_id`)
- Failure mode: In async `call()`, `current_session_id()` uses `h.try_read()` on an `Arc<tokio::sync::RwLock<String>>`. If a writer holds the lock even momentarily during execution, `try_read()` fails and returns `None`. Consequently, `SessionCompleteTool::call` files the task completion event without a `session_id`, bypassing session-bound retrospective memory extraction and severing event correlation.
- Evidence:
```rust
    fn current_session_id(&self) -> Option<String> {
        self.session_id.as_ref().and_then(|h| {
            h.try_read()
                .ok()
                .map(|g| g.clone())
                .filter(|s| !s.is_empty())
        })
    }
```
- Suggested fix: Make `current_session_id` async and await the read lock (`h.read().await`), or fall back to `crate::tools::turn_context::current_session_key()` when the lock handle is absent or empty.
- Confidence: 0.95

### B14-05 [P2] Blocking filesystem calls inside Tokio async loop in `process_journal::spawn_flusher` and `init_and_announce`
- Location: `src/builtin_tools/process_journal.rs:917-943, 1263` (`spawn_flusher`, `init_and_announce`)
- Failure mode: In `spawn_flusher`, a spawned Tokio task loops periodically (every 15 seconds) calling `flush_running_partials`. `flush_running_partials` executes synchronous blocking filesystem calls (`std::fs::create_dir_all`, `std::fs::write`, `std::fs::remove_file`) across all active background jobs directly on the Tokio worker thread. Additionally, async `init_and_announce` calls `init_and_reconcile` and `record_announced`, executing synchronous directory iterations and disk writes directly on the async runtime.
- Evidence:
```rust
    handle.spawn(async move {
        let mut written: HashMap<u64, (u64, u64)> = HashMap::new();
        loop {
            tokio::time::sleep(PARTIAL_FLUSH_INTERVAL).await;
            flush_running_partials(&super::process_registry::process_registry(), &mut written);
        }
    });
```
- Suggested fix: Offload synchronous filesystem operations in `flush_running_partials` and `init_and_reconcile` to `tokio::task::spawn_blocking`, or replace them with `tokio::fs` asynchronous calls.
- Confidence: 0.95
