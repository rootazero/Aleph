### B11-1 [P1] Synchronous blocking `std::fs` calls in async `resolve_output_path` stall Tokio worker thread
- Location: `src/builtin_tools/pdf_generate/mod.rs:207` (`PdfGenerateTool::resolve_output_path`)
- Failure mode: In an asynchronous execution context, `resolve_output_path` calls `std::fs::create_dir_all(&output_dir)` and `output_dir.canonicalize()` synchronously on the Tokio runtime worker thread instead of using `tokio::fs` or `spawn_blocking`. Under slow disk I/O, network filesystems (NFS/CIFS), or filesystem contention, this stalls the entire Tokio worker thread, delaying all concurrent async tasks scheduled on the same worker.
- Evidence:
```rust
        std::fs::create_dir_all(&output_dir).map_err(|e| {
            ToolError::Execution(format!(
                "Failed to create output dir {}: {}",
                output_dir.display(),
                e
            ))
        })?;
        let canonical_output_dir = output_dir
            .canonicalize()
            .unwrap_or_else(|_| output_dir.clone());
```
- Suggested fix: Replace synchronous `std::fs` operations with their non-blocking asynchronous equivalents: `tokio::fs::create_dir_all(&output_dir).await` and `tokio::fs::canonicalize(&output_dir).await`.
- Confidence: 1.0

### B11-2 [P1] CPU-bound synchronous PDF parsing and extraction stalls Tokio executor thread
- Location: `src/builtin_tools/web_fetch/mod.rs:304` (`WebFetchTool::handle_pdf`)
- Failure mode: When `web_fetch` fetches a PDF response up to 20 MB (`MAX_PDF_BYTES`), it directly calls `pdf::extract_pdf(bytes)` inside async `call_impl` on the Tokio worker thread. `pdf::extract_pdf` synchronously parses all PDF objects via `lopdf::Document::load_mem`, decrypts, and extracts text page-by-page. For multi-megabyte PDFs with dozens of pages, this CPU-bound operation blocks the Tokio executor thread for hundreds of milliseconds to multiple seconds, stalling concurrent event handling.
- Evidence:
```rust
        debug!("PDF response detected for {}", args.url);
        let (title, text) = pdf::extract_pdf(bytes).inspect_err(|e| {
            notify_tool_result(Self::NAME, &e.to_string(), false);
        })?;
```
- Suggested fix: Offload `pdf::extract_pdf` to the blocking threadpool using `tokio::task::spawn_blocking(move || pdf::extract_pdf(&bytes_owned))`, matching how `pdf_generate` offloads `native_engine::generate`.
- Confidence: 0.95

### B11-3 [P2] Invalid session kind filter fails open and returns all sessions instead of empty results
- Location: `src/builtin_tools/sessions/list_tool.rs:280` (`SessionsListTool::call`)
- Failure mode: When a caller specifies `args.kinds = Some(vec!["unknown_kind".to_string()])`, `parsed_kinds` is empty. The guard `if !parsed_kinds.is_empty()` evaluates to `false`, causing the tool to skip `rows.retain(...)` completely. Consequently, rather than returning 0 matching sessions as expected when filtering by an unrecognized kind, all accessible sessions are returned as if no filter was requested.
- Evidence:
```rust

            let parsed_kinds: Vec<SessionKind> =
                kinds.iter().filter_map(|s| Self::parse_kind(s)).collect();

            if !parsed_kinds.is_empty() {
                rows.retain(|row| {
                    if let Some(kind) = Self::parse_kind(&row.kind) {
                        parsed_kinds.contains(&kind)
                    } else {
                        false
                    }
                });
            }
        }
```
- Suggested fix: When `args.kinds` is `Some(...)`, run `rows.retain(...)` unconditionally so that if `parsed_kinds` is empty (no valid kinds matched), 0 rows are returned rather than failing open to all rows.
- Confidence: 0.95

### B11-6 [P3] Message length cap measures byte length instead of character count despite `CHARS` naming

- Suggested fix: Either change the condition to `args.message.chars().count() > MAX_CROSS_SESSION_MESSAGE_CHARS`, or rename the constant to `MAX_CROSS_SESSION_MESSAGE_BYTES` and update the error text to report "bytes".

### B11-7 [P3] Redundant parallel enum `ExtractModeKey` violates Occam's Razor
- Location: `src/builtin_tools/web_fetch/cache.rs:43-56` (`ExtractModeKey`)
- Failure mode: `cache.rs` defines a duplicate enum `ExtractModeKey` with variants `Markdown` and `Text`, and implements `From<&ExtractMode> for ExtractModeKey`, solely to be used in the cache key because `ExtractMode` in `types.rs` lacked `Hash, PartialEq, Eq, Copy`. This introduces redundant conceptual duplication and conversion boilerplate.
- Evidence:
```rust
#[derive(Clone, Copy, Debug, Hash, PartialEq, Eq)]
pub(crate) enum ExtractModeKey {
    Markdown,
    Text,
}

impl From<&ExtractMode> for ExtractModeKey {
    fn from(m: &ExtractMode) -> Self {
        match m {
            ExtractMode::Markdown => Self::Markdown,
            ExtractMode::Text => Self::Text,
        }
    }
}
```
- Suggested fix: Derive `Copy, Hash, PartialEq, Eq` directly on `ExtractMode` in `types.rs`, and remove `ExtractModeKey` along with its `From` implementation.
- Confidence: 0.95

### B11-10 [P3] Redundant selector parsing and duplicated `body` rendering in content extraction
- Location: `src/builtin_tools/web_fetch/extract.rs:226-258` (`extract_content`)
- Failure mode: `Selector::parse(...)` is compiled afresh on every call to `extract_content`. Furthermore, `"body"` is included in the priority list `selectors`. If `body` content length is `<= min_content_length`, `render_element` renders `body` once in the loop, rejects it, and then lines 251-256 parse `"body"` again and render it a second time.
- Evidence:
```rust
    let selectors = [
        "article",
        "main",
        ".content",
        ".post-content",
        "#content",
        "body",
    ];

    for selector_str in selectors {
        if let Ok(selector) = Selector::parse(selector_str) {
            if let Some(el) = document.select(&selector).next() {
                let content = render_element(&el, mode, base_url);
                if content.len() > min_content_length {
                    return truncate_content(content, max_content_length);
                }
            }
        }
    }

    // Fallback: return whatever we can get from body
    if let Ok(selector) = Selector::parse("body") {
        if let Some(el) = document.select(&selector).next() {
            return truncate_content(render_element(&el, mode, base_url), max_content_length);
        }
    }
```
- Suggested fix: Use static `Lazy<Selector>` instances for known selectors, and exclude `body` from the priority loop or avoid duplicate rendering in the fallback branch.
- Confidence: 0.90
