### B13-01 [P1] Missing SSRF policy validation on outbound HTTPS image fetch in `CanvasTool`
- Location: `src/builtin_tools/canvas.rs:725-734` (`fetch_https_image`)
- Failure mode: `CanvasTool::call` accepts user/model input for `CanvasAction::InsertImage { location, .. }`. When `location` is an `https://` URL, it invokes `fetch_https_image(url)`. Unlike sister outbound network tools such as `MediaSendTool` and `FetchDocsTool` which enforce `validate_url_with_pinned(&url, &ssrf_policy)`, `fetch_https_image` instantiates an unconstrained `reqwest::Client` with no SSRF check. An LLM or malicious user prompt can point `location` to internal intranet services, cloud metadata endpoints (`https://169.254.169.254`), or loopback listeners (`https://127.0.0.1:8443`), allowing internal port probing and asset exfiltration behind the firewall.
- Evidence:
```rust
async fn fetch_https_image(url: &str) -> Result<(String, Vec<u8>)> {
    let client = reqwest::Client::builder()
        .timeout(HTTP_FETCH_TIMEOUT)
        .build()
        .map_err(|e| AlephError::tool(format!("insert_image: http client: {e}")))?;
    let response = client
        .get(url)
        .send()
        .await
        .map_err(|e| AlephError::tool(format!("insert_image: fetch failed: {e}")))?;
```
- Suggested fix: Accept `ssrf_policy: &SsrfPolicy` (injected via `CanvasTool::new` / `with_ssrf_policy`) and validate outbound URLs using `crate::security::ssrf::validate_url_with_pinned(url, ssrf_policy).await` before executing the HTTP request.
- Confidence: 0.95

### B13-02 [P1] Blocking synchronous file I/O on Tokio async worker thread in `bash_exec.rs`
- Location: `src/builtin_tools/bash_exec.rs:665, 807, 852-855` (`handle_process_action` -> `resolve_forgotten`)
- Failure mode: `handle_process_action` is an `async fn` executing directly on the Tokio async worker thread. When `action` is `"list"`, or when `action` is `"poll"`, `"wait"`, or `"kill"` and the target job is not found in the live in-memory registry, `handle_process_action` invokes `resolve_forgotten(target, caller, live)`. `resolve_forgotten` delegates to `process_journal::list_for_scope` and `process_journal::lookup`, which iterate over disk records and call `hydrate(&dir, record)`. `hydrate` executes `std::fs::read_to_string` synchronously across all job trail and partial capture files. When many background bash jobs exist or disk I/O is slow, this stalls the Tokio worker thread, creating tail latency spikes and task starvation for concurrent gateway requests.
- Evidence:
```rust
// bash_exec.rs:665
let recovered = resolve_forgotten(None, caller.as_deref(), &live);

// process_journal.rs:1696
let Ok(raw) = std::fs::read_to_string(&path) else {
    return Trail::default();
};
```
- Suggested fix: Offload `resolve_forgotten` or the hydration loop to `tokio::task::spawn_blocking`, or refactor `process_journal` reading functions to use `tokio::fs::read_to_string`.
- Confidence: 0.95

### B13-04 [P2] Blocking synchronous `std::fs::canonicalize` on async worker thread in `canvas.rs`
- Location: `src/builtin_tools/canvas.rs:690, 694` (`read_local_image`)
- Failure mode: `read_local_image` is an `async fn`. While it properly uses `tokio::fs::canonicalize(location).await` for the input image location, it performs synchronous `std::fs::canonicalize(&data_dir)` and `std::fs::canonicalize(std::env::temp_dir())` on every local image read. On systems with network mounts, encrypted volumes, or deep symlink chains, these synchronous filesystem calls block the active Tokio thread.
- Evidence:
```rust
let canonical = tokio::fs::canonicalize(location)
    .await
    .map_err(|e| AlephError::tool(format!("insert_image: cannot read {location:?}: {e}")))?;
let mut roots: Vec<std::path::PathBuf> = Vec::new();
if let Ok(data_dir) = crate::utils::paths::get_data_dir() {
    if let Ok(root) = std::fs::canonicalize(&data_dir) {
        roots.push(root);
    }
}
if let Ok(root) = std::fs::canonicalize(std::env::temp_dir()) {
    roots.push(root);
}
```
- Suggested fix: Use `tokio::fs::canonicalize(&data_dir).await` and `tokio::fs::canonicalize(std::env::temp_dir()).await` or cache the canonical roots once at startup.
- Confidence: 0.90

### B13-05 [P2] Case sensitivity and RFC mismatch in `canvas.rs::decode_data_url`
- Location: `src/builtin_tools/canvas.rs:646-651` (`decode_data_url`)
- Failure mode: In `decode_data_url`, `header.strip_suffix(";base64")` checks for an exact lowercase `";base64"` suffix without normalizing the header case first or handling whitespace. If a model generates `data:image/png;BASE64,...`, `data:image/png;Base64,...`, or `data:image/png; base64,...`, or includes MIME parameters (`data:image/svg+xml;charset=utf-8;base64,...`), `strip_suffix` returns `None` and the tool erroneously rejects valid base64 data URLs with `"insert_image: only base64 data: URLs are supported"`.
- Evidence:
```rust
let Some(mime) = header.strip_suffix(";base64") else {
    return Err(AlephError::tool(
        "insert_image: only base64 data: URLs are supported (`data:<mime>;base64,…`)"
            .to_string(),
    ));
};
let mime = mime.trim().to_ascii_lowercase();
```
- Suggested fix: Trim and lowercase header prior to checking for `;base64`, or split header by `;` and check whether any segment trimmed and lowercased equals `"base64"`, extracting the first segment as MIME.
- Confidence: 0.95

### B13-06 [P2] Wire name deserialization mismatch in `ReadConfigGuideTool`
- Location: `src/builtin_tools/config_guide.rs:155` (`ReadConfigGuideTool::call`)
- Failure mode: `ReadConfigGuideTool::call` derives `topic_name` via `format!("{:?}", args.topic).to_lowercase()`. For enum variant `GuideTopic::MultiChannel`, debug formatting produces `"MultiChannel"`, and `to_lowercase()` produces `"multichannel"` without the underscore. However, the official wire ID and serde serialization defined by `GuideTopic::id()` is `"multi_channel"`. Consequently, start and result notifications (`notify_tool_start`, `notify_tool_result`), error messages (`"Guide 'multichannel' not found"`), and the returned `ReadConfigGuideOutput.topic` emit `"multichannel"`, causing a contract mismatch with the schema and the input argument.
- Evidence:
```rust
// config_guide.rs:155
let topic_name = format!("{:?}", args.topic).to_lowercase();
notify_tool_start(Self::NAME, &topic_name);

// config_guide.rs:74
Self::MultiChannel => "multi_channel",
```
- Suggested fix: Replace `format!("{:?}", args.topic).to_lowercase()` with `args.topic.id().to_string()`.
- Confidence: 1.0
