### B5-01 [P1] Broken directory replacement in `extract_dir_contents` due to impossible `ErrorKind::AlreadyExists`
- Location: `src/bundled/extractor.rs:621` (`extract_dir_contents`)
- Failure mode: When updating bundled skills where a previously created directory must be replaced by a file (or if a directory exists at `dest`), `std::fs::rename(&tmp, &dest)` fails with `ErrorKind::IsADirectory` (`EISDIR`) on POSIX or `ErrorKind::PermissionDenied` (`ERROR_ACCESS_DENIED`) on Windows. Neither operating system returns `ErrorKind::AlreadyExists`. The guard `Err(e) if e.kind() == std::io::ErrorKind::AlreadyExists` never matches, falling through to `Err(e) => return cleanup_tmp(e)`. The file extraction fails, the blocking directory is never removed, and the skill remains permanently marked as failed (`version: None`).
- Evidence:
  ```rust
  match std::fs::rename(&tmp, &dest) {
      Ok(()) => {}
      Err(e) if e.kind() == std::io::ErrorKind::AlreadyExists => {
          let remove_result = match std::fs::symlink_metadata(&dest) {
  ```
- Suggested fix: Check whether `dest` is a directory (via `dest.is_dir()` or `std::fs::symlink_metadata(&dest)`) upon rename failure, rather than matching exclusively on `ErrorKind::AlreadyExists`. If it is a directory, remove it via `std::fs::remove_dir_all(&dest)` and retry the rename.
- Confidence: 1.0

### B5-02 [P1] `swap_dir_into_place` fails unconditionally on Windows when target directory exists
- Location: `src/bundled/extractor.rs:462` (`swap_dir_into_place`)
- Failure mode: On Windows, `std::fs::rename(staged, dest)` between two directories calls `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`. Win32 API does not support replacing directories with `MOVEFILE_REPLACE_EXISTING` and returns `ERROR_ACCESS_DENIED`, which maps to `std::io::ErrorKind::PermissionDenied`. `swap_dir_into_place` checks only `matches!(e.kind(), ErrorKind::AlreadyExists | ErrorKind::DirectoryNotEmpty)`. On Windows, this evaluates to false, so `swap_dir_into_place` logs a failure and returns `false` without ever attempting `remove_dir_all(dest)`. Because `plugins_cache` is created on startup before extraction, plugin cache swaps on Windows fail on every run after initialization, preventing `manifest.bundled_version` from advancing and triggering repeated failed extractions on every startup.
- Evidence:
  ```rust
  if let Err(e) = std::fs::rename(staged, dest) {
      let dest_exists = matches!(
          e.kind(),
          std::io::ErrorKind::AlreadyExists | std::io::ErrorKind::DirectoryNotEmpty
      );
  ```
- Suggested fix: Test whether the destination exists using `dest.exists()` upon rename error (or include `ErrorKind::PermissionDenied` when `dest.exists()`), allowing the `remove_dir_all(dest)` and rename retry logic to execute on Windows.
- Confidence: 1.0

### B5-04 [P2] Missing `+` in fetch refspec rejects upstream rebases and force pushes
- Location: `src/bundled/sync.rs:117` (`update_existing_repo`)
- Failure mode: `update_existing_repo` executes `remote.fetch(&["refs/heads/main:refs/remotes/origin/main"], None, None)`. Unlike `checkout_pinned` (which uses `+refs/heads/*:...`), this refspec omits the leading `+` force flag. If upstream (`Aleph-skills` or `Aleph-plugins`) ever rebases or force-pushes `main`, libgit2 rejects the fetch as a non-fast-forward update. The sync fails, causing startup bootstrap and explicit sync to fail permanently until the local cache directory is manually deleted.
- Evidence:
  ```rust
  remote.fetch(&["refs/heads/main:refs/remotes/origin/main"], None, None)?;
  ```
- Suggested fix: Add `+` to the refspec: `remote.fetch(&["+refs/heads/main:refs/remotes/origin/main"], None, None)?;`, matching the hard-reset contract described in the function documentation.
- Confidence: 0.95

### B5-05 [P2] Fixed temp directory path in plugin extraction creates TOCTOU and concurrent deletion race
- Location: `src/bundled/extractor.rs:364, 395` (`extract_plugins`, `extract_plugins_from_dir`)
- Failure mode: Both `extract_plugins` and `extract_plugins_from_dir` use a fixed temp path `cache_dir.with_extension("tmp")` (`~/.aleph/plugins/cache/aleph-official.tmp`). If two sync operations run concurrently (e.g. concurrent gateway RPC requests or an RPC racing startup extraction), thread A prepares the directory and begins copying, while thread B invokes `prepare_plugin_temp_dir(&tmp_dir)` which calls `std::fs::remove_dir_all(tmp_dir)`, deleting thread A's directory mid-copy and causing thread A to fail with an I/O error. In addition, a static predictable path in a shared cache directory reopens symlink-planting windows that `manifest.rs:unique_tmp_path` and `extractor.rs:EXTRACT_TEMP_COUNTER` were specifically added to prevent.
- Evidence:
  ```rust
  fn extract_plugins(bundled: &Dir, cache_dir: &Path) -> bool {
      let tmp_dir = cache_dir.with_extension("tmp");
  ```
  and
  ```rust
  fn extract_plugins_from_dir(src_root: &Path, cache_dir: &Path) -> bool {
      let tmp_dir = cache_dir.with_extension("tmp");
  ```
- Suggested fix: Use unique process-and-counter-tagged temp paths (e.g. via `unique_tmp_path`) or `tempfile::Builder` inside the parent directory for staging plugin extraction before atomic directory swap.
- Confidence: 0.90

### B5-06 [P2] `copy_dir_into` fails when directory replaces file or file replaces directory in skills sync

### B5-07 [P2] File descriptor held open across `std::fs::rename` in `manifest.rs:save` and `restore_manifest`

- Failure mode: `f` is opened via `OpenOptions` and written to via `f.write_all()`, but is not dropped before calling `std::fs::rename(&tmp_path, &path)`.       return cleanup_tmp(e);
  ```rust
  }
  match std::fs::rename(&tmp_path, &path) {
  ```
- Suggested fix: Explicitly `drop(f);` immediately after `f.write_all(content.as_bytes())` before calling `std::fs::rename`.
- Confidence: 0.90

### B5-08 [P3] Dead fallback logic in `manifest.rs:save` due to impossible `ErrorKind::AlreadyExists` on file rename
- Location: `src/bundled/manifest.rs:114-137`, `271-289` (`InstallRegistry::save`, `restore_manifest`)
- Failure mode: In `InstallRegistry::save`, lines 114–137 implement a 24-line fallback intended for Windows under `Err(e) if e.kind() == std::io::ErrorKind::AlreadyExists`. However, Rust's standard library `std::fs::rename` invokes `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`, which replaces existing destination files atomically and never returns `ERROR_ALREADY_EXISTS`. POSIX `rename(2)` also replaces files atomically and returns `Ok(())`. Consequently, the `AlreadyExists` arm is unreachable on all supported operating systems, making the entire fallback block and the private `restore_manifest` helper dead code that only executes in unit tests.
- Evidence:
  ```rust
  match std::fs::rename(&tmp_path, &path) {
      Ok(()) => {}
      // BUNDLED-R4-07: Windows' rename refuses on an existing target.
      // POSIX rename replaces atomically, so the retry never fires there.
      Err(e) if e.kind() == std::io::ErrorKind::AlreadyExists => {
  ```
- Suggested fix: Remove the dead `AlreadyExists` branch and the uncalled `restore_manifest` helper; rely on atomic file replacement via `std::fs::rename`.
- Confidence: 0.95
