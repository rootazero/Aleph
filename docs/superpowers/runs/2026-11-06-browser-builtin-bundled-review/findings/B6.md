### B6-01 [P1] `classify_network_failure` fails to match benign assets with query strings or fragments
- Location: `src/builtin_tools/browser_tools/qa_verdict.rs:136` (`classify_network_failure`)
- Failure mode: `BENIGN_RULES` uses `MatchKind::Suffix` for `.map`, `favicon.ico`, and `apple-touch-icon.png`. `classify_network_failure` tests `haystack.ends_with(rule.pattern)` directly on the raw lowercased URL. In modern web applications, assets frequently carry cache-busting query strings or URL fragments (e.g., `favicon.ico?v=2` or `vendor.js.map?v=4.2.1`). For such URLs, `ends_with` returns `false`, causing the failure to be classified as `Impact::Actionable`. In `qa.rs:476-497`, this emits a hard `CheckOutcome::Fail`, causing `browser_qa` to fail validation on healthy web pages due to harmless missing favicons or sourcemaps.
- Evidence:
  ```rust
  pub fn classify_network_failure(url: &str, resource_hint: &str) -> Impact {
      let haystack = url.to_lowercase();
      let hint = resource_hint.to_lowercase();
      for rule in BENIGN_RULES {
          let hit = match rule.kind {
              MatchKind::Contains => haystack.contains(rule.pattern) || hint.contains(rule.pattern),
              MatchKind::Suffix => haystack.ends_with(rule.pattern),
          };
  ```
- Suggested fix: Strip query strings (`?`) and hash fragments (`#`) before evaluating suffix matches (e.g., `let path = haystack.split(['?', '#']).next().unwrap_or(&haystack); path.ends_with(rule.pattern)`).
- Confidence: 1.0

### B6-02 [P1] `bound_screenshot_png` performs synchronous image resizes and PNG re-encodings on the async executor thread
- Location: `src/builtin_tools/browser_tools/mod.rs:756-807` (`bound_screenshot_png`), called from `screenshot.rs:145` and `exec.rs:1444`
- Failure mode: When a screenshot exceeds `MAX_SCREENSHOT_BYTES` (e.g., full-page captures or dense graphics), `bound_screenshot_png` executes an initial resize plus up to 4 successive iterative resizes and PNG re-encodings (CPU-intensive Deflate compression) directly on the current Tokio worker thread without `tokio::task::spawn_blocking`. Heavy PNG encoding on images up to 1568x1568 blocks the Tokio async worker thread for hundreds of milliseconds, stalling concurrent futures and event processing across the runtime.
- Evidence:
  ```rust
  const SCALE_LADDER: [f64; 4] = [0.7, 0.5, 0.35, 0.25];
  for scale in SCALE_LADDER {
      let w = (f64::from(fitted.width()) * scale).round().max(1.0) as u32;
      let h = (f64::from(fitted.height()) * scale).round().max(1.0) as u32;
      let shrunk = fitted.resize_exact(w, h, image::imageops::FilterType::Triangle);
      let mut attempt = Vec::new();
      if shrunk.write_to(&mut std::io::Cursor::new(&mut attempt), image::ImageFormat::Png).is_err() { break; }
  ```
- Suggested fix: Offload `bound_screenshot_png` to `tokio::task::spawn_blocking` at caller sites in `screenshot.rs` and `exec.rs` (or inside `bound_screenshot_png` when invoked in async context).
- Confidence: 0.95

### B6-03 [P2] `bound_content_head_tail` inverts tail offset and leaks full text when `max_chars == 0`
- Location: `src/builtin_tools/browser_tools/mod.rs:500` (`bound_content_head_tail`)
- Failure mode: When `max_chars == 0` on non-empty text, `head_budget = 0`, `tail_budget = 0`, and `skip = total_chars`. Because `skip == total_chars`, `text.char_indices().nth(skip)` returns `None`. The fallback `.map_or(0, |(i, _)| i)` evaluates to `0` instead of `text.len()`. `byte_start` becomes `0`, and `text[0..].find('\n')` finds the first newline in the document, emitting virtually the entire document as `tail` instead of an empty bounded slice.
- Evidence:
  ```rust
  let skip = total_chars - tail_budget;
  let byte_start = text.char_indices().nth(skip).map_or(0, |(i, _)| i);
  let tail = match text[byte_start..].find('\n') {
      Some(nl) => &text[byte_start + nl + 1..],
      None => &text[byte_start..],
  };
  ```
- Suggested fix: Add an early return `if max_chars == 0 { return (String::new(), !text.is_empty()); }` or change the fallback to `.map_or(text.len(), |(i, _)| i)`.
- Confidence: 0.95

### B6-04 [P2] `browser_network` `mock_clear` and `mock_remove` fail-dead when tab is on an SSRF-blocked origin (Shape 14)
- Location: `src/builtin_tools/browser_tools/network.rs:303` (`BrowserNetworkTool::call`)
- Failure mode: `BrowserNetworkTool::call` invokes `make_backend_and_tab_guarded` unconditionally for all `NetworkAction` variants, including `MockClear`, `MockRemove`, and `MockList`. If a tab navigated to an internal or redirect-blocked URL, `make_backend_and_tab_guarded` fails with `NavigationFailed`. Consequently, the agent cannot clear, remove, or list mock routes (even profile-wide ones), leaving interception active with no off-switch. This violates Shape 14: "闸的两个方向都要问" (fail-dead control when clean-up cannot proceed).
- Evidence:
  ```rust
  let (backend, tab_id) =
      match super::make_backend_and_tab_guarded(&self.manager, &args.profile).await {
          Ok(pair) => pair,
          Err(e) => {
              return Ok(BrowserNetworkOutput::failed(super::backend_error_text(
                  &self.manager,
                  &e,
              )));
          }
      };
  ```
- Suggested fix: Mirror the pattern in `record.rs:249-256`: use `make_backend_and_tab` (unguarded) for mutating cleanup actions (`MockClear`, `MockRemove`, `MockList`), and reserve `make_backend_and_tab_guarded` for reading content (`Log`) or creating new interception routes (`MockAdd`).
- Confidence: 0.95

### B6-05 [P2] Evidence screenshot path TOCTOU race in `save_evidence_png` via non-atomic `uniquify`
- Location: `src/builtin_tools/browser_tools/qa.rs:588` (`save_evidence_png`)
- Failure mode: `save_evidence_png` uses `uniquify()`, which checks `!path.exists()` in a loop. Between this check and `tokio::fs::write(&path, png)` (which opens with standard write/truncate mode rather than `create_new(true)`), a concurrent task or process can claim the same file name, overwriting evidence and violating the stated guarantee ("Never overwrites an existing file — a second run inside the same UTC second moves aside (`uniquify`)"). In addition, `path.exists()` performs synchronous filesystem metadata calls directly on the async runtime.
- Evidence:
  ```rust
  let path = crate::browser::cdp_backend::recording::uniquify(evidence_path(profile, tab_id));
  if let Some(parent) = path.parent() {
      tokio::fs::create_dir_all(parent)
          .await
          .map_err(|e| format!("could not create {}: {e}", parent.display()))?;
  }
  tokio::fs::write(&path, png)
  ```
- Suggested fix: Use atomic file creation (`tokio::fs::OpenOptions::new().write(true).create_new(true)`) in a retry loop or use `tempfile::Builder` in the destination directory before atomically persisting.
- Confidence: 0.90

### B6-07 [P3] `ExecAction::Repeat` permits `max_iterations: 0` which falsely reports loop failure without condition evaluation
- Location: `src/builtin_tools/browser_tools/exec.rs:543` (`plan_action`)
- Failure mode: `plan_action` checks `*max_iterations > MAX_REPEAT_ITERATIONS`, but does not guard against `max_iterations == 0`. When passed 0, `for _ in 0..*max_iterations` executes 0 iterations without ever calling `eval_condition_once`. The loop concludes with `held == false`, emitting the summary `"0 iteration(s) run; the until-condition never held (the cap of 0 was reached)"` even if the condition currently holds on the page.
- Evidence:
  ```rust
  if *max_iterations > MAX_REPEAT_ITERATIONS {
      return Err(format!(
          "repeat is capped at {MAX_REPEAT_ITERATIONS} iterations (got \
           {max_iterations}); a procedure that needs more is several browser_exec \
           calls"
      ));
  }
  ```
- Suggested fix: Enforce `1..=MAX_REPEAT_ITERATIONS` in `plan_action`: `if *max_iterations == 0 || *max_iterations > MAX_REPEAT_ITERATIONS`.
- Confidence: 0.95

### B6-08 [P3] Unbounded `Weak<CompanionManager>` leak in `MANAGERS` global registry
- Location: `src/builtin_tools/browser_tools/companion/manager.rs:554-558` (`CompanionManager::new_with_deps`)
- Failure mode: Every new `CompanionManager` instance pushes `Arc::downgrade(&manager)` into `MANAGERS` without ever retaining or purging dead `Weak` pointers. Neither `new_with_deps` nor `shutdown_all_companions` removes dead entries. Over time in long-running processes or unit tests, the vector accumulates dead `Weak` allocations.
- Evidence:
  ```rust
  MANAGERS
      .get_or_init(|| StdMutex::new(Vec::new()))
      .lock()
      .unwrap_or_else(|e| e.into_inner())
      .push(Arc::downgrade(&manager));
  ```
- Suggested fix: Retain live pointers on push: `managers.retain(|w| w.strong_count() > 0)`.
- Confidence: 0.90
