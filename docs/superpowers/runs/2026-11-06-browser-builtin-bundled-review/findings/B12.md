### B12-01 [P1] Severed wire: `VoiceModeSetTool::call` passes `None` instead of `current_channel` to `execute`, breaking default-to-current-channel voice toggling
- Location: `src/builtin_tools/voice_tools/voice_mode_set.rs:180` (`VoiceModeSetTool::call`)
- Failure mode: When an agent or user invokes `voice_mode_set(enabled=true)` without specifying `channel_id` (the canonical usage documented by `VoiceModeSetArgs::channel_id` as "Defaults to the current channel"), `call()` reads `current_turn_context().channel_id`, but completely discards it and passes `None` to `self.execute(args, None).await`. Inside `execute`, `args.channel_id` is `None` and `current_channel_id` is `None`, so `execute` unconditionally fails closed with `success: false` and the error message: `"voice_mode_set requires a target channel id; pass channel_id in the args or call from the channel whose voice setting you want to change."` Consequently, voice mode cannot be toggled from any chat channel without manually and redundantly spelling out the channel ID.
- Evidence:
```rust

    .map(|t| t.channel_id.clone())
    .unwrap_or_default();
if let Some(target) = args.channel_id.as_deref() {
    if !current_channel.is_empty() && target != current_channel {
        return Err(crate::error::AlephError::tool(format!(
            "voice_mode_set: channel_id '{target}' does not match the \
             caller's current channel; refusing to toggle voice mode on a \
             foreign channel"
        )));
    }
}
Ok(self.execute(args, None).await)
```
- Suggested fix: Pass `current_channel` into `execute`:
```rust

```

### B12-02 [P1] Blocking synchronous file I/O inside async functions stalls Tokio executor threads in `ReadSkillTool` and `ListSkillsTool`
- Location: `src/builtin_tools/skill_reader/read.rs:321, 364-390, 418, 456-458` (`ReadSkillTool::call_impl`), `src/builtin_tools/skill_reader/list.rs:192, 206` (`ListSkillsTool::call_impl`)
- Failure mode: `ReadSkillTool::call_impl` and `ListSkillsTool::call_impl` are `async fn` entry points running directly on the Tokio async worker thread (with `.await` yield points such as markdown inline shell preprocessing). Both methods execute numerous synchronous filesystem operations on the worker thread: `fs::canonicalize`, recursive `std::fs::read_dir` (walking up to depth 16), synchronous reading of up to 5MB files via `fs::read_to_string(&file_path)`, scanning and reading all `SKILL.md` files across sibling directories, and synchronous JSON writes in `record_use_in_dir`. Under high concurrency or on slow/network filesystems, these synchronous I/O bursts stall the Tokio runtime thread, inducing task starvation and latency spikes for concurrent gateway connections.
- Evidence:
```rust
// read.rs:389-390
let raw_content = fs::read_to_string(&file_path)
    .map_err(|e| ToolError::Execution(format!("Failed to read file: {e}")))?;
```
```rust
// list.rs:140
let content = fs::read_to_string(&skill_md).ok()?;
```
- Suggested fix: Offload directory scanning, path canonicalization, and file read/write operations to `tokio::task::spawn_blocking`, or replace `std::fs` calls with non-blocking `tokio::fs` alternatives.
- Confidence: 0.95

### B12-03 [P2] `slug_from_skill_md` performs unanchored line prefix matching without YAML frontmatter boundary checks
- Location: `src/builtin_tools/skill_reader/read.rs:498-511` (`slug_from_skill_md`)
- Failure mode: `slug_from_skill_md` iterates through all lines of `SKILL.md` searching for the first line starting with `name:`. It does not verify whether the line is situated between the YAML frontmatter delimiters (`---`). If a skill omits the `name:` field from its frontmatter, or if markdown body text or fenced code blocks contain `name: <something>`, `slug_from_skill_md` erroneously extracts that arbitrary body line as the skill slug. This leads to invalid skill resolution or incorrect directory matches when resolving skills by slug.
- Evidence:
```rust
let body = std::fs::read_to_string(skill_dir.join("SKILL.md")).ok()?;
for line in body.lines() {
    let trimmed = line.trim();
    if let Some(rest) = trimmed.strip_prefix("name:") {
        let name = rest.trim().trim_matches(['"', '\'']).trim();
        if name.is_empty() {
            return None;
        }
        return Some(name.to_lowercase().replace(' ', "-"));
    }
}
None
```
- Suggested fix: Track frontmatter delimiters (`---`) and only parse `name:` when inside the frontmatter block, or reuse `crate::skill::parse_skill_content` directly as `ListSkillsTool` does.
- Confidence: 0.95

### B12-05 [P2] URL extension extraction uses `rsplit('.').next()` which matches entire path segment when no dot exists
- Location: `src/builtin_tools/media_tools/understand.rs:170-175` (`MediaUnderstandTool::call`)
- Failure mode: In `MediaUnderstandTool::call`, file extension extraction from a media URL uses `name.rsplit('.').next()`. In Rust, `str::rsplit` yields the entire string when the separator is not found. If the URL's final path component has no dot (e.g. `https://example.com/api/doc` or `https://example.com/audio/wav`), `rsplit('.').next()` returns the entire segment (`"doc"` or `"wav"`). When the segment happens to match a recognized extension name (`doc`, `wav`, `mp3`, `png`), it falsely diagnoses the path segment as an extension; otherwise, it triggers spurious extension lookups.
- Evidence:
```rust
let ext_str = args.format_hint.as_deref().or_else(|| {
    url.rsplit('/')
        .next()
        .map(|name| name.split(['?', '#']).next().unwrap_or(name))
        .and_then(|name| name.rsplit('.').next())
        .filter(|ext| !ext.is_empty() && ext.len() < 10)
});
```
- Suggested fix: Use `rsplit_once('.')` instead:
```rust
.and_then(|name| name.rsplit_once('.').map(|(_, ext)| ext))
```
- Confidence: 0.90

### B12-06 [P2] MIME content-type matching in `SpeechGenerateTool` drops audio format when content-type has parameters
- Location: `src/builtin_tools/generation/speech_generate.rs:260-267` (`SpeechGenerateTool::call_impl`)
- Failure mode: When resolving the audio format from the provider output's `content_type`, `ct.as_str()` is matched against exact strings such as `"audio/wav"` or `"audio/mpeg"`. If the upstream provider returns standard HTTP content-type parameters (such as `"audio/wav; codecs=1"` or `"audio/mpeg; charset=utf-8"`), exact matching fails and execution falls through to `_ => "mp3"`. A WAV or FLAC response with MIME parameters is consequently mislabeled as MP3 in both the output payload and subsequent media delivery.
- Evidence:
```rust
match ct.as_str() {
    "audio/mpeg" => "mp3",
    "audio/opus" => "opus",
    "audio/aac" => "aac",
    "audio/flac" => "flac",
    "audio/wav" => "wav",
    _ => "mp3",
}
```
- Suggested fix: Strip parameters before matching:
```rust
let mime = ct.split(';').next().unwrap_or(ct).trim();
match mime {
    "audio/mpeg" => "mp3",
    "audio/opus" => "opus",
    "audio/aac" => "aac",
    "audio/flac" => "flac",
    "audio/wav" => "wav",
    _ => "mp3",
}
```
- Confidence: 0.95

### B12-09 [P3] Dead match branch in config value scalar parsing in `HubInstallRunTool::proceed`
- Location: `src/builtin_tools/hub/install_run.rs:244-247` (`HubInstallRunTool::proceed`)
- Failure mode: In `HubInstallRunTool::proceed`, `raw` is matched against `Value::Null`, `Value::Array`, and `Value::Object`. The remaining variants of `serde_json::Value` are only `String`, `Number`, and `Bool`. Helper `value_to_string` returns `Some(String)` for all three remaining variants. As a result, `value_to_string(raw)` can never return `None`, making `None => continue` unreachable dead code.
- Evidence:
```rust
_ => match value_to_string(raw) {
    Some(v) => v,
    None => continue,
},
```
- Suggested fix: Directly match scalar variants and inline string extraction:
```rust
Value::String(s) => s.clone(),
Value::Number(n) => n.to_string(),
Value::Bool(b) => b.to_string(),
```
- Confidence: 0.95
