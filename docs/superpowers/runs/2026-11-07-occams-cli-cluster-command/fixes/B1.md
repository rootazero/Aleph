## F1 — B1-P1-1: the authority that is actually called is validated before the token is read

- **`src/cli/ipc_client.rs:84`** — new route guard. The admin route must be an **absolute path**
  (`/v1/admin/...`): it must start with `/`, must not start with `//` (an RFC 3986 *authority*
  reference, which `Url::join` resolves by **replacing** the base host) and must not start with
  `/\` (`\` is the same separator as `/` for the special schemes `http`/`https`, so `/\host` is an
  authority reference too). A relative reference (`v1/admin/secrets`) is refused as well — it would
  resolve against the base path and address a different route.
- **`src/cli/ipc_client.rs:102-104`** — the **joined** URL's host is read
  (`joined.host_str()`), not the base's.
- **`src/cli/ipc_client.rs:105-111`** — the joined scheme must be `http`/`https` **and equal to the
  endpoint's own scheme**; anything else is refused.
- **`src/cli/ipc_client.rs:112-121`** — the joined authority must be **exactly** the validated
  loopback endpoint (same host, same effective port, and loopback per the module's existing
  `is_loopback_host` predicate — no second predicate was invented).
- Ordering: both the route guard and the joined-URL validation run **before** `read_token(data_dir)`
  (`ipc_client.rs:129`), so the bearer token is never read out of `security.db` for a route that
  would carry it off-box.
- **`src/cli/ipc_client.rs:543-575`** — new unit test
  `forward_to_server_refuses_a_route_that_carries_an_authority`, covering
  `//attacker.example/v1/admin/secrets`, `/\attacker.example/v1/admin/secrets` and the relative
  `v1/admin/secrets`. The endpoint in the test is `http://127.0.0.1:18790` (loopback, so the
  pre-existing host guard passes) and no `security.db` exists in the temp dir — a request attempt
  would fail with a different error, so the assertion is specifically about the refusal.

**Deviation (must be reviewed):** the instruction said the joined scheme "must be http". The check
is **`http` or `https`, and equal to the endpoint's own scheme** instead of a literal "http only":
the daemon supports a loopback-TLS deployment (`build_endpoint_url` publishes `https://` when TLS is
enabled, and `build_client` explicitly supports a self-signed cert on loopback), so a literal
http-only rule would break the supported TLS mode. The security property the instruction wanted —
the joined URL cannot change scheme, host or port away from the validated endpoint — is preserved.

**Pre-existing check kept unchanged:** the base URL's own loopback guard (`ipc_client.rs:53-63`)
and the "bare `scheme://host:port`" path-prefix guard (`ipc_client.rs:64-76`) are untouched; the new
checks are additive.

## F2 — B1-P1-2: the admin client no longer honours proxy environment variables

- **`src/cli/ipc_client.rs:311`** — `builder = builder.no_proxy();` in `build_client`.
  `reqwest` is built with the `system-proxy` feature (`Cargo.toml:216`), so `HTTP_PROXY` /
  `ALL_PROXY` in the operator's environment would otherwise capture the request: the admin bearer
  token (`Authorization: Bearer …`) and the request body would be handed to a proxy in cleartext.
  The admin IPC channel is loopback-only, so a proxy is never legitimate here.
  In-tree precedent: `src/security/ssrf/fetch.rs:396`,
  `src/builtin_tools/browser_tools/companion/protocol.rs:402`.

## F3 — B1-P2-4: the stale-holder message no longer claims the PID is not running

Producer: `src/utils/instance_lock.rs:250-255` — `classify_lock_failure` folds **two** distinct
situations into `AcquireOutcome::HeldByOrphaned`: the recorded PID is **gone**, or the recorded PID
is **alive but is a different process** (the PID was recycled; `process_matches` compares the
recorded start time with the live one).

- **`src/cli/policy.rs:30-33`** — `LockHolder::StaleRecord`'s doc now says "not running, **or one
  that no longer matches the recorded process identity (the PID was recycled)**".
- **`src/cli/policy.rs:41-48`** — the comment above the `Display` match explains why the arm prints
  the PID for forensics yet states it is **not** the process that wrote the record.
- **`src/cli/policy.rs:51-56`** — the message is now
  `server is running but its holder record is stale (names PID {pid}, which is not the process that
  wrote the record — it may have exited, or its start time no longer matches; do not signal it)`.
  The common suffix (`. This command requires exclusive access — run \`aleph-server stop\` first. Do
  not remove the lock file while it is held. Lock: {path}`) is unchanged.
- **`src/cli/policy.rs:313`** — the existing test
  `lock_held_error_display_for_stale_record` gained `assert!(!msg.contains("which is not running"))`.

**Adjudication — why no new error variant:** the two producer cases are *indistinguishable at the
consumer*. `instance_lock` hands the CLI only `AcquireOutcome::HeldByOrphaned { pid }`; the CLI
never learns whether the PID is gone or recycled, so it cannot word the two cases differently
without inventing state it does not have. A single honest message that covers both ("it may have
exited, or its start time no longer matches; do not signal it") is therefore the correct shape —
**no new variant, no new enum case, no public API change.** The wording keeps the two facts the
old message got right (the lock IS held, the recorded PID is NOT the writer's process) and drops the
one fact it got wrong.

**Wire contract preserved:** the message still starts with `server is running`, still contains
`stale` and the recorded `PID <n>`, still does not contain `orphaned`, and still carries the
"Do not remove the lock file" advice. `scripts/spec_c_regression.sh` (`spec_c_cli_refuse`) greps
`server is running` on stderr — unchanged.

## F4 — B1-P2-5: a failed permission re-assert no longer destroys a valid endpoint

- **`src/cli/endpoint.rs:91-98`** — comment: `write_atomic` creates the replacement file with mode
  `0600` on Unix (`src/utils/atomic_io.rs:49-58`, `tempfile::Builder … open_fresh` with
  `options.mode(0o600)` at line 55) and renames it over the target, so the published endpoint is
  owner-only without a second chmod; the chmod is kept only as an explicit re-assertion of that
  mode.
- **`src/cli/endpoint.rs:104-110`** — on `set_permissions` failure the file is **kept**: the write
  already succeeded and the file on disk is already `0600`, so the old behaviour (delete the file
  and return `Err`) left a **running server with no IPC endpoint at all** — the only production
  caller (`src/bin/aleph-server/commands/start/mod.rs:3944`) only logs a warning on error, so the
  failure was silent and the CLI could no longer reach the server. The failure is now reported as
  `warn!(path = %path.display(), error = %e, "failed to re-assert endpoint file permissions; the
  atomic write is already 0600, keeping the endpoint file")` and the function returns `Ok(())`.
- The redundant chmod itself was **kept** (it is the documented Unix boundary in this module and
  `write_endpoint_sets_owner_only_permissions` asserts mode `0o600`); only its failure handling
  changed. The permission handling is **not** duplicated — it still lives in `atomic_io`.

## F6 — B1-M1 (adjacent module): the shared-token read is deterministic

*Outside the reviewed `src/cli` module, but the defect is real and the fix is small; recorded here
as an adjacent-module fix.*

- **`src/gateway/security/token_readonly.rs:29-36`** — `read_current_token_readonly` now runs
  `… WHERE plaintext_token IS NOT NULL ORDER BY created_at DESC, token_hash DESC LIMIT 1`.
- **`src/gateway/security/store/tokens.rs:120-127`** — `SecurityStore::get_shared_token_plaintext`
  gets the **same** ordering, so the CLI's read-only mirror and the in-process manager select the
  **same row**.
- **`src/gateway/security/store/tokens.rs:81-88`** — `get_shared_token_secret` gets the same
  ordering too, deliberately: the secret and the plaintext of a token are written **together**
  (`set_shared_token_with_secret`, `tokens.rs:59-64`), so ordering only the plaintext read would
  pair the newest plaintext with an *arbitrary* row's secret — a pairing that fails HMAC validation
  (`SharedTokenManager::try_load_token_from_db`, `shared_token.rs:168-203`) and forces a needless
  token regeneration on every restart.
- **`src/gateway/security/token_readonly.rs:16-27`** — the doc states the recency contract and
  that both columns exist in every version of the table; the stale path reference
  (`store.rs:566-577`) was corrected to `src/gateway/security/store/tokens.rs`.
- **`src/gateway/security/store/tokens.rs:292-298`** — the test doc of
  `rotating_the_shared_token_leaves_exactly_one_row` no longer claims the two readers use
  `LIMIT 1` without an `ORDER BY`.

**Correction to the findings file (important — the suggested SQL would not run):** the findings
propose `ORDER BY created_at DESC, id DESC`. **The production `shared_token` table has no `id`
column** — the schema is `token_hash TEXT PRIMARY KEY, created_at INTEGER NOT NULL`
(`src/gateway/security/store/mod.rs:599-602`, schema v3) plus `hmac_secret BLOB` (v4, line 617) and
`plaintext_token TEXT` (v6, line 630). The `id` column only existed in the *test fixtures*, which
mirrored a table shape the production schema never had. Ordering by `id` would fail at runtime with
"no such column: id" on every real store. The fix therefore orders by the columns the store itself
uses: `created_at` (the millisecond timestamp `set_shared_token_with_secret` refreshes on every
write) with `token_hash` (the table's primary key) as the deterministic tiebreak.

**Test-fixture adaptation (forced by the ordering):**
- **`src/gateway/security/token_readonly.rs:50-64`** — the `seed()` fixture now mirrors the
  production table (`token_hash TEXT PRIMARY KEY, plaintext_token TEXT, created_at INTEGER`);
  the inserts at lines 79-83, 104-108 and 120-124 supply `token_hash`, and the NULL insert at
  lines 133-138 uses a literal `NULL`.
- **`src/gateway/security/token_readonly.rs:90-113`** — new test
  `returns_the_newest_token_when_several_rows_exist`: two rows (`created_at` 1000 / 2000) must
  yield the **newest** token.
- **`src/cli/policy.rs:409-417`** — the `shared_token` fixture of
  `lock_or_ipc_retries_local_acquire_when_forward_fails` had the same non-production `id` column;
  it was updated to the production shape, otherwise the CLI's new query would fail with "no such
  column: token_hash" and the test would assert the wrong failure mode.

## F7 — B1-D1: the admin client follows no redirect (one hop only)

**Decision: option (a) — `.redirect(reqwest::redirect::Policy::none())` was added** at
**`src/cli/ipc_client.rs:322`**, next to the `.no_proxy()` of F2.

**Evidence:**
- `Cargo.lock` → `reqwest 0.13.5` (the `reqwest_legacy 0.12.28` entry exists only for
  `reqwest-eventsource` / `teloxide`). `Cargo.toml:216` enables the `system-proxy` feature.
- `reqwest-0.13.5/src/redirect.rs:239-252` — `remove_sensitive_headers` removes `AUTHORIZATION`,
  `COOKIE`, `PROXY_AUTHORIZATION`, … when the next hop's host, port **or** scheme differs from the
  **previous** hop's.
- `tower-http 0.6.11` (`follow-redirect/mod.rs:214-229`, the version reqwest 0.13.5 depends on)
  stores `headers: req.headers().clone()` — the **original** headers, including `Authorization` —
  and re-clones them onto **every** hop, then lets the policy strip the sensitive ones. The strip
  therefore compares against the **immediately previous hop** only: a redirect chain of two hops
  that stays on a foreign host keeps the bearer token, because hop 2's "previous hop" is the
  foreign host itself.
- `tower-http` `follow-redirect/mod.rs:275-291` — `307`/`308` keep the method **and the body**
  (the admin POST bodies carry secret values, e.g. `POST /v1/admin/secrets`), and the body is
  re-sent to a target that is **not** checked at all.
- The local server never redirects: `grep -rn "Redirect" src/gateway/` → no hits; the admin router
  is nested at `/v1/admin` (`src/gateway/server/mod.rs:1161`) and the `src/gateway/admin_api/*`
  routes only serve `/latest`, `/` and `/{key}`.

**Conclusion:** the bearer token **can** reach a foreign host (two-hop chain) and the request body
**can** be re-sent to a foreign host (307/308) — so the redirect target was never covered by F1's
validation. Since the admin channel is local-only and the server never issues a redirect, one hop
is the contract and refusing redirects breaks nothing. A 3xx now surfaces through the existing
`finalize()` error path (`server returned 3xx: …`) instead of being followed.

## F8 — B1-P1-3: the forward path proves the endpoint's writer identity

The `pid` + `start_time` proof was enforced only on the daemon's **STOP** path, so a stale endpoint
file whose PID was recycled by an unrelated local process could still receive the admin bearer token
and the secret body.

- **`src/cli/endpoint.rs`** — `IpcEndpoint::recorded_start_time()` (`self.start_time.filter(|s| *s != 0)`)
  and `IpcEndpoint::writer_is_live()` (the recorded PID is alive **and** its start time still matches
  the recorded one, via the existing `crate::utils::process_alive::process_matches`). Fails closed: a
  record with no usable start time is **not** "live", because "unproven" is not "confirmed" — the same
  stance `src/bin/aleph-server/daemon.rs:253-285` takes before it signals a PID.
- **`src/cli/ipc_client.rs:45`** — `forward_to_server` refuses when `!endpoint.writer_is_live()`,
  **before** `read_token` (the token is never read out of `security.db` for an unproven endpoint).
- **`src/cli/ipc_client.rs:604`** — new test `forward_to_server_refuses_an_endpoint_whose_writer_is_gone`
  (an endpoint whose PID is almost certainly dead, with a start time that cannot match it).

**Scope kept narrow on purpose.** The daemon's stop path keeps its own `verify_endpoint_identity`:
it answers a different question ("is the PID the operator named the server that wrote this record?" —
it compares a **caller-supplied** PID against the record), so moving it wholesale would change the
stop path's error messages for no gain. The shared primitive is the one that matters — `process_matches`
— which both paths already use.

**Compatibility.** The CLI and the server are subcommands of the same binary, so the endpoint is always
written by a build that records `start_time` (`IpcEndpoint::current` → `process_start_time`). A record
without a usable start time can only come from a hand-edited file or a foreign writer, and is refused.
