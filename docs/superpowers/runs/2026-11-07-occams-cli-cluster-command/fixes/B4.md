## F1 — the file jail's READ side now carries the same leaf guard as the write side

**The defect.** `FileReadCommand::run` checked the leaf's type with `symlink_metadata` and then
opened the path with a plain `tokio::fs::File::open`. The WRITE side had been hardened with
`O_NOFOLLOW`; the read side had not. Two independent consequences:

- **The leaf swap (the real hole).** A writer with workspace-internal access could replace the leaf
  with a symlink *after* `resolve_in_jail`'s canonicalize and containment check but *before* the
  open. The plain `open(2)` follows that symlink, so the read could leave the jail. The comment
  above the read's type check claimed the read side was "the read-side counterpart of the write
  side's `O_NOFOLLOW` guard" — **a guard that did not exist**.
- **The FIFO swap (the availability half of the same race).** `symlink_metadata` says a FIFO is
  not a regular file, so the type check rejects it — but the check and the open are two syscalls.
  A FIFO planted in between makes `open(2)` block until a reader appears, parking a Tokio worker
  thread on a remote node.

**The fix** (`src/cluster/node_file_cmd.rs`):

- **read side** — `tokio::fs::File::open(&src)` replaced by
  `tokio::fs::OpenOptions::new().read(true)` + `#[cfg(unix)] opts.custom_flags(libc::O_NOFOLLOW | libc::O_NONBLOCK)`.
  `O_NOFOLLOW` makes the open itself refuse a symlink at the leaf; `O_NONBLOCK` turns the FIFO
  swap into `ELOOP`/`ENXIO`-style errors instead of a blocking open.
- **write side** — the existing `opts.custom_flags(libc::O_NOFOLLOW)` became
  `libc::O_NOFOLLOW | libc::O_NONBLOCK` (the same FIFO class on the write path: a FIFO planted at
  the leaf between the type check and the open used to block the open).
- **the false comment** above the read's type check now describes the guard that is actually there.
- The pre-open `symlink_metadata` type check is **kept**: it rejects FIFOs/directories before any
  open and preserves the existing `"not a regular file"` error strings the tests assert on.

**The happy path is unchanged.** `check_and_resolve_path`
(`src/builtin_tools/file_ops/path_utils.rs:1134`) canonicalizes when the path exists
(`path_utils.rs:1150-1153`), so a symlink that points **inside** the jail is resolved to its
target before the open: the open sees the real file, not the link, and `O_NOFOLLOW` does not fire.
The new test `file_read_follows_a_symlink_that_stays_inside_the_jail` pins that.

**New tests** (`src/cluster/node_file_cmd.rs`):
- `file_read_follows_a_symlink_that_stays_inside_the_jail` — a symlink to a file inside the jail
  still reads (guards against the fix breaking legitimate reads).
- `file_read_refuses_a_symlink_that_leaves_the_jail` — a symlink to a file outside the jail is
  refused (`resolve_in_jail`'s containment check rejects it before the open).

The race itself has **no deterministic test** — it needs an attacker to win a two-syscall window.
The tests cover the two outcomes the fix distinguishes, not the interleaving.

## What the batch found and deliberately did NOT change

- **The parent-directory / root swap window stays open.** `src/cluster/node_file_cmd.rs:75-81`
  already documents it: closing it needs a pinned root directory fd and `openat`/`O_NOFOLLOW` on
  every descendant operation. The leaf-level guard is now on both sides; the parent level is
  **unchanged and still documented as open** — a half-fix would have made the hole look closed.
- **The reverse-RPC waiter map is not an unbounded leak.** `PendingInvokes::register`
  (`src/cluster/reverse_rpc.rs:40-51`) inserts into a `HashMap`, but `ReverseRpcChannel::call`
  wraps the id in a `WaiterGuard` whose `Drop` removes the waiter on **every** exit — timeout,
  error, serialization failure, and a dropped future (the harness cancels a tool call by dropping
  the future). The map's size is therefore the number of **concurrent in-flight calls**, and the
  outbound side is a bounded `mpsc` that fails with `OutboundWedged`. No ceiling was added.
- **`CommandTable::register` keeps its overwrite semantics.** `src/cluster/node_runtime.rs:57-82`
  logs `tracing::warn!("CommandTable::register overwriting an existing entry")` and lets the later
  binding win. The hazard (a later command with a different jail root shadowing an earlier one)
  is real but the fix is a **setup-order** decision, not a code change; the public signature was
  left alone.
- **The two near-identical rate-limited warn helpers** in `src/cluster/node_approval.rs`
  (`rate_limited_warn_drift` / `rate_limited_warn_no_channel`, each with its own `AtomicU64` and
  an `is_multiple_of(100)` gate) are a **P3 duplication** — merging them would trade two
  honestly-named helpers for one with two call shapes. Left alone.
- **`node_approval.rs` and `node_runtime.rs` needed no changes**: the approval path fails closed
  (`Unavailable`, never a locally-minted `Denied`), `outcome_from_str` has an explicit drift arm,
  and `NODE_APPROVAL_TIMEOUT_MS` (130 s) stays above the center's 120 s.
