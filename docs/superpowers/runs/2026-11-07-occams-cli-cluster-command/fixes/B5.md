## The namespace proof (B5-03)

The `allowed_tools` polarity is decided at run time by
`gateway::execution_engine::slash_skill_pregrant::registered_skill`: it looks the
mode's `skill_id` up in the `SkillSystem` and compares the manifest's source
with the mode's `owning_plugin`. A plugin COMMAND's row must therefore be
unable to resolve to a skill manifest. The chain, all verified in this repo:

1. `src/extension/registry/plugin_registry/mod.rs:153` and `:479` — a
   registration whose `plugin_id` is empty is **refused** (`registration.plugin_id.is_empty() || …`).
   `src/extension/slash_effect.rs:47` filters such commands out too.
2. `src/extension/registry/types.rs:159-165` — `namespaced_component_key`
   drops the `<plugin_id>:` prefix **only** for an empty plugin id, so a
   plugin registration's qualified name always contains `:`.
3. `src/skill/manifest.rs:452-463` — a skill manifest's id comes from its
   `name:` through a strict charset transform: every character outside
   `[a-z0-9._]` (and `-`) collapses to `-`. A manifest id can therefore never
   contain `:`.
4. `src/gateway/execution_engine/slash_command_body/mod.rs:315` — the plugin-command
   render path independently refuses a bare (unqualified) `skill_id`.

⇒ The two id spaces are disjoint **by construction**, and a plugin command's
`allowed_tools` is always read as a restriction. The doc now says that, with
the citations, instead of asserting it.

## Invariants preserved

- **Resolution**: no change — `ToolCatalog::resolve_command` still matches by
  name and alias; `routing_regex` was never part of matching.
- **The prompt the model sees**: unchanged. The rule's `system_prompt` still
  reaches the model as the tool's description (truncated to 100 chars), and the
  whole text is still on the tool as `routing_system_prompt`.
- **Public API**: no `pub` item removed. `UnifiedTool::routing_system_prompt`,
  `UnifiedTool::routing_regex`, `UnifiedToolBuilder::with_routing_system_prompt`
  and the `aleph-slot-api` builder all stay.
- **The `allowed_tools` polarity**: unchanged, and now documented with its proof.
- **Wire**: the slash mode JSON loses two keys that had no reader anywhere in
  the repo (including the Panel crate). The mode JSON never crosses a crate
  boundary.

## Not done (deliberately)

- `UnifiedTool::routing_system_prompt` and `routing_regex` are now **read by
  nothing** in `alephcore`. They were kept because they are `pub` fields of a
  cross-crate contract type; removing them is an API-break decision, not a
  refactor. **This is a decision item for the user** — see the batch report.
- The product question ("should a custom command's `system_prompt` become a
  real system prompt?") is untouched: the behaviour today is unchanged, only
  the over-promising documentation was corrected.
- No `cargo` was run (per the task: one unified check at the end).
