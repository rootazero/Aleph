### B4-01 [P1] The node file jail's READ side had no leaf guard
- Location: `src/cluster/node_file_cmd.rs:257-271` (`FileReadCommand::run`)
- Failure mode: `resolve_in_jail` canonicalizes the path and checks that the result is inside the
  workspace root. A writer with workspace-internal access (the node's own `file.write` command, or
  any process in the workspace) can then replace the leaf with a symlink. The read's
  `symlink_metadata` type check and the `open` are **two syscalls**, so a swap between them turns
  the plain `open(2)` into a symlink follow: the center reads a file **outside** the node's
  workspace. The write side had been hardened with `O_NOFOLLOW` for exactly this reason; the read
  side had not, and the comment above it asserted the opposite.
- Evidence:
  ```rust
  // node_file_cmd.rs:250-253 (before the fix)
  // `symlink_metadata` does not follow a symlink, so a symlink planted
  // at the leaf after `resolve_in_jail` canonicalized the path is
  // refused as well — the read-side counterpart of the write side's
  // `O_NOFOLLOW` guard.
  let file = tokio::fs::File::open(&src).await.map_err(|e| format!("file.read: {e}"))?;
  ```
  versus the write side (node_file_cmd.rs:193-204):
  ```rust
  #[cfg(unix)]
  { opts.custom_flags(libc::O_NOFOLLOW); }
  ```
- Minimal fix: open the read side through `tokio::fs::OpenOptions` with
  `custom_flags(libc::O_NOFOLLOW)`, exactly like the write side; keep the pre-open type check (it
  rejects FIFOs/directories before any open and preserves the error strings the tests assert on);
  correct the comment.
- Invariant preserved: a symlink that stays **inside** the jail still reads — `resolve_in_jail`
  canonicalizes the path, so the open sees the resolved target, not the link (pinned by the new
  test `file_read_follows_a_symlink_that_stays_inside_the_jail`).
- Confidence: 0.95

### B4-02 [P2] A FIFO planted at the leaf blocks the open and parks a worker thread
- Location: `src/cluster/node_file_cmd.rs:257-271` (read), `src/cluster/node_file_cmd.rs:198-205` (write)
- Failure mode: the type check rejects a FIFO, but the check and the open are two syscalls. A FIFO
  planted in between makes `open(2)` block until some process opens the other end — a **blocking
  syscall inside a Tokio worker**, on a remote node, indefinitely. The write side had the same
  class of hole (its `O_NOFOLLOW` does not stop a FIFO).
- Minimal fix: add `libc::O_NONBLOCK` to both opens' `custom_flags`. A regular file ignores
  `O_NONBLOCK`; a FIFO then fails immediately instead of blocking.
- Invariant preserved: the happy path (a regular file) is unchanged — `O_NONBLOCK` has no effect
  on regular files, and `O_NOFOLLOW` still refuses a symlink leaf.
- Confidence: 0.9

### B4-03 [P3] A duplicate command registration silently shadows the earlier binding
- Location: `src/cluster/node_runtime.rs:57-82` (`CommandTable::register`)
- Failure mode: registering a name that already exists logs
  `tracing::warn!("CommandTable::register overwriting an existing entry")` and the **later** binding
  wins. `register_file_commands` and `with_bash` are both callable from the same setup path, so a
  misordered init could bind `file.read` / `file.write` to a **different jail root**.
- Assessment: the hazard is real but the fix is a **setup-order** decision, not a code change; the
  public signature was left alone and the warning kept.
- Confidence: 0.7

### B4-04 [P3] Two near-identical rate-limited warn helpers
- Location: `src/cluster/node_approval.rs` (`rate_limited_warn_drift`, `rate_limited_warn_no_channel`)
- Assessment: each has its own `AtomicU64` and an `is_multiple_of(100)` gate. Merging them would
  trade two honestly-named helpers for one with two call shapes. Left alone.

### B4-05 [P3] A comment about a guard that does not exist
- Location: `src/cluster/node_file_cmd.rs:250-253`
- Assessment: fixed together with B4-01.

  `REVERSE_RPC_MAX_TIMEOUT_MS`.
