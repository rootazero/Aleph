### B5-01 [P1] The custom command's `system_prompt` reaches the tool description but never the model as a system prompt — two severed copies ride the mode JSON
- Location: `src/command/parser.rs:79-84` (`CommandContext::Custom`), `src/command/parser.rs:177-187` (`tool_to_command_context`), `src/gateway/inbound_router/command_handler.rs:191-199` (`serialize_parsed_command`)
- Failure mode: an operator writes `[[routing_rules]] regex = "^/translate" system_prompt = "You are a translator"`. `register_custom_commands` (`src/tool_metadata/registry/registration.rs`) puts that string in **two** places: the tool's **description** (truncated to 100 chars — this is the copy that actually reaches the model) and `UnifiedTool::routing_system_prompt`. `parser.rs:178` copies the second one into `CommandContext::Custom.system_prompt`; `serialize_parsed_command` writes it into the slash-mode JSON as `"system_prompt"`. The fast path's `"custom"` arm returns `Fallthrough` **without reading it**, and the agent loop that then runs the turn has no reader for that key — repo-wide grep for `get("system_prompt")` / `get("pattern")` returns only unrelated hits (`src/gateway/tool_display.rs:140` reads a *tool parameter* named `pattern`; `src/gateway/handlers/security_config/toml_io.rs` reads security-TOML patterns; `src/providers/protocols/template.rs:232` reads a provider template; `src/providers/gemini/schema.rs:461` is a test). The operator's prompt never becomes a system prompt. `src/config/types/routing.rs:72` promises it is used "as both the tool description **and the routing prompt**" — the second half has no effect. The same holds for `pattern` (`parser.rs:186`), whose only reader would also have been the mode JSON.
- Evidence:
```rust
// src/gateway/inbound_router/command_handler.rs:195-200
CommandContext::Custom { system_prompt, pattern } => serde_json::json!({
    "type": "custom", "tool_id": parsed.tool_id,
    "system_prompt": system_prompt, "pattern": pattern, ... })
```
```rust
// src/gateway/execution_engine/slash_command.rs:291-296
"custom" => { Err(ExecutionError::Fallthrough { reason: "custom command".to_string() }) }
```
- Suggested fix: **deletion, not reconnection** — the project already made this call once for the same class of defect (`src/tool_metadata/registry/registration.rs:321`: "the copy was a second, reader-less expression of the same string"). Drop `system_prompt` and `pattern` from `CommandContext::Custom`, drop the two keys from the mode JSON, and correct `src/config/types/routing.rs:72` to say `system_prompt` acts as the tool **description** only — mirroring the `provider` precedent in the same file (`:48-58`, "The gate is real; the effect it implies is not"). Two follow-ons the fix must handle: `src/tool_metadata/registry/tests.rs:236-238` currently pins the dead copy ("the prompt must also reach `CommandContext::Custom.system_prompt`") and must be updated; and `UnifiedTool::routing_system_prompt` then has no reader anywhere, so that field and `with_routing_system_prompt` become a write-only pair to be deleted in the same pass (repo-wide grep first — the field is `pub` on a widely used type). *Alternative*, if the product wants the prompt to actually be a system prompt: inject it into the fall-through turn — that is new behavior, not a refactor, and needs an explicit decision. Invariant preserved: the prompt's only live effect (the tool description the model reads) is untouched.
- Confidence: 0.92

### B5-02 [P2] `pattern` falls back to a tool NAME where a pattern is expected
- Location: `src/command/parser.rs:186` (`tool_to_command_context`)
- Failure mode: `pattern: tool.routing_regex.unwrap_or(tool.name)` — when the tool carries no regex the field becomes the command's **name** (e.g. `"translate"`), which is not a pattern. Any consumer that treated the field as a regex would match the literal string `translate` rather than the command. The defect is latent today (no consumer — see B5-01) and becomes live the moment the field is wired up, which is exactly when someone will trust it.
- Evidence: `pattern: tool.routing_regex.unwrap_or(tool.name),` — and the only producer reaching this arm, `register_custom_commands`, always sets `.with_routing_regex(rule.regex.clone())`, so the fallback arm is unreachable today.
- Suggested fix: delete the field (B5-01) and the wrong fallback goes with it. If the field is kept instead, make the fallback `String::new()` and document that a custom command always carries a regex.
- Confidence: 0.88

### B5-03 [P2] `allowed_tools`' doc says the pre-grant list "is read from the skill file" — it is read from this same field, and the doc does not say which of the two meanings it carries
- Location: `src/command/parser.rs:70-76` (`CommandContext::Skill.allowed_tools`)
- Failure mode: the doc tells a maintainer that a skill's `allowed-tools:` arrives "from the skill file (`gateway::execution_engine::slash_skill_pregrant`)". It does not: the **same** `mode["allowed_tools"]` key carries it, and `slash_skill_pregrant::registered_list(&mode)` reads it back out of the mode JSON. A maintainer following the doc goes looking for a second, file-based path and wires the wrong thing. The doc also states the two meanings ("A plugin command's is its tool RESTRICTION … A skill's pre-grants rather than restricts") without saying which side **this field** is on — the field holds the row's declared list either way, and the polarity is decided at **run time**, not at parse time.
- Evidence:
```rust
// src/command/parser.rs:70-76
/// The row's declared `allowed-tools:`, validated at registration. A
/// plugin command's is its tool RESTRICTION: `None` = declared nothing
/// (allow-all); `Some(vec![])` = explicit deny-all. Do not flatten: an
/// empty allow-set means allow-all downstream. A skill's pre-grants
/// rather than restricts, and is read from the skill file
/// (`gateway::execution_engine::slash_skill_pregrant`).
allowed_tools: Option<Vec<String>>,
```
```rust
// src/gateway/execution_engine/slash_skill_pregrant/mod.rs:117-119
mode.get("allowed_tools").and_then(Value::as_array)
```
- Suggested fix: doc-only. State the actual contract: this field is the row's declared list; whether it RESTRICTS the turn or PRE-GRANTS for it is decided by `slash_skill_pregrant::registered_skill()`, which resolves `mode["skill_id"]` against the `SkillSystem` manifest store and checks the owner — `Some` ⇒ pre-grant, `None` ⇒ restriction. Add the safety note, because it is invisible from this file: the two readings are kept apart **only** because a plugin COMMAND's id is plugin-qualified (`<plugin_id>:<name>`, `src/extension/slash_effect.rs:24` `cmd.qualified_name()`, whose comment says "Plugin commands have no SkillManifest behind them") while a plugin skill's manifest id is flat. If a command's id ever resolved to a manifest of the same plugin, its restriction would be stamped as a pre-grant — the approval bypass `src/gateway/execution_engine/slash_skill_scope.rs:5-9` warns about. Invariant preserved: no behavior change; the field and its consumers are untouched.
- Confidence: 0.9

### B5-04 [P3] Two docs claim "one process-wide parser"; boot builds two
- Location: `src/command/mod.rs:17,24-27` (`CommandParserCell`), `src/command/parser.rs:139-143` (`CommandParser::tool_registry`)
- Failure mode: `mod.rs:17` says "Deferred handle to the process's **one** `CommandParser`" and `:24-27` says "It is a *shared* cell, not one per consumer: `chat.send`, `agent.run` and the execution engine's own fallback all resolve slash input through the same parser, which is what stops the surfaces from growing slightly different ideas of what `/foo` means." `parser.rs:141-143` repeats it ("The parser is shared process-wide through `crate::command::CommandParserCell`"). Boot actually builds **two**: `src/bin/aleph-server/commands/start/builder/agent_init/tool_catalog_init.rs:408` (into the deferred cell → `chat.send` / `agent.run`) and `src/bin/aleph-server/commands/start/builder/subsystems.rs:1164` (into the `InboundRouter` → the execution engine's own fallback). Both wrap the same `Arc<ToolCatalog>`, so they resolve against one *catalog* today and no current behavior diverges — but the stated invariant is false, and it is precisely the invariant that keeps the surfaces in lockstep. A future change that gave the InboundRouter a differently-scoped catalog would produce exactly the drift the doc claims to prevent, and the doc would still be assuring everyone that it cannot happen.
- Evidence: the two construction sites quoted above; `src/command/mod.rs:24-27` and `src/command/parser.rs:141-143` for the claims.
- Suggested fix: doc-first — correct both docs to name what is actually shared (the `ToolCatalog`, not the parser) and to say why two parser instances are harmless (both wrap the same `Arc<ToolCatalog>`). Optionally, collapse to one `Arc<CommandParser>` handed to both consumers; that touches the boot wiring in `src/bin/aleph-server` and is not worth it on its own. Invariant preserved: resolution behavior is identical either way — the catalog is the only thing that decides what `/foo` means.
- Confidence: 0.85

### B5-05 [P3] `ParsedCommand.source_type` is read only by a log line, but its doc tells readers to dispatch on it
- Location: `src/command/parser.rs:11-12` (`ParsedCommand::source_type`), `src/command/parser.rs:44-50` (`CommandContext` doc)
- Failure mode: the `CommandContext` doc says "Read `source_type` on the enclosing `ParsedCommand` for the actual source." The only production read of `ParsedCommand.source_type` in the repo is a log line (`src/gateway/execution_engine/slash_command.rs:174`). Anyone following the doc to tell `Builtin` from `Native` from `Plugin` finds a field nothing dispatches on — and the field it *would* dispatch on (`CommandContext::Builtin`'s `tool_name`) deliberately collapses all three into one shape, so the doc is pointing at the only place the distinction is still recorded.
- Evidence: `src/command/parser.rs:49-50` ("Read `source_type` on the enclosing `ParsedCommand` for the actual source."); the sole reader at `src/gateway/execution_engine/slash_command.rs:174` is a `tracing` field.
- Suggested fix: doc-only — state that `source_type` is the diagnostic label carried on `ParsedCommand`, and point at the one consumer. Do not delete the field: it is `pub` on a lib-crate struct and the log line is a real use.
- Confidence: 0.85
