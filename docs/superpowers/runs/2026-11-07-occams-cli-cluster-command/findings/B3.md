### B3-M1 [P0] Admission fails open when the device store cannot be read
- Location: `src/cluster/enrollment.rs:387-393` (`admit_node`)
- Failure mode: A node whose device row is revoked reconnects while `get_device` returns a SQLite error -> the function logs the failure and returns `Admitted`, after which the connection handler registers the session instead of preserving deregistration.
- Evidence: `"node device lookup failed; admitting on LAN-trust"`; `return NodeAdmission::Admitted { node_id: id.to_string(), minted: false }`.
- Suggested fix: Add a non-admitted storage-unavailable result and handle it at `src/gateway/server/connection/mod.rs:1049-1074` as a failed connect; do not degrade a failed revocation check into admission. This preserves the sticky-deregistration and fail-closed identity invariants.

### B3-P1-01 [P1] Re-enrollment cannot recover the persisted revoked identity
- Location: `src/cluster/enrollment.rs:151-169, 209-228` (`match_by_name`, `enroll_node_device`)
- Failure mode: `cluster.deregister` marks the node row revoked, then the operator enrolls the same name -> `list_devices()` hides the revoked row and a new ID is minted, while the node still presents its old ID and is rejected as `Deregistered`.
- Evidence: `list_devices()` selects `WHERE revoked_at IS NULL`; `Ok(NameMatch::None) => mint_node_device(store, node_name).map(|id| (id, true))`; `admit_node` checks a presented ID before name matching.

## Policy and product decisions

### R1 — active-ID/name mismatch
The current behavior is a documented policy: the persisted ID is authoritative and the CLI name is a mutable label, which is required for a legitimate operator rename. Keeping it (the recommended minimal option) preserves reconnect stability and changes no protocol, but accepts possession of an active ID as sufficient identity under LAN-trust; the ID must therefore be treated as a bearer secret in documentation and exposure policy. Binding an active ID to normalized `device_name` would reduce ID theft/impersonation, but breaks renamed-node reconnects, requires an explicit rename/rebind workflow and migration for existing rows, and still does not provide cryptographic proof without a new node credential. This is why P0-1 is not reported as a missing comparison.

### R2 — re-enrollment after deregistration
The code and operator text currently disagree. Reactivating the unique revoked row on an explicit `cluster.enroll` is the smallest recovery behavior and preserves sticky reconnects because ordinary `admit_node` still rejects the row; it does, however, make “enroll again” an explicit authorization to revive the old bearer ID. Minting a new ID is safer for revocation but requires the operator to replace/delete the node's persisted identity and the docs/CLI must say so. Choose one before implementing B3-P1-01.

### R3 — ambiguous first boot
The current minting policy keeps a machine online but permanently deepens duplicate-name damage. The contract and the operator path require fail-closed refusal, which is the recommended option: it takes only the ambiguous machine offline until duplicate rows are repaired by ID, but preserves addressability and idempotency. Keeping minting would require weakening the common ambiguity contract and explicitly accepting more ghost rows; it should not be called a fix.

### R4 — peer-controlled ID and fingerprint
Do not silently truncate IDs because that would change identity and can merge two peers. Decide a maximum accepted ID representation at the connect boundary, reject or fail the admission when exceeded, and use a complete-ID collision-resistant fingerprint. This is a protocol/storage policy change, unlike the name-bound fix, and should be versioned if legacy non-UUID IDs must remain accepted.
