## Safe code fixes

### B1-P1 [P1] Joined URL can bypass the loopback check
- Location: `src/cli/ipc_client.rs:45-88` (`forward_to_server`)
- Failure mode: A caller supplies an authority-bearing route such as `//attacker.example/v1/admin/secrets` or `http://attacker.example/v1/admin/secrets`; the pre-join endpoint is loopback and passes the guard, `Url::join` replaces its authority, and `call_once` sends the bearer token and JSON body to the new host.
- Evidence: `let host = base.host_str()...; if !is_loopback_host(host) { ... }` is followed by `let joined = base.join(route)...` and then `call_once(&url, method, &body, &token)` with no host check on `joined`.
- Suggested fix: Reject routes that are not absolute-path `/v1/admin/...` routes, then validate the final `joined` URL's scheme/host (including loopback) immediately after joining and before `read_token`; do not rely on `build_client` because plain HTTP is allowed there. This is behavior-preserving for the in-tree static `/v1/admin/*` routes and closes the public helper's authority-replacement path.
- Confidence: 0.99

### B1-P1 [P1] System proxy can receive admin credentials
- Location: `src/cli/ipc_client.rs:247-269` (`build_client`)
- Failure mode: With `HTTP_PROXY`/`ALL_PROXY` configured and the normal `http://127.0.0.1:port` endpoint, reqwest's system-proxy support routes the request through the proxy; because the request carries `Authorization: Bearer <token>` and the JSON admin body over plain HTTP, the proxy can read both.
- Evidence: `reqwest::blocking::Client::builder().timeout(...)` is built directly and there is no `.no_proxy()` before `.build()`; `call_once` attaches `.bearer_auth(token).json(body)`.
- Suggested fix: Add the exact builder call `builder = builder.no_proxy();` (or chain `.no_proxy()` on the `Client::builder()` expression) before `.build()`. Separately, decide whether to add `.redirect(reqwest::redirect::Policy::none())`; if redirects are not an intentional admin-channel feature, that exact call should be applied to the same builder so an endpoint response cannot trigger follow-up requests. `.no_proxy()` is the safe code fix; redirect policy is listed below as a product/security decision.
- Confidence: 0.99

### B1-P1 [P1] IPC trusts a stale endpoint's URL without proving process identity
- Location: `src/cli/ipc_client.rs:38-91` (`forward_to_server`), contract at `src/cli/endpoint.rs:38-58` (`IpcEndpoint`)
- Failure mode: The server exits without removing `.ipc-endpoint.json`, an unrelated local process later binds the recorded port, and a CLI command uses the stale URL; the CLI reads the local admin token and sends it plus secret values to that process because it never checks the recorded PID/start-time pair.
- Evidence: `forward_to_server` obtains `endpoint` and immediately parses `endpoint.url`; `IpcEndpoint` documents that `pid` plus `start_time` prove the writer identity, while `src/bin/aleph-server/daemon.rs` performs that proof only for `stop`.
- Suggested fix: Factor the existing daemon identity semantics into a shared helper. Before `read_token`, require `endpoint.start_time.is_some()`, convert `endpoint.pid` to the process API's signed type without lossy conversion, query the live process start time, and reject missing/unqueryable/mismatched identities. Call the helper from both `forward_to_server` and `daemon::verify_endpoint_identity`; preserve the current fail-closed error style. The older record format with no start time must remain unusable for credentialed IPC, as its own documentation requires.
- Confidence: 0.98

### B1-P2 [P2] Concrete bind addresses publish an endpoint the local CLI rejects
- Location: `src/cli/endpoint.rs:12-35` (`build_endpoint_url`) and `src/cli/ipc_client.rs:53-62` (`forward_to_server`)
- Failure mode: A gateway is bound only to a concrete non-loopback address such as `192.168.1.5`; startup records `http://192.168.1.5:port`, but every CLI invocation rejects that endpoint before reading its token, so lock-held admin commands cannot forward and the local command path cannot acquire the running server's lock.
- Evidence: `build_endpoint_url` maps only unspecified addresses to localhost and says concrete addresses are preserved; `forward_to_server` unconditionally bails for every non-loopback `host`.
- Suggested fix: This requires the product decision below; once local-only IPC is confirmed, either reject unsupported non-loopback admin binds at startup with an actionable error or publish a separately configured reachable local-admin URL. Do not merely weaken the loopback check: that would violate the stated token/secret local-only invariant.
- Confidence: 0.97

### B1-P2 [P2] Stale-record error misstates PID-reuse state
- Location: `src/cli/policy.rs:27-49` (`LockHolder`, `Display for LockHeldError`), producer at `src/utils/instance_lock.rs:250-255`
- Failure mode: A lock sidecar contains PID 123 whose current process is alive but has a different start time; `classify_lock_failure` returns `HeldByOrphaned`, but the CLI prints that PID 123 "is not running", misleading an operator about the live unrelated process while the lock remains held.
- Evidence: The producer maps both `!process_matches(pid, expected_start)` and a dead PID to `HeldByOrphaned`; the formatter hard-codes `which is not running`.
- Suggested fix: Change the message to "does not match the recorded process identity" (or distinguish dead from start-time mismatch if the helper exposes that reason). Keep the lock-held instruction and never recommend signalling the recorded PID.
- Confidence: 0.98

### B1-P2 [P2] Endpoint chmod failure deletes a valid atomic write
- Location: `src/cli/endpoint.rs:87-116` (`write_endpoint`), writer at `src/utils/atomic_io.rs:46-57` (`write_atomic`)
- Failure mode: `write_atomic` succeeds and renames a 0600 temporary file, but `set_permissions` returns an error; `write_endpoint` removes the endpoint and returns `Err`, while the startup caller logs a warning, leaving a running server with no IPC endpoint.
- Evidence: `write_atomic(&path, &bytes)?` precedes `if let Err(e) = std::fs::set_permissions(&path, perm)`, whose error branch calls `std::fs::remove_file(&path)` and returns `PermissionDenied`; `write_atomic` creates Unix temporaries with `options.mode(0o600)`.
- Suggested fix: Remove the redundant chmod branch and rely on `write_atomic`'s explicit 0600 creation mode, or retain chmod without deleting the already-secure file. The smallest behavior-preserving fix is to eliminate the post-rename chmod/delete step.
- Confidence: 0.97

### B1-P2 [P2] Read-only token lookup is nondeterministic for legacy duplicate rows (missed by Jev)
- Location: `src/gateway/security/token_readonly.rs:18-29` (`read_current_token_readonly`); matching store contract at `src/gateway/security/store/tokens.rs:40-71,98-119`
- Failure mode: A database created under the prior append/upsert bug still contains multiple `shared_token` rows; `SELECT ... LIMIT 1` has no `ORDER BY`, so SQLite may return an older or otherwise superseded plaintext token. The CLI then sends that arbitrary token, and the server's legacy multi-row validator may still accept any old hash until repair.
- Evidence: The read query is `SELECT plaintext_token FROM shared_token WHERE plaintext_token IS NOT NULL LIMIT 1`; the store documentation explicitly says the transaction's delete repairs stores that already accumulated rows, meaning such legacy state is possible before the next rotation.
- Suggested fix: Make the read deterministic with `ORDER BY created_at DESC, id DESC LIMIT 1`, matching the newest-token semantics, and add a two-row regression test. Prefer also repairing duplicate rows through the existing transactional store path when the server next writes; do not broaden this CLI read into a write.
- Confidence: 0.91

## Policy/product decisions

### B1-P1 [P1] Regression gate does not prove policy dispatch
- Location: `src/cli/policy.rs:93-102` (`run_no_lock`) and `scripts/spec_c_regression.sh:53-55`
- Failure mode: A new command file can omit a real `with_policy(...)`/`run_no_lock(...)` dispatch but include the marker in a comment (or use the nonexistent `with_policy_owned` marker); the gate reports success although the command's lock policy was never applied. Conversely, current helper files without markers can make the gate fail for reasons unrelated to executable subcommand dispatch.
- Evidence: `run_no_lock` is exactly `f()`; the script computes `git grep -L "with_policy\|run_no_lock\|with_policy_owned" ...` rather than checking a call expression or parsed Rust item.
- Suggested fix: Decide whether this gate is retained. If retained, replace the substring scan with a check that is tied to executable dispatch (for example, a narrowly scoped call-pattern scan plus explicit exclusions, or a small parser-based check), remove the nonexistent marker, and add a fixture proving that a comment-only marker fails. Do not claim the current grep is a policy proof.
- Confidence: 0.96

### B1-D1 [P1] Redirect behavior for the credentialed admin client
- Location: `src/cli/ipc_client.rs:247-269` (`build_client`)
- Failure mode: If reqwest follows a redirect emitted by the endpoint, the client may issue a second request to a URL that was not checked by `forward_to_server`; whether credentials/body are retained depends on reqwest's redirect behavior, so the current code has no explicit no-redirect invariant.
- Evidence: `build_client` configures timeout and optional invalid-cert acceptance but no `redirect(reqwest::redirect::Policy::none())`; the endpoint URL is validated only before request construction.
- Suggested fix: Human decision: if admin IPC must be one-hop, add `.redirect(reqwest::redirect::Policy::none())` to the same `reqwest::blocking::ClientBuilder` as `.no_proxy()`, and surface a redirect as an error. If redirects are intentionally supported, define and test a redirect allowlist that re-applies scheme, host, and credential rules on every hop.
- Confidence: 0.86

### B1-D2 [P2] Non-loopback gateway/admin endpoint contract
- Location: `src/cli/endpoint.rs:12-23` (`build_endpoint_url`) and `src/cli/ipc_client.rs:232-246` (`build_client`)
- Failure mode: Operators can configure a concrete non-loopback listener, but the documented local CLI path cannot use it and HTTPS does not provide an escape because `build_client` rejects non-loopback HTTPS as well.
- Evidence: `build_endpoint_url` preserves concrete addresses; `forward_to_server` rejects non-loopback hosts for every scheme; `build_client` separately rejects non-loopback HTTPS.
- Suggested fix: Human decision: either make this an explicit unsupported configuration and fail startup before publishing the endpoint, or introduce a separately designed remote-admin capability with CA validation, explicit trust/auth policy, and a non-local route. Do not weaken the current local-only check as an incidental fix.
- Confidence: 0.98
