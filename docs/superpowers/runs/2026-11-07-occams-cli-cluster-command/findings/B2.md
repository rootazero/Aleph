### B2-01 [P2] The malformed-catalog fail-closed rule is honored on one of three dispatch paths
- Location: `src/cluster/registry.rs:373-379` (`NodeRegistry::resolve`), `src/cluster/registry.rs:103-109` (`NodeMatch`), `src/cluster/registry.rs:431-447` (`resolve_all_by_tags`)
- Failure mode: A node connects with `commands: [{"name":"bash"}]` (an entry missing `schema`, so the **whole array** fails to deserialize). `maybe_register_node` records `catalog_malformed = true` and stores an empty catalog. Then, on the same registry state: `node_invoke(w1,"bash")` is **refused** ("declared a malformed command catalog"), but `node_file(w1,"push",…)` uses `resolve` — which drops the flag — so `declared.is_empty()` is true, the center-side fail-fast is skipped, and the center dispatches `file.write`. The node's own `CommandTable` permits `file.write`, so **the file is written to a node the center refuses to run any command on**. `node_invoke_many` behaves the same way: `invoke_one` sees an empty catalog and dispatches to that node.
- Evidence:
  ```rust
  // registry.rs:377 — the flag is computed and thrown away
  let (channel, declared, _) = self.resolve_with_catalog(name_or_id)?;
  // node_invoke_many.rs:60 — no flag exists on NodeMatch to consult
  if !m.declared_commands.is_empty() && !m.declared_commands.iter().any(|c| c.name == command) {
  ```
  The registry's own contract says the caller *must* fail closed: `registry.rs:381-389` — "a malformed one means the center could not read what the node permits — so the caller has to fail closed instead of skipping the check."
- Suggested fix: delete the flag-dropping `resolve` 2-tuple so `resolve_with_catalog` is the only resolver; `src/builtin_tools/node_file.rs:76` calls `resolve_with_catalog` and applies the same `catalog_malformed` refusal as `src/builtin_tools/node_invoke.rs:81`. Add `pub catalog_malformed: bool` to `NodeMatch`, populate it in `resolve_all_by_tags`, and in `src/builtin_tools/node_invoke_many.rs::invoke_one` return the same per-node error shape as the existing "not declared" error. Invariants preserved: the node-side allowlist stays authoritative (no capability is exposed that the node did not grant); the center's admission layer now fails closed uniformly; the wire format and the node-side protocol are untouched.
- Confidence: 0.95

### B2-02 [P2] `node_list` deep-clones the whole declared catalog (schema included) and then discards the schema
- Location: `src/cluster/registry.rs:294` (`list_environments`), consumed at `src/builtin_tools/node_list.rs:57-77`
- Failure mode: A node declares 64 commands each with an 8 KiB schema — the registry's own per-node maximum (`MAX_COMMAND_COUNT` × `MAX_COMMAND_SCHEMA_BYTES` = 512 KiB). Every `node_list` call clones 512 KiB of JSON **per node** into fresh `CommandDescriptor`s and then keeps only `c.name`; every `environments.list` call clones the same bytes again and ships them over the WebSocket, where the Panel reads `node.commands.len()` and nothing else (`interfaces/webchat/src/platform/wide/views/settings/network/cluster.rs:260`). The schema is read by **no consumer in the tree** — `node_invoke`, `node_file`, `node_invoke_many` and `node_list` all compare `c.name` only. So the center copies and transmits ~512 KiB/node of data that every consumer throws away.
- Evidence:
  ```rust
  // registry.rs:294 — full catalog deep-cloned under the read guard
  commands: n.session.declared_commands.clone(),
  // node_list.rs:67 — the clone's schema is immediately dropped
  "commands": e.commands.iter().map(|c| c.name.clone()).collect::<Vec<_>>(),
  ```
- Suggested fix: add `NodeRegistry::list_node_summaries()` returning a name-only projection (`id`, `name`, `status`, `command_names`, `tags`, `connected_at`, `version`) and switch `src/builtin_tools/node_list.rs:59` to it; `list_environments` keeps the full catalog for the operator path. Invariants preserved: `node_list`'s JSON output is byte-identical (it already projected names only); `environments.list` is unchanged; the Panel is untouched. (Storing the catalog as `Arc<Vec<CommandDescriptor>>` was rejected as the minimal option: `alephcore`'s serde dependency enables only the `derive` feature — `Cargo.toml:44` — so `Arc<T>: Serialize` is not available without a feature change, and `Environment.commands`' type would change.)
- Confidence: 0.85

### B2-03 [P2] The peer-metadata bounds are retention bounds, not intake bounds
- Location: `src/cluster/registry.rs:716` (`params_typed`), `src/cluster/registry.rs:817` (`bound_commands`); the missing intake bound is on `src/gateway/server/connection/upgrade.rs:77-82` (`ws_upgrade_handler`)
- Failure mode: A LAN peer sends one WebSocket frame whose `params.commands` array is ~16 MiB. The `/ws` route sets no `max_message_size`, so axum's `WebSocketUpgrade` inherits tungstenite's defaults (`max_message_size = 64 MiB`, `max_frame_size = 16 MiB` — `tungstenite-0.30.0/src/protocol/mod.rs:101-102`); the sibling route `src/gateway/server/browser_viewer_route.rs:89,360` *does* set a cap, so the omission is a gap, not a policy. The center then: (1) parses the frame into a `Value` (~16 MiB), (2) `params_typed` **clones** the `commands` array (~16 MiB) before deserializing it, (3) `bound_commands` materializes the largest schema a **third** time as a `String` just to measure its length. Peak ≈ 3× the attacker-supplied array per connection — before the 64-command / 8-KiB bounds discard essentially all of it. The bounds therefore cap what is *retained*, not what is *transient*.
- Evidence:
  ```rust
  // registry.rs:716 — the whole peer array is cloned before it is parsed
  match serde_json::from_value::<T>(value.clone()) {
  // registry.rs:817 — the schema is fully materialized a second time to measure it
  let schema_bytes = serde_json::to_string(&command.schema).map_or(usize::MAX, |s| s.len());
  ```
  Note: the `value.clone()` cannot simply be removed — serde_json provides no `Deserializer` impl for `&Value`, so `from_value` needs an owned `Value`.
- Suggested fix: (a) in `src/cluster/registry.rs::bound_commands`, replace the `to_string` length probe with a size-limited `std::io::Write` sink that errors past `MAX_COMMAND_SCHEMA_BYTES`, so the schema is never fully materialized — the stored schema stays ≤ the bound and an unserializable schema still drops to `{}`; (b) add `ws.max_message_size(...)` to `src/gateway/server/connection/upgrade.rs::ws_upgrade_handler`, following the `WS_INBOUND_MAX` precedent — a connect frame that legitimately carries 64 commands × 8 KiB needs ~512 KiB, so a cap of order 1 MiB leaves headroom. (b) is **outside B2's file scope** and should be routed to the gateway batch; with it in place the remaining clone in (a) is bounded by the frame cap.
- Confidence: 0.8

### B2-05 [P3] `Environment`'s `Deserialize` derive yields `Deserialize<'static>` only — it is a landmine, not a capability
- Location: `src/cluster/registry.rs:77-96` (`Environment`)
- Failure mode: `serde_derive` maps a `&'static str` field to `BorrowedLifetimes::Static` (`serde_derive-1.0.229/src/de.rs:292-302`), so the derive *does* compile — but it emits `impl Deserialize<'static> for Environment`, not `impl<'de> Deserialize<'de>`. `Environment` is therefore **not** `DeserializeOwned`, and every ordinary entry point (`serde_json::from_value`, `from_str`, `from_slice`) fails to compile against it with a lifetime error that points at the derive rather than at the `&'static str` field. Nothing in Rust deserializes `Environment` today (only `Serialize`), so the derive buys nothing while making the type *look* round-trippable; the Panel keeps a separate hand-written mirror with `status: String` (`interfaces/webchat/src/api/cluster.rs:22-53`), so one wire contract is held twice with two different types.
- Evidence:
  ```rust
  #[derive(Clone, Debug, Serialize, Deserialize)]
  pub struct Environment {
      pub id: String,
      pub name: String,
      pub status: &'static str,   // ← forces Deserialize<'static>
  ```
- Suggested fix: apply B2-04's `EnvironmentStatus` enum — a normal enum derives `DeserializeOwned`, so the derive becomes a real capability instead of a trap, and the `&'static str` field disappears. If B2-04 is deferred, drop `Deserialize` from `Environment`'s derive list so the next reader is not misled. Invariants preserved: nothing deserializes `Environment` today, so no runtime behavior changes; the wire is unchanged.
- Confidence: 0.9

### B2-10 [P3] `deregister` returns only `bool`, forcing a second, non-atomic lock acquisition to learn the identity
- Location: `src/cluster/registry.rs:262-278` (`NodeRegistry::deregister`); consumer `src/gateway/server/connection/cleanup.rs:68-69`
- Failure mode: The disconnect path reads the identity under one lock and removes under a second. Between the two, the same connection can re-announce (`register_session` overwrites the mapping for that `conn_id`), so `node_identity_by_conn(conn_id)` can return the **pre-re-announce** `node_id`/`device_name` while `deregister(conn_id)` removes the **post-re-announce** session. The published `node.disconnected` event then carries a `device_name` that no longer matches the session that was removed, and `store.touch_device(&node_id)` stamps the wrong device's `last_seen`. `forget` already returns the removed `NodeSession` for exactly this reason ("the caller uses the returned session's `device_name` / `conn_id` to publish `node.disconnected` without a second lookup" — `registry.rs:449-453`); `deregister` did not follow the same shape.
- Evidence:
  ```rust
  // cleanup.rs:68-69 — two critical sections, not one
  let node_ident = ctx.node_registry.node_identity_by_conn(conn_id);
  if ctx.node_registry.deregister(conn_id) {
  ```
- Suggested fix: change `deregister` to return `Option<NodeSession>` (the removed session) instead of `bool`, and have `cleanup.rs` use the returned session's `node_id`/`device_name`/`conn_id`. ## Routing questions — answers

- **D1** (Jev #1, #2): The code implements **"malformed catalog ⇒ the center fails closed"** as a real, documented rule — `registry.rs:124-139` (`RegisteredNode::catalog_malformed`), `registry.rs:381-389` ("the caller has to fail closed instead of skipping the check"), and `node_invoke.rs:77-86` (the one consumer that honors it). It is **not** dead code and not a deliberate node-side-authoritative opt-out. The two fail-open paths (`node_file` via the flag-dropping `resolve`; `node_invoke_many` via a `NodeMatch` that structurally cannot carry the flag) are genuine defects, but the node-side `CommandTable::dispatch` allowlist (`node_runtime.rs:109-118`) still refuses anything the node does not permit, so **no capability escalation** — hence P2 rather than P1. The API shape is the root cause: `resolve` makes the contract unhonorable and `NodeMatch` cannot express it. The external doc (`docs/reference/CLUSTER.md`, §`node_invoke`/`node_invoke_many`/`node_file`) states the center-side fail-fast only in terms of a "non-empty catalog" and does not cover the malformed case at all, so the *documented* contract is silent — the fix should extend that paragraph to state the malformed rule once.
- **D2** (Jev #3): `std::sync::RwLock` is **acceptable here**. `crate::sync_primitives::RwLock` *is* `std::sync::RwLock` (`sync_primitives.rs:49-51`), but that module's own doc mandates `AsyncRwLock` only "to avoid deadlocks when holding a guard across `.await` points" — and no guard in `registry.rs` is ever held across an `.await` (there is no non-test `async fn` in the file). The module doc also names `NodeRegistry` explicitly as a deliberate leaf whose critical sections are "a `HashMap` access plus clones", and `register`/`forget` fire `close_connection()` after dropping the guard. The one genuine cost is the *clone* under the read guard, which is finding B2-02 — not the lock itself.
- **D3** (`now_unix` → `i64::MIN`): **safe**. `connected_at` is consumed by `node_list` (as a raw number the model reads), by `environments.list` (as a raw JSON number), and by `handlers/cluster.rs` (which uses `0`, not `i64::MIN`, for offline rows). No consumer interprets it as a date: the Panel's fleet view renders `last_seen_at` (which is `None` for online nodes and comes from the device store for offline ones — never `i64::MIN`) and `commands.len()`, and never reads `connected_at` at all (`interfaces/webchat/src/platform/wide/views/settings/network/cluster.rs:253-260`; `connected_at` appears only in the API struct and its test fixture). No finding.
- **D4** (truncating a command name): **acceptable — it cannot mis-dispatch.** The center never dispatches the truncated name: it dispatches the *requested* name verbatim (`node_invoke.rs:96`), and the node's allowlist is keyed by the node's own exact declared name (`node_runtime.rs:57-81`). The only reachable effect of truncation is a **false refusal** at the center for a command whose declared name exceeds 64 bytes (no shipped node command does). The doc gap is reported separately as B2-08.
- **D5** (should the read paths clone the catalog?): **No — but not via `Arc`.** `alephcore`'s serde dependency enables only the `derive` feature (`Cargo.toml:44`), so `Arc<T>: Serialize` is unavailable without a feature change, and `Environment.commands`' type is on the wire to the Panel. The minimal fix is a **name-only projection for `node_list`** (B2-02), leaving `environments.list` alone. The stronger Occam observation — the declared `schema` is read by **no** consumer in the tree (`node_invoke`/`node_file`/`node_invoke_many`/`node_list` compare names only; the Panel reads `commands.len()`) — is a **product decision** (dropping `schema` from the wire touches the Panel's `CommandDescriptor`), and is listed as such below rather than fixed unilaterally.
- **D6** (should `deregister` return the removed session?): **Yes, for correctness, not just tidiness.** `src/gateway/server/connection/cleanup.rs:68-69` reads the identity under one lock and removes under a second; between the two, a re-announce on the same connection can replace the mapping, and the published `node.disconnected` then carries the **old** `node_id`/`device_name` while `deregister` removed the **new** session (and `store.touch_device` stamps the wrong device). Returning the removed session — as `forget` already does — closes the window in one critical section. Reported as **B2-10**.
- **D7** (is the `connect` frame size capped on `/ws`?): **No.** `src/gateway/server/connection/upgrade.rs:77-82` uses axum's `WebSocketUpgrade` with no `max_message_size`, so tungstenite's defaults apply (`max_message_size = 64 MiB`, `max_frame_size = 16 MiB` — `tungstenite-0.30.0/src/protocol/mod.rs:101-102`). The sibling route *does* cap itself (`src/gateway/server/browser_viewer_route.rs:89,360`, `WS_INBOUND_MAX = 8 KiB`), so the gap is an omission rather than a policy. Consequence and fix are in B2-03; the route change is **outside B2's file scope** and must be routed to the gateway batch.

## Policy / product decisions (need a human; not fixed unilaterally)

1. **Drop the declared command `schema` from the center's projection and the `environments.list` wire.** No consumer reads it (B2-02), so it is dead payload — but removing it changes the wire the Panel parses (`interfaces/webchat/src/api/cluster.rs:15-20`), so it needs an owner sign-off.
2. **Make the malformed-catalog rule part of the external contract.** `docs/reference/CLUSTER.md` describes the center-side fail-fast only as "reject when the node declared a **non-empty** catalog that excludes the command"; the malformed case (which the code treats as *stricter*) is undocumented. Extend that paragraph once, then the three dispatch paths have a single written rule to satisfy.
3. **Whether `Environment` should be deserializable at all.** The derive is currently unusable (B2-05). Either it becomes genuinely round-trippable (with the enum from B2-04) or it is dropped — the choice belongs to whoever owns the fleet-list persistence story, if any.
