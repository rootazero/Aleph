## Critical Findings

### C1: Arithmetic Overflow in `cron_timer_interval` (src/tasks/cron/service/timer.rs:97)

**Issue**: `as i64` cast on `u64` timestamp subtraction can silently overflow.

```rust
// BEFORE (buggy)
let interval = (next_run.timestamp() as u64 - now.timestamp() as u64) as i64;
```

**Risk**: When `now > next_run` (clock drift or past-due cron jobs), the unsigned subtraction underflows to `u64::MAX`, then the `as i64` cast produces a negative number with catastrophic magnitude (~9e18).

**Fix**: Use `saturating_sub` + explicit `Duration` conversion:

```rust
// AFTER (fixed)
let next_timestamp = next_run.timestamp() as u64;
let now_timestamp = now.timestamp() as u64;
let interval = next_timestamp.saturating_sub(now_timestamp);
```

**Verification**: ✅ Compiles cleanly, semantic equivalent for valid cases, safe for edge cases.

### C3: `panic!` in Production Code Path (src/tasks/heartbeat/dedup.rs:93)

**Issue**: `DedupEngine::noop()` contains `panic!("Noop engine")` and is called from production code at:

- `src/bin/aleph-server/commands/start/mod.rs:1627`
- `src/bin/aleph-server/commands/start/mod.rs:1631`

**Risk**: Any deduplication failure in production triggers process termination instead of graceful degradation.

**Fix**: Eliminated `panic!` by redesigning `DedupEngine` to use `Option<Arc<Mutex<Connection>>>`:

1. **Struct field**: Changed `conn: Arc<Mutex<Connection>>` → `conn: Option<Arc<Mutex<Connection>>>`
2. **`noop()`**: Returns `Self { conn: None }` instead of panicking
3. **All methods**: Handle `None` gracefully (return `Ok(())` for writes, `Ok(false)` for reads)

**Key design decision**: The constructor parameter was kept as `Arc<Mutex<Connection>>` (not Option) to preserve the API contract — callers with a real connection pass it directly, while `noop()` internally uses `None`.

**Verification**: ✅ Compiles cleanly, all call sites (production + test) unaffected.
