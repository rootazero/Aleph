# Logic Review Report — src/metrics
**Date**: 2026-08-28
**Mode**: strict
**Files reviewed**: `src/metrics/mod.rs` (single file, ~371 lines)

## Context

Previous audit (2026-05-31, `docs/engineering-reports/review-results/metrics.md`) found
and fixed a divide-by-zero: when `target_ms == 0`, the `ratio` calc produced
`f64::INFINITY` and `threshold_ms == 0` caused every operation to spuriously
trigger the "slow operation" warning. The fix added a `target_ms > 0` guard
inside `Drop`. A later commit (`5b697ed06`, 2026-06-03, "metrics: remove
zero-caller dead code") also stripped `time_stage!`, `StageTimer::stop()`,
and `StageTimer::start_with_policy()` per R10.

This audit re-examines the surviving 371 lines across all five phases.

## Findings

### [Warning] `warning_multiplier == 0.0` passes init validation but floods warnings
- **Location**: `src/metrics/mod.rs:88-92` (init validation) and `:117-119`
  (`warning_threshold_ms`).
- **Trigger condition**: operator sets `[policies.metrics] warning_multiplier = 0.0`
  (legitimate TOML — `f64` deserializes 0.0 with no bound check). Validation
  is `is_finite() && >= 0.0`, which accepts exactly `0.0`.
- **Expected behavior**: a zero or negative multiplier should fall back to
  `DEFAULT_WARNING_MULTIPLIER` (the precedent already used for NaN / +Inf /
  negatives), since `0.0` collapses `threshold_ms` to `0` for every
  `target_ms`, and `elapsed_ms > 0` then trips the slow warning on **every**
  `StageTimer::drop` whose target is non-zero — i.e., a flood of false
  positives that operators cannot silence without restarting.
- **Actual behavior**: warning fires for every stage at every drop, with
  `ratio = elapsed_ms / target_ms` printed as a small decimal (`0.000123`-ish),
  drowning out real signal.
- **Current impact**: low — the `[policies.metrics]` config is currently a
  no-op at runtime anyway (see Warning #2 below), so this is latent. Becomes
  high the moment any production code adopts `StageTimer`.
- **Suggested fix**: tighten the bound to `> 0.0` (or `>= 1.0`); add a
  `[policies.metrics] warning_multiplier` schema doc that names the bound.

### [Warning] `StageTimer` has zero production callers in `src/`
- **Location**: `src/metrics/mod.rs` (the entire module); `src/lib.rs:247`
  re-exports the type.
- **Evidence**:
  ```
  rg -t rust '\bStageTimer\b' src/
  src/lib.rs:247: pub use crate::metrics::StageTimer;
  src/config/load.rs:240:    // Bridge: honour `[policies.metrics]` in the live `StageTimer`. Without
  src/config/types/policies/metrics.rs:11,13,14:    // doc comments referencing StageTimer
  ```
  Outside `src/`, the only callers are `benches/performance_benchmarks.rs`
  and the unit tests in this module. No `src/desktop/`, `src/interfaces/`,
  `src/memory/`, `src/providers/`, or `src/tools/` invocation exists.
- **Risk**: `[policies.metrics]` (`warning_multiplier`, `enable_logging`,
  `enable_warnings`) is parsed, defaulted, bound into `Config::policies`, and
  fed through `init_metrics_runtime` from `Config::load`, but at runtime the
  values are read by **nothing in production**. The bridge is wired; the
  load is dead. Any operator who tweaks `warning_multiplier` will see no
  behavioural change, with no warning either.
- **Current impact**: low today (no real user-visible effect), high
  prospectively once the obvious next step — instrumenting the gateway
  loop, the memory write path, the AI request fanout — lands without
  someone remembering that the policy has never been read. R10
  (`delete zero-consumer abstractions`) flagged this in 2026-06-03 and
  chose to keep `StageTimer` as a public API for downstream/ext consumers,
  which is defensible; what is NOT defensible is the silent gap between
  `[policies.metrics]` and runtime behaviour going un-noted in the module
  doc.
- **Suggestion**: add a `// Wiring:` block at the top of the module that
  names the consumer contract ("currently benches + tests + library API
  consumers; no internal call sites exist as of 2026-08-28") and a
  pointer to the next planned call site. Do NOT delete the policy or the
  init path: they are load-bearing for downstream users and for the
  capability roster (`metrics_runtime_slot()` is registered in
  `capability::ALL_SLOTS`).

### [Warning] `target_ms` precision loss above 2^53 ms in `warning_threshold_ms`
- **Location**: `src/metrics/mod.rs:117-119`
  ```rust
  pub fn warning_threshold_ms(&self, target_ms: u64) -> u64 {
      (target_ms as f64 * self.warning_multiplier) as u64
  }
  ```
- **Risk**: `u64 -> f64` (`as f64`) is saturating since Rust 1.45, no UB.
  But for `target_ms > 2^53`, f64 cannot represent every u64; the rounded
  value, multiplied by `warning_multiplier`, then re-cast to `u64`, can
  return a threshold that is *less* than `target_ms * warning_multiplier`.
  In practice a target above 2^53 ms (~285 000 years) is absurd, so this is
  theoretical — but combined with `elapsed_ms > threshold_ms`, a stage
  with such a target could trip the warning for an `elapsed_ms` that is
  actually within budget.
- **Current impact**: negligible (no caller supplies targets near 2^53),
  but the cast is also non-idiomatic and would clip in `cargo clippy
  -- -D warnings` if not for an explicit `cast_possible_truncation`
  allow.
- **Suggestion**: if you ever expect targets above ~year-scale, switch to
  `u128` arithmetic or `u64::saturating_mul` divided by `f64::from(1.0)`
  rounded back to u64. Otherwise document that targets are bounded to
  ~285 ky and call it done.

### [Suggested Test] Concurrent double-init does not double-stamp
```rust
#[test]
fn concurrent_init_metrics_runtime_idempotent() {
    use crate::config::MetricsPolicy;
    use crate::metrics::init_metrics_runtime;
    use std::sync::Arc;
    use std::sync::Barrier;
    use std::thread;

    let policy = Arc::new(MetricsPolicy::default());
    let n = 8;
    let bar = Arc::new(Barrier::new(n));
    let handles: Vec<_> = (0..n)
        .map(|_| {
            let p = Arc::clone(&policy);
            let b = Arc::clone(&bar);
            thread::spawn(move || {
                b.wait();
                init_metrics_runtime(&p);
            })
        })
        .collect();
    for h in handles { h.join().unwrap(); }

    // Exactly one install wins; downstream readers must observe
    // Outcome::Installed once, not multiple times.
    // (Pin via the capability census test or a slot-level assertion.)
}
```

    `std::sync::*` and constructs no `Arc`/`Mutex`/`RwLock` directly.
    Synchronization goes through `crate::capability::CapabilitySlot`,
    which uses `OnceLock` (an explicitly allowed primitive).
  - Lock-across-await: N/A — no async surface.
  - Lock hierarchy (L0→L1→L2→L3): N/A — no locks held.
  - Atomic ordering: `OnceLock::get`/`set` supply Acquire/Release
    semantics; no manual `Ordering::*` calls exist.
  - R10 / YAGNI: previous round (2026-06-03) already removed
    `time_stage!`, `StageTimer::stop()`, `StageTimer::start_with_policy()`
    for zero callers. This audit honours that precedent and does not
    propose further deletion.

- **Wiring**:
  - `StageTimer` is a public API surface (`pub use` in `lib.rs:247`),
    with zero internal callers in `src/`. The previous fix-2026-06-03
    commit explicitly preserved this shape per R10, on the rationale
    that downstream consumers and the benches exercise it. This audit
    does not challenge that decision but flags the corresponding
    runtime dead-end for `[policies.metrics]` (Warning #2).
  - `init_metrics_runtime` is wired from two sites:
    `src/config/load.rs:244` (happy path) and `src/config/load.rs:360`
    (no-config-file fallback). Both succeed independently. The
    idempotence contract (`install` first-writer-wins) is upheld by
    `OnceLock::set` in `capability::CapabilitySlot::install`, not by
    the call sites themselves.
  - `metrics_runtime_slot()` is registered in
    `capability::ALL_SLOTS` (verified at `src/capability/mod.rs:309`).
  - `MissingSemantics::IndistinguishableDefault { reads_as }` carries
    the literal "2.0x" sentinel, pinned by
    `the_accessor_exposes_this_handle_to_the_roster` (line 397-422).
    The pin is robust to `DEFAULT_WARNING_MULTIPLIER` changes via
    `format!("{DEFAULT_WARNING_MULTIPLIER:.1}x")`. Good.

- **What was NOT checked**:
  - No `cargo` commands were executed (per instructions).
  - Doctests in the module (`///` examples on `StageTimer::start`,
    `with_meta`) compile but are not run; their imports reference
    `alephcore::metrics::StageTimer`, which is consistent with the
    `pub use` at `lib.rs:247`.
  - The `tracing` macro behaviour under
    `tracing-subscriber` filter configuration was not exercised.
    Drop-time logging relies on a globally-initialised subscriber;
    without one, `tracing::warn!`/`debug!` are no-ops, which is
    expected but worth knowing for tests.
  - The Drop path during unwind was not tested (suggested test #4
    above proposes pinning it).
  - The `(target_ms as f64 * warning_multiplier) as u64` precision
    path was not stress-tested; the theoretical overflow range
    starts above 2^53 ms and is not reachable in practice.
  - `benches/performance_benchmarks.rs` consumers were not inspected
    for behavioural expectations beyond presence.

- **Architectural observation**:
  The module's surface area is small and tight. `StageTimer` is the
  only runtime type, all knobs funnel through one `MetricsRuntime`
  value, and the `CapabilitySlot` integration keeps the install
  /outcome bookkeeping atomic. The principal remaining risk is
  external: the `[policies.metrics]` config being honoured in a
  vacuum because no production code reads the timer yet. Recommend
  the next module audit (2026-Q4) explicitly check whether any new
  caller has landed, and if not, either (a) declare the public API
  stable and document the expected external caller pattern, or
  (b) land the planned gateway/memory/AI instrumentation that
  would justify the policy.
