### [Warning] Custom rule named after a built-in has its action silently overridden

- **Location**: `src/pii/engine.rs:255-265` (`action_for_rule`)
- **Risk**: An operator writes `[[privacy.custom_rules]] name = "email" pattern = ...`. The custom rule is built, sorted into `self.rules`, and runs. But `action_for_rule` matches the **name** before the custom-rule HashMap:

  ```rust
  match rule_name {
      ...
      "email" => &config.email,   // ← clobbers custom action
      _ => custom_actions.get(rule_name).unwrap_or(&PiiAction::Block),
  }
  ```

  So `config.custom_rules[].action` for the colliding custom rule is ignored, and the built-in `config.email` field decides. The custom rule still fires, but the operator's `action = "warn"` (or `"off"`) silently becomes the global email action.
- **Current impact**: medium. Operators are unlikely to clash, but if they do, the rule fires with the wrong action — and `Warn` becoming `Block` silently changes redaction behaviour.
- **Suggestion**: either (a) document the precedence rule (built-in names win, custom actions ignored), or (b) resolve the action at construction time and store it on the rule so the lookup can't disagree. Option (b) is the cleaner fix: a `CustomRegexRule` would carry its own `action`, and `action_for_rule` becomes the rule's own field accessor.

### [Warning] `BUILTIN_RULE_COUNT = 7` is a magic number with no compile-time link to `build_rules`

- **Location**: `src/pii/engine.rs:21` and `src/pii/rules/mod.rs:48-60`
- **Risk**: Adding a new built-in rule (or removing one) requires editing the constant in `engine.rs` plus the literal list in `rules/mod.rs:build_rules`. Drift between the two only surfaces as a slightly-off diagnostic in `warn_if_partial_custom_load` — there is no test or const assertion linking them.
- **Current impact**: low. The diagnostic is operator-facing but cosmetic; the engine itself does not depend on the count being exact.
- **Suggestion**: expose `rules::BUILTIN_RULE_COUNT` from `rules::mod` (or make it a `pub const` derived from the same `build_rules` body) so a single edit covers both call sites. Even better: have `build_rules` return `(builtins, customs)` separately so the count is structurally derivable.

### [Warning] `action_for_rule` defaults unknown rule names to `PiiAction::Block`

- **Location**: `src/pii/engine.rs:265` `custom_actions.get(rule_name).unwrap_or(&PiiAction::Block)`
- **Risk**: A `PiiMatch` whose `rule_name` is not present in the HashMap defaults to the strictest action (Block). This is the safe direction (no leak), but it is undocumented and surprising if a future rule's name drifts from the keys.
- **Current impact**: low. Today the only way to hit this branch is to add a rule that emits matches but isn't keyed in `custom_rule_actions` — impossible with the current `build_rules`.
- **Suggestion**: add a doc-comment stating the default and why it is Block (prefer leak over false-negative for an outbound filter). Consider `PiiAction::Warn` as a more conservative default that surfaces the bug at the audit layer rather than silently re-dacting.

### [Warning] `filter_with_config` performs three `action_for_rule` lookups per rule per match

- **Location**: `src/pii/engine.rs:328-335, 374, 386`
- **Risk**: Each call site does a `match` over 7 strings + a `HashMap` lookup. Negligible cost on its own, but the same action is recomputed 3× per rule per outbound message. With 7 rules and N matches, that's O(rules) wasted work; with 100K outbound messages per minute it adds up.
- **Current impact**: low (O(1) per call). Worth fixing only as part of a broader refactor.
- **Suggestion**: pre-compute `Vec<(rule_name, action)>` once at the top of `filter_with_config` keyed off the rules list, then use the cached action in both the rule-skip check and the per-match branch. Same shape, ~30 fewer instructions per message.

### [Warning] `PiiMatch.matched_text` and `.placeholder` allocate per match even when no redaction happens

- **Location**: `src/pii/engine.rs:46-53`, every rule's `detect`
- **Risk**: Every `PiiMatch` owns a `String` for `matched_text` and `placeholder` even when the caller (e.g. `redact_secrets` in `browser/secret_guard.rs`) only reads the offsets. For a 50KB text with 200 PII matches, that's 400 heap allocations that go straight to dead memory.
- **Current impact**: low (correctness unaffected). Hot-path allocation cost is real but not a bug.
- **Suggestion**: change `matched_text: String` → `Cow<'static, str>` or `&'a str` (borrow from `text`), and `placeholder` → `&'static str` for built-ins (custom rules can keep `String` only if their placeholder is dynamic — it's not, the config sets it). The replacement loop in `engine.rs:402` only needs the placeholder string slice, not ownership.

### [Warning] `is_provider_excluded` and `is_platform_excluded` build per-call `String`s for the lowercase lookup

- **Location**: `src/pii/engine.rs:233-237` (`is_provider_excluded`)
- **Risk**: Every outbound filter call lower-cases the provider name into a fresh `String` to probe a pre-lowercased `HashSet`. For high-throughput outbound traffic this is one allocation per call that could be avoided.
- **Current impact**: low (correctness unaffected). Microbenchmark, not a bug.
- **Suggestion**: `HashSet<String>::contains` can take `&str` if the set is built from `String`s with `into_iter().map(str::to_lowercase)`. The current implementation does exactly that, so the lookup itself is allocation-free; only the `to_ascii_lowercase()` call on the probe key allocates. Replace with a `&str` argument and use `self.excluded_providers.contains(provider_name.to_ascii_lowercase().as_str())` — no, that still allocates. The real fix is `phf`/`foldhash` or a small inline cache. Out of scope for a logic audit; flagging only.

### [Warning] `effective_config` always clones the `PrivacyConfig` on the no-override path

- **Location**: `src/pii/engine.rs:347-349`
- **Risk**: `effective_config(None)` short-circuits with `return self.config.clone();` — i.e. one full clone even when the caller passes `None`. The `filter()` method bypasses this (it uses `&self.config` directly), so the only caller is `filter_with_platform(None)` which is rare. Low impact.
- **Current impact**: low. The clone is bounded (the config has ~10 fields), and the path is rarely taken.
- **Suggestion**: change `effective_config`'s return type to `Cow<'_, PrivacyConfig>` so the no-override case returns `Cow::Borrowed(&self.config)`. The downstream `filter_with_config` takes `&PrivacyConfig` so this is a clean refactor.

### [Warning] `bank_card` regex allows `[ \-]?` between digits, but the `is_decimal_context` check only guards against `.` — `,` (locale decimal separator) leaks through

- **Location**: `src/pii/rules/bank_card.rs:79-88`, `src/pii/rules/bank_card.rs:101-105`
- **Risk**: A European-style amount `1.499,99` has a 5-digit group `14999` that would be matched as a card by the regex (5 digits + `,` + 2 digits = 8 chars, but the regex requires 13-19 digits, so this specific case is safe). The risk is the 13-digit sequence `1234567890,123` (`1234567890123` after stripping `,`) — a CSV export of financial figures. Luhn rejects most, but if a CSV row happens to Luhn-pass, it would be redacted.
- **Current impact**: low. Luhn is a strong filter; the practical risk is small. Documenting for completeness.
- **Suggestion**: extend `is_decimal_context` to also guard against `,` separators. Or extend `has_word_boundary` to also fail on `,` adjacency.

### [Warning] `effective_config` `policy_has_any_override` check is correct but the comments above each `if let Some(ref v) = policy.X` read as if the field were always present

- **Location**: `src/pii/engine.rs:355-381`
- **Risk**: Cosmetic only. Each `if let Some(ref v) = policy.id_card` looks identical to the others; the reader has to remember that `policy_has_any_override` already filtered out the no-op case. Drift between the check and the overrides (e.g., adding `policy.foo` to the check but forgetting to add the corresponding `if let` block) is a silent bug — the override is silently dropped.
- **Current impact**: low. The current list is correct.
- **Suggestion**: extract the override-application into a helper that takes a `(field_name, getter, setter)` triple, or use a macro that pairs the check and the apply. A test should pin the invariant: any field with `policy.X.is_some()` for some override X must have a matching apply block.

fn custom_rule_named_after_builtin_uses_builtin_action() {
    let mut config = PrivacyConfig {
        email: PiiAction::Block,
        ..Default::default()

    assert_eq!(r.blocked_count, 1);

### [Suggested Test] Reload + concurrent filter do not interleave partial state

```rust
#[test]
fn reload_under_concurrent_filter_sees_only_complete_states() {
    // 100 reloads and 100 filter calls in parallel against the same engine.
    // After all threads join, the engine state must be the result of the
    // last `reload` to complete; any filter call that ran during a reload
    // must have observed either the pre- or post-reload rule set, never a
    // mixed state (which would manifest as a PiiMatch whose rule name is
    // no longer in self.rules, defaulting to Block).
    PiiEngine::init(PrivacyConfig::default());
    let engine = PiiEngine::global().unwrap();
    let arc = std::sync::Arc::clone(&engine);
    let mut handles = vec![];
    for _ in 0..100 {
        let arc = std::sync::Arc::clone(&arc);
        handles.push(std::thread::spawn(move || {
            let _g = arc.read().unwrap_or_else(|e| e.into_inner());
            let _ = _g.filter("plain text 13812345678");
        }));
    }
    for _ in 0..100 {
        let mut cfg = PrivacyConfig::default();
        cfg.custom_rules.push(CustomPiiRule {
            name: "x".into(),
            pattern: r"X-[0-9]{4}".into(),
            placeholder: "[X]".into(),
            severity: CustomPiiSeverity::Low,
            action: PiiAction::Block,
        });
        PiiEngine::reload(cfg);
    }
    for h in handles { h.join().unwrap(); }
}
```

**Connectivity & wiring**:
- `PII_ENGINE` `CapabilitySlot` installed unconditionally by `PiiEngine::init`, consumed by `mcp/redact.rs`, `security/runtime_guard.rs`, `providers/http_provider.rs`, `browser/secret_guard.rs` (via `rules::build_rules`). All consumers named on the static are present in the roster.
- `rules::build_rules` is invoked by both `PiiEngine::new` (boot) and `PiiEngine::reload` (hot-reload). Both paths now share `warn_if_partial_custom_load` (no silent partial-load drift between boot and reload — previously flagged).
- The `browser::secret_guard::critical_rules()` uses `build_rules(&[])` then filters on `severity() == Critical`. Same source-of-truth as the outbound path. OK.

**Wiring gap noticed but not in scope** (informational):
- `browser::secret_guard::scan_url_for_secrets` percent-decodes the URL via `decode_utf8_lossy`, which can replace invalid UTF-8 sequences with U+FFFD. An attacker who percent-encodes a key inside an invalid-UTF-8 fragment can bypass the scan (U+FFFD is not `[A-Za-z0-9._\-]` and would break the prefix anchor). Not a bug — the regex's prefix anchors (`sk-`, `ghp_`, …) catch the common case, and `decode_utf8_lossy` is the documented fallback. Worth flagging for a follow-up review of the browser egress path.

**DRY observation** (informational, not raised as a finding):
- `api_key.rs`, `ssh_key.rs`, `email.rs`, `ip_address.rs`, `phone.rs` all share the same `detect` skeleton: `for m in re.find_iter(text) { results.push(PiiMatch { ... }) }`. The phone rule and bank-card rule add anti-false-positive gates; the others are one-liners. A `PiiRule::detect` default method taking a regex iterator and a closure for additional gates would DRY this up. The previous audit already noted this; it remains a future refactor target.

**No state machine, no async ordering issues, no Type coercion** (`as` casts are absent throughout the module).
